### 4.15 Debug Execution Control Endpoints

#### 4.15.1 Debug Operations

##### REQ-5.2.5.2 Debug execution control endpoints

Debug execution control endpoints provide interactive debugging capabilities for test executions enabling breakpoint management, step-by-step navigation, block re-execution, and block skipping. Debug endpoints extend execution control with fine-grained flow control, supporting interactive troubleshooting where engineers inspect state and modify behavior without restarting entire test sequences.

**Start Paused Mode**: Executions may be started in paused mode to enable step-by-step navigation from the first block without requiring a breakpoint. When the `pause_on_first_block` debug option is set, execution begins in paused state at the first block ready for stepping. Debug operations (breakpoints, step-over, step-into, repeat-step, skip, continue) are available on any paused execution regardless of how it became paused.

**Breakpoint Management**: Breakpoint endpoints enable dynamic control over execution pause points. One call replaces the whole set of breakpoints; each is a pause point halting execution before its block begins. Breakpoints may be set before or during execution and persist throughout execution lifetime.

**Step Navigation**: Step-over runs the currently paused block to completion and pauses before its sibling-after. On control-flow parents (loops, try-catch, parallel, assert-split, if-else, switch), the entire sub-graph under the parent runs atomically and the next pause lands on the first node beyond the parent's post-control egress. Step-into runs the paused block's entry logic and pauses before the first inner-body node on parents that have a body (loops, try-catch, parallel) or before the first node along the selected egress on evaluation-routing parents (if-else, assert-split, switch). On leaves, Step-into collapses to Step-over semantics. Both operations transition from paused through running back to paused at the next boundary, or through to a terminal status when the stepped block is the last reachable node.

**Block Re-execution (Repeat Step)**: Re-execute runs the currently paused block in place and re-pauses on the same block after the run completes. Variable writes produced by the re-run are permanent and are reflected in the Variable Manager before the next user action. The re-run may produce a pass or a fail; in either case, the paused-node identifier is unchanged and the Paused Toolbar controls remain active. A repeat that fails, during any kind of pause, stays in the same single pause and never opens a second one. Repeat Step may be invoked multiple times in succession. When the user advances via Continue or Step Over, the latest result drives successor routing; intermediate attempts are not aggregated. Step Into on a container or a Function instance runs the block again, step by step, and the outcome of that stepped run replaces the repeat's result. Skip Block marks the block skipped whatever its result.

**Continue and Skip**: Continue resumes execution running until the next enabled breakpoint, pause-on-errors trigger, or terminal status, respecting dynamically added breakpoints. Skip advances past the current block without execution. On leaf plugins and on single-post-control-egress parents (loops, try-catch, parallel, assert-single), Skip marks the current node skipped, cascades the skipped status to every node on its non-egress branches or inner body, and re-pauses before the first node on the single post-control egress. On diverging parents with multiple mutually-exclusive egresses and no unambiguous sibling-after (if-else, assert-split, switch), Skip is rejected with a conflict error instructing the engineer to step into a branch and skip a leaf.

**Parallel Branch Debugging**: Debugging a parallel section keeps a single cursor. Breakpoints target blocks by identifier anywhere inside the section. The first branch to reach a pause trigger becomes the paused block and the section parks: every sibling stops advancing at its next block boundary and holds there instead of running on while the engineer inspects state. Step operations advance the paused branch alone, and a step that ends a branch releases the section rather than leaving its siblings held. Continue releases the whole section and every parked branch resumes concurrently; a sibling that was itself holding at a trigger becomes the paused block next, so several breakpoints inside one section surface one after another. Variable and progress queries carry no branch context, because branches share the test's live variables and therefore have one variable state rather than per-branch scopes.

**Error Handling**: Operations enforce validation through consistent error responses. Debug operations on non-debug executions return bad request. Invalid block identifiers return not found. Step, repeat-step, and skip on non-paused executions return conflict. Skip on diverging parents returns conflict with a specific guidance message. Repeat-step on a session whose paused-node id is null returns not found. Operations on terminal states (passed, failed, stopped) return conflict with valid operation guidance.
