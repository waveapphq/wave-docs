### 4.9 Variable Management Endpoints

#### 4.9.1 Variable Operations

##### REQ-5.2.4.7 Variable management endpoints

Variable management endpoints provide access to the variable system enabling scope-level storage, variable manipulation, expression evaluation, and runtime variable watching. Variables are stored independently at each level (system, regression, suite, test). Test-level variables are accessed by name in expressions. System, suite, and regression variables are accessed via namespace expressions at runtime. All variables support typed values, computed expressions, and secret masking.

**Scope Discovery**: The system exposes available variable storage levels through a dedicated endpoint returning the ordered list: system, regression, suite, and test. Scope discovery enables clients to understand where variables can be stored and managed. These are storage categories, not an inheritance hierarchy - no level inherits from or resolves against another.

**Variable Retrieval**: Entity-specific variable retrieval accepts scope and entity identifier, returning all variables defined at that scope level. Responses include variable metadata such as type information, secret indicators, and computed expression status. Retrieved variables reflect the declared state at the specific scope. Each variable includes a name and a type, and a value where one was given.

**Variable Modification**: Three modification patterns support different use cases. Setting variables replaces the entire variable collection for an entity, useful for bulk configuration or reset operations. Updating variables performs merge semantics, adding or modifying specified variables while preserving unmentioned ones. Deleting variables removes individual named variables from an entity's scope. All modification operations validate variable names, types, and expression syntax before applying changes, and reject any change that would introduce a circular reference between computed variables.

**Variable Identity and Mutation**: A variable's identity is bound to its name within a scope. Renaming a variable - changing its name without changing other fields - preserves value, type, secret flag, and any associated expression unchanged; the rename is a pure identity change at the storage layer. Type changes are accepted but constitute a redefinition of the variable's data shape: clients that drive a type change supply a value compatible with the new type, and the system replaces the prior value rather than attempting cross-type coercion. The frontend variable editor surfaces this redefinition as an explicit user action so the loss of the prior value is intentional rather than incidental.

**Expression Evaluation**: The expression evaluation endpoint processes variable expressions with optional context, returning computed results. Expression syntax supports direct variable references for test-level variables and namespace-prefixed references for system, suite, and regression variables, along with arithmetic and logical operators and built-in functions. Context objects provide additional variables for evaluation without persisting them. Evaluation resolves namespace references against the appropriate level's variables when entity context is provided. Evaluation uses the evaluator a run uses, so a preview and a run agree: a null result is returned as null, and an expression a run would refuse, or one that fails, fails here with the run's message instead of echoing its text.

**Expression Validation**: Syntax validation enables pre-flight checking of expressions without execution. Validation returns structural correctness, identifies undefined variable references when context is provided, and reports type compatibility warnings. Validation operates without side effects, suitable for real-time editor feedback.

**Variable Watching**: Debug-oriented watch functionality registers interest in specific variables, returning a watch identifier for subsequent polling. Watch registration accepts variable paths with optional namespace qualifiers. Watched value retrieval returns current values for all registered variables in a watch session. Watch unregistration releases resources when debugging completes. Watch functionality integrates with execution context for real-time debugging scenarios described in execution control endpoints.

**Watch List Persistence**: The list of variables a user chooses to watch persists in frontend localStorage as part of the Workbench draft state. This enables watch lists to survive page refreshes while being cleared when the user closes or switches tests. The backend watch registry remains in-memory and ephemeral, serving only as a WebSocket subscription mechanism for real-time value updates. On page reload, the frontend restores the watch list from localStorage and re-registers with the backend for WebSocket notifications.

**Secret Handling**: Variables marked as secrets receive special treatment throughout the system. Secret values are masked by default in API responses, log output, and error messages; the per-surface reveal flags in Settings > General and the MCP reveal tool, which needs its surface's flag on and explicit consent, are the deliberate exceptions. Secret indicators propagate through computed expressions when any referenced variable is secret. Modification operations accept secret values for storage but subsequent retrieval returns masked placeholders.

**Variable Storage**: Each level (system, regression, suite, test) independently stores variables with name, type, and value. System variables provide configuration available to all tests via `system.var_name` namespace expressions. Regression variables establish campaign-wide values accessed via `regression.var_name`. Suite variables customize for functional areas accessed via `suite.var_name`. Test variables specify scenario parameters and are accessed directly by name. System variables are managed through a dedicated settings interface with full CRUD, export, and import capabilities.

**Type System**: Variables support primitive types (string, integer, float, boolean), collection types (array), maps (key-value dictionaries), and tables (two-dimensional matrices). Special modifiers include secret indicators and computed expressions. Type information accompanies variable metadata enabling appropriate handling. Computed variables store expressions rather than literal values, with evaluation occurring at access time within execution context.

**Variable Storage Model**: Each variable is a named entry with a type field and, where the author supplied one, a value field (or an expression flag with the expression as value for computed variables). A variable declared without a value carries no value field at all, rather than an invented default; a variable always holds a value, so one declared with no value holds null, and the creation editors preset the type's default (see REQ-3.1.3.20). There are no external references.

**Variable Value Unwrapping**: During execution, structured variable entries (type + value) are unwrapped to extract the raw value before passing to plugin executors. This applies uniformly across test, suite, and regression execution contexts.

**System Variable Endpoints**: System variables have dedicated endpoints for retrieval, bulk replacement, individual and bulk deletion. Responses use the same structure as entity-scoped variables. Import and export support JSON and YAML formats with optional secret masking.

**Error Handling**: Consistent error responses for: invalid scope (400 with valid scopes), missing entity (404), invalid variable name (400 with naming constraints), malformed expression (400 with syntax details and position), type mismatch (400 with expected/actual types), missing watch registration (404). Individual system variable deletion returns 404 when the variable does not exist.

**Caching and Performance**: Variable metadata caches with invalidation on modification operations. Watch registrations maintain efficient polling with minimal overhead.
