### 5.1 Execution Modes

#### 5.1.1 Normal Execution Mode

##### REQ-3.2.1.1 Normal execution (run to completion)

The normal execution mode provides the foundational workflow execution capability where tests, suites, or regressions run from initiation to completion without manual intervention, following a deterministic flow through the hierarchical test structure while managing state, resources, and errors in a consistent and predictable manner.

**Execution Flow Pattern**: The execution engine traverses the hierarchical test structure in a depth-first manner, processing each level from top to bottom. A regression execution initiates all its contained suites sequentially, each suite execution initiates all its contained tests sequentially, each test execution processes its workflow blocks in the defined order, and each block execution invokes its plugin with the configured parameters. This hierarchical traversal ensures that execution flows naturally from broad organizational contexts down to individual execution units, maintaining the logical structure defined during test composition. The engine coordinates transitions between hierarchy levels, ensuring that each level completes its initialization, execution, and finalization phases before the parent level proceeds to the next sibling or completes its own execution.

**State Progression**: Each execution entity progresses through a well-defined state lifecycle that reflects its current phase of operation. Entities begin in a pending state after creation but before execution starts. Upon initiation, entities transition to a running state indicating active execution is in progress. During execution, internal state updates reflect progress through child entities or workflow steps. Upon successful completion of all defined operations, entities transition to a passed state indicating normal termination. If errors occur that prevent completion, entities transition to a failed state capturing error details for reporting. This state progression provides visibility into execution status at all hierarchy levels and enables the engine to make decisions about error handling, resource cleanup, and reporting based on current execution state.

**Completion Criteria**: An execution entity is considered complete when all its defined operations and child entities have finished processing and the entity has reached a terminal state. For blocks, completion means the plugin execution has returned either successfully or with an error, all return values have been captured and stored, and any cleanup operations have finished. For tests, completion means all workflow blocks have executed in sequence and variable scopes have been properly managed. For suites, completion means all contained tests have finished execution regardless of their individual outcomes. For regressions, completion means all contained suites have finished execution. Completion does not imply success - entities can complete in either a success state (all operations succeeded) or a failure state (one or more operations failed), and the execution engine distinguishes between these outcomes for reporting and error handling purposes.

**Error Propagation**: When errors occur during execution, they propagate upward through the hierarchy following a consistent pattern that balances error visibility with execution continuity while providing configurable termination behavior. By default, plugin or block failures result in graceful termination of the containing test without cascading further up the hierarchy. The failed test is marked with a failed state, capturing error details for reporting, while the parent suite continues execution with the next test. The suite itself is marked as failed (containing at least one failed test) but the regression proceeds with subsequent suites. This default behavior ensures maximum test coverage by preventing individual test failures from halting entire test runs while maintaining clear failure visibility at all levels.

**Exception Handling and Recovery**: Plugin and block failures can be intercepted and handled through try-catch error handling constructs within the test workflow, allowing tests to implement custom recovery logic, perform cleanup operations, or transform errors into alternative outcomes. When a failure is caught and handled, the test can continue execution with subsequent blocks, effectively recovering from the error condition. Unhandled failures follow the default graceful termination behavior described above.

**Configurable Failure Propagation**: A Halt block with suite scope ends its parent suite, preventing execution of subsequent tests in that suite. A Halt block with regression scope ends its parent regression, preventing execution of subsequent suites. This enables critical test scenarios where certain failures indicate that continuing execution would be meaningless or harmful, such as infrastructure setup failures or prerequisite validation failures.

**Resource Management**: The execution engine manages resources following a hierarchical ownership pattern where each execution level is responsible for acquiring, utilizing, and releasing its own resources while coordinating with child entities. At execution initiation, the engine allocates execution context structures containing variable scopes, state tracking, and result accumulators. During execution, plugins acquire external resources such as network connections, file handles, or temporary storage as needed for their operations. Child entities receive resource references from parent contexts where appropriate, such as variable contexts that enable variable access. At execution completion, the engine ensures proper resource cleanup following a bottom-up pattern where child entities release their resources before parent entities release theirs. This hierarchical resource management prevents resource leaks and ensures deterministic cleanup order.

**Execution Context Lifecycle**: The execution context represents the runtime environment available to executing entities and follows a well-defined lifecycle aligned with the entity's state progression. Context creation occurs during entity initialization and establishes the variable context with namespace objects, initializes result collection structures, and creates references to parent contexts for resource access. During the running state, the context remains accessible to the executing entity and its children, allowing variable lookups, result storage, and state queries. Context modifications during execution include variable assignments within the current scope, return value capture from child entities, and state updates reflecting execution progress. Upon reaching a terminal state, the context undergoes finalization where final results are extracted, variable scopes are marked for cleanup, and context references are released to enable memory reclamation. The context lifecycle ensures that execution state remains consistent and accessible throughout the entity's lifetime while preventing memory leaks through deterministic cleanup.
