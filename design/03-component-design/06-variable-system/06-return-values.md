### 3.6.6 Return Values System

#### REQ-3.1.3.6 Return values from plugins

##### REQ-3.1.3.6 Return values from plugins

The plugin return value system provides structured output capabilities enabling plugins to produce typed data that flows into the variable system for subsequent workflow consumption. This design establishes a consistent interface for plugin outputs while preserving type information across execution boundaries and enabling seamless integration with the hierarchical variable scoping model.

**Return Value Structure and Type Preservation**: Each plugin execution produces a structured return value containing typed data elements organized in a map structure. The return structure maps output variable names to plain values, and each value keeps its own type: a string "123" stays distinct from an integer 123, and a string "true" stays distinct from a boolean true.

**Scalar Return Types**: Plugins support three fundamental scalar return types representing atomic values. String scalars represent textual data including empty strings, single characters, multi-line text, and formatted content. Numeric scalars encompass both integer values (whole numbers without fractional components) and floating-point values (numbers with decimal precision), with explicit type distinction between integers and floats preventing unintended precision loss or format changes. Boolean scalars represent logical true/false states with strict boolean semantics. Each scalar type has clear value domain boundaries and validation rules ensuring type safety. String values may undergo encoding validation ensuring proper UTF-8 representation. Numeric values may undergo range validation preventing overflow or underflow conditions. Boolean values accept only true or false rejecting numeric or string interpretations. Every type also holds null (see Null Values below). This strict scalar type system prevents the ambiguity and implicit coercion behaviors that plague weakly-typed systems.

**Array Return Types**: Plugins return array types for ordered collections of homogeneous elements where sequence matters and elements share a common type. Arrays maintain strict element ordering from plugin execution through variable storage to downstream consumption, enabling positional access patterns and order-dependent processing. Array element types are declared explicitly enabling type-safe element access and iteration. Arrays support nesting enabling multi-dimensional structures where an array's elements are themselves arrays, accommodating matrix-like data or hierarchical lists. Empty arrays are valid return values with explicit element type declaration even when no elements are present, ensuring type information persists for empty collections. Arrays provide indexed access semantics where elements are retrievable by zero-based numeric position, enabling workflows to extract specific elements, slice ranges, or iterate sequentially. The array type system aligns with common programming language array semantics while maintaining explicit typing.

**Hash Return Types**: Plugins return hash types (also called maps or dictionaries) for unordered key-value collections where associative access matters and keys provide meaningful semantic labels. Hash keys are always strings providing human-readable identifiers for values, while hash values may be any supported type including scalars, arrays, nested hashes, or tables. This enables arbitrarily complex nested structures representing configuration hierarchies, structured records, or document-like data. Hash types support dynamic key sets where the exact keys present may vary based on runtime conditions or plugin logic, enabling plugins to return optional fields, conditional outputs, or extensible structures without rigid schema requirements. Workflows access hash values by key name using associative lookup semantics where a key either maps to a value or is absent. The hash type system prevents key collision through enforcement of unique keys within each hash scope while supporting multiple hash levels for hierarchical data. Hash ordering is undefined and not guaranteed across serialization boundaries, ensuring workflows do not depend on iteration order for hash contents.

**Table Return Types**: Plugins return table types for two-dimensional structured data with named columns and typed cells, providing spreadsheet-like data structures for test data, query results, and tabular outputs. Tables consist of column definitions specifying column names and data types (string, integer, float, boolean), combined with rows of data where each cell conforms to its column's type. This structure enables data-driven testing patterns where workflows iterate over table rows, extract specific columns, or transform tabular data. Table columns maintain strict ordering matching the column definition sequence, while rows maintain insertion order enabling positional row access. Column types enforce type safety for cell values with None allowed for any type to represent missing data. Tables support empty row sets (zero rows) while preserving column schema, enabling proper initialization of table variables and type-safe empty state handling. Cell access uses two-dimensional addressing combining row index and column name or column index, enabling both positional and named access patterns. Row access returns a read-only view that raises TypeError on assignment attempts, ensuring mutations go through explicit methods like `set_cell()`. Negative indexing is supported throughout (e.g., `t[-1]` for the last row, `t.col(-1)` for the last column). Tables are particularly valuable for plugins that parse structured file formats (CSV, Excel), execute database queries returning result sets, or generate multi-record outputs where each record shares a common schema. For data operations like filtering, sorting, and aggregation, workflows use Python's built-in functions on column data (e.g., `sum(t.col('amount'))`, `max(t.col('score'))`), providing full language capability without duplicating standard library functionality. Unlike hashes which provide arbitrary key-value mapping, tables enforce schema consistency across all rows ensuring every row conforms to the declared column structure.

**Null and Empty Value Semantics**: The return value system distinguishes between null values, empty collections (arrays with zero elements, hashes with zero keys, tables with zero rows), and zero-valued scalars (empty strings, numeric zero, boolean false). Null is a value of every type, distinct from empty and zero, and keeps the declared type, enabling workflows to distinguish between "no result" and "result with empty value." Empty collections are valid typed return values preserving collection type information while containing no elements, enabling proper initialization of collection variables and type-safe empty state handling. Empty tables preserve their column schema even with zero data rows, maintaining type information for all columns. Zero-valued scalars represent actual data values that happen to be empty or zero rather than absence of data. This three-way distinction enables precise modeling of optional outputs, conditional results, and initialization states without conflating different semantic meanings.

**Multiple Output Variables**: Plugins declare and return multiple named output variables in a single execution, enabling extraction of related but distinct data elements from one operation. A bash script might return status code, stdout content, and stderr content as separate variables. A database query might return row count, execution time, and result set as separate variables. An HTTP client might return status code, headers, and body as separate variables. This multi-variable pattern eliminates the need for artificial output concatenation or complex parsing in downstream steps, as each semantic output has its own type and identifier. Named output variables map directly to variable system identifiers enabling automatic population of workflow variables without intermediate extraction logic.

**Integration with Variable Scoping**: Plugin return values integrate seamlessly with the hierarchical variable scoping system through variable assignment operations. When a workflow step captures plugin outputs into variables, those variables are created or updated in the appropriate scope (typically the test scope). The returned values become the variable values, preserving types through the assignment boundary. This integration unifies the return value system with the broader variable architecture rather than maintaining separate channels for plugin outputs and variable data.

#### REQ-3.1.3.10 Store return values as variables for reuse

##### REQ-3.1.3.10 Variable assignment from return values

The variable assignment mechanism bridges the return value system with the hierarchical variable scoping system, enabling workflow steps to capture typed outputs from plugin executions into named variables for downstream consumption.

**Assignment Operation Semantics**: Each plugin execution step may declare an assignment operation mapping return value output names to target variable names. The assignment specifies both source (output from the return value map) and destination (variable name in scope). Assignments execute atomically after plugin execution completes, regardless of success or failure status, ensuring both success outputs and error information are captured. Plugins that crash before producing return values skip assignments, but plugins that execute and produce return values (even with error status) always execute their assignments.

**Variable Naming and Mapping**: Assignment operations use explicit output-to-variable mapping. Workflows specify which plugin outputs to capture and what variable names to use, enabling selective storage and descriptive naming. Outputs not explicitly mapped are discarded. When the same variable name is assigned repeatedly (loops or parallel branches), each assignment overwrites the previous value.

**Type Preservation Through Assignment**: The assignment operation transfers each value with its type into the variable system. Variables created through return value assignment are strongly typed, ensuring type information survives storage and retrieval across scope boundaries.

**Scope Target Selection**: Test-scoped assignment creates variables visible to all workflow steps in the test.

**Assignment Validation**: Plugins declare return value types in their metadata, and the workflow validation engine verifies type compatibility before execution begins. The system validates that all referenced output names exist in the plugin's declared output schema. Type mismatches are surfaced as immediate validation errors preventing workflow save or execution.

**Null and Empty Value Assignment**: A null output writes null into the bound variable, which keeps its declared type. Empty collections keep their type. Zero-valued scalars (empty strings, numeric zero, boolean false) create variables with those explicit values rather than null. This three-way distinction (null vs empty vs zero) propagates through assignment.

**Return Value to Variable Flow Architecture**: Plugin execution produces typed return value map. Assignment maps outputs to variable names. Variables become visible in target scope. Assignment failures trigger the same error handling as plugin execution failures.

#### Null Values

Null is WAVE's one value for "nothing". These subsections hold the whole null design; the variable, Function, block and Web UI pages link here instead of repeating it.

##### REQ-3.1.3.20 Null is the only empty value

**One value for nothing**: Every variable always holds a value. Null is a value of every type - string, integer, float, boolean, array, map and table - distinct from empty text, an empty collection and zero, and a variable holding null keeps its declared type. There is no separate "not set" state: a variable declared with no value, in a test, a Function or a recipe, holds null.

**Where a value starts**: A value created by hand starts at the type's default (empty string, zero, false, empty collection): the one window for a variable, a Function local variable, a Function input and a Function output, in Add, and the suite, regression and system variable editors all preset it; in that window the author can set it to null instead, in Add and in Edit (REQ-3.1.3.24). A variable WAVE creates starts as null: an output bound to a name that is not a variable yet, a new Variable Setter target (declared when the block is saved, with the row's type), a loop's item and index, a recipe capture into an undeclared name, and a variable the test fix action declares. Each takes its type from what created it and holds null until something writes it.

**Null inside collections**: A null array item, map value or table cell stays null and fits any declared element or column type (REQ-3.1.3.19).

**How null looks**: Null has one look wherever a value is shown: the muted gray italic `null` a table cell uses, without quotes, on Variable Manager rows, watchers, the variable window and the suite, regression and system tables, for a whole null array, map or table, for a null item, map value or cell inside one, and for a null string alike (VMGR-93). The text `"null"` as a string value never takes that look. In a watcher, `null` and `no items` sit centered both ways in the body and stay centered as the watcher is resized (VMGR-94). The run console and the logs print a plain `null` (REQ-3.1.3.23).

**Secrets WAVE cannot open**: A stored secret value locked with a key WAVE does not hold, when an import or a restore brings it in, is stored as null (REQ-4.5.19). So is the masked placeholder a masked export leaves, when an import or a restore brings it in, unless a real secret is already stored at the same place. It stays a secret that holds nothing: it shows as owed, listed as a pending action item the same way as a secret declared without a value, and a block that uses it fails before sending anything, naming the field (REQ-3.1.3.21). A secret typed into a block setting that holds null the same way fails the block before it runs and names the setting; a credential left empty on purpose is stored as empty text, never null.

##### REQ-3.1.3.21 Settings and inputs refuse null

**The input rule**: One rule serves every block setting and every Function input, and it is the same whether the value is a literal or an expression:

| Field | Left empty or not set | Given null |
|-------|-------------------------|------------|
| Required | A literal left empty blocks Save | Fails at run time and names the field |
| Optional with a default | Uses the default | Fails at run time and names the field |
| Optional with no default | Is null | Is null |

A setting or input can therefore be null only when it is optional with no default, or when it is one of the data fields below. A field whose fallback the block itself picks - the SQL port per database type, the Kubernetes and Helm namespace taken from the session, the HTTP body - counts as a field with a default: left empty it still falls back, and given null it fails. A field whose default is empty text fails on null the same way. Every optional block setting has a default of one of these kinds, so a block setting takes null only when it is a data field; the third row serves Function inputs, whose authors declare it. A Function that wants an input to take null declares it optional with no default; the input's description is where its author says so.

**Data fields**: A few fields carry data rather than configure the block, so null is a value they pass on. They accept null whether or not they are required or have a default:

| Data field | What null does |
|------------|----------------|
| Variable Setter value (each row) | Writes null into the target |
| Log message | Prints `null` |
| The value a check tests (Assert, If, Switch, While, Wait Until) | Is checked as holding nothing (REQ-3.1.3.25) |
| SQL parameter value and procedure argument value | Binds NULL (REQ-3.1.3.22) |
| Python input variable | Arrives as `None` |
| For Each collection | Runs zero times (REQ-3.1.3.25) |
| For count | Runs zero times (REQ-3.1.3.25) |

Where a data field is an entry of a map setting - SQL Parameters, procedure Arguments, Python Input Variables - the entries accept null, while the setting as a whole has an empty map as its default, so a whole null map fails it. The items of a For Each collection are data the same way: a null item, map value or record value passes on as null.

**Named entries**: The entries of a setting that is not data - HTTP headers, query parameters, form fields and parts, Kubernetes Apply data and secret data, Helm set values, SQL driver options and out arguments, OpenSearch fields and stats, CSV and Excel sorts and filters, Cipher Suites - follow each Block's own rule. A null list item, map value or row reaches the Block as null, whether it was stored or came from an expression, and each Block decides per field: it uses the null its own way, or it fails naming the field and the entry, as the script fields do with `'{key}' in '{setting}' is null` and `Row {n} in '{setting}' is null` (REQ-3.1.3.22). Helm set passes a null as `key=null`; a null SQL out-argument name, a null CSV or Excel sort or filter, and a null Cipher Suites entry fail naming the field and the entry. An entry or row left empty stays empty text, and an {x} entry left blank blocks Save (FIELD-13).

**Function input entries**: A Function input takes null entries: a null item, map value or table cell inside a list, map or table input reaches the Function as null, whether or not the input itself may be null.

**Function inputs**: A Function Block's inputs are its fields, so the input rule applies to them when the Block runs, as it does to any Block's settings, before the first block of the Function starts, and the Function needs no check of its own. Every field is resolved in the flow the Block sits in first; a field that fails to evaluate fails the Function Block and names the input, and its source text is never passed in. A field not set, or holding a blank expression, is nothing given: an input that is not Required takes its default, else null; a Required input is never filled from its default on a Function Block (REQ-3.1.2.10). A Function run on its own - Run or Debug in the library view, or a scoped run with no earlier run to start from - gives each input its own value as its Variable Manager shows it, required or not.

**Function outputs**: A Function that finishes hands back what it wrote into each output, else the output's default, else null; a Function that fails hands back nothing. A null an output returns, such as a null query cell, is never a reason to warn; the warnings are about the Function's definition instead: every run of a Function Block writes a WARN to the run log for an input no block in the Function uses and for an output no block writes (REQ-3.1.2.7).

**Variable Setter rows**: An expression row left empty blocks Save, and so does an emptied number box; a text row left empty writes empty text, which is a value. A row that should write null says so with the expression `None`.

**Failure messages**: A block setting given null fails with `'{setting}' is null`, where `{setting}` is the setting's name as the block declares it, the same name every other block message uses. A Function input is a field of its Function Block, so it fails with the same wording, `'{name}' is null`, where `{name}` is the input's declared name, and a field that fails to evaluate fails with the wording every block setting uses. A Function run on its own uses the same wording.

##### REQ-3.1.3.22 Null in text, scripts and SQL

**`{{ }}` pieces**: A text with `{{ }}` pieces is never null itself, so the pieces carry the rule: a piece whose result is null fails the block and names the piece, with `'{{ {expression} }}' in '{setting}' is null`. Writing the word `null` or `None` into a URL, a path, a name or a stored text would be a silent conversion, so no field does it. The check is on the result of the whole piece, so a piece that supplies its own fallback, such as `{{ x if x is not None else 'default' }}`, never fails. The same rule covers `{{ }}` entries inside a map setting and a template variable (REQ-3.1.3.15). Two fields write null instead, each declared in its block's definition: the Log message prints `null` for a null piece, and the OpenSearch Query DSL writes JSON `null` where the piece stands alone as a JSON value, while a null piece inside quotes there, or anywhere in DQL, fails like any other.

**Scripts**: A shell has no null, and empty text there is dangerous, so a null value never reaches a script as text. Everything that does - Shell Script input variables and arguments, Shell Exec input variables, Python arguments and Environment entries - passes through one step that turns WAVE values into text, and that step fails the block before the script starts when a value is null. A named entry fails with `'{key}' in '{setting}' is null`; an argument row fails with `Row {n} in '{setting}' is null`, counting rows from 1. An entry or row left empty stays empty text. A list, map or table still arrives as one JSON text, with `null` written inside it for a null item, map value or cell. Python input variables are not text: they arrive as `None`.

**SQL**: A SQL parameter value and a procedure argument value are data fields. Empty text binds as empty text and null binds NULL, so a test can tell the two apart in the database.

##### REQ-3.1.3.23 One null across languages

**One null**: Python's `None`, SQL's NULL and JSON's `null` all become WAVE's null, and WAVE's null becomes each of them on the way back. A null a block writes into a variable stays null whatever the variable's type, and the variable keeps its type: a Python export of `None`, a NULL in a query result or in a procedure's out values, a JSON `null` a parser reads, and a `null` in a recipe or from an MCP client, where it is valid for every type. In an expression null is written `None`, as Python writes it.

**Printing**: WAVE's own printing writes a value in WAVE's form: null as `null`, a boolean as `true` or `false`, and a list or map as JSON text with `null` inside for a null item or map value. This holds for a whole value in the run console, the Log message and its `{{ }}` pieces, messages and reports. Text Python builds itself inside an expression, with `str()` or an f-string, still writes Python's own `None` and `True`.

**Expressions that meet null**: An expression that fails because a value is null fails with `A value is null: {message}`, where the message is Python's own with every `NoneType` in it written as `null`, quotes kept as Python wrote them, so the author sees which value was missing rather than Python's type name.

##### REQ-3.1.3.24 Set to null by hand

**Where null is set by hand**: In the one window for adding and editing a variable, a Function local variable, a Function input and a Function output, a "Set to null" checkbox offers null, on its own row under "Mark as secret", for the Initial value (an input's default) and for the Current value alike (VMGR-97, VMGR-111). Ticked, the Kind select and the value field give way to one grayed `null` field with no editor button, whatever the kind, and the window saves a plain null. Unticking brings back the kind and the value from before the tick, unless the null was saved. An emptied number box ticks it when it loses focus, where it is not locked. The checkbox is hidden while Kind is Expression or Template; Kind goes back to Literal first. For an input, null is a null default, so a Function Block that sets nothing passes null; for an output, null means no default, so an output nothing wrote returns null. On a Required input the checkbox is unticked and locked ("off while Required is set"), because a Required input refuses null (REQ-3.1.2.10, REQ-3.1.3.21). On an enum input it is unticked and locked ("off while enum is set"), because an enum input is never null and its default is one of its allowed values (VMGR-112). A secret input has no default: the checkbox is ticked and locked, with a tooltip saying why (VMGR-103).

**Everywhere else, `None`**: Where a value can be an expression, null is the expression `None`: a new variable of Kind Expression, Variable Setter rows, block fields (Function Block inputs included) through the expression toggle, and a recipe's JSON `null`. Inside a list, map or table, `null` written in the Code view text is a null item, map value or cell, and a table cell keeps its own null control. A whole `null` typed as the Code view text of a list, map or table is refused in every editor with that view's existing message (VMGR-96): the checkbox is the one way to a null whole value.

**Where a null control is offered**: A null control is offered only where a whole null is allowed: for a variable, a Function local variable, a Function input or a Function output in its window, through Set to null above; and on a Block window, for a Function input that is optional with no default and a block data field that accepts null, through the null icon (∅) inside the field (FIELD-5). A field that refuses a whole null - a Required field, an optional field with a default, an enum input - never offers one; whether a block field accepts a whole null is part of its declaration in its block's definition. Suite, regression and system variables offer none. Where the null option is off, an emptied number box blocks Save with the type's existing message and never means 0 (VMGR-95).

##### REQ-3.1.3.25 Checks and loops on null

**Checks**: A check treats null as a value that holds nothing, the same in every block that checks a value - Assert, If, Switch, While and Wait Until:

| Operator on a null value | Result |
|--------------------------|--------|
| equals, less than, greater than, less or equal, greater or equal, contains, starts with, ends with, matches, has key, is true, is false | false |
| not equals, does not contain, does not have key | true |
| is empty, length equals 0 | true |
| is not empty, length equals any other number | false |
| is null | true |
| not null | false |

"is null" and "not null" are offered for every type and tell null from empty; they and the other operators that need nothing to compare with - is empty, is not empty, is true, is false - take no compare-to value. A table offers is null, not null, is empty and is not empty, where empty means no rows. A check never fails the block because the value it tests is null: `status not equals 'done'` is true for a null `status` as for any other value that is not `'done'`. The value it compares with is a setting, not data, so a null there fails the block and names the variable being checked. `length equals` compares the item count as a number, and `contains` on a list compares typed values, so the integer `3` and the text `'3'` differ. A failed assertion on a null value shows `actual: null` on its own line, and a row whose operator takes no compare-to value prints none. A Switch offers the same operators in each case's condition rows; a null goes to Default unless a case above catches it first, as a case using is null, not equals, does not contain, does not have key, is empty or length equals 0 does. The CSV and Excel filter rows and the table filter in expressions follow the same rule. A Wait Until whose condition reads a null value keeps waiting, as it does for a field that is not there yet. An expression condition is Python and follows Python's own rules, with the null message of REQ-3.1.3.23 when it fails.

**Loops**: A loop on null runs zero times by the same rule: a For Each over a null collection and a For with a null count run no iterations and continue past the loop. A null item inside a list reaches the loop body as null, never as text.
