### 3.6.5 Secret Variable Masking

##### REQ-3.1.3.5 Secret variable masking in logs

The secret masking system protects sensitive information by replacing secret values with a masked representation in every observable output of a run, preventing credentials, API keys, tokens, and other confidential data from being exposed through logs, console streams, reports, execution artifacts, WebSocket messages, or debugger views, while execution itself always computes on real values.

**Secret Designation Model**: A secret is anything the user or a plugin explicitly declares secret. There is no guessing: variable names, field names, and value shapes are never used to infer secrecy. Secrecy is a property of a variable or of a declared field: a plugin's input field is secret only when the plugin declares it a credential field (REQ-3.1.3.18), and a Function input is secret when its author marks it secret, so it acts as a block's secret field (REQ-3.1.2.9, SECUI-10). Any other input that needs a credential references a secret variable rather than holding a secret of its own. Designation happens through three explicit paths:

1. **Explicit variable flag**: Users mark a variable as secret when they author it. Secrecy is a property of the variable, like its type and its kind, and is set on every surface that authors a variable: the Variable Manager's variable window, in Add and in Edit (in Edit, turning it on for a saved plain variable asks to confirm and seals the value; turning it off for a saved secret asks to confirm and clears it, VMGR-109), the variable setter rows, an output binding, the suite, regression, and system variable editors, and profile parameters. The flag is independent of the variable's data type and scope; any variable at any hierarchy level (system, regression, suite, test) can be secret whether it holds a string, number, boolean, array, map, or table. A secret variable's literal is masked on read, sealed at rest, and replaced write-only: an authoring surface never shows the stored value, and editing opens an empty field. For an array or map the elements' declared types (REQ-3.1.3.19) are masked with the value, so a read names no key and counts no element.

2. **Plugin output declaration**: Plugin output definitions carry a secret designation for outputs that inherently produce credentials. When such an output is bound to a variable, that variable becomes secret for the run and its value is protected, without requiring the user to remember to flag it. A binding may also be marked secret by the user, making the bound variable secret even when the output itself is not declared secret.

3. **Plugin-internal registration**: A plugin that acquires a sensitive value in the middle of its execution (a token returned by a login call, a credential read from a platform secret store, a session cookie issued in a response) registers that value with the run's secret registry the moment it is acquired, before the value is used or logged. Plugins also register credential values that are embedded inside otherwise non-sensitive outputs (such as cookie headers within a response header map), so the containing output remains viewable while the credential bytes themselves are protected.

Designation never propagates through transformation. Copying a secret into another variable does not make that variable secret, and deriving a new value from a secret (encoding, slicing, concatenating into different bytes) produces an unprotected value. Byte-identical copies are still caught by value-based masking wherever they appear; deliberately transformed values are the user's explicit choice to expose.

**Per-Run Secret Registry**: Each run session maintains a registry of secret designations and secret values. The registry fills when secret-flagged variables load or lazily realize, when a secret-flagged variable is written during the run, when values resolve into secret-declared parameters, when secret-declared or user-marked outputs are produced, and when plugins register acquired values. The registry lives and dies with the run session; it is engine-internal state and is never itself serialized to any output.

**Two Masking Mechanisms**: Masking applies at the point where data leaves the engine for user-observable surfaces, through two complementary mechanisms. Value scrubbing replaces every occurrence of every registered secret value inside outbound text with the mask placeholder, regardless of how the value got there: a token interpolated into a composed header map, embedded mid-string in a log message, or echoed inside an error is scrubbed by exact byte match, while surrounding non-secret content stays readable. Container secrets register both their scalar leaves and the string forms of the container itself (and of every nested container), including the form WAVE prints it in, so printing a whole secret list, map or table as text renders one single placeholder rather than exposing its keys or items. Structural masking applies to variable-shaped payloads (variable displays, watch pushes, execution snapshots, report variable tables): variables flagged secret are fully opaque - the entire value collapses to the bare placeholder with no keys, no shape, and no element counts; unflagged entries whose value byte-matches a registered secret are masked as well.

**Mask Representation**: One canonical placeholder, eight asterisks, is used across every channel and surface. The representation never reveals any fragment of the protected value: no leading characters, no partial hints, no length correlation in text, no keys, and no structural outline - a secret displays as the placeholder and nothing else. Non-content metadata (string length, collection size, designation source) remains available to inspection surfaces so users can diagnose credential problems (truncation, wrong encoding, empty values) without value or key exposure.

**Scrub Floor for Very Short Values**: Values whose textual form is shorter than a small floor (six characters) are excluded from text scrubbing, because replacing ubiquitous short strings (single digits, tiny numerals inside unrelated content) would corrupt the readability of every log line. Such values are still fully masked by structural masking in variable displays. Boolean values are never text-scrubbed; a boolean's two possible values carry no secrecy, and scrubbing them would only damage output.

**Comprehensive Output Channel Coverage**: Masking intercepts every engine-produced observability path: execution log entries at their single construction point (which feeds the live console stream, the persisted run log, per-test log artifacts, report log and error sections, and failure summaries), the parallel terminal log sink, WebSocket variable-change pushes and watch updates, breakpoint and completion error texts, step-debugger variable views, execution variable snapshots persisted for later display, and report generation. Because log text is scrubbed at its construction point, everything derived from stored logs inherits masked content. A value that is laid out for display is masked before its width is measured, so no alignment can disclose a protected value's length. The bound on a log message is applied after the last masking step, so a bound can never sever a value out of a masker's reach.

**Masking Boundary - Observability vs. Deliberate Output**: Masking governs what the engine emits about a run. It does not govern content a workflow deliberately produces as its function: when a plugin writes file content on the user's explicit instruction (for example a configuration file that must contain a real password for the system under test), that content is the user's intentional product and is written as instructed. The distinction is intent: engine-originated descriptions of execution are always masked; user-instructed payload output is not.

**Uniform Plugin I/O Logging**: The engine, not each plugin, records what goes into and comes out of every plugin execution. At debug verbosity the execution harness emits one masked inputs line immediately before a plugin runs (the fully rendered parameter values) and one masked outputs line immediately after (the values available for binding) - identical in shape for every plugin, with no per-plugin masking code. Masking in these lines is declaration-driven: parameters declared secret, and outputs that are declared secret by the plugin or marked secret on the block, render only the placeholder. Inside map-shaped values, the entries named by the plugin's declared credential-field catalog are masked individually while the rest of the map stays readable - the catalog is exact protocol or API knowledge the plugin declares (authorization, cookies, API-key headers for an HTTP client), never inference from user data (REQ-3.1.3.16). The block's per-field reveal choices and its run-output masking control apply to these lines exactly as to every other emission. Long values are truncated for readability; truncation is a display bound, not a masking mechanism. Plugins do not print their own inputs or outputs: output values exist only after execution while a plugin logs during it, so plugin-side dumping would structurally bypass the declarations. Plugin logging is reserved for genuine diagnostics (connection progress, retries, transport configuration), and a plugin still registers credentials it acquires mid-execution the moment it acquires them, which also protects credentials no declaration covers yet, such as server-issued cookies in a response.

**Per-Block Run-Output Masking Control**: Because WAVE is a testing framework, a user diagnosing a security system may legitimately need to see real values in a specific block's run output. Every plugin instance carries a run-output masking control - a three-way choice declared in the block's configuration: follow the system default, always reveal, or always mask. Follow-the-system-default inherits the system-wide run-output reveal setting (REQ-3.1.3.17); always-reveal and always-mask override that setting in either direction for this one block. Revealing bypasses value scrubbing and plugin protocol masking for the block's log lines and report entries, and the exposure applies wherever those lines flow (console, stored logs, reports, failure summaries); there is no pretense of a live-only reveal once the value has left the engine. Because every block defaults to inheritance, changing the system setting moves all inheriting blocks at once while per-block overrides stay the exceptions - a global reveal can still keep a chosen block masked, and a global mask can still reveal a chosen block, without touching any other node. The choice is part of the test definition, so the exposure is visible in review, versioning, and export. A block whose effective state is revealing is flagged on the canvas by an amber warning in the node's status area - occupying the same slot as, and superseded by, the red misconfiguration indicator - and a run that contains revealing blocks warns at run start, naming them, and again immediately before each such block executes. All other blocks' output in the same run remains masked according to their own effective state. A rendered table shows its at-rest form, so a block's own declared reveal shows that block's cells while a temporary system-wide reveal does not.

**Raw Values Inside the Engine**: The execution core always operates on real values. Variable resolution, expression evaluation, parameter resolution, assertions, and plugin execution receive unmasked data; a secret system variable resolves to its actual value when injected into a run, never to the mask placeholder. Masking is strictly a property of emission, applied to outbound copies. Masked representations never round-trip back into stored values or into execution state. The mask placeholder carries no authority to overwrite: when a definition is saved and a secret value arrives as the placeholder (the only thing an authoring surface ever holds for a stored secret), the stored secret is preserved unchanged rather than replaced, so editing anything else in the same definition can never destroy a saved secret. This guard applies at every save boundary that persists secret variables (tests, suites, regressions, system variables, functions, and profiles) and at the node-configuration boundary where a variable setter persists a secret literal.

**Masking Consistency Across Execution Modes**: Masking behaves identically in normal runs, breakpoint debugging, and step execution. Debugger variable panels, paused-state inspection, and re-executed block output all present secret values masked, so interactive debugging cannot become an extraction channel. The only paths to a visible secret value are the two deliberate ones: transforming the value into different bytes, or declaring the unmask option on a node.

**Masking Performance**: The registry maintains the set of scrubbable value forms ordered for correct longest-first replacement, so scrubbing is a bounded number of plain substring replacements per outbound text, with no pattern compilation and no scanning of variables per output operation. Structural masking is applied only to variable-shaped payloads at their serialization points. Parallel branches share the run's registry; registration and lookup are simple set operations that do not contend.

##### REQ-3.1.3.16 Per-block protocol-field masking control

The fields a plugin masks by protocol knowledge are not a hidden, all-or-nothing behavior. Each such plugin exposes the exact set of fields it treats as credential-bearing as a per-block control, so the masking is visible and adjustable where the block is configured. The control lists every declared credential field of that plugin, each masked by default, and a user diagnosing one field on one block can reveal that single field for that block without affecting any other field or any other block.

Revealing a field is a value-level exemption scoped to the block: the field is neither masked in the engine's logging of that block's inputs and outputs nor registered with the run's secret registry, so the field's value is visible wherever that block's output flows, while every still-masked field stays protected. Because masking operates on the field's value, a still-masked field is hidden even inside an otherwise-viewable container the block emits: a response header map renders its structure and its non-credential entries in the clear while a masked credential header shows only the placeholder. This is independent of, and composes with, marking a whole bound output variable secret, which collapses the entire variable rather than a single field.

The reveal set is part of the block's configuration, so an exposure is reviewable, versioned, and exported alongside the rest of the definition, exactly like the per-block run-output masking control. The field catalog is exactly what the plugin declares from its own protocol or API knowledge; there is no pattern, shape, or entropy inference and no user-authored field or expression - the plugin declares the catalog and the user only chooses, within it, which fields to reveal. When the block's run output is revealed in full - by its own always-reveal choice or by the inherited system default - the per-field control has no further effect and is inactive, since every field is already exposed.

##### REQ-3.1.3.17 System-wide secret reveal controls

Masking is on by default across every observable surface, and the deployment exposes a small set of system-wide reveal controls that govern where secrets may be shown, each off by default so that the secure state requires no configuration. The controls are scoped by where a secret can be seen rather than one blunt switch: one governs run output (logs, console, reports, execution history); one governs a test's variable values in the workbench, covering the Variable Manager panel and its watchers together; one governs the global, regression, and suite variable editors; and one governs plugin credential input fields (REQ-3.1.3.18). The two variable controls are cut by scope - a test's own variables versus the shared variables inherited from higher levels - so revealing what you are building need not reveal the shared library, and vice versa. Turning a control on reveals secrets in that surface across the whole deployment. The run-output control additionally serves as the default that every block's per-block run-output masking control inherits and may override (REQ-3.1.3.5), so a block's effective run-output state is the resolution of its own choice against this system default.

These controls govern runtime masking only. Export handling keeps its own independent per-export secret choice (keep encrypted, decrypt, or strip to the placeholder), and encryption at rest is unaffected - revealing a surface never decrypts stored data. When run-output masking is revealed system-wide, the run-start and per-block reveal warnings fall silent, because every block is already exposing its values and the warnings would only add noise.

The controls are this WAVE's own settings, kept in its config file (REQ-4.7.17), and change only when the admin saves Settings > General (REQ-4.7.16); a saved change applies to every surface at once and survives a restart.

##### REQ-3.1.3.18 Declared credential input fields

A plugin's input fields carry no user-facing secret toggle; a Function input is the one input an author marks secret, and it then acts as a declared credential field (REQ-3.1.2.9, SECUI-10). A plugin knows from its protocol or API which of its own input fields carry credentials - an SSH session's password, private key, and passphrase; a database profile's password. Those declared credential fields are protected by default wherever a value is entered directly, without introducing a second class of secret carrier: a credential field references either a protected literal it seals itself or a secret variable, and both routes are protected end to end.

A literal typed into a declared credential field is sealed at rest in the block's configuration, in the same encryption envelope used for a secret variable, a variable-setter literal, and a profile credential. A value still being typed, before the definition is saved, stays visible and editable; once saved it is sealed, and the field becomes masked and write-only, with editing clearing it for re-entry - the same drop-to-replace flow as a profile credential. A stored credential is read back in the clear only through its own deliberate system unmask control for plugin credential input fields (REQ-3.1.3.17); while that control is off the field stays masked. The sealed literal is unsealed at run time, so the connection receives real bytes while every observable surface stays masked, and it honors the per-export secret choice (keep encrypted, decrypt, or strip) exactly as a setter literal does. When the field instead holds an expression, protection follows the referenced variable: a reference to a secret variable is protected, and a reference to a non-secret variable is not - its value is stored and displayed in the clear, which the field signals so the choice is visible rather than silent.

A declared credential field that carries a map of values is sealed value by value rather than as one opaque blob: every value takes its own encryption envelope while the keys stay readable at rest, so the stored definition keeps the map's shape and its type. Its protected state hides more than a single-value field's does - the field shows neither the keys nor how many entries there are - and confirming an edit clears the whole map for re-entry rather than one entry. The system unmask control for plugin credential input fields (REQ-3.1.3.17) reaches a stored map only when the definition is loaded with the control already on; turning the control on while the field is open lifts the single-value fields beside it and leaves the map protected.

Each declared credential field carries a single status indicator: a protected state when its value is a sealed literal or references a secret variable, and an unprotected state when it references a non-secret variable. The indicator states the protection status on inspection; the unprotected signal is informational and never blocks saving or running. The treatment is entirely declaration-driven - a plugin gains sealing, the masked write-only field, and the status indicator by declaring which of its fields are credential-bearing, with no per-plugin masking behavior of its own - so every plugin that declares credential fields inherits identical protection. This composes with the runtime masking every plugin already receives (REQ-3.1.3.5): the field's value is registered and scrubbed from run output regardless of which carrier holds it.

While a literal typed into a declared credential field is still visible, the field says so: a line under it states that the typed secret stays visible until the Test (or, in a library Function view, the Function) is saved.
