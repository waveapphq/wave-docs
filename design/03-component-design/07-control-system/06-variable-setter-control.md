#### 3.7.6 Variable Setter Control

##### REQ-3.4.1.14 Variable setter control

The variable setter is a flow control that provides explicit, declarative variable assignment at any point in a workflow. It is registered in the control registry alongside other flow controls (if/else, for, while, etc.) and appears in the Flow category of the block palette.

**Control Purpose and Use Cases**: The setter control allows test designers to explicitly set variable values within a workflow. Primary use cases include initializing configuration variables before executing blocks that require them, storing computed values derived from expressions or previous block outputs, resetting variables to specific states for test repeatability, and establishing baseline values for conditional logic. Unlike implicit variable assignment from block return values, the setter control provides explicit, self-documenting variable assignments visible in the workflow visualization.

**Parameter Schema**: The control accepts a single required parameter - `variables` - which is a map of variable names to values, one entry per row. Each assignment consists of a variable name identifier and a value that can be a literal (string, integer, float, boolean, array, map, table, null), a reference to an existing variable, a computed expression, or a template string whose placeholders are filled from other variables. The map is one Block field: the Block stores each row's value and its expression, template and secret marks, and for a list or map row the entry types in the Block's shared element-type record. The expression, template and element-type records are keyed by the row's name, and an entry inside a row's list or map value is keyed one level deeper; the rows marked secret are kept in one secret record. A row's own type is the declared type of its variable and is never stored on the Block. Multiple variables can be assigned atomically within a single setter instance, with assignments executing in declaration order.

**Expression and Template Resolution**: Resolution operates at the individual variable level rather than the parameter level. The Block's shared marks say which rows - and which entries inside a row's list or map value - are expressions and which are templates, and the shared resolver evaluates only the marked ones, two levels deep - evaluating expressions and rendering templates - so the control receives a fully resolved map. Resolution is eager: a template is rendered at the moment the setter executes, substituting the current values of the variables it references, and the target variable receives the rendered string. This mirrors how the setter evaluates expressions, keeping a single resolution model for both computed kinds. Expression and template marks are mutually exclusive per entry.

**Value Authoring**: Each assignment row's value is the one value field every Block field uses (REQ-3.1.1.5): text and numbers are typed on the row, true / false is a checkbox, a list, map or table is written out as one line, and expand opens the shared value editor the variable window uses - the string editor with Literal / Template, or the structured visual and code editor for complex types - with the same validation and numeric-precision guarantees, so a value authored in the setter is validated and stored identically to one authored anywhere else. A row's value is a data field: it takes null through the null icon, and inside a list or map value each first-level entry has its own mode - plain, expression, or for a text entry template. The value editor is a focused surface scoped to the single value being edited; the assignment's name, type and secret mark are managed on the row.

**Type Preservation**: Values assigned through the setter maintain their data types - numbers remain numbers, booleans remain booleans, and complex types (arrays, maps, tables) preserve their structure. The control validates type compatibility with the variable system's type constraints. A row for a variable that exists takes that variable's declared type, in the window and when the setter runs, so a later change of the variable's type never leaves the setter holding the old one; the type picked for a new target declares that variable when the window saves. A plain value that no longer fits the variable's new type is dropped when the window opens, or as soon as the variable is retyped while the window is open, leaving the row empty with `Value is required`, as a Function Block input is (FNCFG-9); an expression row is kept as written and is not type-checked at Save. A Template row on a variable that is not text, and a Template entry whose entry type is not text, are refused at Save and in the window.

**Scope and Integration**: The setter writes the variables of the flow it runs in (REQ-3.4.3.8): in a Test, test-level variables; inside a Function, that Function's own variables and its declared outputs, never its read-only inputs. A new name becomes a variable of that flow, declared when the block is saved; there is no block-local scope. The control operates within the normal execution lifecycle, logging all assignments at DEBUG level for audit trails.

**Validation**: The `variables` parameter is required and must not be empty. An empty variables map is reported as a required field left empty, and a missing one as a required field missing. On load context, these are reported as warnings; on import and run contexts, they are blocking errors. Each row is checked by the one save check like any Block field: an expression row left blank, a number that breaks the one number rule, a plain value that does not fit its variable's declared type, a name an expression or template reads that is not declared, an expression that would change data, a Template row on a variable that is not text or a Template entry whose entry type is not text, and an element type outside the declared types are refused at Save.
