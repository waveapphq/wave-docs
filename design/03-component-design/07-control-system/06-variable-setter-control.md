#### 3.7.6 Variable Setter Control

##### REQ-3.4.1.14 Variable setter control

The variable setter is a flow control that provides explicit, declarative variable assignment at any point in a workflow. It is registered in the control registry alongside other flow controls (if/else, for, while, etc.) and appears in the Flow category of the block palette.

**Control Purpose and Use Cases**: The setter control allows test designers to explicitly set variable values within a workflow. Primary use cases include initializing configuration variables before executing blocks that require them, storing computed values derived from expressions or previous block outputs, resetting variables to specific states for test repeatability, and establishing baseline values for conditional logic. Unlike implicit variable assignment from block return values, the setter control provides explicit, self-documenting variable assignments visible in the workflow visualization.

**Parameter Schema**: The control accepts a single required parameter - `variables` - which is a map of variable names to values. Each assignment consists of a variable name identifier and a value that can be a literal (string, integer, float, boolean, array, map, table, null), a reference to an existing variable, a computed expression, or a template string whose placeholders are filled from other variables. Multiple variables can be assigned atomically within a single setter instance, with assignments executing in declaration order.

**Expression and Template Resolution**: Resolution operates at the individual variable level rather than the parameter level. The assignment surface marks which entries are expressions and which are templates with per-variable kind flags, and the execution engine resolves only the marked entries - evaluating expressions and rendering templates - so the control receives a fully resolved map. Resolution is eager: a template is rendered at the moment the setter executes, substituting the current values of the variables it references, and the target variable receives the rendered string. This mirrors how the setter evaluates expressions, keeping a single resolution model for both computed kinds. Expression and template marks are mutually exclusive per entry.

**Value Authoring**: The setter's value editing is unified with the rest of the variable system. Each assignment row presents the same type-aware value treatment used everywhere a variable value is authored: compact scalar values (integer, float, boolean) and expressions are edited inline in the row, while string and complex (array, map, table) values open a shared value editor. That editor offers the same string formatting and template authoring, the same structured visual and code editing for complex types, and the same validation and numeric-precision guarantees as the variable manager - so a value authored in the setter is validated and stored identically to one authored anywhere else. The value editor is a focused surface scoped to the single value being edited; the assignment's name and kind are managed on the row.

**Type Preservation**: Values assigned through the setter maintain their data types - numbers remain numbers, booleans remain booleans, and complex types (arrays, maps, tables) preserve their structure. The control validates type compatibility with the variable system's type constraints.

**Scope and Integration**: Variables are created at test scope, with the execution engine determining effective scope from the current execution context. The control operates within the normal execution lifecycle, logging all assignments at DEBUG level for audit trails.

**Validation**: The `variables` parameter is required and must not be empty. An empty variables map triggers `REQUIRED_PARAM_EMPTY` validation, while a missing variables parameter triggers `REQUIRED_PARAM_MISSING`. On load context, these are reported as warnings; on import and run contexts, they are blocking errors.
