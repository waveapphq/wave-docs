#### 3.8.5 Session Ownership and Live Mirroring

The workbench session model is defined for viewers and holders in general - browser tabs, additional users, and the MCP assistant are all the same kind of participant. The MCP introduces no special session mechanics; it exercises the general model.

##### REQ-5.2.7.15 Single-active-session ownership

The workbench allows a single active session at a time. The session is held by exactly one participant - the holder - and only the holder mutates it. Holding is automatic and invisible in the normal case: a user editing alone simply holds the session, with no additional interface presence.

Every other participant viewing the workbench sees the same session live - the graph and its variables changing as the holder changes them, blocks appearing, connections forming, values updating. This is single-writer mirroring, not co-editing: because only the holder ever changes anything, there is nothing to reconcile between participants, and there are deliberately no per-viewer cursors or presence marks, which would only add noise across differing screens. The mirrored stream carries the identity of the surface along with its content - which test is open, or that the surface is an unsaved draft, and whether it holds unsaved work - so every viewer names what it is looking at truthfully, and a mirrored surface can never masquerade as a test the viewer merely had open before.

A mirroring view is read-only and clearly marked. The canvas is visibly non-editable, a prominent banner names the current holder, and a take-over control is always available. The banner distinguishes a person from the assistant: an assistant holder is shown as such and carries its client identity, so it is always clear who - or what - is driving, including across successive hand-offs. When the holder is an assistant, the banner also offers a direct path to that client's entry in the MCP section of System Config, where the connection can be inspected or ended.

The same rule governs a test's own files. Only the holder changes them; a mirroring view reads them and is offered no way to add, rename or remove one. What is on its way in belongs to the test rather than to the tab that started it, so every viewer sees the same uploads live, including ones it did not start, and a file that did not land leaves a notice that outlives the tab. Taking over does not stop an upload already under way, because the bytes exist only in the tab that started it; the session that loses the test simply starts no more. An upload is stopped by the session holding the test or by the one that started it.

The mirror follows the holder only while the viewer stays on the holder's surface. A viewer who opens or closes a workflow of their own choosing browses freely instead: the canvas stays read-only - the session is still held - and the banner states exactly that, naming the holder that has the workbench and, when a run is in flight, that a run is underway. Nothing the holder does moves a browsing viewer's canvas, and following ends implicitly the moment the viewer navigates. The banner carries one control that returns the viewer to watching the live session, converging on the holder's current surface - the draft, or the run in flight.

The mirror carries the holder's execution surface as well as their draft. While the holder has a run in flight, every watcher sees the run the holder sees: blocks painting their execution states as they run, variable values updating as the run writes them, and the Console panel streaming the run's output line by line as it is produced. A watcher who joins mid-run receives what the run has already produced - the painted states and the console lines so far - and then the live remainder, which stays readable after the run ends. The run's environment is reflected read-only to every watcher, in the place the environment control normally occupies, so a mirror always shows which environment the run actually carries rather than the watcher's own last local selection. For the duration of a run the banner's trailing phrase reads "read-only, running live", whoever holds the session.

A mirroring view holds no run control: starting, stopping, and stepping a run belong to the holder alone, and the one live control a watcher keeps during a run is Focus Current, which only moves the viewport. Mirroring is strictly broadcast - watchers are silent recipients of the same streams the holder consumes - so a run watched by any number of mirrors leaves exactly the record, logs, statuses, report, and history that the same run leaves unwatched.

An unattended run the assistant starts is mirrored the same way. For a test run the assistant holds the session for exactly the run's duration - the banner names it as the holder of a run - and releases it when the run reaches its terminal state. Suite and regression runs do not occupy the workbench surface and are not mirrored. When the session cannot be borrowed, the run still starts; it simply goes unmirrored.

Browser sessions are first-class connections in the same way. Every browser connected to WAVE is tracked as a named connection carrying its own identity - the browser and operating system it runs in - along with the address it connects from and its connection and last-active times, where "last active" is its last real interaction rather than connection keepalive. A dedicated WAVE Server section of System Config makes these connections visible and manageable. It presents the two servers behind WAVE - the one that serves the interface and the one that carries the API and the live sessions - as read-only facts: each server's running state, the numeric addresses it is reachable on, its listening port, and its bind scope. These facts are settled when WAVE starts and are shown for transparency rather than as controls, since the server that serves the operator cannot be reconfigured from within itself; anything on the section that is not manipulable as WAVE configuration is presented read-only.

Below the server facts, a live roster lists every connected browser session and the role it currently plays: the session holding the editing lock reads as Active, and any session mirroring it read-only reads as Watching. An administrator can end any one of them behind a confirmation, or end all sessions or all but their own in a single guarded sweep. The administrator's own sessions are marked distinctly, and because one person may hold several tabs at once, every tab of their own browser carries that marking, so their own connections are never mistaken for another's. Ending a session disconnects that browser and returns it to a clearly disconnected state, from which a deliberate reconnect starts a fresh session. The identity a session carries is its connection - browser, operating system, and origin address - so that a session is always answerable to a real, reachable origin.

Because a browser session is a real connection, a person holding the workbench is as traceable as an assistant. A person-held mirror banner names the holder by its connection identity rather than a generic "another session", and carries the same See connection path an assistant-held banner does - opening the WAVE Server section scrolled to and highlighting that exact session, with the means to end it beside it. Whoever, or whatever, is driving a shared session is always one step from the connection behind it.

A participant's identity lasts as long as the browser tab it belongs to, across reloads of the page. Reloading is a continuation, not a departure: the tab comes back as the same participant and resumes whatever it held, without asking and without passing through a read-only state. Two tabs are always two participants, including when one is duplicated from the other - a tab that finds its identity already in use elsewhere in the same browser takes a fresh one, so the single-active-session guarantee cannot be broken by copying a tab.

Holding outlives the Workbench screen. A holder who navigates to another part of WAVE keeps the session, because their draft is still theirs and they are expected back. Both of the signals that keep a session honest therefore belong to the tab rather than to the screen: for as long as the tab is open it goes on showing that it is there, from whatever page it happens to be on, and when it leaves it announces its departure from wherever it is. Neither is inferred from a connection going quiet - a connection can stop being noticed long after the person has gone, and a session that outlives its owner by that margin is indistinguishable, to everyone else, from one still being used. A departing tab's claim is kept for a short, bounded moment so a reload lands back in it; after that the session is free and the next participant takes it.

A session therefore ends for exactly two reasons: the tab holding it is gone, or its holder handed it over. Reading a report, changing settings, working in a second tab, and reloading are all continuations, not departures - none of them ends a session, however long they last. Someone who needs a session that is still held takes it over, which asks the holder first; waiting for it to lapse is not part of the design.

A session is never held by a participant with nothing behind it. Losing a connection releases whatever it held, unless that same participant is already present on another connection - which is precisely the case a reload creates, and the reason a late-noticed dead connection can never evict a tab that has already returned. Ending a session administratively releases what it held by the same rule. So the roster and the lock always agree: a holder named in the interface is a holder someone can actually reach.

##### REQ-5.2.7.16 Take-over semantics

Taking over never seizes the session; it requests it, and the requester waits while the current holder hands off. A person holding the session is asked to approve on their own screen and can hand over or decline. The assistant hands off on its own: asked to yield, it finishes the atomic step it is in - so a test is never left half-written - and releases the session. An idle or abandoned session, with no live holder, hands over immediately. In every case a force option is available to the requester, for a holder that is unresponsive, a decline that must be overridden, or a wait that cannot be afforded.

A claim arriving from the assistant follows the same principle from the other side. A person holding a clean draft with no run in flight yields immediately - their tab flips to watching with no approval step - while any unsaved change refuses the claim, so nothing a person typed is ever put at risk by an arriving assistant. A session the assistant holds for a run hands over immediately on request: a run needs nothing finished before the surface changes hands, the mirror simply ends, and the tracked run continues to completion on its own. When the assistant releases the session gracefully - its build complete or its run finished - the tab that inherits the slot does so silently; inheritance after an unexpected holder loss is announced.

What the inheriting tab holds depends on what it received while yielded. A streamed build is inherited as unsaved work, ready to save or discard. A watched run keeps its painted result with nothing marked unsaved - watching changed no draft. And after a pure storage write - a test created or amended while the slot was borrowed - the tab re-reads the workflow it has open, so the surface it shows is the one the write left behind and a stale save can never resurrect the version from before it.

Whoever takes the session continues the live draft exactly as displayed, and the former holder becomes a read-only mirror of it. Nothing is saved or discarded by the act of taking over - the new holder simply continues editing the same draft. Discarding changes is always a separate, explicit act; it is never a side effect of taking over, opening, or switching. Work that cannot be preserved by saving - notably an unpublished function draft, which can only be published or discarded - is carried over intact and never silently discarded.

The take-over control is also how control returns: a participant regains a session that was handed off by taking it over again through the same request. When the assistant is interrupted mid-build its in-progress work is suspended rather than destroyed - a graceful hand-off lets it finish the step it is in, and a forced one sets its remaining work aside so it can resume if the session is handed back.

##### REQ-5.2.7.17 Watch-mode authoring

Recipe authoring offers two modes, and the assistant lets the person choose between them. In the fast mode the assistant simply hands over a finished recipe and the test is compiled and saved in one step, with no live building. In the live mode - watch-mode - the assistant holds the session and builds the test through it, so the person can watch it take shape and step in at any moment.

In watch-mode the assistant works out the whole test up front and then reveals it into the live draft one piece at a time, at a pace a person can follow. Every mirroring viewer sees the test grow: variables seed first, then blocks appear in the order an engineer would narrate them, each with its incoming connection and each landing at its final position so nothing reshuffles. As each block lands it pulses once to draw the eye, and the block the assistant is currently placing also carries a steady holder-colored border. A viewer can turn on Follow Changes to keep the viewport tracking whatever just moved: it re-centers on the block that changed - re-firing on each change, including a repeated change to the same block - and drills into a function's interior when the changed block is nested there. Variables carry a live cue too, but only where something happened: a row stays in its resting state until its value is seeded or changed, at which point it briefly shows a holder-colored bar that pulses and settles. A row a viewer is inspecting keeps its inspect bar throughout.

An interruption during a live build is nothing special. The half-built test lives as an ordinary unsaved draft that every watcher already mirrors, so taking over - or the assistant simply dropping - leaves the draft intact for whoever continues it, exactly as a person's own workbench survives a browser crash and reopen. Nothing is saved or discarded by the act, and nothing is lost. When the assistant finishes a build uninterrupted it saves the test once and releases the session; the mirrored surface then reads as that saved test - named, bound, and clean - so the tab that inherits it holds the finished work with nothing left to save. If the assistant needs a human decision first, it releases and leaves the recoverable draft. A name conflict is reported before any building starts, with the option to amend the existing test instead.
