#### 3.8.5 Session Ownership and Live Mirroring

The workbench session model is defined for viewers and holders in general - browser tabs, additional users, and the MCP assistant are all the same kind of participant. The MCP introduces no special session mechanics; it exercises the general model.

##### REQ-5.2.7.15 Single-active-session ownership

The workbench allows a single active session at a time. The session is held by exactly one participant - the holder - and only the holder mutates it. Holding is automatic and invisible in the normal case: a user editing alone simply holds the session, with no additional interface presence.

Every other participant viewing the workbench sees the same session live - the graph and its variables changing as the holder changes them, blocks appearing, connections forming, values updating. This is single-writer mirroring, not co-editing: because only the holder ever changes anything, there is nothing to reconcile between participants, and there are deliberately no per-viewer cursors or presence marks, which would only add noise across differing screens. The mirrored stream carries the identity of the surface along with its content - which test is open, or that the surface is an unsaved draft, whether it holds unsaved work, and, while the assistant authors through it, whether it is building a test or changing a saved one - so every viewer, including one that joins late, names what it is looking at truthfully, and a mirrored surface can never masquerade as a test the viewer merely had open before. The stream never carries a secret value: a variable reaches a mirroring view in the same form the browser receives it when it opens the saved test, and the real values of the secrets in an assistant's streamed draft stay on the server, kept for whoever continues that draft (REQ-5.2.7.17).

A mirroring view is read-only and clearly marked. The canvas is visibly non-editable, a prominent banner names the current holder, and a take-over control is always available. Undo history belongs to the surface a tab holds, so a mirroring view keeps no undo of its own and the undo shortcuts do nothing there (REQ-5.2.1.24). The banner distinguishes a person from the assistant: an assistant holder is shown as such, under the client's display name (its title when it sends one, else its short name; REQ-5.2.7.14), so it is always clear who - or what - is driving, including across successive hand-offs. When the holder is an assistant, the banner also offers a direct path to that client's entry in the MCP section of System Config, where the connection can be inspected or ended.

The same rule governs a test's own files. Only the holder changes them; a mirroring view reads them and is offered no way to add, rename or remove one. What is on its way in belongs to the test rather than to the tab that started it, so every viewer sees the same uploads live, including ones it did not start, and a file that did not land leaves a notice that outlives the tab. Taking over does not stop an upload already under way, because the bytes exist only in the tab that started it; the session that loses the test simply starts no more. An upload is stopped by the session holding the test or by the one that started it.

The mirror follows the holder only while the viewer stays on the holder's surface. A viewer who opens or closes a workflow of their own choosing browses freely instead: the canvas stays read-only - the session is still held - and the banner states exactly that, naming the holder that has the workbench and, when a run is in flight, that a run is underway. Nothing the holder does moves a browsing viewer's canvas, and following ends implicitly the moment the viewer navigates. The banner carries one control that returns the viewer to watching the live session, converging on the holder's current surface - the draft, or the run in flight.

The mirror carries the holder's execution surface as well as their draft. While the holder has a run in flight, every watcher sees the run the holder sees: blocks painting their execution states as they run, variable values updating as the run writes them, and the Console panel streaming the run's output line by line as it is produced. A watcher who joins mid-run receives what the run has already produced - the painted states and the console lines so far - and then the live remainder, which stays readable after the run ends. The run's environment is reflected read-only to every watcher, in the place the environment control normally occupies, so a mirror always shows which environment the run actually carries rather than the watcher's own last local selection. For the duration of a run the banner's trailing phrase reads "read-only, running live", whoever holds the session.

A mirroring view holds no run control: starting, stopping, and stepping a run belong to the holder alone, and the one live control a watcher keeps during a run is Focus Current, which only moves the viewport. Mirroring is strictly broadcast - watchers are silent recipients of the same streams the holder consumes - so a run watched by any number of mirrors leaves exactly the record, logs, statuses, report, and history that the same run leaves unwatched. A watching tab never takes control on its own either. If the test it watches is deleted, it drops that test's suites and its suite and regression variables and goes on mirroring, with no dialog. The Test not found dialog never comes up in a tab that follows the holder's surface. A tab browsing on its own still meets it for a test it opened, and the dialog's Close clears the session on the server only in the tab that holds the session, so a tab that does not hold it never ends the holder's session or stops its run.

An unattended run the assistant starts is mirrored the same way. For a test run the assistant holds the session for exactly the run's duration - the banner names it as the holder of a run - and releases it when the run reaches its terminal state. When such a run starts playing in a viewer's tab, the viewport first fits the whole test, the same fit the canvas's own Fit View makes, so the run plays where the viewer can see it rather than on whatever part of the canvas happened to be in view. When the run ends, every tab it played in keeps the environment the run used in its environment control - whether the control was empty or held another environment before the run - so the screen matches the run the person just watched and their next run uses the same environment; if that environment no longer exists, the control stays as it was. Suite and regression runs do not occupy the workbench surface and are not mirrored. When the session cannot be borrowed, the run still starts; it simply goes unmirrored.

Browser sessions are first-class connections in the same way. Every browser connected to WAVE is tracked as a named connection carrying its own identity - the browser and operating system it runs in - along with the address it connects from and its connection and last-active times, where "last active" is its last real interaction rather than connection keepalive. A dedicated WAVE Server section of System Config makes these connections visible and manageable. It presents the two servers behind WAVE - the one that serves the interface and the one that carries the API and the live sessions - as read-only facts: each server's running state, the numeric addresses it is reachable on, its listening port, and its bind scope. These facts are settled when WAVE starts and are shown for transparency rather than as controls, since the server that serves the operator cannot be reconfigured from within itself; anything on the section that is not manipulable as WAVE configuration is presented read-only.

Below the server facts, a live roster lists every connected browser session and the role it currently plays: the session holding the editing lock reads as Active, and any session mirroring it read-only reads as Watching. An administrator can end any one of them behind a confirmation, or end all sessions or all but their own in a single guarded sweep. The administrator's own sessions are marked distinctly, and because one person may hold several tabs at once, every tab of their own browser carries that marking, so their own connections are never mistaken for another's. Ending a session disconnects that browser and returns it to a clearly disconnected state, from which a deliberate reconnect starts a fresh session. The identity a session carries is its connection - browser, operating system, and origin address - so that a session is always answerable to a real, reachable origin.

Because a browser session is a real connection, a person holding the workbench is as traceable as an assistant. A person-held mirror banner names the holder by its connection identity rather than a generic "another session", and carries the same See connection path an assistant-held banner does - opening the WAVE Server section scrolled to and highlighting that exact session, with the means to end it beside it. Whoever, or whatever, is driving a shared session is always one step from the connection behind it.

A participant's identity lasts as long as the browser tab it belongs to, across reloads of the page. Reloading is a continuation, not a departure: the tab comes back as the same participant and resumes whatever it held, without asking and without passing through a read-only state. Two tabs are always two participants, including when one is duplicated from the other - a tab that finds its identity already in use elsewhere in the same browser takes a fresh one, so the single-active-session guarantee cannot be broken by copying a tab.

Holding outlives the Workbench screen. A holder who navigates to another part of WAVE keeps the session, because their draft is still theirs and they are expected back. Both of the signals that keep a session honest therefore belong to the tab rather than to the screen: for as long as the tab is open it goes on showing that it is there, from whatever page it happens to be on, and when it leaves it announces its departure from wherever it is. Neither is inferred from a connection going quiet - a connection can stop being noticed long after the person has gone, and a session that outlives its owner by that margin is indistinguishable, to everyone else, from one still being used. A departing tab's claim is kept for a short, bounded moment so a reload lands back in it; after that the session is free. No tab is moved into it on its own: a tab that was watching stays a watcher, even when it is the only tab left, and takes the session only when it takes over to edit, which a session with no holder grants at once.

A session therefore ends for exactly two reasons: the tab holding it is gone, or its holder handed it over. Reading a report, changing settings, working in a second tab, and reloading are all continuations, not departures - none of them ends a session, however long they last. Someone who needs a session that is still held takes it over, which asks the holder first; waiting for it to lapse is not part of the design.

A session is never held by a participant with nothing behind it. Losing a connection releases whatever it held, unless that same participant is already present on another connection - which is precisely the case a reload creates, and the reason a late-noticed dead connection can never evict a tab that has already returned. Ending a session administratively releases what it held by the same rule. So the roster and the lock always agree: a holder named in the interface is a holder someone can actually reach.

##### REQ-5.2.7.16 Take-over semantics

Taking over never seizes the session; it requests it, and the requester waits while the current holder hands off. A person holding the session is asked to approve on their own screen and can hand over or decline. The assistant hands off on its own: asked to yield, it finishes the atomic step it is in - so a test is never left half-written - and releases the session. An idle or abandoned session, with no live holder, hands over immediately. In every case a force option is available to the requester, for a holder that is unresponsive, a decline that must be overridden, or a wait that cannot be afforded.

A claim arriving from the assistant follows the same principle from the other side. A person holding a clean draft with no run in flight yields immediately - their tab flips to watching with no approval step - while any unsaved change refuses the claim, so nothing a person typed is ever put at risk by an arriving assistant. A session the assistant holds for a run hands over immediately on request: a run needs nothing finished before the surface changes hands, the mirror simply ends, and the tracked run continues to completion on its own. When the assistant releases the session gracefully - its build or change complete, a test created or amended, or its run finished - a take-over request waiting at that moment still goes to its requester; with none waiting, the session goes back to the person tab that gave way to the assistant, when that tab is still connected, and otherwise the slot is free and any tab may claim it. A streamed build or change releases it this way whether it finishes, is ended gracefully, ends in a refused save or is taken over. The tab that inherits the slot does so silently; inheritance after an unexpected holder loss is announced. A stream that ends because the assistant dropped is such a loss: a waiting take-over request still goes to its requester, but the session is not handed back, and the tab that takes the slot next inherits the half-done work as unsaved and is told so.

What the inheriting tab holds depends on what it received while yielded. A streamed build or change the assistant finished is inherited as the test it saved, clean, with nothing left to save; one it left unfinished is inherited as unsaved work, ready to save or discard. The tab that gets the session back takes on the saved state of the draft it inherits, so unsaved work it inherits goes on refusing an assistant's claim. A watched run keeps its painted result with nothing marked unsaved - watching changed no draft. And after a pure storage write - a test created or amended while the slot was borrowed - the tab re-reads the workflow it has open, so the surface it shows is the one the write left behind and a stale save can never resurrect the version from before it. A tab that was browsing on its own when the session is handed back to it re-reads the test it has open the same way, so it never holds a version from before the change.

Whoever takes the session continues the live draft exactly as displayed, and the former holder becomes a read-only mirror of it. A tab that takes over or inherits the session starts a fresh undo history at that surface, so undo never brings back content from before the switch. Nothing is saved or discarded by the act of taking over - the new holder simply continues editing the same draft. Discarding changes is always a separate, explicit act; it is never a side effect of taking over, opening, or switching. Work that cannot be preserved by saving - notably an unpublished function draft, which can only be published or discarded - is carried over intact and never silently discarded.

The take-over control is also how control returns: a participant regains a session that was handed off by taking it over again through the same request. When the assistant is interrupted mid-build its in-progress work is suspended rather than destroyed - a graceful hand-off lets it finish the step it is in, and a forced one sets its remaining work aside so it can resume if the session is handed back.

##### REQ-5.2.7.17 Watch-mode authoring

Recipe authoring offers two modes, and the assistant lets the person choose between them. In the fast mode the assistant simply hands over a finished recipe and the test is compiled and saved in one step, with no live building. In the live mode - watch-mode - the assistant holds the session and builds the test through it, so the person can watch it take shape and step in at any moment.

In watch-mode the assistant works out the whole test up front and then reveals it into the live draft one piece at a time, at a pace a person can follow. Every mirroring viewer sees the test grow: variables seed first, then blocks appear in the order an engineer would narrate them, each with its incoming connection and each landing at its final position so nothing reshuffles. Every viewer learns that the assistant holds the session before the first block reaches it, so a tab that yields to the build shows it from its first block. As each block lands it pulses once to draw the eye, and the block the assistant is currently placing also carries a steady holder-colored border. Because every block lands at its final position, where the finished test will sit is known before the first block appears, and the stream carries that footprint to every viewer. When a build starts in a viewer's tab - the holder that yielded to the assistant and every tab watching it, including one that joins mid-build - the viewport first frames the finished test, the same fit the canvas's own Fit View makes once the test is complete, and then holds still while the blocks fill in place. A finished test too big to show whole even at the canvas's smallest zoom is shown at that smallest zoom on its top, where the build begins, and the view then moves only when a new block would land off screen, just far enough to bring that block into view. A viewer can instead turn on Follow Changes to keep the viewport tracking whatever just moved: it re-centers on the block that changed - re-firing on each change, including a repeated change to the same block - and drills into a function's interior when the changed block is nested there. While Follow Changes is on it takes the place of the framing. Variables carry a live cue too, but only where something happened: a row stays in its resting state until its value is seeded or changed, at which point it briefly shows a holder-colored bar that pulses and settles. A row a viewer is inspecting keeps its inspect bar throughout.

An interruption during a live build is nothing special. The half-built test lives as an ordinary unsaved draft that every watcher already mirrors, so taking over - or the assistant simply dropping - leaves the draft intact for whoever continues it, exactly as a person's own workbench survives a browser crash and reopen. Nothing is saved or discarded by the act, and nothing is lost. The draft's secrets survive too: the stream shows them masked, and the server keeps their real values for whoever continues the draft, also after the assistant drops. When that person saves, a secret that arrives as the mask is filled from the kept value, while a value they typed or cleared is theirs; a save never stores the mask as a secret value, and one with no value to fill it from is refused and names the variable, credential field or Variable Setter row, so its value is entered again. Only a save made by the tab that holds the session and continues that draft uses the kept values or ends them; a save from any other tab or page neither uses nor drops them. A take-over waits until the frame being sent has reached every tab, so the person continues exactly what their canvas shows. When the assistant finishes a build uninterrupted it saves the test once and releases the session; the mirrored surface then shows the test exactly as it was saved, any repairs the save made included, and reads as that saved test - named, bound, and clean - so the tab that inherits it holds the finished work with nothing left to save. If the assistant needs a human decision first, it releases and leaves the recoverable draft. A name conflict is reported before any building starts, with the option to amend the existing test instead. A recipe the save refuses is answered with the same findings the fast mode gives, and nothing is saved. The save's checks that can run without saving run before anything is streamed, so a recipe they refuse never reaches a viewer; a refusal only the save itself can make comes at the end, and the streamed test then stays in the tab as unsaved work.

##### REQ-5.2.7.18 Watched change

Changing a saved test offers the same two modes as creating one, and the assistant lets the person choose between them. In the fast mode the revised recipe replaces the stored test in one step. In the watched mode the assistant holds the session and makes the change through it, the way a person editing in another tab would, so the tab that gave way and every tab watching see the change play out on the test. Both modes take the same recipe and save the same test. The claim follows the general rule: a person holding unsaved work refuses it, and nothing is streamed or written. A watched build or change from an assistant session that already holds the session, for a run or another stream, is refused as held before anything streams.

The assistant works out the finished test up front and then plays the change in turns. Making room is the first step, and the person can follow it: every block that moves glides to its new place, still in its stored form, all at once, in about a third of a second; every removed block goes, and the variables take their final values. With reduced motion set, the blocks move without the glide. Only then does each added block and each changed block take its turn, one at a time, in the flow order of the finished test and at the pace of a build: an added block appears in the space made, and a changed block - one whose name, settings or anything else in it differs from the stored one - takes its final form. A block moved into another branch leaves in the first step and comes back at its turn. Lines go with their blocks: a line the stored test had and the finished test keeps - the same two blocks joined at the same points - stays throughout; any other line of the finished test appears once both its ends have their final form; every other line of the stored test goes in the first step. The block of each turn pulses once and carries the steady holder-colored border, and it is the block Follow Changes re-centers on; the first step marks no block, so Follow Changes has nothing to follow until the first turn.

Every frame of the change is bound to the test being changed and marked unsaved. Each viewer's view follows the rules of a build: it frames the finished test as the change starts and then holds still, or, for a test too big to show whole, starts on its top and moves only to bring an off-screen block of a turn into view; Follow Changes, when a viewer turns it on, takes their place. When the change finishes uninterrupted the assistant saves the test once and hands the session back to the tab that gave way (REQ-5.2.7.16); the last frame is the test exactly as saved, any repairs the save made included - named, bound, and clean. A recipe the save refuses is answered as in a build. When the test was saved in any way while the change streamed, a rename or an edit of only its variables included, the change answers that the test is out of date and saves nothing; when the test was deleted meanwhile, it answers that the test was not found.

An interruption during a watched change is no more special than one during a build. The half-done change stays as unsaved work of the test being changed, for whoever continues it to save or discard; nothing is saved or discarded by the interruption, and the stored test keeps its saved version until someone saves. Its secrets are kept as in a build: a block that already has its final form keeps the secrets the recipe gave it, the variables keep their final values, and a changed block still shown in its stored form keeps its saved secrets until its turn.
