#### 3.8.6 Configuration and Deployment

##### REQ-5.2.7.1 Embedded server configuration

The MCP server is configured from Settings > MCP Server and is off by default. The page offers two ways to enable it - persistently, surviving restarts, or until-restart, reverting to disabled when the server next starts - both defaulting to off. The two modes are mutually exclusive: turning one on turns the other off, so exactly one mode is ever responsible for the endpoint being up. Like every settings page, the page holds every change, the enablement modes included, until the admin saves it, with Cancel and Save disabled until something changed (REQ-4.7.16); saving an enablement change starts or stops the endpoint without restarting the WAVE server. The persistent settings live in the config file (REQ-4.7.17); the until-restart mode is held only by the running server.

Endpoint configuration - the port the MCP endpoint listens on, the bind scope (local-only, reachable solely from the server's own machine, or network-exposed for deployments where the assistant client runs elsewhere), and authentication - is saved by the same Save. Saving an endpoint change while the endpoint runs restarts the MCP endpoint with the new configuration and disconnects connected assistants, and the page says so in a confirmation before proceeding - noting that the platform itself and running executions are unaffected, since only the MCP listener restarts; when the change widens the bind scope to the network, the same confirmation carries the exposure warning. A Save that only starts or stops the endpoint asks nothing. Cancel always discards the page's changes.

Endpoint configuration is validated where it is edited: the port field accepts only numbers in the valid service range and immediately rejects the ports WAVE itself serves on, blocking Save while invalid. A port that is in range but already occupied on the host is caught when the change is saved or the endpoint is enabled - the request is refused with the reason, and neither the stored configuration nor the running endpoint changes. A port that becomes occupied while the endpoint is down (for example, taken by another process before WAVE starts) surfaces as an error on the status readout instead.

The endpoint optionally requires HTTP Basic authentication: a username and a password that is sealed at rest like every platform credential and never revealed: once set it is shown masked, and replacing it goes through the clear-and-edit confirm used for every protected value. A password written into the config file by hand in plain text is refused at startup: it is set on the page, which seals it. While a new password is being typed and not yet saved, it can be shown and hidden for verification; every new password starts hidden, also after a Save or a Cancel. The page shows how strong the typed password is: a score from 0 to 4 and its label, from very weak to very strong, worked out on the server by a standard password-strength estimator that also counts the username against the password. A password longer than the estimator's input limit is scored on its first characters up to that limit. The score informs and never blocks Save, and the password sent for it is neither stored nor logged. With authentication off, the MCP endpoint carries the same trust model as the rest of the server: any client that can reach it may act through it. The local-only default binding keeps that reach to the machine's operator, which matches the platform's single-operator deployment posture; widening the bind scope is a deliberate administrative act confirmed with the exposure warning, which recommends requiring authentication.

The server has no outbound AI dependency; the MCP endpoint is a listener, not a caller. An air-gapped site pairs it with whatever local MCP-capable client the site operates, and the recipe format guide served by the MCP itself means no external documentation is required for a client to become productive.

##### REQ-5.2.7.14 Status visibility

The System Config MCP section shows the endpoint's live status: whether it is running, the concrete addresses it is reachable on - one per network interface within the bind scope, each individually copyable - how many clients are connected, and a scrolling feed of recent assistant tool calls. Addresses are always numeric: a hostname or "localhost" may not resolve, or may resolve to an address family the endpoint does not listen on, for the client that needs to connect. An administrator answers "is it on, and is anything talking to it?" from the same place they enable it; deeper protocol inspection is the province of standard MCP developer tooling pointed at the endpoint, not of the product.

Connected clients are listed individually: each session shows the client's declared identity, its network address, and when it connected and was last active. An administrator can terminate any session from the list, immediately disconnecting that client.

##### REQ-5.2.7.2 Ordinary-client guarantee and attribution

Everything the assistant does is attributable. Executions it starts carry the assistant client as their initiator in the execution history. Entities it creates and amends move through the standard services, so version history records its changes like any other client's. Attribution rests on identity: every connected client holds an identifying session, and the endpoint serves only protocol modes that establish one - a client attempting a sessionless mode is refused and, through the protocol's standard fallback, reconnects via the session-forming handshake, appearing among the connected clients like any other. There is no MCP-only side channel to storage: disabling the MCP section removes the entire surface. Secret values the assistant writes meet the same rule as every other save: a value locked with a key this WAVE does not hold is refused, naming the secret, exactly as a save from the web interface is (REQ-4.5.19).
