#### 3.8.3 Tool Surface

The MCP exposes a small, deliberate tool surface in four families. Tools are self-describing: each declares its purpose and inputs to the client, and the recipe format guide with worked examples is served alongside them as reference material.

##### REQ-5.2.7.8 Discover tools

Read-only visibility into everything an authoring or diagnosing assistant needs: the block catalog with each block's declared settings and outputs; the Functions library as searchable contract cards (name, description, tags, typed inputs and outputs) with a deep-inspect lookup that returns a Function's full definition and dependencies for the cases where the card is not enough to decide; tests, suites, and regressions with their variables; environments and profiles; system and global variables; a test's own test data files, listed as the same entries the Test Data sheet shows so an assistant references real paths rather than guessed ones; and past executions with their outcomes. Variable visibility across the suite, regression, system, and global scopes exists because correct authoring depends on it: a recipe that relies on an inherited value must be able to see what is declared above it.

##### REQ-5.2.7.9 Author tools

Creation and amendment of entities, always through the same validated services the UI uses. Tests are authored exclusively through recipes: a dry-run validation tool checks a recipe without persisting anything, a creation tool compiles and saves a new test, an amendment tool applies a revised recipe to an existing test, and a readback tool returns any test as a recipe. Suites and regressions are created and updated as organizational entities, including attaching tests and suites. Updates are additive: an entity or membership omitted from an update is left untouched rather than removed, removal is always an explicit act, and a referenced test or suite is confirmed to exist before the change is accepted, so an assisted edit never silently drops a variable, a member, or points at something that is not there. Profiles and system and global variables are authored with the secret-handling modes described in the secret handling subsection. A test's files are authored through the surface too: one tool writes a file (text or base64-encoded bytes) into the test's test data, one creates a folder, one renames an entry and one deletes it. They go through the same service as the Test Data sheet, answer with the same messages and are refused while the test is running (TDATA-12). Placing a file this way is how an assistant makes a testdata:// reference resolve after creating the test, since the files come after the recipe. Function publishing is not part of the surface: promoting work to the shared library is a human act performed in the UI.

##### REQ-5.2.7.10 Run tools

Starting an execution of a test, suite, or regression against a chosen environment, with optional profile selection and variable overrides, and checking the progress and outcome of a running or completed execution. Executions started here are ordinary tracked executions: they appear in the execution history attributed to the assistant client, indistinguishable in structure from human-triggered runs. An override gives a declared variable its value for that run only, null included; a name the test does not declare is refused and nothing starts.

##### REQ-5.2.7.11 Report tools

A structured failure report for an execution: the overall outcome; each failed test with the failing blocks, their error messages, and the surrounding warning-and-above log excerpt; and the pending manual action items: secrets authoring declared without a value, and secrets an import or a restore stored as null because WAVE could not open them or they arrived as a masked placeholder. The family also retrieves the platform's generated run reports - structured data for the assistant's own reasoning, or the rendered document for handing to a person. Log content in reports is masked exactly as it is masked at rest.
