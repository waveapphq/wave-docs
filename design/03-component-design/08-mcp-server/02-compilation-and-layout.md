#### 3.8.2 Compilation and Automatic Layout

Compilation turns a recipe into a genuine canvas test: the same document shape, the same block and connection model, the same storage and versioning as a test built by hand in the workbench. A compiled test carries no capability a hand-built one lacks and is fully editable in the workbench afterwards. Compilation is also where the platform's guarantees attach - a recipe that does not produce a valid test is rejected, never persisted.

##### REQ-5.2.7.4 Generated wiring and automatic layout

**Wiring generation.** The compiler derives all connectivity from the recipe's structure: sequential steps chain in order, construct children wire into their construct's sections and branches, and construct completions rejoin the parent flow. Multi-section constructs receive their section anchoring from the construct's own declared structure, so generated wiring is always anchored the way the canvas expects. A conditional whose sections do not cover every outcome - an if without an else, a switch without a default - still continues: the uncovered path is wired explicitly to the step that follows, exactly as a person would wire it, so no authored step is ever left unreachable. The compiler refuses to emit any graph containing a block that cannot be reached from the start of the flow - a wiring fault surfaces as a validation finding, never as a silently dead block.

**Deterministic layout.** The compiler places every block using a layout engine that follows the canvas's natural conventions: the main flow descends top to bottom on a steady vertical rhythm along the main line, x 0, which is the center of the Start node (CANVAS-248), so the link from Start to the first block is straight; branches fan out into side-by-side columns beneath their construct and rejoin below it, and loop and section bodies are grouped visibly within their construct's column. A construct with a single inner lane and a continuation exit - a loop or a remote execution with its body, a wait with its retry lane - hangs that lane to the left of the main line and places the step on its continuation exit one row below the construct, on the main line beside the lane, so that connection stays short; the steps after it run down the main line beside the lane, and whatever follows an enclosing construct starts below both the lane and those steps. When such a construct ends a branch of an if, the step after the if sits below the if on the main line, never beside the lane in that branch's column. A construct with several lanes keeps its continuation below all of its lanes. The engine sizes each block kind as the canvas draws it - wider function blocks, multi-section constructs whose width grows with their section count, the whole card's height with its status bar and description lines, and a Note by the rule under Block sizing - so blocks never overlap and connections remain readable. Rows sit 140 pixels apart, which leaves at least 32 pixels under the tallest card the canvas draws with its description collapsed (108 pixels); a taller card, such as a long Note, takes as many whole 140-pixel rows as its height plus 32 pixels needs. Layout is a pure function of the flow's structure: the same recipe always yields the same picture.

**Block sizing.** A block a recipe creates is sized to fit its name, bounded by the canvas resize limits and never narrower than the block's own handle row, so a step's name is legible on the canvas the moment it is generated rather than after a person widens it. A block placed by hand still starts at the canvas minimum width, because its name is not known when it is dropped. A Note has no generated width: only a person sets it. The layout sizes a Note by the width and height stored on it, and estimates each size the Note does not store from the size the canvas draws for its text: its longest line at 8 pixels a character plus 26 pixels of padding and border, at least 120 pixels wide with no upper limit, and 22.75 pixels for each line of its text plus 51 pixels of padding and status bar, at least 60 pixels tall, each rounded up to a whole pixel. A Note's text breaks only at its own line breaks until a person resizes it, because a Note left at its own size grows with its longest line. A long Note therefore never crowds the block after it: a fresh build gives the Note whole extra rows, and an amendment moves that block down under the rule for blocks that come too close, below.

**Stability under amendment.** When a revision amends an existing test, layout is stability-preserving. A block untouched by the revision is recognized by what it is - its kind, its name and its settings, within the same section of the same construct - never by where it sits in the list, so adding, removing or moving other blocks never costs it its place; a step the recipe names with a key of its own is recognized by that key. Sections are matched the same way, by what they are - a switch case by its value, a parallel branch by its identity - never by their number, so a case or branch added or removed in the middle leaves the blocks of every other section recognized. Every block the amendment recognizes, untouched or with its name or settings revised, keeps its identity in the test and its canvas settings, and keeps its place unless the change needs the room or closes a gap WAVE left, so a fast and a watched change of the same recipe save the same test. After any change by an assistant, fast or watched, the test reads in flow order the way a fresh build does: each block under the block before it, each branch in its own column under its if or switch, the block after a lane one row below its parent beside the lane, nothing overlapping. A new block goes under the block before it, in that block's column; a new branch gets its own column. When there is no room, the blocks below or beside move to make room, keeping their order and how they sit relative to each other. Blocks the change does not need to move stay where they are, including blocks a person placed by hand; a person's own arrangement is kept, and the blocks after a new block in it move down only as far as needed. When a change removes a block, the blocks below it that WAVE placed move up to close the gap, so the test stays as tight as a fresh build; a gap a person left stays, and nothing slides sideways. Rows follow the fresh build's rules, top down in flow order: a block WAVE laid out one row step below the block before it keeps that step, and a block with room above it stays until the flow reaches it. Columns only move apart, never together, and only as far as needed: lanes move as whole lanes and keep their left-to-right order, a lane beside a continuation moves left so the main line stays straight, and the main line never moves sideways. If two blocks still come closer than 32 pixels from top to bottom and 40 pixels from side to side, which happens only when a block a person placed, or a Note, stands in the room the flow now needs, the later one in the flow moves down to one row step below the other - that block's height plus the 32 pixels, rounded up to whole 140-pixel rows - and the layout is worked out again; the 32 pixels are the space a row leaves under the tallest collapsed card, so a fresh layout never moves. A fast change ends with exactly the same layout as a watched change of the same recipe. A width a person set by resizing is kept, as a place a person gave a block is, while a block still at its generated width is re-sized when its name changes; a block that grew keeps its center, so its column stays straight. Every width stored on a Note is a person's, so an amendment keeps it whatever its value. Besides its identity, a width a person set and its place, kept unless the change needs the room or closes a gap WAVE left, a recognized block keeps the canvas settings a recipe cannot express: its secret reveal choices, for its run output and for each of its credential fields, and whether its description is expanded, so an open description takes its room in the layout. The blocks inside a local Function body are recognized the same way and keep all of this too, their place and width included, and a Note keeps the width and height a person gave it. Only a block that is still the same kind keeps these settings: one its key pairs with a stored block of another kind starts on the defaults. A Shared Function Block stores the name its library Function has when the recipe compiles, on creation and on every amendment, so the block names its library Function the way one dropped from the library does (REQ-3.1.1.5). The author's spatial memory of a test survives assisted edits.

**Geometry is generated, never authored.** Positions and sizes are the compiler's output, not part of the recipe: a recipe never carries them, and a readback of a compiled test does not emit them.

**Layout as a platform capability.** The layout engine belongs to the workflow domain, not to the MCP. It is defined over the canvas model itself, so any surface that holds a workflow can invoke it; the MCP compiler is one consumer.

##### REQ-5.2.7.5 Validation relay

Submissions pass two validation stages. Recipe-level validation checks the document against the format and the catalog: unknown block kinds, missing or mistyped settings, references to undeclared variables, malformed structure. Platform-level validation is the same save pipeline the UI runs, applied to the compiled result. Errors from both stages are reported in recipe coordinates - which step, which setting, what is wrong - with a proposed fix wherever the platform knows one and a plainly stated blocker where it does not. The authoring path over MCP is therefore a fully validated ingress: nothing persists in a state the UI's own save would refuse.
