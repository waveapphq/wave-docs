#### 3.8.1 Recipe Format

A recipe is a complete, declarative description of a single test in human-readable structured text. It carries the test's identity (name, description, tags), its variable declarations, and its flow. Recipes contain no canvas geometry, no block identifiers, and no wiring - those are compilation outputs, never authoring inputs.

##### REQ-5.2.7.3 Recipe-based test authoring

**Structural control flow.** The flow is an ordered sequence of steps. A step either invokes a block from the catalog or opens a structural construct - a conditional with its branches, a loop with its body, an error-handling scope with its sections, a parallel split with its branches - whose contents are themselves nested flows. Connectivity is implied by structure: consecutive steps run in order, a construct's children belong to it, and a construct rejoins its parent flow when it completes. Because wiring is derived rather than declared, a recipe cannot express a dangling connection, an orphaned block, or a cycle; the document's shape is the flow's shape. In a condition, is null and not null take no value and need no value type: they take the checked variable's declared type when it has one, and otherwise work for a value of any type.

**Catalog-driven block settings.** A block step names its block kind using the same identity the workbench palette exposes, and provides that block's settings. Settings are validated against the block's own declared metadata - required settings, types, allowed values, minimum and maximum, and unknown settings - which is the same source of truth and the same check the UI configuration forms and a Test save use. A free-entry setting a step leaves out is not set: the step stores nothing for it, and the run fills it from its default when the block runs. A choice setting or true / false a step leaves out is written with its default when the recipe compiles, as a block created in the workbench holds it from the start (FIELD-8); a choice whose default lives in Settings, such as the SSH host key action, takes the Settings value at that moment. A setting that takes one of a fixed list of words also accepts the YAML true or false that exactly one of those words is read as, so a word such as off needs no quotes. A block added to the platform is therefore immediately expressible in recipes with no format change. Settings accept the full expressiveness of the UI: literal values, variable references, templated text, and expressions, on a whole setting or on an entry of a list or map. A list setting the configuration window shows as one line - the Shell and Python Arguments, the SQL Out arguments - is written in a recipe as its rows: each row is a plain value or an expression, in the list's order. A step may also capture the block's outputs into declared variables; a capture target the recipe does not declare is declared with the output's type, holding null. A step may bind profile fields where the block consumes credentials or environment-specific values.

**Variables.** A recipe declares the variables it uses, with their types and, where the author has one, an initial value or expression. A declaration carrying a type alone is valid and declares the variable holding null, and an explicit null value is valid for every type; the type is what a declaration cannot omit (see REQ-3.1.3.20). Recipe validation enforces the same declaration discipline the platform enforces: a reference to an undeclared variable is an error, reported in recipe terms. Variables declared at enclosing scopes - suite, regression, system, global - are visible to the author through the Discover tools, so a recipe can rely on inherited values knowingly rather than accidentally.

**Functions.** A recipe defines local functions inline: a named unit with its own declared inputs, outputs, variables, and nested flow, usable as a step within the same test. A Function step has the same shape as a block step: it names a local function, or a Published Function from the shared library by name and version, and gives the Function's inputs as its settings, with the same setting forms, element types, captures, Secret outputs and label as any block step. A choice-list or true / false input the step leaves out is written with the Function's default when the recipe compiles, Required included. An input's default is always a plain value, and a secret input takes none: a recipe that gives a secret input a default is refused. An output declares its kind the way a variable does - a plain default, an expression or a template (REQ-3.1.2.8) - and a secret output's default is masked wherever a tool reads it back. A template builds text, so a variable or output that takes one is a string; any other type is refused. A Function step marks which outputs are Secret the way the Function Block window's Secret column does (SECUI-11): unless the step lists its own choice, the outputs the Function declares secret are marked, and a capture target the step declares for a marked output is declared secret. A block step marks its Secret outputs the same way, starting from the outputs its schema marks secret (SECUI-4). A marked output captured into a variable the recipe declares plain makes that variable secret, with a warning that names it, as a block Save does (SECUI-12). Publishing itself is not a recipe concern - promoting a local function to the library is performed by a person in the UI.

**Declared element types.** A map or list written in a recipe - a variable's value, a map block setting that takes typed entries, or a Variable Setter row - declares the type of each element beside it, keyed like the value: on the variable declaration for a variable, beside the step's settings or its set rows for a setting or a row (REQ-3.1.3.19). An element the declaration does not list takes the type its written value has - a quoted value is text, an unquoted whole number an integer. A number declared integer or float may be written as its exact text, which is the only way to keep digits such as `1.0` or a 28-digit decimal through the recipe's own text format, and the declared type is checked against the element exactly as a scalar literal is checked against its variable's type. A readback writes every element in its stored exact form with the complete declaration, so amending a test from its readback reproduces the same stored values and types.

**Secrets.** A recipe may declare secret-typed variables and secret-valued settings, authored in one of the secret write modes defined in the secret handling subsection; values are never emitted into a recipe read back from the platform.

**Files.** A setting that takes a file accepts testdata:// (the test's own read-only files, placed with the test data tools or uploaded in the Test Data sheet), artifact:// (the run's outputs) or a plain path, absolute or relative, where the block runs, with `..` followed in every form; inside a Remote Execution body a block that runs on the remote host fails at run time on either scheme, and the recipe still validates, while a block that is not remotable (Shell Script, Shell Exec, Excel, SFTP) runs on WAVE there and keeps both schemes. Validation warns when a testdata:// literal names no file in the target test - a warning, never a blocker, because the files can be placed after the recipe; creation warns for every such literal, since the test does not exist yet. The warning names the setting and suggests placing the file or correcting the reference.

##### REQ-5.2.7.7 Self-serve format guide

The MCP serves the recipe format guide and a set of worked examples as reference material alongside its tools. A client LLM in any deployment - including air-gapped ones - learns to author recipes from the running WAVE instance itself, with the guide versioned together with the server so documentation and behavior cannot drift apart.

##### REQ-5.2.7.6 Recipe round-trip

A test compiled from a recipe reads back as a recipe. The readback leaves out every secret-marked setting that holds a literal, and has no word for a disabled block; a secret-marked setting written as an expression names a variable, not a value, so it reads back as written. Apart from those it lists the settings each block holds and only those, each in the mode it is stored in, never guessed from how the value looks: a setting left out stays left out, and every stored choice value is written, even one equal to the block's default today. Hand-built tests read back as recipes too; in the rare case a hand-built graph uses connectivity the structural format cannot express, the readback says so explicitly rather than silently approximating. The round-trip is what makes the amend loop work: fetch the test as a recipe, revise it, submit the revision. Because an amendment re-applies a whole recipe, a test whose graph the format cannot fully express is read back with its inexpressible parts named but is not amendable through the recipe loop; such a test is revised directly in the workbench, where its hand-built wiring stays intact.
