##### REQ-3.4.3.1 Store files in test artifacts directory

File-addressed blocks (File I/O, HTTP file bodies and downloads, Excel, K8s Copy, SFTP uploads and downloads, Helm charts, Shell Script and Shell Exec) integrate with the test artifact directory system, enabling workflows to store generated files, captured data, and intermediate results in the current execution's artifact directory without explicit path management. Shell Script and Shell Exec also receive the run's artifacts folder as WAVE_ARTIFACTS_DIR in their environment; the files a script or command writes there are not logged one by one, and the artifact directory listing shows them. An SFTP Download writes into the run's files, and one whose Destination is left empty lands there under the source's own name (SFTP-4).

**Artifact Directory Integration**: The plugin receives the current run's artifact directory path through the execution context, eliminating the need for workflows to construct or manage artifact paths. When the destination path parameter uses a special artifact:// scheme prefix (e.g., artifact://output.json), the plugin automatically resolves this to the full path within the current run's artifact directory. This integration provides path abstraction where workflows reference logical artifact names rather than absolute filesystem paths, automatic directory creation ensuring the artifact directory structure exists, and isolation ensuring each execution's artifacts are stored separately without collisions.

**Resolution Scope**: The scheme behaves uniformly across run modes. Tracked executions resolve to the execution's artifact directory; test runs that belong to a suite or regression execution resolve to that parent execution's directory; interactive workbench runs without an execution record resolve to the session's temporary artifact directory. Workflows therefore use identical artifact:// paths whether run interactively or as part of a tracked execution. A reference resolves from the artifact directory, and a `..` segment is followed wherever it leads, including out of that directory. The scheme names a folder on WAVE, so a block running on the remote host inside a Remote Execution body refuses an artifact:// path at run time.

**Artifact Path Scheme**: The artifact:// scheme provides intuitive artifact storage references. artifact://filename.txt resolves to the root of the execution's artifact directory. artifact://subdir/filename.txt creates subdirectories within the artifact directory automatically. The scheme works consistently across all write, copy, and move operations. Workflows using artifact paths remain portable across different execution environments since artifact directory locations are configured per environment rather than hardcoded in workflows. Reading from artifacts uses the same scheme, enabling workflows to read previously written artifacts by logical name. Slashes after the scheme never leave the artifact directory, and a bare artifact:// names the directory itself: blocks list, inspect and copy it through that reference, while every block that deletes or moves a path by reference refuses the directory itself.

**Artifact Metadata Tracking**: When files are written to the artifact directory, the plugin logs artifact creation at INFO level, providing visibility into artifact generation during execution. Artifact logs include logical artifact name, actual filesystem path, file size, and operation type. This logging creates an audit trail of artifact generation visible in execution reports. The artifact directory itself is the source of truth for what exists - discovery enumerates the directory rather than consulting a manifest.

**Artifact Organization Patterns**: Workflows can organize artifacts using subdirectory hierarchies within the artifact directory. Common organization patterns include artifacts by type (artifact://logs/service.log, artifact://data/results.json, artifact://screenshots/state.png), artifacts by workflow stage (artifact://setup/config.yaml, artifact://execution/trace.log, artifact://teardown/cleanup.log), and artifacts by component under test (artifact://component-a/output.json, artifact://component-b/metrics.csv). The plugin creates these subdirectories automatically, enabling self-documenting artifact structures without explicit directory management operations.

##### REQ-3.4.3.2 Read test data files from configured paths

File-addressed blocks (File I/O, HTTP file bodies and downloads, Excel, K8s Copy, SFTP uploads and downloads, Helm charts, Shell Script and Shell Exec) read a test's own input files through the testdata:// scheme, so sample payloads, reference files, schemas and templates travel with the test instead of being embedded in the workflow definition. Shell Script and Shell Exec also receive the running test's own folder as WAVE_TESTDATA_DIR; their writes into it fail on the file permissions (TDATA-2). An SFTP Upload reads its Source from Test Data or from the run's files; the SFTP block never writes Test Data (SFTP-4). Beside the two schemes these blocks take a plain path. On WAVE a relative one starts at the Working Directory on Shell Script and Shell Exec, whose own relative Working Directory starts at the home folder of the operating-system user the WAVE server runs as, and at that home folder on every other block; on the remote host inside a Remote Execution body it starts at the SSH user's home folder.

**Test Data Belongs to One Test**: Test data belongs to exactly one test. It lives in a per-test folder in a test data zone beside the artifacts, created on the first upload, removed when the test is deleted, copied when the test is cloned, and carried by test export and import (a test with files exports as an archive holding the document and the files, and import accepts that archive as well as the bare document) and by backup and restore inside the tests entity. There is no shared library, no configured root and no server-side configuration of test data: the zone is a fact of the storage base.

**Test Data Path Scheme**: testdata://folder/name resolves against the running test's own folder. A test run as a suite or regression child resolves against its own test's folder, never a sibling's; a Function run without a test has no test data, and a testdata:// reference in that run fails with a message saying so. The scheme is a single-root lookup with no search order and no layering; a `..` segment is followed wherever it leads, including into another test's folder, which such a reference can read. A bare testdata:// names the test's folder itself: blocks list, inspect and copy it through that reference, and a write, move or delete of it is refused as read-only. The scheme names a folder on WAVE, so a block running on the remote host inside a Remote Execution body refuses a testdata:// path at run time. When a reference names a file that is not there, the error names the reference and the path that was searched, so the author sees at once which file the test expected and where it was looked for.

**Read-Only in Three Layers**: Blocks read test data and never change it. First, a write, move or delete whose target is testdata://, or whose resolved path lies anywhere inside the test data zone - any test's folder, not only the running test's - however it was addressed, is refused - for File I/O, Excel, K8s Copy, SFTP downloads and HTTP downloads alike. Second, files are stored without write permission; only WAVE's own upload, rename, delete, folder creation, clone, restore and reset lift it, and only for the duration of that act. Third, while any execution of the test is in progress - alone or inside a suite or regression, tracked or in the workbench - upload, rename, delete and folder creation are refused with a message naming the test, so a running test never sees its inputs change underneath it.

**Test Data Organization**: Inside the test's own folder, authors organize files by purpose and type. Common patterns are input data (testdata://inputs/) holding sample payloads, requests and event data; reference data (testdata://reference/) holding expected outputs and golden files; schema definitions (testdata://schemas/) holding XSD, JSON Schema and validation files; configuration templates (testdata://templates/) holding reusable configuration fragments; and fixture data (testdata://fixtures/) holding database seeds and mock responses. Folders are the author's choice; the scheme imposes none.

**Discoverability**: Every file-taking setting offers a picker over the test's files and the session's artifacts (see 15.5.5), so a reference is chosen rather than typed, and every file row in the Test Data sheet and on the artifact surfaces offers its reference for copying, so a path seen in one place can be pasted where a block reads it.

**One Session Changes, Every Session Watches**: Changing a test's files is workbench work and follows the same rule as the canvas and the variables, so only the session holding the test changes them and every other session reads them. What is on its way in is state of the test, not of the tab, so a session that follows the holder sees the same rows live, including uploads it did not start. A take-over does not stop an upload in flight, and the session that loses the test starts no new ones. An upload is stopped by the session holding the test or by the one that started it.

**What a File That Did Not Land Leaves Behind**: A file that was stopped on purpose leaves nothing: an amber row for whoever was watching at the time, gone once Test Data is closed. Any other reason a file did not land is kept with the test, with the reason, until it is dismissed or the same file lands, and it survives a refresh, a reopen and a different session. The session that still holds the bytes sends them again; the one that does not is asked for the file, under the name the row expects. Half-written bytes stop holding their name five minutes after nothing more arrives, and every change to a folder lifts its write bit under a shared count so two changes never lock each other out.

##### REQ-3.4.3.12 Relative paths start at the home folder

Every relative path a block takes starts at the home folder of the account the block runs as, or at the block's Working Directory where its design says so; nothing starts at the folder WAVE was started from. On the WAVE host that is the home folder of the account WAVE runs under; on a remote host inside a Remote Execution body it is the SSH user's home folder.

| Path | A relative value starts at |
|------|----------------------------|
| File I/O, CSV and Excel files, HTTP file bodies and multipart file parts, Netcat payload files, K8s Copy's WAVE-side path, SFTP's WAVE side, SQL script files, Load table sources and SQLite databases, a Helm local chart | the home folder |
| The CA, client certificate and client key rows of the HTTP, SQL and OpenSearch blocks | the home folder |
| Working Directory on Shell Script, Shell Exec and Python | the home folder |
| Script File, Shell and Interpreter on those blocks | the Working Directory (SHRUN-3, SHRUN-10, PYRUN-3) |
| SSH Session Open's Private Key | the home folder of the account WAVE runs under |
| Helm Path on every Helm block | the home folder of the account the block runs as; a bare name is looked up on the PATH (HELM-1) |

Each path row's help says where a relative value starts. Rows that take certificate text rather than a path, K8s Connect's CA and Helm's repository CA, have no base. helm itself runs inside its per-call folder, so even a chart name helm would treat as a path never resolves against the folder WAVE was started from (REQ-3.5.3.6).
