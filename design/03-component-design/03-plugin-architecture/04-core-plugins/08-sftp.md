#### SFTP Block

##### REQ-3.4.1.8 SFTP file transfers

The SFTP block moves files between WAVE and a server WAVE reaches over SSH, and manages files on that server: it uploads, downloads, lists, inspects, deletes, moves and creates folders, over a file-transfer channel on an SSH session the test already holds. It is the block a test uses when the system under test takes its input and leaves its output as files on a remote machine.

**Purpose and Test Scenarios**: A file-driven system is tested the way its operators feed it. A typical test uploads an input file from its Test Data under a temporary name, moves it to the name the system watches for, so processing never starts on a half-written file, then waits for the output file with a Stats inside a Wait Until until Exists turns true, downloads the output into the run's files and checks it with File I/O or the CSV block, and finally deletes what it left on the server. The block transfers and manages files; reading or writing a file's text is File I/O's job, on the downloaded file or on the file before it is uploaded (SFTP-2).

**Session Model and Multi-Hop**: The block has no connection rows. Its Session ID row names an SSH session that SSH Session Open opened, and the block opens a file-transfer channel on that session's live connection, the same way SSH Session Exec and SSH Tunnel Open ride a session. Login, host-key checking, jump hosts and keepalive therefore all come from the session, and the block adds none of its own: host keys are checked against WAVE's trusted SSH hosts list, and the login uses only what SSH Session Open names (REQ-4.5.14, REQ-4.5.15). A server reachable only through other hosts is reached by opening the session through them with Parent Session; every hop is a session WAVE holds, so a transfer always runs between WAVE and the server of the session it names. In a chain A (WAVE) > B > C > D, a transfer on the session to D goes from A to D directly, carried through B and C without landing on them. Moving a file between two hops is a Download on one session followed by an Upload on the other, and no hop ever receives another hop's credentials. There is no SFTP profile type: the SSH profile bound on SSH Session Open carries the connection (SFTP-1).

**Operations and Rows**: One Operation row, with no expression toggle and Upload by default, picks one of seven operations named as the File I/O block names them, and each operation shows only its own rows (SFTP-2):

| Operation | Rows | Outputs besides Success |
|-----------|------|---------|
| Upload | Source (a file or folder on the WAVE side, with Browse), Destination (on the server), If the file exists | Summary |
| Download | Source (on the server), Destination (on the WAVE side, with Browse, may be left empty), If the file exists; Advanced adds Max size (MiB) and Max files | Summary |
| List | Path, Include subfolders | Entries, Count |
| Stats | Path | Exists, Type, Size, Modified |
| Delete | Path, Ignore missing | - |
| Move | Source, Destination, If the file exists | - |
| Create folder | Path | - |

Session ID, required, and Operation open the sheet on every operation. Advanced holds Timeout, 300 seconds by default, on every operation, and Failure Handling and Secrets work as on every block. If the file exists offers Replace it, the default, or Fail the block; Include subfolders and Ignore missing start off.

**Paths, Browse and Wildcards**: The WAVE side of a transfer is a file-taking row like any other. Upload's Source is a file or folder picked with Browse, over the test's Test Data and the run's files, or typed as a Test Data reference, an artifact reference, or an absolute or relative path. Download's Destination is a save-as target on the WAVE side, picked with Browse over the run's files or typed; left empty, the download lands in the run's files under the source's own name. The server side is plain text with no Browse: Upload's Destination, Download's Source and every path of the other operations are paths on the server. The block never writes Test Data (SFTP-4). The paths of Upload, Download, List and Delete accept the sftp wildcards `*`, `?` and `[...]`, and there is no separate pattern row. When nothing matches, Upload and Download fail with a message naming the pattern, Delete follows Ignore missing, and List returns no entries and a Count of 0, so a Wait Until around a List can poll for a file's arrival as well as a Stats can. A wildcard matches a name that starts with a dot only when the pattern starts with a dot, and List, at one level or with Include subfolders, leaves out symbolic links and folders whose names start with a dot (SFTP-3).

**Transfer Rules**: A destination that is an existing folder, or that ends with `/`, receives the files under their own names; any other destination is the new name, and it is valid only when exactly one file matches. A folder is transferred with everything inside it, and folders missing on the receiving side are created. If the file exists decides what happens when the destination is taken. Upload and Download copy: a folder merges into a folder of the same name, and for each file already there Replace it overwrites it while Fail the block stops before anything is written; a file never lands on a folder, nor a folder on a file, whatever the choice. Move renames: Replace it removes whatever already holds the target name, a file or a whole folder tree, and the source takes its place, so folders are never merged; Fail the block stops when anything holds that name. A Move whose target is the source itself or a folder holding it is refused before anything is removed, and Move refuses a Source that names the account's home, a folder above it or the server root, like Delete. Delete removes a file or a whole folder tree; with Ignore missing off, a path that is not there fails the block, and with it on, the block passes. A path that names the account's home, a folder above it or the server root (for example empty, `.`, `..`, `~` or `/`) is refused before anything is deleted; a wildcard such as `*` is allowed. Create folder creates the folder together with any missing parent folders (SFTP-5).

**Limits**: A download is bounded so that a runaway match on the server cannot fill the WAVE server's disk. Advanced carries Max size (MiB), 1024 by default, and Max files, 10,000 by default, shown for Download only; 0 means no limit. The block works out the total size and file count of the match before it writes anything, and refuses a match over either limit with a message naming the limit. The Advanced group's footer reads "Limits for this block" (SFTP-6).

**Safety and Partial Files**: A folder download walks the server tree itself rather than trusting names the server hands back: symbolic links are skipped, and an entry name that could reach outside the destination folder fails the block. A failed, timed-out or stopped transfer leaves no partial file behind: a download lands under a temporary name and takes its real name only when it is complete, and a partial upload is removed from the server. Collisions are checked before the block acts, so a refusal names the path and the setting that would change the outcome rather than repeating the server's generic failure (SFTP-7).

**Timeout, Stop and Failure Handling**: Timeout bounds the whole block, every file of a folder transfer included; its bounds are declared once and enforced both in the form and when the block runs. Timeout and Stop end the transfer at once, with the partial-file rule above. On error is Fail the block, the default, or Record and continue: Success is always an output, and Error and Reason appear under Record and continue, as on every block with Failure Handling (SFTP-8).

**Outputs and Console**: Upload and Download give Summary, a table with one row per file transferred, carrying its source, its destination and its size. List gives Entries, a table with the name, path, type, modified time and size of each entry, and Count; with Include subfolders on, the listing walks into subfolders. Stats gives Exists, Type, Size in bytes and Modified in ISO-8601 UTC; a missing path is not a failure and gives Exists false, an empty Type and a Size of 0, which is what lets a Wait Until poll on it. Delete, Move and Create folder give only Success. The run console shows one summary line per operation, and every file written into the run's files is logged with its name, path and size; file contents never appear in the console (SFTP-9).

**Where the Block Runs**: The block always runs on WAVE, because the session it rides lives on WAVE. Inside a Remote Execution body it carries the L badge and still runs on WAVE, as every block that is not remotable does there, so its Test Data and artifact references keep resolving on WAVE. A server behind a jump chain is reached through the session opened along the chain, and a server behind an SSH Tunnel through a session opened on the tunnel's Local Port, whose host key is checked and recorded under the tunnel's far host (SSH-8). In both cases the block itself needs nothing beyond the session.

**Secrets**: The block holds no credentials. The login, the password, the private key and its passphrase belong to SSH Session Open and its SSH profile, which seal and mask them on every outbound surface; nothing the block does can reveal them, and no hop in a chain ever receives another hop's credentials.

**Palette and Catalog**: SFTP belongs to the Remote category everywhere, together with the six SSH blocks and Remote Execution: it sits in the palette's Remote section beside the SSH blocks, and the block catalog the assistant reads lists it under Remote. It keeps its existing FolderSync glyph and carries the cyan Remote category color like the rest of the section (SFTP-10, REMICON-1).

**Recipe Surface**: The block is catalog-driven like every block: a recipe step names it and provides its rows, which are validated against the block's own declared rows (REQ-5.2.7.3), so the block is expressible in recipes with no format change. Its WAVE-side file rows, Upload's Source and Download's Destination, follow the recipe file rules: a Test Data reference, an artifact reference or a plain path, with both schemes kept inside a Remote Execution body because the block runs on WAVE there. Server-side paths are plain text.

**Design System Reference**: UI components follow the Design System. Design decisions: SFTP-1 through SFTP-10. The K8s Copy sheet's From Pod limit rows match the SFTP download limits (K8SEXEC-10). Related decisions: SSH-7 for the private keys a session opens with, and SSH-8 for sessions opened through a tunnel.
