#### OpenSearch Block

##### REQ-3.4.1.15 OpenSearch operations (query, index, bulk)

The OpenSearch block reads what the system under test sent to an OpenSearch cluster: log lines and events come back as a table of results, and numbers OpenSearch works out from them come back as a table too. It works against OpenSearch 1.x, 2.x and 3.x, on WAVE, on a remote host and through an SSH tunnel, and it hands back what the cluster answered as WAVE values.

**Purpose and Locus**: One block with no Operation row. A Mode row right after Query picks Search, which returns the matching documents with the fields the author picks, or Aggregate, which returns numbers OpenSearch works out from those documents; each mode shows only its own rows, and Mode takes no expression because it decides which rows show. The block is read-only. OpenSearch is where the application under test leaves its outcome - its logs, its events, its counters - and the block reads that outcome and writes nothing: it creates no index, loads no document, updates nothing and deletes nothing. Writing a file is not its job either: a Results table that should be kept as a file goes to the CSV block. WAVE reaches the cluster's REST port directly or over SSH, never through OpenSearch Dashboards. There is no Connect operation and no session value: every block carries its own connection rows, typed in or bound from an OpenSearch profile, opens its own connection, sends its requests and closes it, which is the one shape that runs the same everywhere. The block never waits or polls: a search answers with what the cluster holds at that moment, and waiting for a line to land is the job of a Wait Until around the block (REQ-3.3.2.2).

**Rows**: The top rows are Cluster URL, Index pattern, From, To, Query language, Query and Mode, shared by both modes, then the chosen mode's ungrouped rows, then Timeout, then the groups: Sort (Search only), Authentication, TLS / Certificates, Advanced and Failure Handling. Cluster URL is one address such as `https://host:9200`. The scheme decides TLS; a path prefix is kept, for a cluster behind a proxy mount; a URL with no port uses the scheme's default port, and the Unreachable error names the port it tried; credentials written inside the URL are refused. An address that answers as OpenSearch Dashboards gets the message "This is the OpenSearch Dashboards address. The block needs the cluster address, usually port 9200". The Authentication group, collapsed, holds Username, Password, API Key and Bearer Token with no mode picker: emptiness carries the meaning. Password, API Key and Bearer Token are sealed secrets. A username and password, an API key and a bearer token all travel in the one Authorization header, so more than one set fails validation with one message saying so; none set means an anonymous cluster or a cluster with security off; a value typed with its scheme word in front gets an amber note on the row. The group's footer line reads "How WAVE identifies itself to the cluster: a username and password, an API key, a bearer token, or none. A client certificate under TLS / Certificates can go with any of them." The TLS / Certificates group, collapsed and with no toggle because the URL already says whether TLS is on, holds Verify Server Certificate (on by default), CA Certificate, Client Certificate and Client Key, the rows the HTTP and SQL blocks already have, with WAVE's certificate trust rule: a CA Certificate set on the block is the only certificate trusted, and a blank one trusts the Additional Certificates and the public authorities chosen in Settings (REQ-4.5.16); they are used only for an https URL, and filled on an http URL they show an amber note that they are not used. Advanced holds Time field (`@timestamp` by default) and Connect timeout (30 seconds). Failure Handling carries On error and Secrets work as on every block. Timeout, 300 seconds, bounds the whole block, paging included: when it runs out the search is ended on the cluster, not merely abandoned.

**Search Mode**: Search reads the documents of the Index pattern (REQ-3.3.2.5) inside the From / To window on the Time field (REQ-3.3.2.3) that match the Query (REQ-3.3.2.6) and hands them back as Results (REQ-3.3.3.1). Its rows are Fields, an ordered list of the columns that come back, which opens with `@timestamp` and where every entry can be removed, empty meaning the whole document as one column; Max results, 10,000 by default and 0 for all, where past 10,000 the block pages through the matches in sort order behind the scenes; and the Sort group, closed by default, holding Sort by, the Time field by default or any sortable field, and Order, Newest first by default or Oldest first.

**Aggregate Mode**: Aggregate asks OpenSearch to work out numbers from the same documents - the same Index pattern, window and Query - and hands back the numbers, not the documents behind them. Its rows are a plain form rather than pasted JSON: Group by time, Group by field with Top values, and Stats, the list of numbers wanted (REQ-3.3.3.2).

**Outputs and Failure Handling**: Both modes have the same outputs: Success; Results, a Table, holding the documents in Search and the numbers in Aggregate; and Total results, the exact number of matching documents at any size. Error and Reason appear under Record and continue. Every run checks the Index pattern and every field the rows name against the cluster's field list for the pattern, because a search that quietly finds nothing reads as a pass (REQ-3.3.2.6). Two outcomes end the block amber rather than failed, each with a WARN line naming the cause: an Index pattern that matches no index or a named field the cluster does not know, and partial results, where some shards failed or the search timed out on the cluster. A Time field that is not a date field fails the block. Reaching Max results is not a failure: Results keeps the first documents in sort order and the log says so at WARN. Neither is Top values leaving documents out of the groups: the log says how many at WARN.

A failure while the block runs follows On error and carries the reason shown:

| Failure | Message | Reason |
|---------|---------|--------|
| The host, the port or the TLS handshake does not answer | names the host and the port it tried, with the network's own text | Unreachable |
| The cluster refuses who WAVE is: any 401, including the security layer's plain-text Unauthorized, or a 403 security exception | OpenSearch's own words: the error's type and reason, or for a plain-text answer its status and first line, such as `HTTP 401: Unauthorized` | AuthFailed |
| OpenSearch refuses the request: a query it cannot parse, a field of the wrong type for the query, a setting it rejects | OpenSearch's own words: the type and reason of the error's first root cause; when all shards failed, OpenSearch's summary, then the first root cause and the query as sent | RequestFailed |
| The whole block runs past Timeout | says how long it ran; the search is ended on the cluster | Timeout |
| The rows cannot make a request: a filled `{{ }}` value broke the query, a Query that does not parse, an empty Fields entry or a Stats entry that cannot work, settings that conflict such as more than one credential set, credentials inside the URL, a From or To in epoch seconds; or the cluster's first answer shows a Dashboards address or a Time field that is not a date | names the row and what to change, before anything is sent except for the two the cluster's answer shows; a time in epoch seconds says "for seconds, multiply by 1000" | Validation |

Stop and Timeout shut the live connection down, and the search ends on the cluster rather than running on after the block has let go of it.

**Console Output**: The run console receives these lines and no result data: the documents and numbers are in Results. Credentials and secret values are never logged.

| When | Level | Line |
|------|-------|------|
| A run finished | INFO | one line with the index pattern, the window in UTC, the total results, the results kept (Search) or the rows (Aggregate) and the duration |
| Max results reached | WARN | `Kept N of M results (Max results)` |
| Top values left matching documents out of the groups | WARN | how many documents fall outside the kept values |
| The Index pattern matched no index, or a named field is unknown to the cluster | WARN | names the pattern or the field; the block ends amber |
| Partial results | WARN | the failed shards, or that the search timed out on the cluster; the block ends amber |
| From is later than To, or later than now | WARN | names both ends in UTC |
| A whole Query DSL request was pasted into Query | INFO | `Query: kept only "query" from the pasted request; dropped ...`, naming the dropped keys |
| Every request to the cluster | DEBUG | the method, the path and the body exactly as sent; never a header |
| A failure under Record and continue | WARN | `Search failed (Reason): message` or `Aggregate failed (Reason): message` |

**The Query Editor**: Query opens in the shared Edit value sheet in a DQL mode built on the SQL editor: DQL coloring, `{{ }}` expressions in the variable color, line numbers, a FIELDS suggestion list wherever a field name goes, and for a field the cluster does not know an amber underline and a line in the validation strip. A DQL line is checked with the grammar Dashboards itself uses and reports Dashboards' own error text. Query DSL opens in the same editor with JSON coloring and suggests keys, their allowed values and their descriptions from OpenSearch's published API specification; its check allows comments, as OpenSearch does, flags duplicate keys, and underlines an unknown query key or a value of the wrong kind. A Custom (JSON) stat opens in the JSON editor the same way. Checks and suggestions run on the WAVE server after each typing pause; their findings are warnings that never block Save or Run, since the cluster is the judge on Run. The editor footer carries the Fields chip, whose states are Get fields; Getting fields... with a Stop; Got N fields with a checkmark; Fields · N with a refresh button; and Could not get fields. Run and Stop follow PYRUN-21 and SQL-13, as in the SQL editor: Run executes this block once with the text as it sits in the editor; a running Run turns into Stop, and Stop ends the search on the cluster.

**Get Fields**: Get fields, the counterpart of the SQL block's Get Tables, connects from the WAVE server with the block's own connection rows or bound profile, trusting certificates and using the Proxy setting the way the block does, reads which indexes the Index pattern matches and the fields they hold with their types, and disconnects. It runs only when the author clicks for it. The result is one field list per connection, cached while the workbench has the test open, and it is offered first on Time field, Fields, Sort by, Group by field and a stat's Field, and in the editor. A field list needs an Index pattern: while the row is blank, those rows and the editor pull nothing and say so. The Index pattern row offers the same pull as Get indexes: the indexes, aliases and data streams the pattern matches, or every index the credentials may see while it is blank. Daily indexes fold into their wildcard, so a pattern matching 412 dated indexes reads `logs-*, 412 indexes` rather than 412 lines. A failed pull raises one error toast with the cluster's reason; a refusal to list every index is said in plain words, and a refusal to read the pattern names the pattern in plain words before OpenSearch's own text.

**Where the Block Runs**: The block is remotable and carries the R badge inside a Remote Execution body. A remote host has nothing installed on it: WAVE's own REST client, the same one the WAVE server runs, travels with the run as source and needs nothing beyond the Python the host already has. DQL is turned into Query DSL where the block runs, because the field types the translation needs can only be read from where the block reaches the cluster. Through an SSH tunnel the block behaves as SQL and Netcat do: a Cluster URL on 127.0.0.1 or localhost at the Local Port of an open tunnel goes through that tunnel, and both the TLS server-name check and the host the request names use the far host. On the WAVE host, when the Proxy setting is on, the block reaches the cluster through the proxy or directly as the setting's route decision says for the cluster's address; a Cluster URL on a local address, a tunnel's Local Port included, connects directly unless the setting sends local addresses through the proxy too; on a remote host the block never uses the proxy (REQ-4.7.14).

##### REQ-3.3.2.2 Collect logs from OpenSearch with query filtering

A log collection is a Search: an Index pattern for where the application's logs land, a From / To window, a Query that picks the lines, the Fields that matter as columns, and an order by time. The lines come back as the Results table; the run log shows only the summary line and any warnings. The block writes no file: to keep every line of a long test as a file in Artifacts, Results goes to the CSV block.

**Waiting Is the Control's Job**: The block never waits for data; a Wait Until in Retry mode re-runs a Search in its retry sub-flow on every round until its condition comes true, the same idiom every block uses. A document becomes searchable only after the cluster's next refresh, about a second by default, so a line the application just wrote may be missing from a search sent at the same moment; the wait absorbs that.

**Wait, Then Collect**: To collect every line up to the application's final line without re-reading every line on every round, the pattern is two Searches. The Search inside the Wait Until's retry sub-flow looks only for the final line - a Query such as an error line OR the final info line, the Fields that tell them apart, Oldest first, Max results 1 - so each round costs one small answer, and the wait's condition checks Total results. An If/Else on the found line's level branches the error path from the success path. A short Delay, a few seconds, lets lines still on their way land. Then one collecting Search with Max results 0 reads the whole window, from the test's start to the final line's timestamp taken from the first Search's Results. WAVE expressions have no clock, so the test's start is captured by the author with a Python or Shell block early in the test and handed to From as a variable; a relative From such as `now-15m` could match lines from before the test started.

##### REQ-3.3.2.3 Filter logs by time range

Every search, in either mode, reads a window on the Time field, `@timestamp` by default under Advanced; the Time field must be a date field of the matched indexes. From and To each show their value as written - `now-15m`, `now`, `2026-09-25T10:42:05Z` - and their expand opens a popover with three tabs, as OpenSearch Dashboards' date picker does, ending with Cancel and Save (FIELD-9): Absolute, with the shared calendar, a time of day and a box for a typed ISO timestamp; Relative, with a number, a unit from seconds to years, ago or from now, Round to the unit, and the resulting value such as `now-15m` shown underneath; and Now. From defaults to 15 minutes ago and To to now. With the expression toggle a row takes a variable or an expression instead, whose value is a timestamp, epoch milliseconds, or OpenSearch's own relative time such as `now-1h` or `now/d`. Relative time counts back from the moment the search runs. A timestamp with no zone is read as UTC, and the row shows a muted hint saying so; both ends are inclusive. A number that reads as epoch seconds is refused with "for seconds, multiply by 1000"; a From later than To or later than now runs and logs a WARN, since the search can only find nothing. The run log states the window in UTC. In Aggregate the time slots of Group by time span the whole window, from From to To.

##### REQ-3.3.2.5 OpenSearch index pattern selection (wildcards, date math)

Index pattern is required and takes what OpenSearch takes: one name, a wildcard such as `logs-*`, a comma list, exclusions written with a leading minus, an alias, a data stream, or a date-math name such as `<logs-{now/d}>` for today's daily index. WAVE sends the pattern as written, encoded for the request, and OpenSearch resolves it on the cluster; WAVE keeps no pattern resolver of its own, so the block matches exactly what the same pattern matches in Dev Tools, and date math resolves in UTC as the cluster resolves it. A pattern that matches no index ends the block amber with a WARN naming the pattern rather than handing back an empty table that reads as a pass. Get fields shows what the pattern matches before the test runs, with daily indexes folded into their wildcard.

##### REQ-3.3.2.6 OpenSearch field-based filtering and queries

**Query Languages**: Query language picks DQL, the default, or Query DSL. DQL, the language of Discover's search bar, covers everyday filters in one line: a field and a value, `and`, `or` and `not`, parentheses, ranges, wildcards and field existence, so a filter such as an error line OR the final info line is one DQL line and a line copied from Discover works unchanged. WAVE translates a DQL line into Query DSL with Dashboards' own rules. Query DSL covers what DQL cannot say and holds only the query part of a request; a whole request pasted into the row keeps only its query part, because what comes back and in what order is set by the block's own rows. The query string syntax and OpenSearch's SQL and PPL are not query languages of the block. The Query filters the documents in both modes: in Aggregate it picks the documents the numbers are worked out from.

**Values in a Query**: In text mode, `{{ }}` expressions are filled by default in the Query row, and each value is escaped for where it lands: inside a DQL quoted phrase it is quoted text; in DQL outside quotes it is one literal value however many words or operator words it holds, while a `*` the author typed beside it stays a wildcard; inside a JSON string it is JSON-escaped text; and standing alone as a JSON value it becomes that value in JSON form, a null value becoming JSON `null`. A null value inside quotes, in a JSON string or anywhere in DQL fails the block before anything is sent and names the `{{ }}` (see REQ-3.1.3.22). A trace ID or a user name from an earlier block can therefore never change what the query means. The one value DQL cannot hold outside quotes is a lowercase "not" followed by a space: DQL reads it as the NOT operator, even inside a word such as "cannot stop", and has no escape for it, so the block fails before sending anything and names the `{{ }}` to put inside quotes. A capital "Not" or "NOT" is escaped as usual.

**Expression Mode**: Query has the expression toggle. In expression mode the row holds an expression whose result is the query: DQL text, or for Query DSL a map or JSON text. The where-it-lands escaping applies to text mode only, because an expression builds the whole query itself.

**Fields and Sort**: In Search, Fields picks the columns that come back, and Sort by and Order pick the order; nested fields are named with dots, as Discover names them.

**No Silent Zeros**: OpenSearch answers a filter on a field it does not know with no results and no error, so every run checks the Index pattern and every field that the Query, Fields, Sort by, Time field, Group by field and the stats name against the cluster's field list for the pattern. A pattern that matches nothing or a field the cluster does not know ends the block amber with a WARN naming it.

##### REQ-3.3.3.1 Retrieve JSON events from OpenSearch index patterns

**Results**: Search hands the matching documents back as the Results table, one row per document and one column per Fields entry in the order listed; since Fields opens with `@timestamp`, the time is the first column unless the author removes it. A nested object becomes dotted columns in name order, `user.id` beside `user.name`, as Discover shows them; an array is JSON text in its cell; a field a document lacks is a null cell. With Fields empty, Results holds the whole document as one column. An empty result keeps its columns, so a check on a column still finds it. Total results is the exact number of matching documents at any size.

**Max Results and Paging**: Max results, 10,000 by default, bounds how many documents Results keeps; 0 keeps them all. OpenSearch answers at most 10,000 documents to one request, so past that the block pages through the matches in sort order, continuing after the last document of each page with the document ID as tiebreaker, so no line is dropped or repeated when several share a timestamp. When Total results is larger than Max results, Results keeps the first documents in sort order and the log says `Kept N of M results (Max results)` at WARN.

##### REQ-3.3.3.2 OpenSearch statistics validation

**Two Kinds of Number**: The simplest statistic is Total results, which both modes give: the count of errors in a window is an error Query over that window followed by an Assert on Total results. Anything else - a count per minute, a sum, an average, a percentile, a unique count, how much a counter grew - is Aggregate mode, and it is checked the same way: the block hands back Results and Assert compares its cells.

**The Aggregate Form**: The author describes the numbers in a plain form. Group by time splits the window into time slots: No, or Every 10 seconds, 30 seconds, 1 minute, 5 minutes, 15 minutes or 1 hour, with Every 1 minute by default. Group by field, optional and picked from the field list, splits by that field's values, and Top values, 10 by default, sets how many of its most frequent values get rows; documents outside those values are left out and the log says how many at WARN. Stats is an ordered list that opens with one Count entry. Each entry reads in words, such as "Count" or "95th percentile of latency_ms", and opens a popover with Stat, Field and the column name the entry produces:

| Stat | What it gives | Column name |
|------|---------------|-------------|
| Count | the number of matching documents; it needs no field | count |
| Sum | the sum of the field's values | sum of X |
| Average | the average of the field's values | average of X |
| Min | the lowest value of the field | min of X |
| Max | the highest value of the field | max of X |
| Percentile | the value below which the given Percent of the field's values fall; Percent is set on the entry | percentile 95 of X |
| Unique count | the number of distinct values of the field | unique count of X |
| Increase | how much a running total, such as a request counter, grew: each time slot counts the rise from the previous slot's highest value, the first slot with documents counts the rise inside it, and a slot where the counter restarted counts the rise from its own lowest value, so the drop at a restart is never counted | increase of X |

Custom (JSON), the last choice of Stat, takes one OpenSearch aggregation written as JSON for anything the list does not offer; it opens in the JSON editor with the same checks and suggestions as Query DSL.

**Results in Aggregate**: Results has one row per time slot, one row per field value, or one row per slot and value pair when both groupings are set, and one row for the whole window when neither is. The time column is named after the Time field, the value column after the grouped field, and each stat adds one column. A time slot with no documents shows 0 rather than being left out, so a quiet minute stays visible. Total results is the exact number of matching documents; the run log shows only the summary line and any warnings, never the table.

**Checking the Numbers**: Checks go through Assert on Results, such as the highest per-minute error count staying under a limit, and waiting for a number to reach a value is a Wait Until around the block, as for any other value.

##### REQ-3.3.3.6 Query OpenSearch documents by ID or search criteria

A document ID is one more field condition in the query, not a separate operation: `_id` is named in DQL like any other field, or in the Query DSL's ID query, and it combines with any other criterion. In Search the document comes back as a one-row Results table with Total results 1; an ID that is not there gives an empty table with Total results 0 and the block passes, so an Assert decides whether absence is a failure. Search criteria of any other kind go through the same Query row. Because the block searches, a document the application has just written is found after the cluster's next refresh, and a Wait Until around the block covers the gap.
