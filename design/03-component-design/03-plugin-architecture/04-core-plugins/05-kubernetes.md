##### REQ-3.4.1.5 Kubernetes API operations

## Purpose

WAVE's Kubernetes support is a family of blocks in the Kubernetes palette category modeled on kubectl's verbs rather than on resource types: one block per verb, and every verb kind-agnostic. The author picks the verb, then names the kind, so StatefulSets, Jobs, Ingresses and custom resources are served by the same blocks as Pods and ConfigMaps, and no generic escape-hatch block is needed. Together they let a test read cluster state, change cluster configuration, manage and observe workloads, run commands inside containers, and verify outcomes - the "change config, restart, verify behavior" loop of Kubernetes-deployed products - without any host tooling: no kubectl, no kubeconfig files on the server, no cloud CLIs. Each block versions independently, mirroring the SSH plugin family.

## Cluster Context Model

K8s Connect is the single entry point to a cluster. It takes the API server URL, credentials, server CA, and a default namespace - typically bound from a Kubernetes profile - verifies reachability and version, and emits the cluster context as its K8s Session output: a kubectl-compatible kubeconfig document carried in a secret-protected variable. Every other K8s block requires that context as an input, referenced by expression.

The context is a value, not a live connection: Kubernetes API access is stateless HTTPS, so there is nothing to hold open and no Close block. Because the context travels as a value, it goes wherever the block runs, and two Connect blocks yield two independent contexts, so a single workflow drives multiple clusters side by side.

## Authentication

Connect authenticates as a ServiceAccount - the machine identity every automation product uses - in one of two modes: a bearer token, or a client certificate and key. A CA certificate, when set, is the only certificate the session trusts, and with it blank the session trusts the Additional Certificates and the public authorities chosen in Settings (REQ-4.5.16); a TLS server-name override keeps verification honest when the server is reached through a tunnel or by IP; verification can be explicitly disabled for lab clusters. Interactive login mechanisms (cloud CLI plugins, OIDC browser flows) are out of the model: they are human-login machinery, and their tokens expire mid-run.

Connect optionally acquires a run token: it asks the cluster's own token-issuing API to mint a ServiceAccount token with a chosen lifetime, and embeds that token in the emitted context instead of the supplied credential. A short-lived organization token then only needs to be valid at the moment Connect runs; the rest of the run uses the cluster-minted token. Where the cluster or the caller's permissions do not allow minting, Connect fails with the cluster's own explanation.

## The Blocks

| Block | What it does | Notable outputs |
|-------|--------------|-----------------|
| K8s Connect | Establishes the cluster context | K8s Session (secret, kubeconfig-shaped), Cluster Version |
| K8s Get | Reads any kind: one object by name, a filtered set by selector, or the whole list | Result, Names, Count |
| K8s Events | Lists events for a namespace, the whole cluster, or one named object | Result, Count |
| K8s Logs | Reads one container's log from one pod | Logs |
| K8s Top | Reads pod or node CPU and memory usage from the metrics API | Usage, Count |
| K8s Apply | Creates or updates objects from a manifest or from a per-kind form | Summary, Result, Names, Count |
| K8s Delete | Removes objects by name or by selector | Summary, Names, Count |
| K8s Scale | Sets the replica count of any scalable kind | Summary |
| K8s Rollout | Restarts a workload, reports the state of its rollout, or rolls it back to an earlier revision | Summary, Status (Status operation only) |
| K8s Exec | Runs one command in a running container | stdout, stderr, exit code |
| K8s Script | Runs a script through an interpreter in a container | stdout, stderr, exit code |
| K8s Copy | Copies files and directories between a pod and the WAVE side, in either direction | Summary |

Every operational block - every block except Connect - shares three outputs on top of its own: Success, Error, and Reason. Error carries the exact human message, Reason carries the cluster's stable machine enum (NotFound, AlreadyExists, Forbidden, Conflict and the rest), so a workflow branches on Reason and never matches on error text. Every operational block also shares the session input, the request timeout, the namespace override, impersonation, and the failure-handling control. The Helm blocks - Helm Install, Helm Upgrade, Helm Rollback, Helm Uninstall, Helm Test and Helm Status - share this family's session, core outputs and Failure Handling control, and are described in the Helm design.

**Naming the kind.** Where a block reads or writes any kind the cluster serves, the kind is named through a pair of rows: a source selector offering Default or Custom, then the kind itself. Default renders a grouped, searchable list of the kinds a stock Kubernetes install serves, ordered Workloads, Networking, Config, Storage, Cluster, with kubectl's short names beside the entries that have one. Where a verb only applies to a fixed few kinds the pair narrows or disappears: Scale's Default list is the kinds a cluster serves a scale endpoint for, and Rollout offers the three workload kinds that have a rollout with no Custom alternative at all, because a kind without one has nothing to roll. Custom replaces the list with a plain text field that takes anything the cluster serves, custom resources included. WAVE keeps no list of its own: the cluster's live discovery resolves case, plural forms and short names to the endpoint that serves them, and a kind the cluster does not serve fails the block, naming the kind and telling the author to check the spelling or whether the CRD is installed. A frozen WAVE-side catalog would go stale the moment an operator is installed, so discovery is the only authority. K8s Events names the kind of the object an event is about rather than a kind it reads, and it resolves that name the same way: discovery turns whatever the author typed - the singular, the plural or the short name - into the canonical kind the event's involved-object field carries, so every spelling kubectl accepts matches, and a kind the cluster does not serve fails the block instead of answering with no events at all.

**Reading.** K8s Get offers three explicit ways to find objects, with no combinations: by Name, which reads exactly one object and fails when it is absent; by Selector, which filters on labels and fields; and as a List, which reads them all. Selector and List return a list, where nothing matching is a legitimate result with a count of zero - which is why an existence check that tolerates absence is a list read and never a name read. The response shape is chosen by the output format: the parsed structure, the cluster's own printed table with every column the cluster provides, or the same objects as JSON or YAML text for storing or comparing whole. Every read that hands back objects strips Kubernetes' own field-management bookkeeping from them, as kubectl does by default, so a result carries the object's content and not the record of which controller last wrote each field; the JSON and YAML forms are re-serialized from the parsed objects rather than being the bytes the cluster sent.

**Writing.** K8s Apply takes either a manifest the author pastes or a short form for the few kinds worth one, and both paths converge on the same write. An object that is already there is merged field by field by default, and the block can instead be told to treat an existing object as a failure. A field the cluster does not recognize is refused rather than dropped, so a misspelled key fails the test instead of passing it quietly, which is the strictness kubectl applies to every write. A multi-document manifest applies in order and does not roll back: a later failure leaves the earlier objects applied, and the count reports how many landed. A manifest is written as YAML or as JSON, and the engine normalizes it to one canonical form before the block reads it, so the same text applies identically wherever the block runs; a scalar that merely looks like a date stays text, and a stream that declares no document at all is refused before anything is written.

**Waiting is not an operation.** Readiness and rollout waits compose from the Wait Until control or a loop around read blocks and assertions, keeping polling policy in the workflow where it is visible and debuggable. The one wait a block owns is Delete's: kubectl's own delete waits for the object to be gone, so Delete does too, bounded by the block's timeout and switchable off.

## Resource Usage

K8s Top reads CPU and memory usage from the cluster's aggregated metrics API, the separate API group a metrics component serves alongside the object API - the same source kubectl top reads. Figures come back in raw units, cores and bytes, never percentages, so the workflow picks its own denominator: a pod's figure is the sum over its containers, with an optional per-container breakdown, and a node row also carries that node's capacity and allocatable so a ratio can be computed where one is wanted. A node the cluster has but the metrics API does not cover is still a row of its own: its capacity and allocatable come from the node itself, it carries no cpu or memory reading, and it counts toward the returned count, so a gap in metrics coverage is visible instead of a node quietly missing from the answer. Targets are chosen the same three ways as elsewhere in the family: all of them, one by name, or a label selector, and all of them is the default, so a Top block measures everything until it is narrowed - what the equivalent kubectl command does with no arguments. A cluster that does not serve the metrics API is a configuration fact rather than a cluster answer, so Top fails the block whichever failure-handling setting it carries, and says which API is missing.

## Command Execution in Containers

The execution split mirrors the SSH family deliberately. K8s Exec runs one command line in a running container and returns its streams and its exit code. The command is written as a single line and split the way a shell splits one, so quotes group arguments, and it is then run directly rather than through a shell, which is how the Kubernetes exec API runs it. Exec has no standard input at all - one command line in, the two streams and the exit code out, on every cluster the family supports - and a non-zero exit code is data the workflow branches on, not a block failure. K8s Script hands a multi-line script to a chosen interpreter by writing the script to the interpreter's standard input and then finishing it, so nothing is written to the container's filesystem and the script's length is not bounded by a command-line argument limit. The script body's format picker is pinned to Plain, with none of the JSON, YAML, XML or Auto choices; Template stays available as the value Kind (PYRUN-15). Finishing standard input without aborting the command exists only from Kubernetes 1.30, so K8s Script requires 1.30 or newer; on an older cluster it is an ordinary block failure carrying Error and Reason, and a script reaches such a cluster by being copied in and then executed. Nothing on the block's configuration surface states the requirement: it is stated on the block's own reference page. K8s Script has no working directory, because the Kubernetes exec API has no such notion. Both ride the Kubernetes exec channel: a WebSocket stream negotiated with the API server, multiplexing the standard streams and a status channel that carries the exit code. Richer WAVE-native logic running from a pod belongs to the Remote Execution model, which owns "WAVE plugins act from another vantage point".

## Copying Files Into and Out of Containers

K8s Copy moves files and whole directories between a pod and the WAVE side over the same exec channel, the way kubectl cp does: it drives the container's own archiving tools rather than an API the cluster serves for the purpose, so a pull needs tar present in the container and a push additionally needs a shell and base64, and stages its encoded archive in a directory it creates beside the target and removes once the copy finishes, so the space it needs there falls on the filesystem the copy is landing on. It uses no standard input in either direction, so unlike K8s Script it carries no cluster-version requirement of its own. Direction is an explicit choice of From Pod or To Pod, and the two path rows keep fixed names whose meaning follows that choice, so a path row never silently changes sides and each row states plainly whether it is a pod path or a WAVE path. The WAVE side of a copy is the run's artifacts, and because the path row takes the vocabulary the file-handling blocks share, an absolute or relative path also resolves; artifacts are the route that works end to end. K8s Copy grows no upload path of its own: a push sources a file an earlier block in the same test wrote.

What was copied is reported as a Summary table, one row per file carrying where it came from, where it landed, and its size. There is no separate count and no list of paths: the table's own row count carries that. Of kubectl cp's own options K8s Copy carries the container choice and the option not to carry permissions and ownership across, which by default do carry across, as kubectl carries them. It has no retry option: a broken transfer is what the block's failure handling is for. A copy from the pod is written to disk as it arrives, so WAVE's memory does not grow with the size of the copy or with its limits. For From Pod the Advanced group carries Max size (MiB), 256 by default, and Max files, 10,000 by default, where 0 means no limit; the limits guard the disk on the WAVE side, and a copy that crosses either one is stopped at that moment, what it had written is removed and any file it had replaced is put back as it was, so a runaway path in a container cannot fill the WAVE server. To Pod carries no size limit, because the files it copies come from the WAVE side. The stop reads as a cluster-side failure and follows the block's On error choice. The Advanced group's footer reads "Namespace and identity in place of what the session provides, and size limits for copies from the pod" (K8SEXEC-10).

## Kubernetes Secrets as Credentials

The family treats cluster secrets as credentials end to end. The wire-level base64 encoding is invisible in both directions, so an author never types or reads an encoded value, and every value a block reads from or writes to a cluster Secret registers with the run's secret registry the moment the block touches it. Registration is by kind, not by field name or by guesswork, and it is what protects a value a block reads back: once a value is registered it is masked in logs, console, reports, and exports wherever it later appears, regardless of which output it arrived in or what the author does with it next. On the write side the Apply form's Secret Data is additionally a declared credential: readable while the author is typing it, sealed in the saved test, masked on the block's input line, and protected in the sheet once stored, where reopening it clears it for re-entry. The ConfigMap form's key-value data carries no such treatment and stays readable. A Secret's type is chosen from Opaque, kubernetes.io/tls and kubernetes.io/dockerconfigjson, with Opaque as the default; the two typed forms offer the key names the cluster requires for them, and the cluster rejects a typed Secret that is missing one. Reading a cluster Secret with K8s Get is therefore the supported way to load credentials held in Kubernetes for use by downstream blocks.

## Version Alignment

The verbs speak only generally-available Kubernetes APIs, which Kubernetes guarantees stable, so one implementation covers every supported cluster from 1.19 up without version-specific code. Connect reads the cluster version at connect time and refuses clusters below the 1.19 floor. The one block that does not cover that whole range is K8s Script, which feeds the interpreter on standard input and so needs the mid-session stream finishing the API server serves from Kubernetes 1.30; every other block in the family runs on the whole supported range. There is no version pin to set: a kind is named on its own, and the cluster's live discovery resolves it to the group and the version that cluster prefers, so one workflow stays correct across clusters that serve the same kind at different versions. A manifest is the one place a version is stated, because a manifest carries its own, and there the stated version is the one the object is written at; a cluster that does not serve it fails plainly, naming the kind and the version. That is the same mechanism kubectl uses to stay version-correct.

## Execution Loci and Reachability

Every K8s block runs wherever it is placed: on the WAVE server, or inside a Remote Execution container on that container's host, so the API server has to be reachable from wherever the block sits, and a private API server has two routes to it. From WAVE, reachability composes with the SSH Tunnel plugin: the tunnel's local port feeds Connect's server URL by expression, and the TLS server-name override keeps certificate verification strict across the loopback rewrite. From inside a Remote Execution container on a host that already sees the cluster, Connect takes the server's own URL and nothing is rewritten. On the WAVE host, when the Proxy setting is on, every K8s block, over REST and over the exec stream, goes through the proxy or directly as the setting's route decision says for the API server's address; a server URL on a local address, the tunnel's local port included, connects directly unless the setting sends local addresses through the proxy too; inside a container a block never uses the proxy (REQ-4.7.14). The same implementation runs in both places, because the verb logic of every block lives in a self-contained, standard-library-only core that the remote bundle carries unchanged - a block inside a container is the block, not a subset of it - and the canvas locus badge on every block reflects true routing.

Only structured data crosses the boundary, and WAVE reconstitutes it on return: a table comes back a table, a result that renders as YAML text is rendered on WAVE, and every secret value a block discovered is registered with the run's secret registry before any line the block logged is replayed and before any output is bound, so the credential treatment above holds regardless of locus. Input validation and Record and continue behave identically on both sides: a bad input is refused with the same message wherever the block sits, and a refusal under Record and continue yields the same Success, Error and Reason, the same warning line and the same warning status on the canvas. An API refusal reads the same on both sides, the remote one additionally carrying the host attribution the Remote Execution design defines. A session opened on one side is usable on the other, because the context is a self-contained value: a Connect on WAVE feeds a Get inside a container, and the reverse.

K8s Copy inside a container works against the remote host's own filesystem: its WAVE-side path row names a path on the remote host, absolute or relative to the SSH user's home folder, made absolute with its `..` segments collapsed before use as on WAVE, which is what a copy staged from a bastion needs. The test saves with an artifact or test-data reference there, but the remote host refuses such a reference on the local side at run time, before any exec, because on the remote host there are no run artifacts or test data to read or write.

## Error Handling Strategy

Failures carry exact, distinguishable messages: missing objects name the object and namespace; authentication and authorization failures are separate ("authentication failed" versus "permission denied", the latter carrying the cluster's RBAC explanation); transport, TLS, and timeout failures are attributed to the connection, not the operation. Reading one object by name and not finding it is a failure, never a silent default - the tolerant form of that check is a list read, which answers with an empty list and a count of zero. Deleting a name that is already gone is an error, exactly as it is in kubectl; ticking Ignore not found turns it into a pass with a count of zero, which is what a teardown flow that tolerates absence uses.

What a cluster's refusal then does is the author's choice, made once per block in its Failure Handling control. Fail the block is the default: the refusal becomes a block error and the Try / Catch control handles it. Record and continue is the alternative: the block finishes, Success is false, Error and Reason carry the message and the cluster's reason, the block's own outputs hold their empty defaults, and one warning line names what the cluster refused, so the outcome stays visible on the canvas and in the console without stopping the run. The choice governs cluster answers only. A missing or unreadable session, a transport, TLS or timeout failure, and parameters or manifests WAVE itself rejects are dependency errors rather than results, and they fail the block under either setting.

## Frontend Integration

Every block is schema-driven: the standard element-configuration table renders every parameter, and the blocks introduce no bespoke configuration components. Mode selectors gate which parameters are visible - the kind source swaps the kind row between the grouped searchable picker and a plain text field, and the read mode decides whether a name row, the selector rows, or neither appears. Outputs are gated only where a mode makes one meaningless: Error and Reason belong to Record and continue, which is the only setting that lets a refusal reach them, and Rollout's Status belongs to the Status operation. Success is deliberately never gated, so a workflow can bind one outcome check on every block regardless of its setting.

Parameters group in the same order on every operational block: Connection (the session and the request timeout), the block's own verb group, Advanced, and Failure Handling. Advanced holds the per-block overrides of what the session already provides - the namespace field, All namespaces where the block has it, and impersonation - with All namespaces above the namespace field, hiding it while it is ticked because the two are mutually exclusive. On K8s Copy, Advanced also holds the From Pod size limits, Max size (MiB) and Max files, after the impersonation rows and only while Direction is From Pod (K8SEXEC-10). The namespace field is plain, always visible and optional: no control reveals it, and leaving it empty means the namespace the session carries, the way an omitted kubectl flag does. All namespaces appears only where it can apply: never on a block reading one named object, never when Top measures whole nodes, and not at all on Logs, whose namespace field is therefore unconditional, matching kubectl in each case. Connection and the verb group open expanded, so the sheet opens on the rows an author has to fill in; Advanced and Failure Handling open collapsed. Connect, which takes no session, groups instead into Connection, Authentication (which carries the Get SA Token toggle and the Service Account, SA Namespace and Duration (s) fields it reveals), and TLS / Certificates.

## Design System Reference

UI components follow the Design System. The config sheets are schema-only renderings of the standard parameter table. Design decisions: K8SCON-1 through K8SCON-6, K8SREAD-1 through K8SREAD-19, K8SWRITE-1 through K8SWRITE-8 and K8SEXEC-1 through K8SEXEC-10.

##### REQ-3.5.2.1 ConfigMap CRUD operations

ConfigMaps are covered by the kind-agnostic verbs. K8s Get reads them - one by name, a filtered set by label selector, or the whole list - and its structured result feeds assertions and downstream configuration directly. K8s Apply creates and updates them, either from a manifest or from the ConfigMap form, whose key-value editor spares the author from writing YAML for the common case; by default Apply updates an object that already exists, and it can instead be told to treat an existing object as a failure. K8s Delete removes them; a ConfigMap that is already gone is an error unless Ignore not found is ticked, which turns it into a pass with a count of zero.

##### REQ-3.5.2.2 Secret CRUD operations

Secrets use the same verbs with the credential treatment described under "Kubernetes Secrets as Credentials": invisible base64, registration of every value with the run's secret registry the moment a block touches it, and a type row on the Secret form offering Opaque, kubernetes.io/tls and kubernetes.io/dockerconfigjson, defaulting to Opaque. Get reads them, Apply writes them from the form or from a manifest, Delete removes them; the registration is triggered by the kind, so it holds on all three paths. The write path adds the credential treatment the form itself carries: the Secret form's data is a declared credential, so it is readable while the author is typing it, sealed in the saved test and masked on the block's input line, and protected in the sheet once stored, where reopening it clears it for re-entry. The ConfigMap form's data is not a credential and stays readable.

##### REQ-3.5.2.3 Deployment management

Deployments are managed by verb rather than by a Deployment-specific block: K8s Apply for manifest-driven create and update, K8s Scale for a replica count, K8s Rollout for a restart, for the rollout's own state (complete, progressing or failed, with the cluster's message), and for rolling the workload back to an earlier revision or to the one before the current, and K8s Get for observation - spec and ready replica counts, container images and the full status object, which combine with loops and assertions into rollout verification. Because the verbs are kind-agnostic, the same blocks scale a StatefulSet or restart a DaemonSet.

##### REQ-3.3.5.1 Pod status monitoring

K8s Get over the Pod kind returns the object as the cluster holds it, so phase, readiness conditions, node placement and pod IP arrive together in one result; a selector or list read adds the names and the count. Polled by the Wait Until control or by a loop, it implements status monitoring with the workflow in control of cadence and timeout.

##### REQ-3.3.5.2 Container restart detection

A pod read returns the container statuses, each carrying that container's restart count and its last terminated state, so asserting on the count across a scenario detects crash loops and unexpected restarts. K8s Events over the same pod names the reason the cluster gave for the restart, and K8s Logs with the previous-instance option reads what the container printed before it died.

##### REQ-3.3.5.3 Resource state verification

K8s Get reads any kind the cluster serves, built-in or custom, and returns structured state the Assert control verifies directly. The output format picks the shape the check needs: the parsed object or list for field-level assertions, the cluster's own printed table when the columns are what matters (which is also how a custom resource's operator-defined columns are asserted on), and JSON or YAML text when the response is stored or compared whole.

##### REQ-3.3.5.4 Event monitoring

K8s Events is a first-class block, not a list read over the Event kind. It reads events for a namespace, for the whole cluster, or about one named object, filters them by type, by reason and by age, caps how many come back, and returns them newest first. Scheduling failures, image pull errors and probe failures surface with the cluster's own reason string, which is what an assertion branches on.

##### REQ-3.3.2.1 Collect logs from pod containers

K8s Logs reads one container's log from one pod through the cluster's log subresource - container selection, a tail limit, a since window, a byte cap, optional per-line timestamps, and the previous-instance flag - into a variable for assertion, storage, or downstream parsing. The container is named on every read, including on a pod that declares only one, so every block in the family that addresses a container addresses it the same way. WAVE chooses no container on the author's behalf, which is a deliberate divergence from kubectl's own client-side choice of a default container.

##### REQ-4.6.3 Kubernetes 1.19+ compatibility

Satisfied by the version-alignment model above: generally-available endpoints only, live-discovery resolution of every kind to the version its cluster prefers, and a connect-time floor check that refuses clusters below 1.19 with a plain message.

##### REQ-4.5.5 K8s RBAC compliance

WAVE operates entirely within the RBAC grants of the identity it is given and adds no privilege of its own. Authorization denials are first-class, distinguishable block errors carrying the cluster's explanation, so a permissions problem reads as exactly that - never as a product failure. Every operational block can also send its request as another user, with optional group memberships, through the cluster's own impersonation mechanism: what that identity may do is decided by the cluster against that identity, never simulated by WAVE, so a test can prove a role's limits from one connected session. Impersonating without the right to impersonate is itself an ordinary authorization denial.

##### REQ-4.5.6 Load credentials from K8s secrets

Reading a cluster Secret with K8s Get is the supported path for loading credentials held in Kubernetes: every value registers with the run's secret registry as the block reads it, so it is masked in logs, console, reports and exports wherever it later appears, and it feeds downstream blocks by ordinary variable reference.
