##### REQ-3.4.1.6 SQL database operations

The SQL block runs SQL against one database from a test: a script, a stored procedure, or a table load. It works against PostgreSQL, MySQL / MariaDB, Oracle, SQL Server and SQLite, on WAVE, on a remote host and through an SSH tunnel, and it hands back what the database answered as typed WAVE values.

**Purpose and Locus**: One block, three operations picked on its Operation row: Run SQL, Call procedure and Load table (SQL-1). The database type is picked on the block too, and it selects the driver, the dialect the editor colors, checks and suggests, and the default port. There is no Connect operation and no session value: every block carries its own connection rows, typed in or bound from a database profile, opens its own connection, does its work and closes it. That is the only shape that runs everywhere, because on a remote host every block is its own process; an author who needs the same database in six blocks duplicates the block. A consequence the block's documentation states: session state does not carry from one block to the next, so a `USE`, a `SET search_path`, an `ALTER SESSION` or a temporary table lives only inside the script that made it, and a script that ends on such a statement is flagged with a warning (SQL-3).

**Connection Rows**: The top rows stand ungrouped in the order Operation, Database type, Host, Port, Database, Username, Password, then the operation's own rows, then Timeout (SQL-8). Port left blank means the type's own default - 5432, 3306, 1521, 1433. Database is the database name, and on Oracle the service name. Password is a secret. On SQLite a File row replaces Host through Password: a path chosen with Browse over Test Data and Artifacts, or a path where the block runs. The TLS / Certificates group holds a TLS toggle that takes no expression, because it decides which rows show: on, it reveals Verify Server Certificate, CA Certificate, Client Certificate and Client Key, the rows the HTTP block already has; it is on by default on SQL Server only, matching each driver's own default. Off means a plain connection: on PostgreSQL, whose driver would otherwise try TLS unasked, WAVE asks for none. With Verify Server Certificate on, a CA Certificate set on the block is the only certificate trusted, and with it blank the block trusts the Additional Certificates and the public authorities chosen in Settings (REQ-4.5.16). On Oracle, an address or protocol given in Driver options must agree with the TLS toggle (REQ-3.4.1.19). Advanced holds Connect timeout (30 seconds), Max rows (10000, 0 for no cap) and Driver options, a name / type / value list handed to the driver under the driver's own names - the block's documentation lists the common ones per database, and on Oracle a `dsn` entry, a full connect descriptor or an Easy Connect string, replaces Host, Port and Database, while a bare TNS alias there is refused because WAVE never reads Oracle's network configuration on the WAVE host (REQ-3.4.1.19). Each row declares its type with the shared element type picker (text, whole number, decimal, true/false, list or map, REQ-3.1.3.19) and the driver receives the value as that type: SQLite's `cached_statements` declared a whole number arrives as the number 16, SQL Server's `readonly` declared true/false arrives as a boolean, and an application name `2024` declared text stays text. A row may instead hold an expression, whose result is the value. A database profile's Driver options field carries the same per-row types, and a block bound to the profile receives them. There is no pasted connection string: five databases have five formats and the password would sit inside it. Every database that accepts a program name is told WAVE, and an Oracle session uses the database's own time zone, never the WAVE host's (REQ-3.4.1.19). Failure Handling carries On error as everywhere. Timeout, 300 seconds, bounds the whole block: when it runs out the running statement is canceled on the database, not merely abandoned.

**Run SQL**: Script Type is Source or File, as on the Python block; Source opens the SQL in the shared Edit value sheet in a SQL mode, File takes a `.sql` file from Test Data or Artifacts, read on WAVE and sent along, or a path where the block runs. The SQL row also takes the expression toggle: in expression mode the row holds an expression whose result is the SQL text, and the `:name` placeholders in that text are still bound from Parameters. Values reach the SQL as bound parameters (SQL-2): the author writes `:name` where a value goes and lists the name and its value in Parameters. The statement and the values travel to the database separately, so quoting and escaping are never the author's problem, a number stays a number, empty text binds as empty text and a null value binds NULL (see REQ-3.1.3.22); one entry covers every use of the name, and the `:name` form is the same on all five databases. A placeholder with no entry fails the block before anything is sent, naming it. A table or column name, which no database can bind, varies through a `{{ }}` expression in the SQL text. A script is split the way the database's own tool splits it - `;` on every database but SQL Server, where only a `GO` line splits and each batch counts as one statement, and a `/` line after a PL/SQL block on Oracle - so a script pasted from psql, SSMS or SQL Developer runs unchanged, and its statements go in order (SQL-3). WAVE opens no transaction of its own: each statement commits on its own, and an author who wants a transaction writes BEGIN and COMMIT in the script. Stop on error, ticked by default, stops the script at the first failing statement and fails the block with that statement's error; unticked, every statement runs, each failure is a WARN line carrying the database's own text, the block passes, and when every statement failed it ends amber. Max rows caps what is kept from a result on the fetch side, without touching the SQL (SQL-4): the rows so far are kept and a WARN line says so. WAVE never injects LIMIT, TOP or FETCH FIRST.

**Call procedure**: Procedure names the procedure or function with its schema or package. Arguments is a list in the procedure's own order whose entries are the parameter name and the input value; an argument value is a data field like a parameter value, so a null value binds NULL and empty text binds empty text. Out arguments names the arguments the procedure writes back (SQL-6). The call is built per database - a PL/SQL block with out variables on Oracle, `EXEC` with `OUTPUT` parameters on SQL Server, `CALL` with session variables read back on MySQL, `CALL` or `SELECT * FROM` on PostgreSQL - and uses named notation where the database has it. A PostgreSQL function is selected with its Arguments only; its OUT parameters named under Out arguments fill Out values the same way a procedure's out arguments do. SQLite has no procedures, so the operation is not offered there.

**Load table**: Table is the rows to load, a WAVE table variable or a CSV or Excel file from Test Data or Artifacts chosen with Browse; Target table must already exist, because WAVE creates no tables and the schema stays the DBA's (SQL-7). Columns match by name. Before any row is sent the target's columns are read from the database, so a WAVE column with no match fails at once by name and a database column with no match is left to its default. Values are bound with their types and the database converts them the way it converts any bound value; the one WAVE-side rule is that booleans become 1 and 0 on Oracle and SQL Server, which have no boolean type. A value the database refuses fails the load with the database's own error plus the row number and column. Mode is Add (plain inserts; a duplicate key is the database's error), Add or replace (matching on Key columns, empty meaning the table's primary key, read from the database; a table with no primary key and no key columns fails before sending; on MySQL the database matches any unique key and the documentation says so) or Overwrite, which empties the table with DELETE and loads in the same transaction and never drops it. Commit each batch, off by default, makes every batch commit on its own and reveals Stop on error with the Run SQL semantics - ticked, a failed batch stops the load and fails the block with the earlier batches kept; unticked, the failed batch is skipped with a WARN line and the block passes, amber if every batch failed. Off, the whole load is one transaction across every batch: all rows or none. Batch size, 1000 under Advanced, is rows per round trip, never a commit.

**Outputs and Failure Handling**: Success is an output of every operation. Rows, a Table, and Row count are outputs of Run SQL (the last statement that returned rows, or an empty table) and Call procedure (rows the procedure returned). Rows changed is an output of Run SQL (the sum over the script) and Load table (rows committed). Out values, a one-row Table with a column per out or in-out argument typed as the database typed it, is an output of Call procedure - a table rather than a map for the reason Ping's Summary is one: it reads as a grid in the run log and the inspector (SQL-6, SQL-9). Column types follow the database's own; a type WAVE has no match for comes as text. A NULL in a result or in Out values becomes null, keeping the column's type (see REQ-3.1.3.23). Error and Reason appear under Record and continue.

A failure while the block runs follows On error and carries the reason shown (SQL-5):

| Failure | Message | Reason |
|---------|---------|--------|
| The host, port or TLS handshake does not answer | `Could not connect to {database type} at {host}:{port}: {driver's own text}` | Unreachable |
| A SQLite file cannot be opened: the file or its folder is not there, a Test Data file that does not exist included | `Could not open the SQLite file {file}: {SQLite's own text}`; a Test Data file that does not exist is named as typed | Unreachable |
| The login is refused | `Authentication failed for {user} at {host}: {database's own text}` | AuthFailed |
| The database refuses a statement: syntax, a missing object, a constraint, a permission | the database's own code and text, unchanged (`ORA-00942: table or view does not exist`) | DatabaseError |
| The whole block runs past Timeout | `Statement timed out after {n} seconds` (singular "second" when {n} is 1); the running statement is canceled on the database | Timeout |
| A `:name` in the SQL has no Parameters entry | `Parameter '{name}' is used in the SQL but not defined`, before anything is sent | Validation |
| A remote host has no driver build for its Python, CPU or libc | `{host} cannot run {database type}: it has Python {x.y} on {cpu} / {libc}; WAVE carries {list}` | Unsupported |

The log names a failing statement by its number and first line, because a script may hold ten. Reaching Max rows is not a failure: the rows so far are kept and the log carries `Stopped after {n} rows (Max rows)` at WARN.

**Console Output**: The run console receives these lines; parameter values and row contents are logged at DEBUG only and secret values never:

| When | Level | Line |
|------|-------|------|
| Connected | INFO | `Connected to {database type} {server version} at {host}:{port}` |
| A statement finished | INFO | `Statement {i}: {rows} rows, {ms} ms` or `Statement {i}: {n} rows changed, {ms} ms` |
| A call finished | INFO | `Called {procedure}: {rows} rows, {n} out values, {ms} ms` |
| A statement failed under Stop on error off | WARN | `Statement {i} ({first line}) failed: {database's own text}` |
| A script ends on a session-state statement | WARN | `Statement {i} ({first word}) ends the script; its effect ends with the block` |
| Max rows reached | WARN | `Stopped after {n} rows (Max rows)` |
| Load table | DEBUG then INFO | the statement once in the database's placeholder form, then `batch {i}/{n}: {rows} rows`, then `{rows} rows into {table}, {s} s`; with Commit each batch on, a batch's line follows its commit, so a batch whose commit the database refuses writes none |
| A one-transaction load failed (Commit each batch off) and rolled back | INFO | `Transaction rolled back: 0 rows into {table}`, so batch lines already written never read as rows that landed |

**The SQL Editor**: The SQL body opens in the shared Edit value sheet in a SQL mode (SQL-10): SQL coloring for the chosen database type in the sheet's existing highlight styles, `:name` placeholders in the variable color, line numbers, Kind Literal by default with Template opt-in for an author who needs `{{ }}`, and Format locked to SQL. The syntax check lives on the WAVE server and runs while typing: after each typing pause the whole script goes to the server once, the server parses it with a dialect-aware SQL parser set to the chosen database and answers the lines and messages, and an answer that arrives after further typing is discarded. It runs only on a body that holds no `{{ }}`, because a template is not SQL until it is expanded. Its findings, together with a `:name` that has no Parameters entry, a Parameters entry no placeholder uses, a `{{ }}` expression the expression field would flag, a script ending on a session-state statement and - once the tables are loaded - a table or column the catalog does not know, show as underlines and in the validation strip. They are warnings: they never block Save or Run, since the database is the judge on Run; an unknown table is amber because the catalog may be stale or the table may be created by an earlier block. Suggestions come in three kinds, each only in its place (SQL-11): tables and their columns where a name goes (after FROM, JOIN, INTO, UPDATE and after `table.`), the Parameters entries after `:`, WAVE variables inside `{{ }}`, with the database's keywords and functions underneath as the baseline. Run and Stop follow PYRUN-21 (SQL-13): Run executes this block once with the SQL as it sits in the editor; a running Run turns into Stop, and Stop cancels the statement on the database. The Python editor's Run has the same Stop.

**Get Tables**: The catalog is never read on its own (SQL-12). Get Tables, a chip in the editor footer, and the same action as the first row of the suggestion list at a table position while nothing is loaded, connect from the WAVE server with the block's own connection rows or bound profile, trusting server certificates by the block's own rule (REQ-4.5.16), read the tables and views with their columns for the schema the connection lands in, and disconnect. While it runs the chip reads Connecting... then Getting tables... with a square Stop that cancels it; done, it reads Got N tables with a checkmark for three seconds or until the next keystroke, then settles to Tables · N with a refresh button beside it; failed, the chip says so and a click tries again. The result is cached per connection while the workbench has the test open, so blocks on the same database share one pull and never pull on an edit, and Refresh re-pulls the connection the editor is in. The Tables popover holds a search box that filters the loaded tables with their columns under each and inserts the chosen name at the cursor. A connection row whose value exists only at run time - set by an earlier block - cannot be resolved when the sheet is open, so the pull works when the connection is described by fixed values, Environment variables or a profile.

**Where the Block Runs**: The block is remotable and carries the R badge inside a Remote Execution body. A remote host has nothing installed on it (SQL-15): PostgreSQL's and MySQL's drivers travel as source like every other pure-Python dependency, and what exists only compiled - Oracle's driver, the TLS layer SQL Server's driver needs, and WAVE's own SQLite - travels with the run as the prebuilt build that fits the host's Python (3.10 to 3.14), CPU (x86_64, aarch64) and libc (glibc, musl), in the scratch directory the worker already owns and removes. A host outside that set fails the block at once with reason Unsupported, naming the host, the database type, what the host has and what WAVE carries. WAVE's own SQLite needs glibc 2.28 or newer (or musl 1.2); a host where it cannot be loaded fails the block at once with reason Unsupported. SQLite is WAVE's own bundled build on the WAVE host and on every remote host, so a script meets the same SQLite version everywhere, and the Connected line names it. Through an SSH tunnel the block behaves as Netcat does: a Host of 127.0.0.1 or localhost on the Local Port of an open tunnel goes through that tunnel, and the TLS server-name check then uses the far host.

**Documentation Page**: The block's documentation page carries one table per database type: how statements are separated, the placeholder form the DEBUG log prints, the boolean mapping, the statement Add or replace builds, the common Driver options, and what is not offered on SQLite. It also states that session state ends with the block, and how Call procedure returns rows on each database: a `SELECT` in the procedure on MySQL / MariaDB and SQL Server, a cursor handed back with `DBMS_SQL.RETURN_RESULT` on Oracle, and on PostgreSQL a function called with `SELECT * FROM` when `CALL` finds no procedure by that name.

##### REQ-3.3.3.3 SQL database state checks

A database state check is a Run SQL block followed by the checks every other value gets. The block hands back Rows as a typed table and Row count as a number; Assert compares them, and Wait Until in Retry mode re-runs the block on every round until the condition comes true, which is how a test waits for a pipeline to land a row. The SQL block itself never waits or polls: a query returns what the table holds at that moment, its outputs land when the block ends, and waiting for data is the job of the control around it, so one waiting idiom serves every block (SQL-1). Because the values are bound and typed, a check reads the database's own numbers, dates and text rather than their string forms.
