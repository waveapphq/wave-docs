##### REQ-3.4.1.4 HTTP/HTTPS client operations

The HTTP client plugin performs request/response operations over HTTP and HTTPS for service API testing: configurable method, URL, headers, query parameters, and request body; response status, headers, and body capture; TLS verification with optional custom certificate authority; redirect handling; retry with backoff; and a per-request timeout.

**Header model.** The headers map stores user intent; the editor additionally renders every header WAVE itself generates - the composed authentication header and the body section's automatic content type - as read-only rows, so the visible map always matches what the plugin sends. Standard transport headers (Host, User-Agent, Accept, and peers) are sent automatically and any user row overrides them. Duplicate-key validation is case-insensitive per HTTP semantics and counts generated rows like any other; deleting a generated row switches off the feature that produced it, except the multipart content type, whose row is locked because the transport owns its boundary. The single header the HTTP stack physically refuses to let a caller override, Content-Length, is rejected with a message saying exactly that; every other header, Transfer-Encoding included, is forwarded verbatim, and a value the transport refuses fails the block with the transport's own error. One key policy, with identical exact messages, applies in the visual editor, in the code view of the map, at save validation, and - for dynamically produced header maps - when the block executes, with the offending source named.

**Map and part values.** Each value in the request maps - a header value, a query parameter value, a form field value - and each multipart text part's value is either a plain literal or a single whole-value expression; there is no mixing of literal text with expression fragments inside one value. A literal is stored and sent verbatim, and characters that look like an expression inside a literal stay literal and are never evaluated. An expression is one expression evaluated when the block runs, the same expression capability every other value field in WAVE offers. Map keys and multipart part names are always literal. The value field is WAVE's standard value input: a plain input for a literal, with the usual toggle that switches it to the full expression editing experience (inline autocomplete, live validation, and the full editor). The code view of a map keeps a valid-JSON shape so it can be validated - a literal value appears as a quoted string and an expression appears as a bare {{ expression }} in the value position, with keys always quoted - and a value that is neither a quoted string nor a braced expression is rejected. An expression that resolves from a secret variable stays masked on every scrubbed surface, and a credential-catalog key holding a plain literal draws the non-blocking unsecured-credential advisory, while an expression value, which may reference a secret variable, does not.

**Authentication.** A dedicated auth section composes the credential header for the ubiquitous schemes: Basic (username and password, encoded automatically), Bearer token, and API key under a chosen header name. The secret inputs are sealed credential fields. The composed value registers as a runtime secret at send; the composed header renders in the headers editor as a masked read-only row that participates in duplicate validation, and deleting it disables the section. Enabling the section with a required field empty fails the run before anything is sent, naming the mode and the missing fields. At runtime the composed header wins over a same-named header arriving from a dynamic map. Manual credential headers remain legal and keep the advisory and send-time masking treatment.

**Request bodies.** A body may accompany any method; an empty body sends nothing. Body modes: raw text (with an advisory when the content is JSON but no content type is set), URL-encoded form fields, multipart form-data assembled from text and file parts, and a single file as the body. The body section owns automatic header management: a control governs whether the content type the mode implies is generated - form mode generates its URL-encoded type, file mode sends a type chosen from common media types or detected from the file extension in WAVE's own file-type table (REQ-3.4.3.10), and multipart always sends the transport-generated boundary type with the control locked on. With automatic headers off, WAVE sets nothing: the form encoding falls to the transport's own default while file and text bodies go out with no content type, and the editor shows a non-blocking amber advisory naming the header the mode would have supplied. File sources are artifact references, test-data references, or absolute or relative paths, resolved where the block runs, with a `..` segment followed wherever it leads; multipart and file bodies stream from disk without buffering in memory.

**Responses.** Response handling is a mode: body capture (response text as an output) or file download, where the response streams to the execution's artifacts - or to a host path when the block runs remotely - and the body output carries the resulting path, with a digest output for integrity assertions. Both modes honor a size cap; exceeding it truncates what is kept and logs a warning, never an error. Verdicts about a response belong to the Assert and flow controls; transport failures fail the block.

**Evidence.** Every run leaves a wire-level evidence trail. The summary log states method, URL, status, duration, and size. At debug verbosity the block logs a combined trace: connection establishment with negotiated TLS protocol, cipher, and the server certificate's identity and validity window; each exchange with the headers actually sent and received (every redirect hop and retry attempt is an exchange); and a timing breakdown from connect through first byte to download. Bodies never appear in the trace. The same facts are available as a structured trace output for assertions such as certificate days-to-expiry or time-to-first-byte. Duplicate response headers are preserved in order within the trace while the plain headers output remains a map. Header values under known credential names are masked inside the trace by name at capture time, in both directions and on every hop including redirects and retries, regardless of value length; the per-block unmask choice keeps named values readable, and marking the trace output secret extends the same treatment to every hop header. The timing total covers the wire window only - from the first transport event to the last across all attempts - never the plugin's own preparation or artifact writing. All evidence surfaces are additionally masked through the run's secret registry.

**Transport security.** TLS is provided by a bundled pure-Python client rather than the host's system TLS library, so a test's protocol-version and cipher choices put the same bytes on the wire on every operating system and stay reproducible over time and across the local backend and remote execution hosts. The plugin verifies server certificates by WAVE's certificate trust rule (REQ-4.5.16): a CA Certificate set on the block is the only certificate it trusts, and with it blank the block trusts the Additional Certificates and the public authorities chosen in Settings, on the WAVE host and on a remote host alike. It presents client-certificate identity (a certificate and a sealed private key) for mutual TLS whenever the server requests it; identity is presence-based, with no separate switch. The negotiated protocol version can be pinned at both ends of a range spanning TLS 1.0 through 1.3, with the ordering validated, so a test can exercise and assert how a server responds to a specific version. Cipher preference is an ordered selection drawn from a fixed, host-independent catalog of common suites, each carried under both its OpenSSL and IANA names; unknown names are rejected by name. The catalog is split by protocol family: the suites usable at TLS 1.0 through 1.2, each tagged with the versions it applies to, and the TLS 1.3 suites, which are independently selectable and ordered. Only suites and families whose versions fall inside the selected range are offered; anything outside the range is not shown. Left unset, the block offers every catalog suite inside the selected range and nothing else - the same list it shows as the default - and deliberately selecting none offers no ciphers at all.

**Network path.** The block's proxy choice (REQ-3.4.3.9) has two values. WAVE setting, the default, follows the Proxy setting in Settings for a request made from the WAVE host (REQ-4.7.14); Off overrides the Proxy setting for that block and connects directly. The block holds no proxy address of its own. Inside a Remote Execution body the request uses the remote host's own proxy settings, and the Proxy row, disabled, says so. Requests are made over HTTP/1.1. On the WAVE host the block uses the far host of an SSH tunnel the way SQL and OpenSearch do: a connection made directly to 127.0.0.1 or localhost at the Local Port of a tunnel open in the same run sends the tunnel's far host as the TLS server name and checks the server's certificate under it, while the URL and the Host header stay as written. Each connection is looked up on its own, so a redirect to an address that is not a tunnel's Local Port is checked under its own host.

**Remote execution capability surface.** When the block runs inside a Remote Execution body its capability surface is honest: a body on any method, composed authentication, certificate verification, and the full TLS configuration - protocol-version pins, cipher selection, and client-certificate identity - behave identically on the remote host, because the same bundled pure-Python TLS client travels in the bundle. Every capability the remote bundle does not carry - the form, multipart, and file body modes, file responses, and the size cap - is rejected at design time with a message naming the capability, never silently ignored. Since every file-taking mode is among them, no file path reaches the remote host from this block.

**Pure-Python, Location-Transparent Implementation**: The plugin is implemented purely in Python - both its HTTP layer and its TLS layer, the latter a bundled pure-Python client rather than the host's system TLS library or any native-extension client - so a single implementation runs unchanged in two places: on the WAVE backend, and - when the block is placed inside a Remote Execution container - inside a self-contained bundle executed by a remote host's own interpreter. This makes the plugin remotable, and it makes a test's TLS behavior - protocol version, cipher offering, and verification - identical and reproducible on every operating system and on both the local and remote paths. Running the request on a host, rather than only tunneling egress to it, still gives the request that host's true network context: its routing and reachability and its proxy settings. Client-certificate identity and the certificate-authority trust it verifies against are WAVE-configured and portable, presented from wherever the block runs. A tunnel can carry connectivity but cannot supply that end-client fidelity, which is why HTTP participates in Remote Execution rather than relying on port-forwarding alone. The request path carries no native dependency and exchanges plain structured data, keeping the host requirement to a compatible Python interpreter.

##### REQ-3.4.3.9 HTTP proxy choice

The HTTP block's Proxy row offers two choices. WAVE setting, the default, follows Settings > Network > Proxy on the WAVE host: with the setting off the request connects directly, and with it on the request goes through the proxy or connects directly as the setting's route decision says for its address (REQ-4.7.14). Off makes a direct connection and overrides the Proxy setting for that block, so a test can show that a request fails without the proxy. The block holds no proxy address of its own: the only proxy it can use is the one the Proxy setting holds. The WAVE host's proxy variables are never read on their own: they take part only when an admin chooses them as the Proxy setting's source. Inside a Remote Execution body the request uses the remote host's own proxy settings, because the Proxy setting covers requests made from the WAVE host only; there the Proxy row is disabled and reads "Remote host's settings". The row does not show the block's own choice there, so saving the block's configuration inside a Remote Execution body stores no proxy choice, like a hidden row (REQ-4.7.16); when the row shows again it starts on its default, WAVE setting (FIELD-8). A block moved into a Remote Execution body keeps its choice until its configuration is saved there. A block run on the WAVE host whose request went through a proxy says so in the run log.

##### REQ-3.4.3.10 HTTP Auto content type

When a file body or a multipart file part has its content type on Auto, the type comes from the file's extension in WAVE's own file-type table, never from the WAVE host's file-type configuration, so the same file is sent with the same type from every WAVE host. The table covers the common types, spreadsheets, YAML, JSON Lines and TypeScript source (sent as text) among them; an extension it does not know is sent as generic binary data. An explicit content type always overrides it. The types WAVE names for artifacts and file downloads come from the same table.
