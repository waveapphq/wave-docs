## Purpose

WAVE's Helm support is six blocks in a palette category of their own, Helm, one per helm verb: Helm Install, Helm Upgrade, Helm Rollback, Helm Uninstall, Helm Test and Helm Status. They sit beside the Kubernetes category and share its session, its outputs and its failure handling. They drive the real helm command rather than a reimplementation of it: charts are Go templates, and a chart under test has to be rendered by the same tool the product ships with, or the result says nothing about the product. WAVE ships no helm of its own; a block calls the helm found where the block runs. The blocks follow helm parity, the same rule the K8s verbs follow for kubectl: every control is a real helm flag, named as helm names it, carrying helm's own default, and a control that would exist only because of how WAVE drives helm never reaches the sheet.

## Where Helm Runs

Every Helm block carries a Helm Path row in its Advanced group, empty by default. Empty means the executable named helm on the PATH of wherever the block runs - the WAVE host, or the execution host inside a Remote Execution container. A bare name is looked up on the same PATH, an absolute path is called as given, and a relative path starts at the home folder of the account the block runs as, like every other relative path a block takes (REQ-3.4.3.12); the row's help says so. There is no system-wide setting: a team sets the row once by binding it to an environment or global variable. A missing helm is a plain block failure naming what was tried and where. WAVE never asks helm for its version on its own initiative. Only when helm rejects a flag as unknown does WAVE read the version once and report that the helm it found is older than 3.13, the oldest helm whose flag surface matches what the blocks emit.

## The Blocks

| Block | What it does | Notable outputs |
|-------|--------------|-----------------|
| Helm Install | Installs a chart as a named release | Result, Status |
| Helm Upgrade | Upgrades a release to a chart version, optionally installing it when absent | Result, Status |
| Helm Rollback | Rolls a release back to an earlier revision, or to the one before the current | Result, Status |
| Helm Uninstall | Removes a release, optionally keeping its history, tolerating an absent one and choosing how its resources are reclaimed | Shared core only |
| Helm Test | Runs the chart's test hooks and reports each one's Phase | Result, Logs |
| Helm Status | Reads a release, current or by revision | Result, Status |

Every Helm block shares the K8s family's Success, Error and Reason outputs, its session input, its Failure Handling control, and its namespace override and impersonation rows. Every block takes the K8s Session that K8s Connect emits; there is no Helm connect block, no Helm profile of its own, and no kubeconfig on disk beyond the life of one helm call.

## Chart Sources and Values

The Chart row takes what helm's own chart argument takes: a chart name resolved against the Repository URL row, a reference into an OCI registry, a URL to a packaged chart, or a path on the machine where the block runs. As in helm, a value is a local path when it names something that exists there or starts with a dot, and a chart name otherwise; a relative local path starts at the home folder of the operating-system user the WAVE server runs as when the block runs on WAVE, and at the SSH user's home folder inside a Remote Execution container. Version pins a version or a range; empty means the latest helm finds. Values takes a YAML document that reaches helm as a values file; Set takes key-value pairs that reach helm one by one under helm's own typing rules. Repository credentials and trust live in an Auth & TLS group of their own: a username, a password that is a declared credential, a CA certificate for the repository, and server-certificate verification, on by default. They concern the chart repository only; the cluster's trust travels in the session. Repository trust follows WAVE's certificate trust rule: a repository CA certificate, when set, is the only certificate trusted for the repository, and with it blank the repository is checked against the Additional Certificates and the public authorities chosen in Settings (REQ-4.5.16). A private chart, in a classic repository or an OCI registry, is pulled with the block's own username and password; logins stored on the WAVE host are ignored (REQ-3.5.3.6). A local chart directory whose dependencies are not yet downloaded is prepared ahead of the Helm block with helm's own dependency update, run on the same machine - from a Shell Script block when the Helm block runs on WAVE, or from SSH Session Exec on the container's session when it runs inside a Remote Execution container.

On upgrade the values in effect follow helm's rules, stated plainly on the sheet. With nothing passed, the previous release's values stay. With values passed, the previous values are forgotten unless Reuse Values keeps them as the base. Reset Values forgets them even when nothing is passed. The two are exclusive, and the sheet enforces it by unticking one when the other is ticked; both may be off. Install if missing turns an upgrade of an absent release into an install, and only then does Create Namespace apply, as in helm.

## Waiting Is Not an Operation

As in the K8s family, readiness is composed from Helm Status or K8s Get under the Wait Until control, so no Helm block carries a wait row and helm's own default of not waiting is kept. Two flags that need a wait to deliver a state guarantee stay, in Failure Handling. Atomic waits for the release to come up within Timeout and on failure removes a fresh install or rolls an upgrade back to the previous revision, so a failed install never blocks the next use of its name. Cleanup on Fail removes the resources a failed upgrade or rollback newly created, which a rollback alone would leave behind. Timeout is helm's own operation timeout, 300 seconds by default, on every block but Status, where it is WAVE's bound on the read. It is also the wall-clock bound on the block: the run is stopped the moment it runs out, and every call a block makes - the write, the release read-back, the history read that fills the chart cells - is bounded by that same number. Atomic and Cleanup on Fail are the one exception, because helm has to keep working after its timeout fires to undo what failed. A block carrying one of them offers a Cleanup Timeout, 300 seconds by default, which is the room helm gets for that repair, and the block's whole bound is the two added together. The row appears only while the flag that earns it is ticked, so a block with nothing to undo is bounded by Timeout alone.

## Release Results

Install, Upgrade, Rollback and Status report the release through one Result output whose shape follows the Output Format row. Table is one row carrying helm's own list columns - Name, Namespace, Revision, Updated, Status, Chart, App Version; Map is the release document helm reports; JSON and YAML are that document as text, notes and rendered manifest included. Status is also a scalar output, so Wait Until polls it directly, and a release removed by Atomic reads as absent. Rollback prints only text, so its result is the release read back after the rollback. helm's release record carries no chart on a read, so the Table row of a read composes that record with the release history, matched on the revision the read returned, to fill Chart and App Version; the Map, JSON and YAML forms stay the record helm reports, and a history that cannot be read leaves the two cells empty rather than failing the block. Test reports one row per test hook - Name, Kind, Phase, Started, Completed - read from the release record rather than parsed from helm's text, and with Logs ticked it returns every test pod's log under helm's own per-pod headers; a chart with no tests reports an empty table and succeeds, as helm does. Uninstall reports the shared core outputs only.

## Version Alignment

The blocks emit only flags that behave the same on Helm 3.13 and later and on every Helm 4, so one block works against whichever helm a machine carries. Which Kubernetes versions a given helm supports is helm's own policy - the four minors up to the one it was built against - and WAVE adds no check of its own. Helm 4 installs charts written for Helm 3 and upgrades releases Helm 3 created; a release Helm 4 created may not be manageable by Helm 3, which matters when a release installed from the WAVE server is later handled from a bastion whose helm is older. The blocks' reference pages state both facts.

## Execution Loci and Reachability

Every Helm block runs wherever it is placed, as the K8s verbs do. The session is handed to helm as a kubeconfig written for the duration of one call and removed after it; the server URL, credentials, CA, server-name override and verification choice carry across, a blank CA carrying WAVE's certificate trust set instead (REQ-4.5.16), while the session's cipher-suite and TLS-version pins cannot bind a helm process and do not. helm starts with a clean environment that WAVE builds for the call: its configuration, cache, data, registry and repository locations point at a directory that lives only as long as the call, helm runs inside that directory, and nothing else from the WAVE host reaches it except the proxy of the Proxy setting when that is on, so nothing of the run persists on the WAVE host or on the execution host and no login stored there is used (REQ-3.5.3.6). From WAVE a private API server is reached through the SSH Tunnel, as for every K8s block. Inside a Remote Execution container the same logic runs on the execution host and calls that host's helm, so the host needs a Python interpreter and helm. Only structured data crosses the boundary: the Result table, the parsed release and every secret registration are reconstituted on WAVE. A helm run on WAVE is owned by the block that started it: helm and anything it starts run in one process group of their own, and a Stop, a timeout or a server shutdown ends that group, so a stopped block never leaves a helm running behind it. Inside a Remote Execution container the execution host's worker holds that same ownership over the helm it started.

## Error Handling Strategy

A refusal from helm is a block failure carrying helm's own message: the release not found, a name still in use, a chart the repository does not have, a hook or test pod that failed, the operation timing out, a permission the cluster denied. Reason carries one of a small fixed set derived from that wording - NotFound, AlreadyExists, Forbidden, Timeout, Failed, Invalid, Unreachable - so a workflow branches on Reason and never on text. The Failure Handling control decides what the refusal then does, exactly as in the K8s family, with one deliberate difference on Helm Test: a failed test under Record and continue still fills Result and Logs, because each hook's Phase and the logs exist and are what the test is for. A missing helm, an unreadable session, a transport or timeout failure before helm runs, and inputs WAVE itself rejects fail the block under either setting.

## Frontend Integration

Every block is schema-driven and introduces no bespoke configuration components. Parameters group in the same order on every block: Connection, the block's own verb group, Auth & TLS where a chart is fetched, Advanced, and Failure Handling; Connection and the verb group open expanded, the rest open collapsed. Reuse Values and Reset Values uncheck each other; Create Namespace on Upgrade renders only while Install if missing is on; Error and Reason render only under Record and continue; Test's Logs output renders only while its Logs toggle is on.

## Design System Reference

Design decisions: HELM-1 through HELM-11.

##### REQ-3.5.3.1 Chart installation

Helm Install installs a chart as a named release from any source helm's own chart argument accepts - a name resolved against the Repository URL row, a reference into an OCI registry, a URL to a packaged chart, or a path where the block runs - with Version pinning a version or a range, Values passing a YAML document as a values file, and Set passing key-value pairs under helm's typing rules. Atomic waits for the release to come up within Timeout and removes a failed install, so the name is free for the next attempt. The release lands in Result, shaped by the Output Format row, and in the scalar Status output. A private chart is pulled with the block's own repository username and password, OCI registries included (REQ-3.5.3.6); the repository and the cluster are both trusted by WAVE's certificate trust rule (REQ-4.5.16); and a relative Helm Path starts at the home folder of the account the block runs as (REQ-3.4.3.12).

##### REQ-3.5.3.2 Chart testing

Helm Test runs the chart's test hooks and reports them as one row per hook - Name, Kind, Phase, Started, Completed - read back from the release record rather than parsed from helm's text. With Logs ticked, every test pod's log comes back under helm's own per-pod headers. A chart with no tests reports an empty table and succeeds, as helm does. A failed hook is a block failure under Fail the block; under Record and continue the block still fills Result and Logs, because they are what the test is for.

##### REQ-3.5.3.3 Chart upgrade

Helm Upgrade moves a release to a chart version under helm's own values rules: with nothing passed the previous values stay, with values passed they are forgotten unless Reuse Values keeps them as the base, and Reset Values forgets them even when nothing is passed; the two are exclusive and the sheet keeps them so. Install if missing turns the upgrade of an absent release into an install, and only then does Create Namespace apply. Atomic rolls a failed upgrade back to the previous revision within Timeout, and Cleanup on Fail removes the resources the failed upgrade newly created, which the rollback alone would leave behind.

##### REQ-3.5.3.4 Status monitoring

Helm Status reads a release, current or by revision, into Result and into the scalar Status output. Polled under the Wait Until control, Status is the readiness signal for a release, with the workflow in control of cadence, and Timeout on this block is WAVE's bound on the read, honored exactly: helm status takes no timeout of its own, so the block's number is the only clock on it. Under Record and continue a release that is not there reads as absent, with Success false and Reason NotFound, instead of stopping the run, which is how a workflow checks whether a release exists - including one that Atomic removed.

##### REQ-3.5.3.5 Rollback capability

Helm Rollback rolls a release back to a named revision, or with no revision to the one before the current. helm prints only text for a rollback, so the block's Result is the release read back after it, in the shape the Output Format row picks, with Status alongside. Cleanup on Fail removes the resources a failed rollback newly created. Helm Uninstall with Keep History keeps the release's revision history instead of removing it, which is the way to keep a rollback target across an uninstall. It carries the same two rows K8s Delete does where helm has the flag: Ignore Not Found makes an absent release a pass rather than a failure, so an uninstall is safe to repeat, and Cascade picks how the cluster reclaims the release's resources - background by default, foreground to wait for the dependents, orphan to leave them.

##### REQ-3.5.3.6 Helm environment and registry credentials

Helm starts with a clean environment that WAVE builds for each call, never with the WAVE host's: the session's cluster settings as a kubeconfig written for that one call, WAVE's own per-call folders for helm's configuration, cache, data, registry logins and repositories, the PATH helm needs to find itself, and the proxy route WAVE decides for the call. Nothing else from the WAVE host reaches helm: no helm overrides of the cluster connection, the storage driver or the history limit, no discovery cache from the account's home folder, and none of the WAVE host's own proxy variables. helm runs inside its per-call folder, so a chart name never resolves against the folder WAVE was started from.

**Proxy**: Helm is a separate program that makes its own connections, so WAVE decides the route by the Proxy setting's one route decision (REQ-4.7.14) for the two addresses it knows, the cluster and the chart source (a chart repository, a chart URL or an OCI registry), and hands helm the result. When the chart source goes through the proxy, the clean environment carries the proxy variables. The cluster's route is written into the kubeconfig WAVE generates for the call; when the cluster connects directly while the chart source is proxied, the cluster's host is the one NO_PROXY entry helm is given. Any other host helm contacts during a download takes the chart source's route. helm cannot keep the two routes apart when the cluster connects directly and the chart source's host is the cluster's host, or a name under it, on the same port: the chart source then connects directly too, and the run log says so. A chart source on a local address is never proxied by helm, whatever "Use the proxy for local addresses too" says, and the run log says so. A block run on the WAVE host whose chart or cluster traffic went through the proxy says so in the run log.

**Registry credentials**: Logins stored on the WAVE host - helm's registry configuration, the Docker configuration and its credential helpers - are ignored, because helm's registry configuration lives in the per-call folder. A private chart, in a classic repository or an OCI registry, is pulled with the block's own repository username and password, and the repository is trusted by WAVE's certificate trust rule (REQ-4.5.16).

**Remote hosts**: Inside a Remote Execution container the same clean environment is built on the execution host, keeping only that host's own proxy variables, because a remote host keeps its own proxy settings.
