##### REQ-3.4.1.3 SSH remote execution

WAVE provides SSH remote execution enabling workflows to run commands on remote hosts, reach systems not directly accessible from the WAVE backend, and perform operations that require a specific host context such as Kubernetes node access, administrative tasks, and diagnostic collection.

**Plugin family**: SSH remote execution is delivered as a small family of plugins addressing different workflow needs. A stateful session trio (Session Open, Session Exec, Session Close) manages a connection's lifecycle explicitly, so a single authenticated connection is reused across many workflow nodes. A session-riding Script plugin runs a whole script, in an interpreter of the user's choice, over an open session. A separate tunnel plugin forwards a local port through SSH for service reachability. Every one of these rides the same session transport, so each inherits multi-hop reachability and the session's authentication without redeclaring them.

**Stateful sessions**: SSH Session Open establishes one connection and records it in a per-run session registry, returning a session identifier. SSH Session Exec runs a single command on a named session and returns its standard output, standard error, and exit code; each execution is independent (no shell state such as working directory or environment carries between executions, so a sequence that must share shell state combines its steps in one command). Remote output is read as UTF-8, and a byte that is not UTF-8 shows as the replacement character. Text WAVE sends is never replaced: a command or script that cannot be written as UTF-8 fails its block before anything is sent. SSH Session Close tears a session down. The session identifier flows the same way every other value does in WAVE: Session Open publishes it as an output bound to a workflow variable, and Session Exec and Session Close reference that variable, so a single test can hold several concurrent sessions and address each explicitly.

**Script execution**: where Session Exec runs a single command line, SSH Session Script runs an entire script against a named session. The script is authored inline and delivered to an interpreter named on the node - a POSIX shell by default, but any interpreter the host provides (a shell, Python, Perl, Node) - so a host is served by whatever it actually has rather than by assuming a particular interpreter is installed. The script body's format picker is pinned to Plain, with none of the JSON, YAML, XML or Auto choices; Template stays available as the value Kind (PYRUN-15). The script reaches the interpreter through its standard input rather than being written to the host's filesystem, so a run needs nothing beyond the SSH connection and the chosen interpreter: no file-transfer channel, no writable working area, and no cleanup, which keeps the plugin usable against the most minimal hosts. Standard output, standard error, and the exit code are returned; a non-zero exit is reported rather than raised, and a missing interpreter or a connectivity failure surfaces through the exit code and standard error for a downstream assertion to act on. Remote output is read as UTF-8, and a byte that is not UTF-8 shows as the replacement character. An optional working directory sets where the interpreter runs. Because it rides an open session, a script executes equally on a directly connected host or on one reached through a chain of intermediary hosts, inheriting the session's host-key policy, credentials, and hops; optional execution is expressed by wrapping the node in the Try-Catch control, as with the rest of the family. Every numeric row on the SSH blocks - Session Open's port, connection timeout and keep-alive rows, Session Exec's and Session Script's timeout, Tunnel Open's local and remote ports - declares its bounds once, and they are enforced both in the form and when the block runs, as on every other block (SSH-9). A Port on Session Open or a Local Port on Tunnel Open left empty takes its default, 22 and 0, when the block runs; a null value, from an expression or a variable, fails the block and names the field (see REQ-3.1.3.21), while any text, empty text included, is refused before the block runs (SSH-10).

**Connection configuration**: The connection's host, port, username, and authentication are parameters of the Session Open node. Credentials are typically drawn from a bound SSH connection profile, referenced field by field in expression mode (an alias to the profile resolves each field), which keeps host and credential definitions centralized and reusable while leaving the node in full control of how they are composed; literal values are also accepted. Authentication supports password and private key (with an optional passphrase for an encrypted key, in every format ssh-keygen writes, including its default OpenSSH format; SSH-7). Host key verification is configurable between strict checking, trust-on-first-use (Accept New) and disabled (the default), always against WAVE's trusted SSH hosts list (REQ-4.5.14). The connection authenticates only with what the block names and reaches jump hosts only through the session chain; the SSH config file, default keys and SSH agent of the account WAVE runs under are never used (REQ-4.5.15).

**Multi-hop by parent linkage**: A chain to a host reached only through one or more intermediary hosts is expressed by linking sessions rather than by configuring a jump list inside a single node. A Session Open node carries an optional reference to a parent session; when set, the new connection is established through the parent session's live connection, making the parent the jump host. Chains of arbitrary depth are assembled by opening parent-linked sessions across nodes, each hop a session in its own right that can also be the target of an Execute. Because a child's transport rides on its parent, closing a session cascades to every session opened through it, and the engine closes any session left open when a run terminates.

**Liveness and failure semantics**: A connection failure raises, failing the node; optional connectivity is expressed by wrapping the node in the Try-Catch control rather than by a per-node soft-fail mode. When keep-alive is enabled, a session exposes a liveness signal that is true while the connection holds and flips to false, with a warning logged, when a missed keep-alive reveals the connection has dropped; a subsequent Execute against a dropped session fails. The liveness signal is therefore a coarse, keep-alive-paced indicator suitable for periodic connectivity checks, not an instantaneous probe. Session Open also surfaces the remote server's identification banner and the number of hops used to reach the host.

**Authentication and security**: Credentials are never written to logs or exposed in output. Secret parameters register their values with the run's secret registry so every outbound surface (logs, console, reports, artifacts, serialization) masks them. Authentication failures produce clear messages distinguishing credential problems from network reachability.

**Service reachability by tunnel**: A tunnel makes a service that is reachable from an SSH host reachable from wherever a plugin runs, by forwarding a local port over an established session. SSH Tunnel Open references an open session by the same identifier the session trio uses and forwards a chosen local port, bound to the loopback interface, to a destination host and port reachable from that session's host. Because the forward rides the session's connection, a destination reachable only through a chain of intermediary hosts is served by opening the tunnel on the last session in the chain - the tunnel carries no hop, credential, or host-key configuration of its own, inheriting all of it from the session. The local port is chosen explicitly or auto-assigned; the resolved port is published as an output alongside the tunnel's own identifier, so downstream nodes address the forwarded service. SSH Tunnel Close tears a named tunnel down and is idempotent on an unknown or already-closed tunnel. A tunnel is a child of its session: closing that session, cascading a session chain, or the end of a run tears down the tunnels opened on it, so a tunnel never outlives its session; when the session's connection drops while the session stays open, as it does with keep-alive off, each connection to the tunnel fails with a run-log warning until the session is closed or the run ends. Forwarding is fixed local port-forwarding and by default behaves like plain `ssh -L`: opening binds the local port and checks nothing else, every connection reaches for the destination afresh, and a connection the SSH host refuses or cannot complete fails alone and writes a run-log warning carrying the host's reason. An opt-in Validate Target setting checks the destination at open, bounded by the session's connection timeout, fails the node when the SSH host refuses to forward or cannot reach the destination, and hands the connection that proved it to the tunnel's first client. Optional reachability is expressed by wrapping the node in a Try-Catch control, as with the session plugins.

**Primary use cases**: SSH remote execution serves Kubernetes node access (packet capture and log inspection on worker nodes reached through a bastion or master node), administrative and maintenance commands on remote systems, and configuration and diagnostic retrieval across distributed hosts. The stateful session trio is the right tool when many commands run against the same host, or against a host reached through a chain, because the connection and its authentication are established once and reused. A tunnel complements the trio when a test must reach a network service - a database, an API, a management port - that is accessible from such a host, rather than run a command on the host itself.

##### REQ-5.1.5 SSH protocol for node access

The SSH plugins realize WAVE's SSH-protocol integration for node access. The transport is a pure SSH client so any host exposing a standard SSH service is reachable without WAVE installing anything on it. Reaching a host that is only accessible through intermediary hosts is handled by chaining SSH connections (a session established through a parent session's connection), which generalizes bastion and Kubernetes-master access patterns to chains of any depth. This SSH-protocol channel is the foundation on which the tunnel (service port forwarding) and remote-execution (running a plugin's logic from a chosen host) capabilities build.
