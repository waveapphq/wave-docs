##### REQ-3.4.1.1 Shell script execution

The Shell Script block runs a shell script on the WAVE server and returns what the script printed, its exit code, and the values of the shell variables the author exports, each bound to a WAVE variable.

**Purpose and Locus**: The block runs on the WAVE server only (SHRUN-1). It is not remotable: placed inside a Remote Execution body it carries the L badge and runs on WAVE, under the same mixed-locus rule as every other non-remotable block. Running a script on a remote host is the job of SSH Session Script. There is no sandbox of any kind (SHRUN-2): no resource limits, no container, no separate operating-system user and no locked working directory. The script runs as the WAVE server's own operating-system user, with exactly the file, network and process rights the execution trust model grants that user. The block exists to run the tools the author would otherwise have run by hand on that machine. The block's documentation page carries one version, 1.0.0, whose changelog names every setting (SHRUN-16).

**Script Source**: Script Type selects where the script comes from (SHRUN-3). Source, the default, is a multi-line script typed into the block. File is a script file chosen with Browse in file mode over Test Data and Artifacts, or typed as a `testdata://` reference, an `artifact://` reference or an absolute or relative path on the WAVE server. Shell names the shell that runs the script, `/bin/bash` by default. The script runs under the shell named there whatever its first line says, and WAVE never works out which shell that is: there is no shell-type detection anywhere in the block. Both sources share one launch path: a typed script is first written to a private temporary file, so in both cases the script's own name is a file path. Standard input is empty, so a script never waits for input. The script body's format picker is pinned to Plain, with none of the JSON, YAML, XML or Auto choices; Template stays available as the value Kind (PYRUN-15).

**Arguments**: An ordered list of rows, each a value or an expression (SHRUN-4). The script receives them as its positional parameters `$1` to `$n`, in exactly the row order. Rows are reordered with the same up and down arrow pair the If-Else, Switch and Parallel branch rows use, removed with the row's delete button, and added with "+ Add argument". An empty row is passed as an empty string, because a row is an argument; a row whose value is null fails the block before the script starts and names the row (see REQ-3.1.3.22). There is no named-flag handling: a script that takes flags parses them itself. The list is the same for Source and File.

**Input Variables**: A map from a shell variable name to a WAVE value or expression, the alias pattern of the JSON parser's queries (SHRUN-5). Each entry is exported into the script's environment, so the script and every program it starts see it. Scalars arrive as text, with booleans as `true` or `false`; arrays, maps and tables arrive as JSON text, with `null` inside where an item, map value or cell is null. A shell has no null, so an entry whose value is null fails the block before the script starts and names the entry (see REQ-3.1.3.22). A name must be a shell identifier - a letter or underscore followed by letters, digits or underscores - and must not start with `WAVE_`, the prefix WAVE keeps for the folder variables it sets.

**Variable Exports**: The author names the shell variables the script sets, and each one becomes an output of the block that binds to exactly one WAVE variable through the ordinary output binding (SHRUN-6). They appear in the Output Variables section as rows of the output table, under the columns Script Variable, Type, Secret and WAVE Variable, and are added with "Add variable export"; a row is marked secret the way every other output row is. The Type cell is the Variable Setter's type select (VARSET-5): when the WAVE Variable cell names a variable that exists, the select is locked to that variable's type; otherwise (an empty cell, or a name that is not a variable yet) it is a free select, String by default, and a variable that does not exist yet is created with the chosen type when the sheet is saved, holding null until the script sets it. Picking an existing variable in the WAVE Variable cell sets the row's type to that variable's type. The captured value is read as the bound variable's type:

| Bound type | Captured value it accepts |
|------------|---------------------------|
| Integer | A whole number |
| Float | A decimal number, kept exact |
| Boolean | true, false, 1, 0, yes or no, in any letter case |
| String | Any text, as captured |
| Array | A shell array, or JSON array text |
| Map | A shell associative array where the shell has them, or JSON object text |
| Table | JSON array-of-objects text |

Structured values are JSON only: nothing else is read as an array, a map or a table. A table's first row fixes the column names and their types, and every later row must match it. A value that does not fit its bound type fails the block with reason OutputVariable, and the message names the syntax the value should have used. An export the script never set is not a failure: the WAVE variable it is bound to keeps the value it already had, and a DEBUG line records that the export was never set. An export left unbound is captured and discarded. A name follows the shell identifier rule, may not reuse the name of a fixed output (stdout, stderr, exit_code, success, error, reason) and may not be listed more than once.

**Reading the Exports**: Exports are read whenever the script ends on its own: normally, with a non-zero exit code, through set -e or through exit. A script that installs its own exit trap replaces WAVE's, so its exports are not read (SHRUN-7). The read is one piece of POSIX shell code used with every shell, and it never asks which shell it is in. It probes each named variable itself, so a shell that has arrays hands back the elements and a shell without them hands back the value as text; an associative array comes back as a map from the shells whose key syntax the probe can read, and from any other shell a map is written as JSON by the script. Each variable is written separately, with its kind, into a WAVE-owned file outside the working directory, so no value is misread whatever characters it contains. When the exit hook never ran at all, because the script replaced it or handed its process over to another program, the block ends amber with one WARN line, `Variable exports were not read: the script replaced WAVE's exit handler`, and every bound variable keeps its value. A script that WAVE stops on timeout, on Stop or on shutdown returns Stdout, Stderr and Exit Code but no exports, because immediate termination leaves the shell no chance to run its handler. A pattern stop is not an immediate kill: WAVE terminates the process group first, gives the shell a short grace to run WAVE's exit handler, then kills the group, so the exports are read after a pass match and after a fail match. When the shell does not end within that grace, the block turns amber with one WARN line, `Variable exports were not read: the script did not end after the pattern match`, and every bound variable keeps its value. The private temporary folder holding the script copy and the capture file is removed when the block ends.

**Outputs and Failure Handling**: Stdout, Stderr, Exit Code and Success are always outputs; Error and Reason are outputs only while On error is Record and continue, the output core shared with the K8s family (SHRUN-8). Every output lands only when the block ends; nothing is published while the script runs. A non-zero exit code is a failure. The Failure Handling group's On error setting decides what a failure does (SHRUN-9). Fail the block, the default, makes the failure a block error and binds nothing. Record and continue lets the block finish: every output binds with whatever was captured, Success reads false, Error carries the message, and Reason carries one of:

| Reason | When |
|--------|------|
| NonZeroExit | The script exited with a non-zero code |
| Timeout | The script was still running when Timeout ran out |
| FailPattern | An output line matched the fail pattern |
| StartFailed | The script file, the working directory or the shell itself was not found, a path was refused, or the script could not be started |
| OutputVariable | An exported value is not readable as its bound type |

Under Record and continue a failed conversion binds the exports that did convert, leaves the failed one's WAVE variable untouched, still binds Stdout, Stderr and Exit Code, and turns the block amber with reason OutputVariable. A fail-pattern stop under Record and continue also binds the exports that converted, because the shell ran WAVE's exit handler during the grace before the kill. Exit Code is always present: the script's own code; 137 when WAVE ended the script, which is 128 plus the number of the kill signal and the same code a shell, Docker and Kubernetes report for it; -1 when it never started. Each captured stream keeps its last 16 MiB; a stream that had to drop earlier output logs one WARN naming the stream and how many bytes were dropped.

**Working Directory, Test Data and Artifacts**: Working Directory, left empty, is the temp folder Python reports on the machine the block runs on (SHRUN-10). It takes a folder chosen with Browse in folder mode over Test Data and Artifacts, a `testdata://` or `artifact://` reference, or an absolute or relative path on the WAVE server. A relative Working Directory starts at the home folder of the operating-system user the WAVE server runs as; a relative Script File, and a relative program path in Shell, start at the Working Directory; a `..` segment is followed wherever it leads. A folder that is not there fails the block before the script starts, with reason StartFailed. Browse stays visible on this row inside a Remote Execution body, because the block runs on WAVE there; Browse is hidden inside a body only for remotable blocks (TDATA-8). Test Data keeps its own protection: its files and folders are read-only on disk and only WAVE's own changes lift that, so a script's write into Test Data fails with the operating system's "Permission denied", and WAVE adds no detection of its own (SHRUN-11, TDATA-2).

**Environment**: The script inherits the WAVE server's environment as the server has it (SHRUN-2). Nothing is removed, nothing is built up in its place and no login shell runs, so the tools the script calls find the settings they would find if the author had run them on that machine by hand. That includes the WAVE host's proxy variables: the Proxy setting in Settings governs only the web requests WAVE itself makes and never changes a script's environment (REQ-4.7.14). The Proxy Blocks page in Settings therefore lists the script blocks under "Blocks that do not use this proxy" (REQ-3.4.2.10). Two folder variables are added (SHRUN-11): `WAVE_TESTDATA_DIR`, the running test's own Test Data folder that `testdata://` resolves against, and `WAVE_ARTIFACTS_DIR`, the run's artifacts folder. The Input Variables are exported on top of these. When the run has no such folder, for example a Function run outside a test, the variable is still present and empty.

**Console Output**: As the block starts, whatever Log Output says, the run console receives one INFO line naming what runs, under which shell and where (SHRUN-12): `Running the script under {shell} on the WAVE server` for a typed script, whose body is never echoed, or `Running {script file} under {shell} on the WAVE server` for a script file, named as the author wrote it. The shell is the Shell row as written, flags included. The line comes before anything is resolved, so it also precedes a start failure, and secret values in it are masked as in every console line. Log Output is a checkbox, off by default. While it is ticked, each stdout line goes to the run console at INFO and each stderr line at WARN as it arrives. A stream whose Secret box is ticked on its Output Variables row (Stdout or Stderr) is never written live, because WAVE cannot mask a value it has never seen; secret input values are masked in live lines as they are everywhere else.

**Stop on Pattern**: Stop on pattern is a checkbox, off by default, with a Pass pattern row and a Fail pattern row (SHRUN-13). Both are regular expressions in Python's syntax, searched for in each line of stdout and stderr; a line that arrives in pieces is matched as a whole line. While it is ticked at least one pattern is required, and both may be set. A Pass match stops the script and the block passes, and the run console receives one INFO line, `Output matched the pass pattern: {line}`, the line cut to 200 characters; when the matching stream is marked secret the line is omitted and the message is just `Output matched the pass pattern`. A Fail match stops the script and the block fails with reason FailPattern; a line that matches both fails. Stopping is the pattern stop described under Process Lifecycle: WAVE terminates the group, gives the shell a short grace to run WAVE's exit handler, then kills the group, so the variable exports are read after a pass match and after a fail match. A script that ends on its own before any match is judged by its exit code as usual. After a Pass match the block passes with its exports bound. A Fail match under Record and continue records the failure and still binds the exports that converted; it reads as a warning the test continues past.

**Timeout**: Timeout is the number of seconds the script may run, 300 by default, and must be positive (SHRUN-14). When it runs out the whole process group is ended at once, with no exports read, and the block fails, or records, with reason Timeout.

**Process Lifecycle**: A block owns every process it starts, and a stop ends them (SHRUN-15). The script and everything it starts run in one process group of their own, so a stop always reaches the whole group, never only the shell, and nothing the script started is left behind. A timeout, a user Stop and a server shutdown end the group at once. A pattern stop terminates the group, lets the shell run WAVE's exit handler for a short grace, then kills the group. The Exit Code reads 137 for every WAVE stop. When the script ends on its own, anything it left running in the group is ended too: a leftover would otherwise hold the output open until the timeout. A Stop reaches a block running inside a Parallel branch the same way, because a Stop cancels every lane. WAVE starts the script through a small watchdog of its own that holds a lifeline to the WAVE server: while WAVE is alive WAVE ends the group itself, and if WAVE dies without the chance to clean up, including being killed or running out of memory, the broken lifeline makes the watchdog end the group by itself, on Linux and macOS alike. The watchdog reports the shell's exit code back. The same ownership holds on an execution host, where the Remote Execution worker plays the watchdog's part for whatever it started there. A program that deliberately detaches into a session of its own has left the group and is its own: once the script has ended or been stopped, WAVE reads what it still prints for a short grace and then closes the output, so it never holds the block.

**Error Handling**: Validation refuses a misconfigured block before it runs, whatever On error says; a setting given the wrong shape, or a value outside the choices a setting offers, is refused the same way, before the script starts. A failure while the block runs follows On error and carries the reason shown:

| Failure | Message | Reason |
|---------|---------|--------|
| Script Type is Source and the script is empty | `Missing required parameter: script` | Validation |
| Script Type is File and no file is named | `Missing required parameter: script_file` | Validation |
| Shell is blank | `Parameter 'shell' cannot be empty` | Validation |
| Timeout is zero or negative | `Parameter 'timeout' must be positive` | Validation |
| Stop on pattern is ticked with both patterns empty | `Set a pass pattern, a fail pattern or both` | Validation |
| A pattern is not a valid regular expression | `Invalid pass pattern: {reason}` or `Invalid fail pattern: {reason}` | Validation |
| An input variable name is not a shell identifier | `Invalid variable name: '{name}'` | Validation |
| An input variable name starts with WAVE_ | `Variable names may not start with WAVE_: '{name}'` | Validation |
| An exported variable name is not a shell identifier | `Invalid script variable name: '{name}'` | Validation |
| An exported variable reuses a fixed output's name | `Script variable '{name}' has the name of a block output` | Validation |
| An exported variable is listed more than once | `Script variable '{name}' is listed more than once` | Validation |
| The script file is not there | `Script file not found: {path}` | StartFailed |
| The working directory is not there | `Working directory not found: {path}` | StartFailed |
| The shell is not installed on the server | `Shell not found on the WAVE server: {shell}` | StartFailed |
| The operating system refuses to start the script | `Could not start the script: {os error}` | StartFailed |
| The shared path resolver refuses the script file or the working directory | The resolver's own message, passed through unchanged, for example `artifact:// scheme requires artifacts directory, but none configured in context` | StartFailed |
| Script File names only a testdata:// or artifact:// root | `Path is the root folder: {path}` | StartFailed |
| The script exits with a non-zero code | `Script exited with code {code}: {line}`, where the line is the last line of Stderr that is not blank, trimmed and cut to 200 characters; just `Script exited with code {code}` when Stderr is empty or marked secret | NonZeroExit |
| Timeout runs out | `Script timed out after {n} seconds` (singular "second" when {n} is 1) | Timeout |
| A line matches the fail pattern | `Output matched the fail pattern: {line}`, the line cut to 200 characters; without the line when the matching stream is marked secret | FailPattern |
| A captured scalar does not fit its bound type | `Script variable '{name}' is not a valid {type}`, never echoing the value | OutputVariable |
| A captured value is not valid JSON for its bound type | `Script variable '{name}' is not a valid array: the value must use valid JSON array syntax`, `Script variable '{name}' is not a valid map: the value must use valid JSON object syntax` or `Script variable '{name}' is not a valid table: the value must use valid JSON array-of-objects syntax` | OutputVariable |

The run console also receives WARN lines of its own:

| Situation | Console line |
|-----------|--------------|
| A failure recorded under Record and continue | `Script failed ({reason}): {message}` |
| A captured stream dropped earlier output | `Stdout truncated: {n} bytes dropped` or `Stderr truncated: {n} bytes dropped` |
| The script replaced WAVE's exit handler, so no export was read | `Variable exports were not read: the script replaced WAVE's exit handler` |
| The shell did not end within the grace after a pattern match, so no export was read | `Variable exports were not read: the script did not end after the pattern match` |

##### REQ-3.4.3.11 Empty Working Directory

A Shell Script, Shell Exec or Python block whose Working Directory is empty, left blank in the form or absent from a recipe, starts in the temp folder Python reports on the machine the block runs on: the WAVE host, or the remote host for a Python block inside a Remote Execution body. No temp path is fixed anywhere in WAVE: the empty field shows the placeholder System temp folder, the block catalog publishes no default value for the row, and a blank value is accepted rather than refused, so a test built in the canvas and one built from a recipe start in the same place (SHRUN-10). A Working Directory that is set follows the relative-path rule of REQ-3.4.3.12.
