##### REQ-3.4.1.2 Python script execution

The Python block runs a Python script on the WAVE server or on a remote host and returns what the script printed, its exit code, and the values of the script's own variables the author exports, each handed back as a typed value and bound to a WAVE variable.

**Purpose and Locus**: The Python block is the Shell Script block with a different variable contract (PYRUN-1). It runs a Python script on the WAVE server, or on a remote host when placed inside a Remote Execution body: it is remotable and carries the R badge there. There is no sandbox of any kind (PYRUN-1, SHRUN-2): no resource limits, no container, no separate operating-system user and no locked working directory. The script runs as the WAVE server's own operating-system user, or on a remote host as the user the Remote Execution worker runs as, with exactly the file, network and process rights the execution trust model grants that user. Local and remote runs share one local-process core (PYRUN-12): the runtime half that launches the script, captures its streams, matches patterns, keeps the timeout, ends the process group and holds the watchdog lifeline is the same on both sides, needs nothing beyond a plain Python installation, and travels inside the remote bundle; the WAVE-side half that resolves the settings, reads the files that stay on WAVE and binds the outputs stays on the server. Shell Script and Shell Exec ride the same split, unchanged in behavior. The block's documentation page carries one version, 1.0.0, whose changelog names every setting and, in plain words, every rule on this page an author cannot see on the sheet (PYRUN-1, PYRUN-17): the interpreter command-line rule and its default, the per-Environment variable pattern, that WAVE installs nothing, the 3.8 floor, that the body is never templated, the module path rule, the type mapping in and out, that exports are read after an exception, how `sys.exit` and exit codes are judged, what resolves on the remote host and what arrives at the end there, and how logging reaches the console.

**Script Source**: Script Type selects where the script comes from (PYRUN-2). Source, the default, is a multi-line script typed into the block. File is a script file chosen with Browse in file mode over Test Data and Artifacts, or typed as a `testdata://` reference, an `artifact://` reference or an absolute or relative path. A `testdata://` or `artifact://` script is read on WAVE and sent along with the request as script text, so File mode works on a remote host; the temporary file on the remote host keeps the original file name. A plain path is read where the block runs, on WAVE or on the remote host, relative to the Working Directory. Both sources share one launch path: a typed script is first written to a private temporary file, so in both cases the script's own name is a file path. The script is sent as source, never as bytecode (PYRUN-10). Standard input is empty, so a script never waits for input. The body is never template-expanded: `{{` in the script is just Python (PYRUN-13).

**Interpreter**: Interpreter takes the place of Shell Script's Shell row (PYRUN-3). It is a command line, a program plus any flags, to which WAVE appends the script path and then the Arguments: `/opt/venv311/bin/python`, `uv run --project /opt/lab-env` and `conda run -n lab python` are all valid. The program resolves the way the Shell row's does: a bare program name is looked up on PATH, a relative path starts at the Working Directory. Empty means WAVE's own interpreter: the one the WAVE server runs on, or on a remote host the one the Remote Execution worker runs on. The row takes an expression, so a global variable set per Environment (`{{py}}`) makes one interpreter the default for every test and lets each Environment - a lab PC, a CI runner - name its own path. WAVE never installs packages, creates environments or copies libraries: the interpreter decides what the script can import. There is no Requirements row and no Python profile type. The bridge, the small WAVE program that runs inside the chosen interpreter, is written for Python 3.8 and newer and uses only the standard library, so an interpreter older than WAVE's own, for example a vendor SDK pinned to 3.8, works (PYRUN-10). The bridge announces itself first: a program that is not Python 3.8 or newer, or that is not Python at all, never sends that announcement, so the block fails before the script runs, naming the program, whatever exit code the program returned.

**Arguments**: An ordered list of rows, each a value or an expression (PYRUN-4, SHRUN-4). The script receives them as `sys.argv[1:]`, in exactly the row order. Rows are reordered with the same up and down arrow pair the If-Else, Switch and Parallel branch rows use, removed with the row's delete button, and added with "+ Add argument". An empty row is passed as an empty string, because a row is an argument; a row whose value is null fails the block before the script starts and names the row (see REQ-3.1.3.22). There is no named-flag handling: a script that takes flags parses them itself. The list is the same for Source and File.

**Input Variables**: A map from a Python name to a WAVE value or expression, the alias pattern of the JSON parser's queries (PYRUN-5). Each entry is a global in the script's namespace before the first line runs; nothing is exported into the process environment for them. An entry is a data field and accepts null, which arrives as `None` (see REQ-3.1.3.21); a whole null map for the setting itself fails like any setting with a default. A value arrives as the Python object its WAVE type maps to:

| WAVE type | Arrives as |
|-----------|------------|
| String | `str` |
| Integer | `int` |
| Float | `decimal.Decimal`, because WAVE floats are exact |
| Boolean | `bool` |
| Null | `None` |
| Array | `list` |
| Map | `dict` |
| Table | The bridge's table object: iterate it for rows as dicts, index a row, take `len`, read `.columns` and `.rows`; the same access a table has in an expression, without the mutating methods |

A name must be an ASCII name: a letter or underscore, then letters, digits or underscores, and must not start with `__`. Typed values are encoded in the worker's typed envelope before a request leaves WAVE, so a script on a remote host receives the same objects a script on WAVE does (PYRUN-12). The process environment is Shell Script's (SHRUN-11): the server's or the remote host's environment plus `WAVE_TESTDATA_DIR` and `WAVE_ARTIFACTS_DIR` on the WAVE server, plus the block's own Environment map, the Environment setting of Shell Script; Input Variables are never part of it.

**Variable Exports**: The author names the script variables the block hands back, and each one becomes an output of the block that binds to exactly one WAVE variable through the ordinary output binding (PYRUN-6, SHRUN-6). They appear in the Output Variables section as rows of the output table, under the columns Script Variable, Type, Secret and WAVE Variable, and are added with "Add variable export"; a row is marked secret the way every other output row is. The Type cell is the Variable Setter's type select (VARSET-5): when the WAVE Variable cell names a variable that exists, the select is locked to that variable's type; otherwise (an empty cell, or a name that is not a variable yet) it is a free select, String by default, and a variable that does not exist yet is created with the chosen type when the sheet is saved, holding null until the script sets it. Picking an existing variable in the WAVE Variable cell sets the row's type to that variable's type. The value is the script's global of that name when the script ends, and it must fit the bound type the way a Variable Setter result must:

| Bound type | Value it accepts |
|------------|------------------|
| Integer | An `int`; a `bool` is not an integer |
| Float | An `int`, a `float` or a `Decimal` |
| Boolean | A `bool` |
| String | A `str` |
| Array | A `list` |
| Map | A `dict` |
| Table | The bridge's table object, or a list of dicts whose columns come in first-row key order with their types inferred as the Variable Setter infers them |

`None` fits every bound type and the bound variable becomes null, keeping its type (see REQ-3.1.3.23). Anything else fails the export with reason OutputVariable, and the message never echoes the value; a value that cannot be carried back at all, even nested inside a list or map, fails the export the same way and with the same message, on WAVE and on a remote host alike. Values come back over the wire in the typed envelope the remote worker already uses, never by printed text or JSON guessing. An export the script never set is not a failure: the WAVE variable it is bound to keeps the value it already had, and a DEBUG line records that the export was never set. An export left unbound is captured and discarded. A name must be an ASCII name: a letter or underscore, then letters, digits or underscores, must not start with `__`, may not reuse the name of a fixed output (stdout, stderr, exit_code, success, error, reason) and may not be listed more than once. Each row whose name the script never assigns at top level gets a warning on the row and in the block's issues; a warning never marks the block invalid, because a script may set a name in a way the check cannot see, through an import or `globals()` (PYRUN-14).

**Reading the Exports**: Exports are read whenever the script ends on its own: a normal end, `sys.exit`, or an uncaught exception (PYRUN-6). The globals exist in every one of those cases, so a failed script still hands back what it set before it failed. A script that WAVE stops on timeout, on Stop or on shutdown returns Stdout, Stderr and Exit Code but no exports, because immediate termination leaves the interpreter no chance to hand them over. A pattern stop is not an immediate kill: WAVE terminates the process group first, gives the interpreter a short grace to hand the exports over, then kills the group, so the exports are read after a pass match and after a fail match (PYRUN-11). When the interpreter does not end within that grace, the block turns amber with one WARN line, `Variable exports were not read: the script did not end after the pattern match`, and every bound variable keeps its value. The private temporary folder holding the script copy is removed when the block ends.

**Outputs and Failure Handling**: Stdout, Stderr, Exit Code and Success are always outputs; Error and Reason are outputs only while On error is Record and continue, the output core shared with the K8s family (PYRUN-7, SHRUN-8). Every output lands only when the block ends; nothing is published while the script runs. `print` writes to stdout. Stdout and Stderr are UTF-8 on every host, whatever its locale. An uncaught exception fails the block with the message `{ExceptionType}: {message}` and reason Exception; the traceback is written to Stderr and to the run console at ERROR, and Exit Code reads 1, Python's own code for an uncaught exception. `sys.exit(n)` ends the script with exit code n; a non-zero code is a failure with reason NonZeroExit, and `sys.exit()`, `sys.exit(None)` and `sys.exit(0)` pass. Any other value, such as `sys.exit("no rows")`, ends the script the way plain Python does: its text is written to Stderr as the last line and the exit code is 1, so the block fails with reason NonZeroExit and the message `Script exited with code 1: no rows`, or just `Script exited with code 1` when Stderr is marked secret, on WAVE and on a remote host alike. The Failure Handling group's On error setting decides what a failure does (SHRUN-9). Fail the block, the default, makes the failure a block error and binds nothing. Record and continue lets the block finish: every output binds with whatever was captured, Success reads false, Error carries the message, and Reason carries one of:

| Reason | When |
|--------|------|
| NonZeroExit | The script exited with a non-zero code |
| Exception | The script raised an exception it did not catch, or does not parse |
| Timeout | The script was still running when Timeout ran out |
| FailPattern | An output line matched the fail pattern |
| StartFailed | The script file, the working directory or the interpreter was not found, the interpreter is not Python 3.8 or newer, a path was refused, or the script could not be started |
| OutputVariable | An exported value does not fit its bound type |

Under Record and continue a failed export binds the exports that did fit, leaves the failed one's WAVE variable untouched, still binds Stdout, Stderr and Exit Code, and turns the block amber with reason OutputVariable. A script that raised, or exited non-zero, under Record and continue binds its exports too, because they are read after an exception and after `sys.exit`; a fail-pattern stop binds the exports the interpreter handed over during the grace before the kill. Exit Code is always present: the script's own code; 137 when WAVE ended the script, which is 128 plus the number of the kill signal and the same code a shell, Docker and Kubernetes report for it; -1 when it never started. Each captured stream keeps its last 16 MiB; a stream that had to drop earlier output logs one WARN naming the stream and how many bytes were dropped.

**Logging**: The script's standard `logging` is wired by the bridge (PYRUN-8): every record on the root logger reaches the run console at its own level, DEBUG as DEBUG, INFO as INFO, WARNING as WARN, ERROR and CRITICAL as ERROR. On WAVE a record arrives as it is emitted; on a remote host the records arrive when the block ends. Logging records are always delivered; the Log Output checkbox governs stdout and stderr lines only. A record logged with the exception or the stack attached, as `logging.exception` does, carries that traceback into the console line with its message. Secret input values are masked in console lines as they are everywhere else.

**Working Directory and Module Path**: Working Directory, left empty, is the temp folder Python reports on the machine the block runs on (SHRUN-10). It takes a folder chosen with Browse in folder mode over Test Data and Artifacts, a `testdata://` or `artifact://` reference, or an absolute or relative path. A relative Working Directory starts at the home folder of the operating-system user the script runs as; a relative Script File, and a relative program path in Interpreter, start at the Working Directory; a `..` segment is followed wherever it leads. On a remote host the Working Directory and a plain-path Script File are resolved on that host. A folder that is not there fails the block before the script starts, with reason StartFailed. The Working Directory is first on `sys.path`, so a helper module beside the data, in a Test Data folder chosen as the Working Directory, imports by name (PYRUN-9). In File mode the script's own folder is on the path too, which is Python's own rule, and that holds when the file is read where the block runs; a `testdata://` or `artifact://` file pushed to a remote host ships as source, so its folder is not on the path there. In Source mode the private temporary folder is not on the path: WAVE replaces it with the Working Directory. Test Data keeps its own protection: its files and folders are read-only on disk and only WAVE's own changes lift that, so a script's write into Test Data fails with the operating system's "Permission denied", and WAVE adds no detection of its own (SHRUN-11, TDATA-2).

**Environment**: The process environment is Shell Script's (PYRUN-5, SHRUN-11): the script inherits the WAVE server's environment as the server has it, or on a remote host the environment the Remote Execution worker has. Nothing is removed, nothing is built up in its place and no login shell runs, so the tools the script calls find the settings they would find if the author had run them on that machine by hand. Two folder variables are added: `WAVE_TESTDATA_DIR`, the running test's own Test Data folder that `testdata://` resolves against, and `WAVE_ARTIFACTS_DIR`, the run's artifacts folder; the block's own Environment map, the Environment setting of Shell Script, is added on top of these. An Environment entry left empty is empty text; an entry whose value is null fails the block before the script starts and names the entry (see REQ-3.1.3.22). When the run has no such folder, for example a Function run outside a test, the variable is still present and empty. Both folder variables are a WAVE-server fact: a block running on a remote host gets that host's own environment plus the block's Environment rows, and neither variable is set there, because a remote host has no WAVE Test Data folder and `testdata://` is refused on it. Input Variables never touch the process environment: they are globals in the script's namespace.

**Console Output**: As the block starts, whatever Log Output says, the run console receives one INFO line naming what runs, under which interpreter and where (PYRUN-11, SHRUN-12): `Running the script under {interpreter} on the WAVE server` for a typed script, whose body is never echoed, or `Running {script file} under {interpreter} on the WAVE server` for a script file, named as the author wrote it. The interpreter is the Interpreter row as written, flags included, and an empty row reads `WAVE's own interpreter`. Inside a Remote Execution body WAVE writes the line as the request leaves for the remote host, ending `on the remote host`, so it comes before every line the remote host delivers. The line comes before anything is resolved, so it also precedes a start failure, and secret values in it are masked as in every console line. Log Output is a checkbox, off by default. While it is ticked, each stdout line goes to the run console at INFO and each stderr line at WARN as it arrives on WAVE, and when the block ends on a remote host. A stream whose Secret box is ticked on its Output Variables row (Stdout or Stderr) is never written live, because WAVE cannot mask a value it has never seen; secret input values are masked in live lines as they are everywhere else. Logging records are not governed by this checkbox: they always reach the console.

**Stop on Pattern**: Stop on pattern is a checkbox, off by default, with a Pass pattern row and a Fail pattern row (PYRUN-11, SHRUN-13). Both are regular expressions in Python's syntax, searched for in each line of stdout and stderr; a line that arrives in pieces is matched as a whole line. While it is ticked at least one pattern is required, and both may be set. A Pass match stops the script and the block passes, and the run console receives one INFO line, `Output matched the pass pattern: {line}`, the line cut to 200 characters; when the matching stream is marked secret the line is omitted and the message is just `Output matched the pass pattern`. A Fail match stops the script and the block fails with reason FailPattern; a line that matches both fails. Stopping is the pattern stop described under Process Lifecycle: WAVE terminates the group, gives the interpreter a short grace to hand the exports over, then kills the group, so the variable exports are read after a pass match and after a fail match. A script that ends on its own before any match is judged by its exit code as usual. After a Pass match the block passes with its exports bound. A Fail match under Record and continue records the failure and still binds the exports that fit; it reads as a warning the test continues past. On a remote host the same supervisor runs inside the worker's request process: the patterns act there, and stdout, stderr and console lines are delivered when the block ends.

**Timeout**: Timeout is the number of seconds the script may run, 300 by default, and must be positive (PYRUN-11, SHRUN-14). When it runs out the whole process group is ended at once, with no exports read, and the block fails, or records, with reason Timeout. On a remote host the timeout acts inside the worker's request process, on the same clock the stop on pattern uses there.

**Process Lifecycle**: A block owns every process it starts, and a stop ends them (PYRUN-11, SHRUN-15). The interpreter and everything it starts run in one process group of their own, so a stop always reaches the whole group, never only the interpreter, and nothing the script started is left behind. A timeout, a user Stop and a server shutdown end the group at once. A pattern stop terminates the group, lets the interpreter hand the exports over for a short grace, then kills the group. The Exit Code reads 137 for every WAVE stop. When the script ends on its own, anything it left running in the group is ended too: a leftover would otherwise hold the output open until the timeout. A Stop reaches a block running inside a Parallel branch the same way, because a Stop cancels every lane. WAVE starts the script through a small watchdog of its own that holds a lifeline to the WAVE server: while WAVE is alive WAVE ends the group itself, and if WAVE dies without the chance to clean up, including being killed or running out of memory, the broken lifeline makes the watchdog end the group by itself, on Linux and macOS alike. The watchdog reports the interpreter's exit code back. The same ownership holds on a remote host, where the same supervisor runs inside the Remote Execution worker's request process and the worker plays the watchdog's part for whatever it started there. A program that deliberately detaches into a session of its own has left the group and is its own.

**Script Editor**: The Script body opens in the shared "Edit value" sheet in a Python mode (PYRUN-13): Python coloring using the sheet's existing highlight styles for keywords, strings, numbers, comments and function names, with identifiers, operators and brackets in the normal text color in both themes; line numbers; a syntax check by the same Python parser the expression editor already loads, and live checks of names, methods and operators on that same parse; and autocomplete offering this block's Input Variables by name plus WAVE's builtins catalog with nothing filtered out, because the expression editor's blocked-builtins filter does not apply to a script. The sheet shows neither the Kind nor the Format dropdown for the body: it is never template-expanded, so `{{` in the script is just Python, and its format is fixed. The footer's left side carries one chip, `F1 Help`; F1 or the chip opens a small help popover over the editor with two sections. The first lists the keyboard: `Ctrl+Space` Autocomplete, `Shift+Enter` Run, `Ctrl+Enter` Save, `Esc` Close, `F2` Rename symbol, `Ctrl+/` Toggle comment, `Ctrl+F` Find and replace, `Ctrl+G` Go to line, `Tab` / `Shift+Tab` Indent / outdent, `Ctrl+Z` / `Ctrl+Y` Undo / redo. Below it a `Show tips` link expands the Tips, collapsed by default and reading `Hide tips` while open, in four subsections, each line a short sentence plus a mono example. Inputs: "Input Variables are globals" `limit = float(threshold)`; "A table iterates as row dicts" `for row in readings: row["temp_c"]`; "Floats arrive as Decimal" `float(price) * 2`. Outputs: "Assign a name to fill a Variable Export" `summary = {"mean": mean_temp}`; "A list of dicts fills a table export" `rows = [{"id": 1, "ok": True}]`; "Exports are read even when the script raises". Logging and failure: "logging goes to the run console, print to Stdout" `logging.info("done %d", count)`; "An exception or a failed assert fails the block with its traceback" `assert ok, "no rows"`; "sys.exit ends with that exit code" `sys.exit(2)`. Files and modules: "Modules in the Working Directory import by name" `import helpers`; "Test Data and Artifacts folders come from the environment" `os.environ["WAVE_TESTDATA_DIR"]`. The popover has an X close control in its top-right corner; Esc or a click outside closes it too. No hints or tips are shown anywhere else on the sheet. Syntax errors show as underlines in the text and in the sheet's validation strip, the first message with a "(+N more)" expander, each message `Line {n}: {message}`; a syntax error never blocks Save, but it marks the block invalid on the canvas, and a block with a syntax error cannot run. The check has two halves. While the author types it is the editor's own Python parser, in the browser, with no request: it reports one entry per error, each naming the line and saying what that parser can say about it. On Save and on Run WAVE checks the same script with Python's own parser, on the WAVE server, and its precise sentence replaces the editor's wording in the strip and in the block's issue. Neither half ever blocks a save - not the sheet's Save, not the configuration dialog's, not the test's. The same parse, with no request, also checks the script for what the expression field already catches, wherever that check holds for a whole script. A name the script reads is flagged when nothing defines it where Python would look: no assignment, import, function or class, parameter, loop, with, except, walrus, comprehension or match target, and no global or nonlocal declaration binds it in a scope Python searches, and it is neither an Input Variable, nor a global the bridge sets, nor a Python builtin. The scopes are Python's own - module, function, lambda, comprehension and class - so a class body's names are not visible inside its methods, and a module-level name bound anywhere in the script counts inside every function. There is no flow analysis: a read before its assignment is not flagged, and neither is a read inside a try whose handler catches NameError. A called name reads `Function '{name}' is not recognized`; any other name reads `Variable '{name}' is not defined`, and `Variable '{name}' not defined. Did you mean '{other}'?` when a name in scope, an Input Variable or a builtin is close. An Input Variable whose type is known, because its value references a variable, and that the script never rebinds, is checked against the Python type the script really receives - `str`, `int`, `decimal.Decimal`, `bool`, `list`, `dict` or the bridge's table object: a method that type does not have reads `'{method}' is not a valid method for type '{type}'`, and a call with an argument count that method never accepts reads `Method '{method}' takes {expected}, got {n}`. A binary operator whose operands are literals or such Input Variables is flagged only when Python rejects those two types at run time, with `Cannot use '{operator}' with {left} and {right}` - for example a float Input Variable, which arrives as Decimal, times 1.5. Method sets, argument counts and operator rules follow every Python the bridge supports, 3.8 and newer, so nothing is flagged that one of them accepts. A script with a star import, or one that reaches its namespace dynamically through globals, locals, vars, exec, eval or the builtins module, is not checked, and a script with a syntax error shows its syntax errors only. Each finding is underlined on its name, method or operator with the expression field's underline for the same finding, amber for an unknown variable and red otherwise, and is listed in the validation strip together with the syntax errors, in line order, with the same "(+N more)" expander. The findings are warnings: they never block Save, never disable Run and never mark the block invalid on the canvas; they appear in the block's issues as warnings. The sheet opens at 720 by 460 in Python mode and has a maximize control in its header; there is no pretty-print for it. The script bodies of Shell Script, K8s Script and SSH Session Script have their format picker pinned to Plain, with none of the JSON, YAML, XML or Auto choices, while Template stays available where it always was, as the value Kind (PYRUN-15). A parameter declared as never taking an expression shows no Kind dropdown in the sheet at all (PYRUN-16).

**Editor Facilities**: In Python mode the sheet offers, from the editor library WAVE ships, auto-indent (Enter after a colon indents; Tab and Shift+Tab indent and outdent the selection), bracket matching and auto-close of brackets and quotes, comment toggle (Ctrl+/), find and replace (Ctrl+F), go to line (Ctrl+G), code folding from the gutter, and active-line and selection-match highlight (PYRUN-18). It does not offer formatting on save, hover on a variable, which the inspector covers, or select-next-occurrence.

**Completion, Documentation and Rename**: Completion, documentation and rename are backed by the WAVE server (PYRUN-19). The editor asks the server, which introspects the block's interpreter, WAVE's own by default or the virtual environment the Interpreter row names, and answers with member completions after a dot for any imported module, each with its signature and docstring shown in a documentation panel beside the completion list; builtins and WAVE-type methods show the same panel from the catalog. F2 Rename symbol is scope-aware and renames every use of the name in the script; when the name is an Input Variable or a Variable Export, the row is renamed with it. Limits, stated on the details page: an Interpreter row that is a command line, `uv run` for example, or an expression that does not resolve to a local interpreter path cannot be introspected, so completion falls back to WAVE's own interpreter; a remote host's interpreter is never introspected. Requests are debounced and never block typing, and a failed request degrades to the catalog silently.

**Run from the Editor**: The footer's right side reads Close, Save, Run, with Run as the primary button and Shift+Enter as its shortcut (PYRUN-21). Run never saves: it executes this block once with the script exactly as it sits in the editor, unsaved, against the variables as they stand; the block's saved script, on the canvas and on the server, is untouched until Save. Output, the exception and log lines land in the run console, and the sheet stays open. When a debug run is paused at this block, Run is the Paused Toolbar's Repeat Step with the editor's script substituted for that one execution. Otherwise Run executes only this block, exactly as the canvas's Run Current does, and it uses what the block's Save would save: the configuration sheet's whole unsaved draft, every editor open from it, and this editor's script, for that one run only. It runs against the Environment selected in the canvas toolbar and asks for one only when none is selected, and an Environment picked there becomes the toolbar's selection; it runs this block alone and ends when the block ends, so the next Run again runs this block alone. Before it starts, Run is refused only for what this block runs with: a problem on this block other than on the script the editor replaces, a problem on a variable this block reads or binds, or a test that cannot be checked at all. A problem on any other block, or on the saved script, does not stop it; the canvas's Run, Debug, Run Current and Debug Current still refuse on any problem in the test. Run is disabled while the script has a syntax error, while a run is in progress anywhere other than paused at this block, and while something other than this script would block the sheet's Save - then it says why with that same note. A repeat executes the block with the substituted script, never a copy taken when the run started. As for every parameter of every block, Save and Ctrl+Enter apply the value and keep the editor open, Save is disabled until the value differs from what was last saved, Close closes the editor, and Close with unsaved changes asks Keep Editing / Close / Save, where Save applies the value and then closes (PYRUN-20).

**Error Handling**: Validation refuses a misconfigured block before it runs, whatever On error says; a setting given the wrong shape, or a value outside the choices a setting offers, is refused the same way, before the script starts. A failure while the block runs follows On error and carries the reason shown:

| Failure | Message | Reason |
|---------|---------|--------|
| Script Type is Source and the script is empty | `Missing required parameter: script` | Validation |
| Script Type is File and no file is named | `Missing required parameter: script_file` | Validation |
| Timeout is zero or negative | `Parameter 'timeout' must be positive` | Validation |
| Stop on pattern is ticked with both patterns empty | `Set a pass pattern, a fail pattern or both` | Validation |
| A pattern is not a valid regular expression | `Invalid pass pattern: {reason}` or `Invalid fail pattern: {reason}` | Validation |
| An input variable name is not a valid name | `Invalid variable name: '{name}'` | Validation |
| An input variable name starts with `__` | `Variable names may not start with __: '{name}'` | Validation |
| An exported variable name is not a valid name or starts with `__` | `Invalid script variable name: '{name}'` | Validation |
| An exported variable reuses a fixed output's name | `Script variable '{name}' has the name of a block output` | Validation |
| An exported variable is listed more than once | `Script variable '{name}' is listed more than once` | Validation |
| The script file is not there | `Script file not found: {path}` | StartFailed |
| The working directory is not there | `Working directory not found: {path}` | StartFailed |
| Working Directory is a `testdata://` or `artifact://` reference inside a Remote Execution body | `testdata:// paths are not available on the remote host` (or the `artifact://` form) | StartFailed |
| The interpreter program is not installed where the block runs | `Interpreter not found on the WAVE server: {program}` or `Interpreter not found on the remote host: {program}` | StartFailed |
| The interpreter starts but is older than 3.8 or is not Python | `Interpreter is not Python 3.8 or newer: {program}` | StartFailed |
| The operating system refuses to start the script | `Could not start the script: {os error}` | StartFailed |
| The shared path resolver refuses the script file or the working directory | The resolver's own message, passed through unchanged | StartFailed |
| Script File names only a testdata:// or artifact:// root | `Path is the root folder: {path}` | StartFailed |
| The script has a syntax error | `SyntaxError: {message} (line {n})` | Exception |
| The script raises | `{ExceptionType}: {message}` | Exception |
| The script exits with a non-zero code | `Script exited with code {code}: {line}`, where the line is the last line of Stderr that is not blank, trimmed and cut to 200 characters; just `Script exited with code {code}` when Stderr is empty or marked secret, on WAVE and on a remote host alike | NonZeroExit |
| Timeout runs out | `Script timed out after {n} seconds` | Timeout |
| A line matches the fail pattern | `Output matched the fail pattern: {line}`, the line cut to 200 characters; without the line when the matching stream is marked secret | FailPattern |
| An export does not fit its bound type | `Script variable '{name}' is not a valid {type}`, never echoing the value | OutputVariable |

The run console also receives WARN lines of its own:

| Situation | Console line |
|-----------|--------------|
| A failure recorded under Record and continue | `Script failed ({reason}): {message}` |
| A captured stream dropped earlier output | `Stdout truncated: {n} bytes dropped` or `Stderr truncated: {n} bytes dropped` |
| The interpreter did not end within the grace after a pattern match, so no export was read | `Variable exports were not read: the script did not end after the pattern match` |
