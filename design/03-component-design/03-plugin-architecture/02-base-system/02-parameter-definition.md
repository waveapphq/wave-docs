##### REQ-3.4.2.2 Plugin parameter definition

Plugins declare structured parameter schemas that define their input interface, enabling GUI form generation and basic type checking. WAVE keeps parameter definitions simple while users build custom validation logic visually in their workflows.

**Schema-Driven Parameter Declaration**: Each plugin declares its parameters through minimal schemas specifying: parameter identifier (unique within the plugin), display name for GUI presentation, data type (string, integer, float, boolean, array, map, table), whether the parameter is required or optional, default values for optional parameters, an optional minimum and maximum for a number, and human-readable descriptions explaining the parameter's purpose and any constraints. A default is never written into a Block: a free-entry field the user has not set shows its default in gray and stores nothing, and the run fills it from the default current at run time (FIELD-2). Descriptions serve as documentation for users who then implement their own validation logic using Assert blocks or scripts. A parameter that carries a secret never declares a default (SECUI-13).

**Type System Support**: The parameter system supports both simple and complex data types. Simple types include strings (text values), integers (whole numbers), floats (decimal numbers), and booleans (true/false flags). Complex types include arrays (ordered lists), maps (key-value structures), and tables (two-dimensional matrices for test data). Null is a value of every type, not a data type of its own. A field declares two things about null in its block's definition: whether its whole value accepts null at run time, which also decides whether its value field offers the null icon - only a field that accepts a whole null offers it, never one that refuses one (FIELD-5) - and whether a null `{{ }}` piece prints `null`; each entry or row of a list or map reaches the block as given, null included, and the block decides what a null entry means (FIELD-13); the rules they feed are in Null Values (see REQ-3.1.3.21 and REQ-3.1.3.22). A field may also declare that it accepts a value of any type, which only the Log message does: an expression giving a whole value of another type is not refused, and the field prints it in WAVE's print form (see REQ-3.1.3.23). WAVE validates that values match the declared type, except in a field that accepts any type (integer parameters reject decimals, float parameters accept any numeric value). Beyond the declared type and the declared rules below, validation is the user's responsibility.

**Enumerated Values**: Parameters may declare enumerated values for strict selection. When a parameter specifies enum values, the GUI renders a dropdown as the default input widget. Every enumerated parameter declares a default, and a new Block holds that value from the moment it is created (FIELD-8). Enum parameters support the expression toggle, allowing switching from the dropdown to a Python expression input. At runtime, the resolved value is validated against the allowed enum list, rejecting values not in the list. The info icon displays allowed values as documentation for the user.

**Rules beyond type**: A parameter can also declare that it is an ordered list of rows, each row a value or an expression, kept in row order; that a map's keys follow a name pattern and may not start with given prefixes, each rule with its own message; that it belongs to a group of which at least one must hold a value, optionally only while a condition holds, with one message for the group; and that its entries name extra outputs of the block, which are bound, typed and marked secret like any output, and which recipe validation accepts as capture targets. The ordered list, the key name pattern and prefixes, and the at-least-one group are declared in the configuration sheet's descriptor; the backend descriptor carries the extra-outputs marker and the variable name rules of the Shell Script, Shell Exec and Python blocks, which the save checks with the run's messages, and the block's own validation enforces the key and at-least-one rules with the same messages the configuration sheet shows.

**Conditional Parameters**: The schema system supports conditional parameter visibility where certain parameters only appear when related parameters have specific values. This UI optimization keeps forms simple without hiding validation logic.

**Parameter Groups and Organization**: For plugins with many parameters, the schema supports logical grouping organizing related parameters together. Groups have display names and descriptions providing structure to parameter forms. Parameters within groups can be collapsed/expanded in the GUI.

**Expression Mode**: All parameters support an `is_expression` flag. When enabled, the parameter value is a pure Python expression evaluated at runtime with safe builtins. The GUI provides an expression toggle (`{}` button) on every parameter widget, switching between literal input and expression mode. In expression mode, the editor provides syntax highlighting for the full expression and autocomplete for available variables and functions. At design time, the system validates expression syntax via AST parsing. At execution time, the expression is evaluated and the result type is checked against the declared parameter type - a mismatch raises `ExpressionTypeError`.

**Numeric Expression Rules**: Numeric parameters in expression mode accept any Python expression that evaluates to the correct numeric type. Examples: `delay_ms` (variable reference), `base * 2` (arithmetic), `int(config_value)` (type conversion). The resolved value must match the declared type: `integer` parameters reject float results, while `float` parameters accept any valid numeric value.

**Template Mode**: String parameters support a template kind alongside literal and expression modes. A template parameter holds a string containing `{{ expression }}` markers that are rendered at execution time using the same safe expression evaluator as expression parameters, with each marker replaced inline by its evaluated result. The template kind is symmetric with the variable template kind, so a `{{ }}` value behaves identically whether it lives in a variable or a parameter. Single-line and multiline string parameters both support all three kinds; the kinds are mutually exclusive for a given parameter, and the GUI surfaces the choice through the value editor (literal or template) together with the expression toggle.

**Input Trimming**: A parameter that holds a strictly-formatted single-line value declares a trim flag. For a flagged parameter the system strips leading and trailing whitespace from the resolved value before the plugin receives it. Trimming is applied after resolution, so it normalizes literal, expression, and template results uniformly: an accidental newline or stray space, whether typed into the value editor or produced by an expression, cannot reach the plugin and break a URL, file path, hostname, file mode, encoding, or enumerated selection. Free-form and multiline payloads are never trimmed, because leading or trailing whitespace can be significant there: request and response bodies, file content, scripts and code, structured document content (JSON, XML, and query bodies), log messages, and certificates preserve their value verbatim. Trimming is opt-in per parameter; the default preserves the value exactly as provided.

**Validation Philosophy**: Beyond the declared type, the enumerated values, a number's minimum and maximum, and the rules beyond type described above, WAVE intentionally avoids further validation schemas such as cross-parameter constraints. Users document constraints in parameter descriptions and build explicit validation at workflow start using Assert blocks, If/Else conditionals, or script blocks. This approach keeps validation logic visible, editable, and flexible rather than hidden in opaque configuration.
