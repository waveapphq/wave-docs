##### REQ-3.4.2.3 Plugin validation logic

Plugins include built-in validation mechanisms that verify parameter correctness and execution preconditions before any work is performed, enabling fast failure and clear error messages.

**Multi-Stage Validation**: Validation occurs at multiple points in the plugin lifecycle providing progressive validation from composition through execution. Composition-time validation checks parameter schemas during workflow design, catching missing required parameters and type mismatches in the GUI before saving. Load-time validation ensures stored parameter values still satisfy schema constraints after workflows are loaded from storage. Pre-execution validation performs final checks immediately before plugin execution, validating computed parameter values and checking execution preconditions.

**Schema-Driven Validation**: The system automatically validates parameters against declared schemas without custom validation code. Type checking ensures parameter values match declared types, converting when safe and rejecting when conversion would lose information. A field that declares it accepts a value of any type is not checked, so an expression result of any type reaches it (see REQ-3.4.2.2). Required parameter checking ensures all non-optional parameters have values. Default value application happens at run time, the same way for every Block: Save stores only what the user set, and the run fills every setting given nothing, or holding a blank expression, with its default as it stands when the run starts (for a Shared Function Block, the pinned version's default; a Required Function input is never filled from its default). A stored setting the Block does not declare is refused at Save and ignored by the run. A setting given null is not missing: it fails and names the setting, unless it is a data field that accepts null (see REQ-3.1.3.21). Constraint checking evaluates validation rules (patterns, ranges, enumerations) against parameter values.

**Unified Enumeration Validation**: Enumeration constraints declared in a parameter's schema are enforced at runtime by a single shared validator that all plugins and controls call into. The validator reads the allowed values from the schema rather than from a duplicated literal at the call site, ensuring the schema remains the single source of truth. Validation runs after expression evaluation and template substitution, so values produced by expression-mode parameters or computed expressions go through the same gate as literal values. When the actual value falls outside the allowed set, the validator emits a structured error message that lists every allowed value and the actual offending value. To keep the message bounded for runtime values that may be arbitrarily long (for example, when an expression resolves to a large string), the actual value is presented in a length-bounded form: at most fifty characters, with the trailing portion replaced by an ellipsis when the original is longer. Non-string values are stringified before measurement and presentation. The shared run path applies it once to every Block's fields, Function Block inputs included. This unified approach guarantees that every plugin and control surfaces enumeration violations identically regardless of whether the violating value came from direct authoring, expression evaluation, or imported data.

**Custom Validation Logic**: Beyond schema validation, plugins can implement custom validation logic for complex constraints that can't be expressed declaratively. Custom validators receive all parameter values and can check cross-parameter relationships, validate parameter combinations for consistency, verify external preconditions (e.g., file existence, network connectivity), and return detailed error messages explaining validation failures. Custom validation integrates seamlessly with schema validation providing a comprehensive validation pipeline.

**Validation Error Reporting**: When validation fails, the system produces structured error messages identifying which parameters failed validation, explaining why validation failed (constraint violated, type mismatch, etc.), suggesting corrective actions when possible, and indicating the validation stage (composition, load, execution). These detailed error messages help users quickly identify and fix configuration issues without trial-and-error debugging.
