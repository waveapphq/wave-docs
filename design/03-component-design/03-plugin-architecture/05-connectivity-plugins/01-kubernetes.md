##### REQ-5.1.1 Kubernetes API

WAVE connects to Kubernetes API servers through its own pure-Python client layer: a narrow REST client, a WebSocket stream client, and the per-verb operation cores the Kubernetes blocks run on, built on WAVE's TLS engine and the standard library only. The layer speaks Kubernetes REST conventions directly - API group/version/resource paths, standard HTTP verbs, JSON bodies - for exactly the operations the Kubernetes blocks need. It deliberately does not embed a generated Kubernetes client library: the surface is small, and self-contained purity is what lets the identical client run on the WAVE server and inside a pushed Remote Execution bundle with the same TLS behavior in both places.

**Stateless Context Model**: Kubernetes API access is authenticated per request over HTTPS; there is no session to establish or tear down. The unit of connectivity is a context bundle - server URL, trust material, credential, default namespace - produced by the K8s Connect block as a kubectl-compatible kubeconfig document in a secret-protected variable and consumed by every Kubernetes block. There is no server-side connection registry and no pooling layer: each block execution opens what it needs and closes it, and the context travels as a value into any execution locus, including remote ones.

**Authentication**: Two credential forms are supported, both ServiceAccount-shaped: bearer tokens, sent per request, and client certificates, presented during the TLS handshake. Server trust follows WAVE's certificate trust rule (REQ-4.5.16): a profile- or parameter-supplied CA certificate is the only certificate trusted, and with none the session trusts the Additional Certificates and the public authorities chosen in Settings; a TLS server-name override directs certificate verification when the server is reached through a tunnel or by IP literal; verification can be explicitly disabled. Credentials are supplied by the user - from a Kubernetes profile, a variable, or a prior block's output - and WAVE performs no interactive or plugin-based login flows and reads no kubeconfig files from the backend host, keeping engine behavior free of hidden host state.

**Proxy**: When Settings > Network > Proxy is on, the REST client and the exec WebSocket client reach the API server from the WAVE host through the proxy or directly, as the setting's route decision says for the server's address. Through the proxy the connection is a tunnel the proxy opens to the server, so TLS and its checks stay end to end. A server URL on a local address, an SSH tunnel's local port included, connects directly unless the setting sends local addresses through the proxy too, and a block on a remote host never uses the proxy (REQ-4.7.14).

**Impersonation**: Any request the layer sends can be attributed to a different identity: a user, optionally with group memberships, carried in the standard Kubernetes impersonation headers beside the session's own credential. The cluster decides what that identity may do, so a test proves a role's real permissions instead of a WAVE-side approximation of them, and one connected session can check several roles in turn without holding a credential for any of them. The session's own identity must hold the right to impersonate; where it does not, the cluster refuses in the ordinary authorization path and the denial reads like any other. Groups named without a user are rejected before the request leaves WAVE, because the API server answers that shape with a bare server error that explains nothing.

**Run-Scoped Tokens**: The connectivity layer exposes the cluster's TokenRequest API: given any credential permitted to mint tokens for a ServiceAccount, it requests a token with a caller-chosen lifetime (the API's minimum is ten minutes, enforced up front). The granted lifetime is read back from the cluster's response, because servers cap requests silently. K8s Connect uses this for its run-token mode, exchanging a possibly short-lived organization credential for a token that lasts the test run; on the oldest supported clusters the endpoint exists only where the API server issues bound service-account tokens, and the ordinary permission-error path reports that plainly. Token lifecycle beyond this single exchange is the workflow author's domain, composed from ordinary blocks.

**Streaming Channel**: Command execution in containers uses the Kubernetes exec subprotocol: an HTTP connection upgraded to a WebSocket, with the standard streams and an error/status stream multiplexed as prefixed channels. WAVE's WebSocket client implements the handshake and framing over the same TLS engine as the REST client, honors deadlines, and surfaces the exit status carried on the error channel. API servers have served WebSocket exec across the entire supported version range; WAVE always negotiates at least the protocol version that carries structured exit codes, and uses the newer stream-close-capable version where the server offers it. Closing a single stream mid-session (finishing standard input without aborting the command) exists only in that newer version, served from Kubernetes 1.30, so the one block that feeds content on standard input requires 1.30 or newer and says so plainly when the server does not offer it, while every other block over this channel uses no standard input and runs across the whole supported range. File copying between a pod and the WAVE side rides this same channel rather than an API of its own: it drives the container's own archiving tools over an exec session and, like command execution, needs nothing of the channel beyond the standard streams and the status the error channel carries.

**Discovery and Version Alignment**: The layer reads the cluster's version endpoint and its API discovery documents. The version read enforces the 1.19 minimum at connect time; discovery maps resource kinds to their serving endpoints and scopes (namespaced or cluster-wide) and validates author-supplied API versions before any operation, producing a plain "this cluster does not serve X" failure instead of a raw HTTP error. Resolution follows the cluster's own precedence, so a kind, its plural, its singular form and its kubectl short name all reach the same endpoint, and a group whose discovery document the cluster refuses to serve is skipped rather than treated as fatal - the same tolerance kubectl shows. Aggregated API groups, the ones an add-on serves through the API server rather than the API server itself, are reached over the same paths with the same credential; the resource metrics group is read that way, and its presence is established by asking for the group root, so a cluster without it is reported as missing that API rather than as a failed read. Operations pin generally-available endpoints only, which Kubernetes guarantees stable, so compatibility with new cluster versions requires no WAVE changes.

**Response Shapes**: A read asks for one of three wire shapes. The default is the JSON the API returns, parsed into structure. A read can instead ask the API server to print the objects as a table - the same server-side rendering that produces kubectl's columns - which means the server owns the column set and a custom resource's operator-defined columns arrive with no WAVE knowledge of that resource; the printed columns and rows become a WAVE table, keeping the column types the server declares and falling back to text for a column whose cells contradict it. A server that will not print a table for a kind says so, and that refusal is reported as exactly that, with the formats that do work named. The third shape is raw: the body is carried as received and handed on undecoded, which is how YAML, unparsed JSON and log text come back, because a log is not JSON and a workflow that stores a response whole should not pay for a parse it never uses. A body that should be JSON or YAML and is not is reported with its likely cause - a proxy or gateway answering instead of the cluster - rather than as an empty result. Writes carry the reverse contract: a manifest reaches the operation core as canonical JSON, parsed there and nowhere else, so the core needs no YAML reader of its own and stays vendorable unchanged.

**Error Classification**: API failures map to exact, distinguishable messages: authentication failures (rejected credentials), authorization denials (RBAC, carrying the cluster's explanation), missing objects (named, with namespace), write conflicts, transport and TLS failures (attributed to the connection), and deadline expiries. The classification keeps configuration problems, permission problems, and product-under-test problems apart at a glance, and every message is stable enough to assert on.

**Remote Execution Fitness**: The clients and the verb cores above them import nothing outside the standard library and WAVE's TLS engine, carry no framework types, and are vendored source-identical into the Remote Execution bundle. A verb answers in plain structured data, which WAVE turns back into its own runtime values on return, registering the secrets the verb found before any of those values is handed on. A Kubernetes block inside a remote container therefore behaves byte-for-byte like the same block on WAVE, differing only in network vantage point - which is the point of running it there.
