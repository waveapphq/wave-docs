##### REQ-5.1.5 SSH protocol for node access

The SSH plugins implement the SSH protocol using standard Python SSH libraries providing secure encrypted transport for remote command execution and system access. The implementation supports SSH protocol version 2 with modern encryption algorithms (AES-256, ChaCha20-Poly1305) and MAC algorithms (HMAC-SHA2-256, HMAC-SHA2-512) for message authentication. Connection establishment follows standard SSH handshake: TCP connection, protocol version exchange, key exchange using Diffie-Hellman or Elliptic Curve methods, server authentication via host key verification against WAVE's trusted SSH hosts list (REQ-4.5.14), and client authentication via password or public key (RSA-2048+, Ed25519). Host key verification supports strict mode (the host key must already be on record), accept-new mode (trust on first use, where an unrecorded host has its key written to the record the first time WAVE connects and every later connection is checked against that record), and disabled mode (no verification, for dynamic test environments). Disabled is SSH Session Open's own default, used when a block holds no host key action, and while trusted hosts are locked in Settings accept-new acts as strict. The record is WAVE's own trusted SSH hosts list, kept in WAVE's data folder, so it survives restarts, never depends on a person having logged in on the WAVE host, and is part of backup and restore. It is the only source of host keys: the host keys recorded for the account WAVE runs under are never read (REQ-4.5.14). Trust on first use is decided once per connection: the key accepted when a connection is established is the only key that connection will accept, so the periodic re-keying SSH performs on a long-lived connection can neither introduce a new key nor add one to the record. Verification happens during the handshake, before any credential is sent, so a host presenting an unexpected key is refused while the password or key is still unsent, and the refusal names the host, states whether the key changed or the host was never recorded, and points to Settings > Network > SSH Hosts. A record that cannot be read stops the connection instead of being treated as empty, so verification is never silently skipped. A session opened on the Local Port of an SSH Tunnel open in the same run checks and records the server's host key under the tunnel's far host and port, never under the loopback address, so strict and accept-new mode behave exactly as they do for a direct connection (SSH-8). The protocol implementation supports essential SSH features for test automation including remote command execution, script delivery to an interpreter over standard input, working directory selection for a script, exit code retrieval, and separate stdout/stderr stream capture.

**SSH Tunnel Plugin**

The SSH Tunnel plugin provides local port forwarding, enabling workflows to access remote services not directly reachable from the WAVE backend by forwarding local ports to remote destinations over open SSH sessions. The plugin exposes two UI elements: tunnel open and tunnel close.

**Plugin Purpose and Port Forwarding Model**: The SSH tunnel plugin forwards a local port over an open SSH session, enabling workflows to access services on remote networks as if they were running locally on the WAVE backend host (SSHTUN-1). Primary use cases include accessing databases on remote networks through SSH bastion hosts, connecting to internal Kubernetes services via master node tunnels, reaching web services behind firewalls for API testing, and enabling connections to any TCP service accessible from the session's host but not directly from WAVE. The tunnel creates a listening socket on the WAVE backend's localhost at the Local Port, forwarding all connections to that port through the session's connection to a destination host and port specified relative to the session's server. This enables blocks such as the SQL or HTTP clients to connect to localhost at the Local Port while traffic flows securely through the session to the actual remote service.

**Tunnel Architecture and UI Elements**: A tunnel builds on an open SSH session rather than opening a connection of its own (SSHTUN-1). The plugin exposes two UI elements, both rendered on the shared schema-driven element config form with no bespoke component (SSHTUN-2): SSH Tunnel Open, which forwards a local port through a named session and returns a tunnel identifier, and SSH Tunnel Close, which closes a named tunnel. Tunnel identifiers are assigned by WAVE and bound to workflow variables, preventing collisions and eliminating manual ID management. A tunnel cannot execute commands and serves solely as a port forwarding conduit. It remains active, forwarding connections, until it is closed, its session is closed or the run ends (SSHTUN-4).

**Tunnel Open Operation**: The tunnel open element forwards a local port through an open SSH session rather than opening a connection of its own, and returns a tunnel identifier assigned by WAVE (SSHTUN-1). Its rows sit in a Forwarding group, expanded by default: Session ID, bound to an SSH Session Open's Session ID output; Local Port, the port on the WAVE backend where the tunnel listens, where 0 picks a free port automatically and a field left empty takes 0 when the block runs, a null value fails the block and names the field (see REQ-3.1.3.21), and any text, empty text included, is refused before the block runs (SSH-10); Remote Host, the destination as seen from the session's server; and Remote Port. A collapsed Advanced group follows with a single checkbox, Validate Target, off by default. The listener binds to the loopback interface (127.0.0.1) only, and there is no bind-address row (SSHTUN-2). By default opening binds the Local Port and checks nothing else, matching plain `ssh -L`: every connection accepted on the Local Port asks the session's server to connect to the destination afresh, so a destination that comes up after the tunnel opened is reached by later connections, and a connection that fails fails only itself (SSHTUN-6). The element returns two values: the Tunnel ID, and the Local Port actually in use, which is the resolved port when 0 was given, so downstream blocks address the forwarded service through it. The remote destination is not an output, since it would only echo Remote Host and Remote Port (SSHTUN-3). The local port becomes available to other blocks as soon as the element completes, with all traffic forwarded through the session to the remote destination.

**Target Validation**: With Validate Target on, opening the tunnel also asks the session's server to connect to the destination once, and Tunnel Open fails when the server refuses to forward or cannot reach the destination, waiting no longer than the session's connection timeout. The connection that proved the destination is kept rather than closed and becomes the first connection of the tunnel's first client, whether that is a block connecting to the Local Port or a Netcat block addressing it, so the destination sees no connection beyond those the test makes and a listener that accepts a single connection stays usable. If the destination closed that connection before its first use without sending anything, the first client gets a fresh one instead. Otherwise the first client receives everything the destination sent on that connection since the tunnel opened, even if the destination has closed it since (SSHTUN-7).

**Tunnel Lifetime**: A tunnel has no lifetime setting of its own; there is no per-tunnel scope. A tunnel is a child resource of the session it rides: it stays open until SSH Tunnel Close closes it, until its owning session is closed, directly or through a cascade along a session chain, or until the run ends, whichever comes first, and each of these tears it down automatically, so a tunnel never outlives its session. When the session's connection drops while the session stays open, as it does with keep-alive off, the Local Port stays bound until the session is closed or the run ends, and each connection to it fails with a run-log warning that the SSH connection is closed (SSHTUN-6). Each of these also closes a connection that Validate Target is still holding because no client used it (SSHTUN-7). SSH Tunnel Close takes a Tunnel ID and is an idempotent no-op on an unknown or already-closed tunnel (SSHTUN-4).

**Tunnel Close Operation**: The tunnel close element takes a Tunnel ID and closes that tunnel, stopping its listener and releasing the local port; the session the tunnel rode is not affected. Connections already in progress through the tunnel keep running until the session closes. Closing an unknown or already-closed tunnel is a no-op rather than an error (SSHTUN-4).

**Tunnel State**: A tunnel is a child resource of the session it rides and is known by its Tunnel ID, which stays valid until the tunnel is closed, its session is closed or the run ends (SSHTUN-4). Test designers bind the Tunnel ID and Local Port outputs to workflow variables and reference them in later blocks (SSHTUN-3).

**Use Case: Database Access Through Bastion Host**: A common use case is validating data in a database that is reachable only through a bastion host. The test opens an SSH session to the bastion (SSH Session Open), opens a tunnel on that session to the database host and port with Local Port 0 (SSH Tunnel Open), and points the SQL block at localhost and the returned Local Port, so its traffic flows through the session to the database server. The tunnel lasts until it is closed, its session is closed or the run ends. This pattern gives secure access to internal services without exposing them directly to the WAVE backend host.

**Use Case: Kubernetes Service Access**: Another use case is API testing against an internal Kubernetes service. The test opens an SSH session to a Kubernetes master node, opens a tunnel on that session to the service's cluster address and port, and sends HTTP requests to localhost at the tunnel's Local Port, reaching the internal service through the session. This gives controlled access to cluster-internal services without ingress configuration or external exposure.

**Connection Lifecycle**: A tunnel holds no connection of its own: its forwarded traffic rides the session's live connection, so multi-hop reach, authentication and host-key policy all come from the session (SSHTUN-1). Forwarding is fixed local port-forwarding, one local port to one remote host and port. Opening fails only when its session is not open, when the Local Port cannot be bound or, with Validate Target on, when the check of the destination fails; a connection refused later fails that connection alone, is reported as a run-log warning and leaves the tunnel open for the connections that follow (SSHTUN-5, SSHTUN-6). Optional reachability is expressed by wrapping the block in a Try-Catch control, as with the SSH Session blocks (SSHTUN-5).

**Error Handling for Tunnel Operations**: Tunnel Open fails when its Local Port is already in use or cannot be bound, and when another branch closes its session while the tunnel opens; that error reads that the SSH connection is closed, and no Local Port stays bound. With Validate Target on, it also fails when the SSH host refuses to forward to the destination, when the SSH host cannot connect to it, or when no answer arrives within the session's connection timeout; each of these errors names the destination and the SSH host, with the host's own reason when it gave one. Optional reachability is expressed by wrapping the block in a Try-Catch control, consistent with the SSH Session plugins (SSHTUN-5, SSHTUN-8). Every connection accepted on the Local Port that the SSH host refuses or cannot complete writes a warning to the run log naming the Local Port, the destination, the SSH host and the host's reason, whether or not Validate Target is on (SSHTUN-6). A refusal by the host's forwarding policy is reported as administratively prohibited, the standard name for it, because the text OpenSSH sends with it says nothing about the cause; a connect that fails on the host carries the host's own text, such as Connection refused or No route to host (SSHTUN-8). The SSH host is named as the session identifies it, so for a session opened on another tunnel's Local Port it is the far host (SSH-8). A Netcat block that addresses a tunnel's Local Port reports a refusal in its own results and adds no tunnel warning (SSHTUN-6, NETCAT-8). Credential, host-key and reachability problems of the SSH host itself belong to the session the tunnel rides and are reported by the SSH Session Open element that carries them (SSHTUN-1). Closing an unknown or already-closed tunnel is not an error (SSHTUN-4).

**Security Considerations**: A tunnel carries no credentials, jump configuration or host-key settings of its own: authentication and host-key verification are those of the session it rides (SSHTUN-1). The local port listener binds only to localhost (127.0.0.1), and there is no bind-address row, so only processes on the WAVE backend host can use the forwarded port and a tunneled service is never exposed to the network by accident (SSHTUN-2). Forwarded traffic travels inside the session's encrypted connection.

**SSH Remote Session Plugin**

The SSH Remote Session plugin provides explicit connection lifecycle management for complex workflows requiring multi-command sequences on one connection, nested SSH connections via jump hosts, and precise control over when connections open and close. The plugin exposes three related operations as separate UI elements: session open, command execution, and session close.

**Plugin Architecture and UI Elements**: The remote session plugin implements a stateful session management model where test designers explicitly open connections, execute multiple commands on those connections, and explicitly close connections when done. The plugin exposes three UI elements in the visual workflow designer: SSH Session Open (establishes connection with optional jump host and returns session identifier), SSH Session Exec (runs commands on an open session), and SSH Session Close (terminates session and closes connection). These elements work together through session identifiers that test designers reference across workflow steps, enabling complex multi-hop SSH scenarios including jump host access patterns.

**Session Open Operation**: The session open element establishes an SSH connection to a target host and returns an auto-generated session identifier for use in subsequent operations. Configuration parameters are the target host and port, the login user, either a password or a private key with an optional passphrase, the host key policy, a connection timeout, keep-alive settings to maintain connections during idle periods, and compression. A port left empty takes the default 22 when the block runs, a null value fails the block and names the field (see REQ-3.1.3.21), and any text, empty text included, is refused before the block runs (SSH-10). Credentials are normally drawn field by field from an SSH connection profile, and literal values are accepted as well. An optional setting routes the new connection over an already-open session, which makes that session's host the jump host; the connection fails when the referenced session is not open. WAVE does not compare the target against the hosts already in the chain, so a chain that revisits a host is accepted and simply adds another hop. The element returns four values: a session identifier, a connected flag that reads true while the session is open and flips to false when it closes or keepalive detects the connection dropped, the identification string the server announced (empty when it sends none), and the number of hops in this session's chain, which is one for a direct connection and grows by one per parent. Session identifiers are assigned by WAVE rather than typed by the test designer, which eliminates manual ID management and prevents collisions; the designer binds the identifier to a workflow variable and later session elements reference that variable. The Session ID help shared by the SSH blocks names every block that references a session: SSH Session Exec, SSH Session Script, SSH Session Close, SSH Tunnel Open, SFTP, Remote Execution, and a chained SSH Session Open's Parent Session (SSH-11).

**Session Exec Operation**: The session execute element runs commands on an open SSH session identified by session ID. Configuration parameters are the session identifier, which the test designer supplies as the workflow variable the opening element bound it to, the command string to execute, and an optional timeout that defaults to five minutes. Return values include stdout, stderr, and exit_code providing complete execution results. The element validates that the referenced session exists and is open, producing clear error messages when attempting to use closed or invalid sessions. When a running command is abandoned, either because its timeout expired or because the run was stopped, the element asks the remote system to stop the command and then closes that command's channel regardless of the answer, giving back the session capacity the command held. When a command is abandoned while its channel is still being opened, the close happens as soon as that channel exists, so the capacity comes back a moment later rather than at once, and a channel whose opening never completes is never closed. Stopping a run is never delayed by this: WAVE sends the stop request and frees the channel without waiting for the remote system to reply. The session itself survives both cases and stays usable by later elements; only an explicit close or automatic cleanup ends it. Every numeric row on the SSH blocks - Session Open's port, connection timeout and keep-alive rows, Session Exec's and Session Script's timeout, Tunnel Open's local and remote ports - declares its bounds once, and they are enforced both in the form and when the block runs, as on every other block (SSH-9).

**Session Close Operation**: The session close element terminates an SSH session, performing graceful connection closure. The operation accepts a session identifier and closes that session together with every session chained through it, child before parent, and it closes the tunnels opened on each of them. It returns the identifiers of the sessions it actually closed. Closing a session that is unknown or already closed (due to server disconnect, idle timeout, or an earlier close) returns an empty list rather than an error, so a workflow can close defensively. After closure, the session identifier becomes invalid and subsequent operations referencing it report that the session is not open.

**Session State Management**: The plugin maintains a registry of the sessions open in the current run. Each session represents a single SSH connection to a target host, optionally reached by chaining through a parent session. Session identifiers uniquely identify connections and remain valid until the session is closed, whether explicitly, through a cascade from its parent (SSH-3), or by the automatic cleanup when the run ends. Test designers reference session IDs throughout their workflow to execute multiple commands on the same connection without repeated connection establishment overhead.

**Automatic Session Cleanup**: The plugin closes sessions the workflow left open, so a forgotten close does not leak a connection. When a run reaches its own end, whether it passed or failed, every session still open is closed, child before parent, along with the tunnels on them. Two cases deliberately keep sessions alive instead: an Immediate Stop, and running a single element or a partial flow on its own, both of which exist so the author can point another element at the same live session without reconnecting. Closing or resetting the test closes whatever those cases left behind. Test designers may add explicit SSH Session Close elements for clarity and explicit lifecycle management, but automatic cleanup provides a safety net preventing resource leaks from forgotten close operations or error conditions.

**Jump Host Integration**: A host that is not directly reachable from the WAVE backend but is reachable from an intermediary host is accessed by chaining sessions. An SSH Session Open element may reference an already-open Parent Session; when it does, the new connection is carried over that parent's live connection, which makes the parent's host the jump host and routes all traffic to the target through it transparently. This avoids manual nested SSH commands, shell state tracking complexity, and command escaping challenges. Chains of any depth are expressed by chaining Open elements, so an ordered chain (WAVE to A to B to target) is one Open element per hop, and every hop is a session in its own right that can also run commands and carry tunnels. This is the proxy-jump behavior standard SSH libraries provide and it covers Kubernetes node access patterns (master to worker) and bastion host scenarios. Jump hosts come only from this chain: a jump host or proxy command named in the SSH config file of the account WAVE runs under is never used (REQ-4.5.15).

**Error Handling for Session Operations**: Session operations implement comprehensive error handling specific to connection lifecycle management. Attempting to execute commands on closed or invalid sessions produces immediate errors with clear messages identifying the problem session ID. Network failures during session operations trigger connection-specific errors while leaving other sessions unaffected. Every hop in a chain authenticates in its own Session Open element, so a credential problem is reported by the element that carries those credentials and names the host it was reaching; a chained Open whose parent session is not open reports the missing parent instead of a connection failure. A command cannot end the session from inside it: every execute opens its own channel and its own process on the connection, so nothing a command does to its own shell reaches the next one. Keep-alive is what detects a dropped connection: with it on, when the server disconnects or keepalive gives up on the connection, the session is dropped and later operations report that it is not open. With keep-alive off, a lost connection does not drop the session by itself, so it still counts as open and a later operation on it fails on the lost connection. Session close operations handle already-closed connections gracefully as idempotent operations.

**Use Case: Kubernetes Node Access via Jump Host**: A primary use case demonstrates accessing Kubernetes worker nodes through master nodes for packet capture and diagnostics. The workflow opens a session to the master node, then opens a second session to the worker node that references the master session as its parent, executes tcpdump on the worker node capturing network traffic (SSH Session Exec), transfers the packet capture file from worker to a shared location accessible to the master using scp commands, closes the worker session (SSH Session Close), downloads the packet capture file from the master to WAVE with the SFTP block, which rides the master session's own connection rather than opening one of its own (SFTP-1), and closes the master session. This pattern extends WAVE's Kubernetes testing beyond API-level operations to include low-level node diagnostics and network traffic analysis essential for comprehensive event processing pipeline validation.

**Authentication and Security**: The SSH plugins use identical authentication mechanisms supporting password-based and key-based authentication. A private key is supplied either as key content or as the path of a key file on the WAVE host, where a relative path starts at the home folder of the account WAVE runs under (REQ-3.4.3.12), with support for RSA and Ed25519 key types, and is normally held as a secret field of a connection profile. A connection authenticates only with what its block names: the default keys and the SSH agent of the account WAVE runs under are never tried (REQ-4.5.15). Credentials are never logged or exposed in output variables: a secret parameter registers its value with the run's secret registry, so every outbound surface masks it, logs and console included. Host key verification is what keeps those credentials from reaching an impostor: the server's key is checked while the connection is still being established and before anything is sent, so under the two verifying modes a host that offers a key WAVE did not expect is refused rather than authenticated against. A command line, and a script, reach the remote host exactly as the workflow composed them, with workflow values already substituted into the text, and the remote shell or interpreter parses the whole of it; WAVE adds no quoting around a substituted value, so a workflow that builds a command out of values it does not control is the one that quotes them.

##### REQ-4.5.4 Secure SSH key management

A private key reaches SSH Session Open as key content or as the path of a key file on the WAVE host, and is normally held as a secret field of an SSH profile, so it is masked on every outbound surface like any other secret. A key file is read by WAVE itself, a relative path starting at the home folder of the account WAVE runs under as the Private Key help says, so only that key is offered: neither the files beside it, nor the account's default keys, nor its SSH agent take part (REQ-4.5.15). Session Open unlocks a passphrase-protected private key in every format ssh-keygen writes, including the OpenSSH format that is ssh-keygen's default, with the passphrase taken from the Passphrase row, and the passphrase is a secret in the same way (SSH-7).

##### REQ-4.5.14 WAVE's trusted SSH hosts list

WAVE keeps its own list of trusted SSH hosts in its data folder, and it is the only source of host keys for every SSH connection WAVE makes: SSH Session Open, direct and chained, and everything that rides a session (Session Exec, Session Script, SSH Tunnel, SFTP and the Remote Execution transport). The known hosts file of the account WAVE runs under is never read.

**Entries**: An entry is a host, a port, a key type and the host's public key, shown with its SHA-256 fingerprint and the time it was added. A host on a port other than 22 is an entry of its own, and a session opened on a tunnel's Local Port is checked and recorded under the tunnel's far host and port (SSH-8). Entries name hosts plainly: hashed host names, wildcard patterns, and certificate-authority or revoked markers are not part of the list.

**Who adds a host**: A block set to Accept New adds an unknown host's key the first time it connects, unless the list is locked, and from then on that key is the only one accepted for that host, port and key type. An admin adds hosts in Settings > Network > SSH Hosts in one of two ways. Detect from host asks the host for its keys: the WAVE host connects directly, never through a proxy, and reads the key of each supported type (ED25519, ECDSA, RSA) without logging in, within ten seconds. Paste lines takes lines in the known hosts format or the output of the standard key-scan tool. A line that names several hosts becomes one entry per name. A key already in the list is shown as already trusted; a different key for a host, port and key type already in the list is shown as a changed key and cannot be added until the admin removes the old entry, so trusting a changed key is always a deliberate act.

**Lock**: Lock trusted hosts, off by default, stops every block from adding hosts: a block set to Accept New then acts as Strict and an unknown host is refused. Lock does not affect a block set to Disabled.

**Default block action**: Settings holds the host key action (Strict, Accept New or Disabled; Disabled by default) that is stamped into an SSH Session Open block when it is placed, from the palette, from Quick Add, or by an MCP recipe that does not set it. Disabled is the default because strict fingerprinting pays off where an admin curates the list and locks it; where nobody curates it, verification goes unnoticed and the list would only accumulate hosts. A block that holds no host key action, and a placement that cannot read the Settings value, use Disabled as well, so every path agrees. The value is never looked up at run time, so changing it never changes an existing test, and existing blocks keep their value. Turning Lock on while the default is Accept New makes the default Strict, and Accept New cannot be chosen while the list is locked.

**Saving**: Every change on the page, the lock and the default action as well as added and removed hosts, is held on the page until Save writes it in one step, and Cancel restores the saved state. The lock and the default action are written to this WAVE's config file and the host changes to the list by the same Save; when the list cannot be written, the config file is put back (REQ-4.7.16). Save sends only the changes, never the whole list, so hosts that blocks added while the page was open are kept. Every addition is checked again when it is saved, and a conflict found then, such as a block having trusted a different key for the same host in the meantime, is refused naming the host, port and key type, with the page's changes kept.

**Refusals**: An unknown host under Strict, or under Accept New while the list is locked, and a changed key are refused before any credential is sent. The refusal names the host and port, says whether the key changed or the host was never trusted, and points to Settings > Network > SSH Hosts; the Host Key Verification help speaks of WAVE's trusted hosts list.

**Storage and backup**: The list lives in the data folder as shared work. Every write replaces the list whole and atomically under a lock, so concurrent first contacts and an admin's Save never lose an entry. The list is part of backup and restore; the lock and the default block action are this WAVE's own settings, kept in its config file (REQ-4.7.17).

##### REQ-4.5.15 SSH login and routing sources

An SSH connection authenticates only with the host, port, username, password, private key and passphrase its block names, and reaches a jump host only through WAVE's session chain. Nothing of the account WAVE runs under takes part: its SSH config file is not read, so no host alias, user, port, identity, jump host or proxy command there applies; its default key files are not tried when the block names no private key; and its SSH agent is not asked, even when one is running. Kerberos login and certificate-based host trust are not used either. A private key named by path is read by WAVE itself, so only that key is offered (REQ-4.5.4).

The rule holds on every SSH path: SSH Session Open, direct and chained, and everything that rides a session (Session Exec, Session Script, SSH Tunnel, SFTP and the Remote Execution transport). A test therefore connects the same way from every WAVE host, and a key that happens to sit in an account's agent can never make a test pass.

#### Remote Execution

##### REQ-3.4.1.3 SSH remote execution

Remote Execution is a container element that runs an inner sub-flow of blocks on a remote host reached over an SSH chain, making network and system validations act "from" that host rather than from the WAVE backend. It generalizes single-host operation into location-transparent operation: a plugin author writes one implementation, and the same implementation runs either on the WAVE backend or, when wrapped in a Remote Execution container, on the chosen host. This is the mechanism by which host-anchored network validations - port reachability and ping - execute at the correct vantage point in a distributed topology, where the observation must originate on a node that WAVE cannot reach directly but an SSH chain can.

**Container Model and Body Semantics**: The element is a container in the visual builder, presented like the loop controls: an ingress, a body path whose sub-flow runs on the remote host, and a continuation path taken after the sub-flow completes. Each block in the body is routed by whether it can run remotely: remotable blocks execute on the remote host, while blocks that are not remotable execute on the WAVE backend, and every body block carries a locus indicator showing where it runs. Blocks outside the container always execute on the WAVE backend. The routing reaches every depth of the body: a block inside a control in the body (a loop, a branch, a Parallel lane, a Try/Catch path, a Wait Until) or inside a Function Block in the body is routed the same way, while the controls and the Function boundary themselves run on the WAVE backend. Every remotable block in the body runs through the one worker the container opened for its Execution Host, and Parallel lanes in the body run on that worker at the same time. A Remote Execution placed inside another's body is a container of its own: it opens its own worker on its own Execution Host, the remotable blocks in its body run there, and it closes that worker when its body ends. The container carries a single required input, the Session ID of an open SSH session (produced by SSH Session Open, optionally the tail of a multi-hop chain), and a single output, a Remote Session identifier that references the remote execution context for the duration of the run. The container has no execution timeout of its own (each body block owns its timeout) and no interpreter selection input (interpreter compatibility is verified on the host at run time). A run that starts inside a body on its own - Run Current or Run from Here on a block or a control in the body, or Run Scope of a Function whose instance sits in the body, at any depth - runs the way the full run does: it uses the Execution Host session of the innermost Remote Execution whose body holds its starting point and routes every remotable block through a worker on that remote host. That worker opens when the run first reaches a block that runs on the remote host and stays open until the run ends, so a run that reaches no such block needs no session and opens no worker. When that session is closed or not connected, the blocks before the first block that runs on the remote host run as usual and the run fails at that block with that reason, so a block marked as running on the remote host never runs on the WAVE backend. A body that never starts, because the worker never opens, paints skipped, like any lane a container did not run.

**Agentless Execution**: Remote Execution is agentless. The only standing requirement on a target host is a compatible Python interpreter (plus elevated capability where an operation inherently needs it). The framework packages the body's execution logic and its pure-Python dependencies as source in a self-contained bundle, transfers it over the SSH session's existing connection, runs it under the host's own interpreter, collects structured results, and removes the bundle - leaving nothing WAVE-authored on the host. Where a block needs a driver that exists only compiled, the run carries the prebuilt build that fits the host's Python, CPU and libc into the same scratch directory and removes it with the rest; nothing is ever installed on the host. Because the bundle must run under an unmodified host interpreter, the remotable execution path is decoupled from the validation framework's data-modeling layer, exchanging plain structured data in and out.

**Stopping Work on the Host**: A block owns every process it starts, on the WAVE backend and on an execution host alike, and the worker running the bundle is what holds that ownership on the remote host. The worker keeps nothing in memory between requests: it runs every request in a process of its own on the remote host, in a process group of its own, so the network calls a request makes and every program it starts belong to that one group. Each request carries an identifier and its answer carries the same identifier, so the worker serves several requests at once and the framework matches every answer to the request that asked for it. The worker keeps listening on the session while it works, so it can be reached in the middle of an operation rather than only between operations. When the framework cuts off one remotable block before it answers (a Parallel lane or section time limit, a Parallel that finishes with its first lane, a Wait Until timeout), it cancels that one request: the worker ends that request's process group, writes no answer for it, and keeps serving every other request, so the remotable blocks that follow in the same body still run on the remote host. The framework never waits for or uses the answer of a canceled request. A stop request carried over the session, the session closing under the worker, and the body ending all end the process group of every request the worker is serving and then the worker itself within a short grace. A stopped run therefore leaves the remote host as it was found, with nothing WAVE-authored still running and nothing WAVE-authored left on disk.

**Runtime Fidelity and Observability**: Running on the host, rather than merely tunneling egress to it, gives validations the host's own environment - its client certificates, its proxy configuration, its network stack and interfaces, and true end-client fidelity. Certificate trust follows WAVE's rule there too: WAVE's built-in list and the Additional Certificates travel with the run, and when Settings chooses the WAVE host's store, the remote host uses its own store plus the Additional Certificates (REQ-4.5.16). The SSH chain that carries the worker checks host keys and authenticates on every hop only as REQ-4.5.14 and REQ-4.5.15 state. Results, output bindings, and logs from body blocks surface in the run exactly as they would for local execution, and secret values remain masked across the remote boundary in logs, console, and reports. A missing or closed session, an incompatible interpreter, or a failure inside the remote sub-flow surfaces as a clear, host-attributed error.
