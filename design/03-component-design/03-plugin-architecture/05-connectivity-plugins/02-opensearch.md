##### REQ-5.1.2 OpenSearch REST API

WAVE reaches OpenSearch clusters through the cluster's REST API with a REST client of its own, so that the same OpenSearch block runs on the WAVE server, on a remote host and through an SSH tunnel. It talks to the cluster's REST port, usually 9200, directly or over SSH, and never through OpenSearch Dashboards.

**Client Model**: WAVE speaks OpenSearch's REST API over HTTP and HTTPS with its own client and no client library. The client does what the OpenSearch block needs and nothing more: send a search to an index pattern, asking for the matching documents in Search mode or only for the numbers in Aggregate mode, with the matching documents counted exactly; page past OpenSearch's 10,000-document window by continuing after the last document's sort values with the document ID as tiebreaker; read the answer into WAVE tables; read which indexes a pattern matches and the fields they hold; and end a search on demand. It is read-only: it has no call that writes, updates or deletes. The same client runs on the WAVE server and on a remote host, where it travels with the run as source and needs nothing beyond the Python the host already has, so nothing is installed on a remote host and the host is left as it was found. DQL is turned into Query DSL inside this client, where the block runs, because the field types the translation needs can only be read from where the block reaches the cluster. The index pattern is sent as written and OpenSearch resolves wildcards, comma lists, exclusions, aliases, data streams and date-math names on the cluster; WAVE resolves no pattern itself.

**Connections**: Every block opens its own connection, sends its requests and closes it; there is no connection pool, no connection manager, no keepalive between blocks and no failover list, because nothing persists a connection between blocks and a pool could not exist on a remote host where every block is its own process. A block names one cluster by one URL. Connect timeout, 30 seconds, bounds reaching the host and the TLS handshake. A failed request is not retried inside the block: it fails the block with its reason, and waiting or trying again is the job of a Wait Until around the block. Through an SSH tunnel the block dials the tunnel's far side the way SQL and Netcat do, by an implicit lookup of the open tunnel on the Local Port when the Cluster URL names 127.0.0.1 or localhost, and the TLS server-name check and the host the request names both use the far host, so a cluster behind a reverse proxy that routes by host name still answers. When Settings > Network > Proxy is on, a block on the WAVE host reaches the cluster through that proxy or directly, as the setting's route decision says for the cluster's address; through the proxy the connection is a tunnel the proxy opens so TLS stays end to end. A Cluster URL on a local address, an SSH tunnel's Local Port included, connects directly unless the setting sends local addresses through the proxy too; a block on a remote host never uses it (REQ-4.7.14).

**TLS**: The URL scheme decides: an https URL uses TLS and an http URL does not, so a lab cluster with security off works over plain http and there is no TLS toggle. TLS uses the four trust rows the HTTP and SQL blocks already have: Verify Server Certificate, on by default, CA Certificate for an internal authority, and Client Certificate with Client Key for mutual TLS. Verification follows WAVE's certificate trust rule (REQ-4.5.16): a CA Certificate set on the block is the only certificate trusted, a blank one trusts the Additional Certificates and the public authorities chosen in Settings, and any trusted certificate, root or intermediate, completes a chain. The handshake is standard TLS as the platform negotiates it, with no version or cipher rows. The trust rows are used only for an https URL; filled on an http URL they are not used, and the block says so with an amber note.

**Authentication**: WAVE presents who it is in one of the ways OpenSearch's security layer accepts: a username and password, an API key on the clusters that issue them (OpenSearch 3.7 and later), a bearer token such as a JSON Web Token, a client certificate, or nothing at all for an anonymous cluster or one with security off. Username and password, API key and bearer token all travel in the one Authorization header, so more than one set fails validation with one message before anything is sent; a client certificate rides the TLS handshake and goes with any of them. There is no mode picker: which fields are filled decides. Credentials written inside the URL are refused, because a URL is not a sealed field. Every credential is a secret: never logged, never in an output.

**Profile Binding**: The OpenSearch profile carries what describes the cluster under the block's own names - the cluster URL, username, password, API key, bearer token and the four trust rows - and nothing that is a choice or a per-request bound: the index pattern, the time range, the query, the mode and its rows, the Time field and the timeouts stay on the block. There is no host and port pair; the URL carries both. A profile is never required: every row can be typed on the block, and a bound profile supplies values that the block's rows reference, as every profile binding does.

**Errors**: OpenSearch's own words are never rewritten, so a type and reason found in the log can be looked up in one step. The author sees them whatever shape the answer takes: the standard error envelope as the type and reason of its first root cause, a plain-text body such as the security layer's refusal as its HTTP status and first line (`HTTP 401: Unauthorized`), and an empty body as its HTTP status. When all shards failed, the error carries the first root cause and the query as sent, so a DQL line OpenSearch refused shows what it became. Each class of failure carries its own reason so that On error and a Try / Catch can tell them apart: Unreachable when the host, the port or the TLS handshake does not answer, naming the host and the port tried; AuthFailed for a 401, or a 403 security exception; RequestFailed for anything else OpenSearch refuses; Timeout when the block runs past its Timeout; and Validation when a filled value cannot work: most of these checks run before anything is sent, while a Dashboards address and a Time field that is not a date are known only from the cluster's first answer. Partial results are not a failure: a search where some shards failed or that timed out on the cluster ends the block amber with a WARN.

**Supported Clusters**: The block works against OpenSearch 1.x, 2.x and 3.x. Every call it makes has the same shape on all three lines, so it never asks the cluster for its version. API keys exist only on clusters that issue them. Elasticsearch is not a target: common calls may answer, and none is tested. AWS request signing is not offered; a managed domain that accepts a username and password works like any other cluster.

**Stop and Timeout**: Timeout, 300 seconds, bounds the whole block, paging included. Stop and Timeout shut the live connection down rather than only abandoning the wait, and OpenSearch ends a search whose connection closes, so a stopped or timed-out search does not keep running on the cluster. The same holds for Stop in the editor.
