#### 3.5.8 Function Execution Semantics

##### REQ-3.2.1.1 Function variant of normal execution

Function instances participate in normal execution (run to completion) via the invocation semantics described in this section. When a workflow author triggers Run on a Test containing one or more Function instances, the workflow engine traverses the Test's graph and, upon reaching each Function instance, performs an invocation following the pipeline below. The Test's run completes when its terminal state is reached, identical to a Test composed only of plugins and controls; Function instances are not externally distinguishable from any other Block in the run's result.

A Function invocation is a discrete unit of execution with well-defined boundaries. When control flow reaches a Function instance, the platform performs an invocation: it resolves the Function Block's fields, establishes the Function's runtime scope, executes the Function's internal subgraph, collects the declared outputs, and applies the Function Block's output bindings. The invocation completes atomically as seen from the flow the Block sits in: that flow observes that the Function's outputs have been applied to its scope, and execution proceeds to the next Block downstream.

**Invocation boundary when the Block runs.** The boundary opens when control flow reaches a Function Block. The platform creates a fresh runtime scope for the invocation; the scope contains the Function's declared inputs (each holding the value of the Block's field, else, for an input that is not Required, its default, else null; a Function Block never fills a Required input from its default), declared outputs (initially set to their defaults, or null when there is none), and a space for the Function's local variables. The runtime scope of the flow the Block sits in is not visible to the new scope; the isolation contract enforces this at both validation and runtime.

**Field resolution in the flow the Block sits in.** Before the new scope is populated, the platform resolves the Function Block's fields the way it resolves any Block's fields, in the flow the Block sits in. A stored field the Function no longer declares is ignored. A field not set, or holding a blank expression, takes the input's default, never a Required input's. A literal yields the literal; a template fills its `{{ }}` pieces; an expression evaluates over that flow's scope; per-entry expressions in a list or map evaluate entry by entry. Each value is checked against the input's declared type and allowed values once evaluated, then realized by that type, so a Function Block's fields keep exact numbers. Inputs may not refer to each other; each field is resolved independently. A field that fails to evaluate fails the Function Block and names the input, and a whole null given to a required or defaulted input fails it the same way, with the wording every Block uses; in both cases the Function body never starts. A null item, map value or table cell reaches the Function as null (see REQ-3.1.3.21).

**Value copy into the Function's inputs.** After all fields are resolved, the resulting values are copied into the new invocation's input variables. The copy is by value: the Function operates on the values present at the moment the invocation began. Subsequent changes to the variables of the flow the Block sits in during the Function's execution do not propagate into the Function. Attempts by the Function's body to assign to an input are validation errors at composition time; at runtime they cannot occur because inputs are read-only.

**Internal execution.** Once the new scope is established, the Function's internal subgraph begins executing from its entry. Internal Blocks read from the Function's inputs and local variables, produce additional local variables, invoke plugins, controls, and nested Functions, and write to the Function's outputs. The execution semantics inside a Function are identical to the execution semantics at the Test level: same flow rules, same error handling, same retry and timeout semantics on plugin invocations, same parallel and sequential composition. The only behavioral difference is the variable visibility restriction.

**Output collection on return.** When the Function's subgraph reaches its terminal state (either reaching a successful end of flow or being interrupted by an uncaught error), the platform reads the current value of each declared output. Declared outputs that the Function's body did not assign during this invocation hold their declared default, or null when there is none. The platform returns a single result document containing the outputs and an execution status.

**Output bindings into the flow the Block sits in.** On successful return, the platform applies the Function Block's output bindings against the result document, the same way it applies a plugin Block's. Each binding names a destination variable in scope where the Block sits and the source output; the platform writes the source value to the destination variable. After all output bindings are applied, the invocation's runtime scope (local variables included) is no longer reachable from the flow the Block sits in, and control flow proceeds to the next downstream Block after the Function Block. In a Workbench session the platform keeps each Function instance's last runtime scope - its inputs, local variables and outputs as that invocation left them - as the state later ad-hoc runs on that instance start from (see the drilled-in scoped invocation below); the flow the Block sits in never reads it.

**Error semantics.** A Function whose internal execution raises an uncaught error fails the Function invocation. The failure shows at the Function Block; the surrounding flow (including any try-catch wrapping the Function Block) handles the failure with the same rules that apply to any other Block. Output bindings are not applied on failure because the result document is not produced. Partial output state inside the Function is never observable from the flow the Block sits in; a Workbench session keeps it only as the instance's last runtime scope for later ad-hoc runs.

**Scope-fail propagation.** A Function body is a scope. When a block inside the body marks the scope failed (a split-mode `Assert` with `fail_current_scope` whose assertions evaluated to false), the mark lands on the innermost enclosing Function body wherever inside the body the block sits - a loop body, a branch, a Parallel lane, a Try/Catch path. The mark does not stop the body's flow, which runs to completion; the Function Block then reports failed. That is a block failure in the flow the Block sits in: that flow stops at the Function Block exactly as it stops at any failed block, and the failure travels outward from there - a Try/Catch around the Function Block catches it, otherwise it ends the enclosing Function or Test failed. The mark itself never crosses the Function boundary. A mark is distinct from a block failure: a mark lets the flow continue to the end of its scope, a block failure stops the flow where it happens. Halt is distinct from both: it is an explicit stop signal carried with its own scope parameter.

**Debug step semantics.** Functions integrate with the platform's step debugger as discrete units. Stepping over a Function instance executes the entire Function invocation (input evaluation, internal execution, output collection, output binding) as one step in the flow the Block sits in; the debugger pauses on the next Block after the Function Block, with the Function's outputs applied. When the paused instance already has a result - Repeat Step ran it, or it failed and caused an error pause - stepping over or continuing does not invoke it again and proceeds from that result. Stepping into a Function instance descends into the Function's inner canvas at the entry point; subsequent step actions advance through the Function's internal Blocks one at a time. Stepping out returns control to the flow the Block sits in at the Block immediately after the Function Block, applying any outputs that have been produced. Breakpoints set on internal Blocks of a Function are honored when that Function is being executed, whichever Function Block runs it.

**Embedded local-function wire format.** Local Functions are not stored in the Functions library; their definitions live inside the owning Test's storage as part of the workflow data. A Local Function instance appears in the Test's workflow as a Block whose type identifies it as a Function and whose data carries the full definition inline (input contract, output contract, internal subgraph, declared dependencies). At load time the platform treats the embedded definition the same way it treats a definition fetched from the library, so the execution path is uniform regardless of state. The wire format distinguishes Local from Published purely by the presence of the embedded definition versus a library identifier reference; everything downstream of the resolver is unified.

**Concurrent invocations.** Two concurrent invocations of the same Function (for instance, two instances reached through parallel branches) operate on independent runtime scopes. There is no shared state between concurrent invocations of the same Function; their inputs are populated from each Function Block's own fields independently, their local variables are isolated, and their outputs are collected and bound back to the scope of each Function Block without crosstalk.

**Drilled-in scoped invocation.** The platform exposes one additional invocation entry point intended for iterative authoring: when the workflow author is drilled into a Function on the workbench canvas and triggers Run Scope (or Debug Scope), the platform invokes only that Function as a discrete unit rather than running the parent Test from the top. This works wherever the Function's instance sits: on the Test canvas, inside any container, or inside another Function's body at any depth; the run identifies the instance by its path of Function instances from the Test canvas. The invocation runs the same pipeline as a normal Function Block run - isolated execution, output collection - but it is not a run from within the flow the Block sits in, so it starts from what the session holds now instead of resolving the Block's fields when the Block runs. When the instance ran earlier in the session, its inputs and outputs start exactly as its most recent run left them, each local variable a block wrote keeps the value it was given, and each local variable no block wrote follows its definition as it stands when the invocation starts, so a value edited after the last run is used. When the Function Block has not run but the flow it sits in has, each input takes the value of the Block's field resolved over that flow's most recent runtime state (the Test's variables, or the enclosing Function instance's last runtime scope), a field not set taking its default. When no run has happened in the session, or the session was Reset, or that flow has no runtime state either, each input and local variable takes its declared default, or null when there is none, and the platform surfaces an advisory note that prior-run state was unavailable. Nothing is reset by starting the invocation: the Test's variables, block states and open SSH sessions, and every Function instance's last runtime scope, carry into it, and what this invocation gives the instance's scope becomes the state the next ad-hoc run starts from. Output bindings are not applied back to the flow the Block sits in (there is no active frame of that flow to bind into); the result document is shown in the workbench's execution panel for inspection. The scoped invocation is an authoring aid; it does not participate in tracked execution history and does not produce a session result equivalent to a Test run.

**Standalone library-View invocation.** The platform exposes the same isolated invocation from the standalone library View, where a Published Function is opened directly from the library with no parent Test. Run (which coincides with Run Scope because the Function is the only scope present) invokes the Function as a discrete unit through the same pipeline. Because there is no Test in this context, there is no prior-run state to source inputs from: each input is materialized from its own value as the Variable Manager shows it (its declared default, or null when there is none), required or not, and outputs are collected into a result document shown in the execution panel rather than bound back to any flow. When the author is in edit mode in the View, the invocation runs the edit-mode draft body rather than a published version, so unpublished changes can be exercised before they are committed. The standalone invocation is an authoring aid: it is ephemeral, does not participate in tracked execution history, and does not require the Function to be saved into any Test first - the platform stages the body for execution on the author's behalf and discards the staging when the session ends.

**Run of the in-memory working state.** Every run entry point - a Test run, a drilled-in Function scoped run, and a run while an instance is in edit mode - executes the author's exact in-memory working state, not the last-persisted definition. When the canvas carries unsaved edits, the platform submits the working copy (the unsaved Test graph, the drilled-in Function body, or the active edit-mode draft) for execution and validates that working copy with the same gate a persisted run uses; the run remains ephemeral and persists nothing. Running the last-saved version instead is reached by discarding the unsaved edits first. This keeps the authoring loop tight: a change can be exercised the moment it is made, without a save or a publish.

**Edit-mode run advisory.** Whenever execution enters a Shared Function instance that is in edit mode, the platform emits a warning log line for that instance noting it is running an unpublished draft and is unlinked from the shared library. The advisory makes the divergence from the published version explicit in the run output, so an author exercising a draft is reminded the changes are not yet committed to the library.

##### REQ-3.2.1.2 Debug mode for the standalone Function View

The standalone library View integrates with the platform's step debugger on the same terms as any other canvas. Debug starts the same isolated invocation that Run does - declared-default inputs, ephemeral staging, no tracked history - but under debugger control: breakpoints set on the Function's internal Blocks are honored, execution pauses at the first breakpoint or first Block per the active debug options, and the step controls (continue, step over, step into, skip-at-pause) advance through the body exactly as they do inside a Test. The Variable Manager and console re-scope to the Function's parameters and local variables while paused, so the author inspects the in-flight state of the isolated invocation. Edit-mode debugging runs the draft body, letting the author step through unpublished changes. Because the invocation is ephemeral, a debug session in the View leaves no execution record and does not alter the library entry.

##### REQ-3.2.1.3 Step Over and Step Into for Function instances

On the canvas it sits in, a Function Block is a single-egress composite: it has one entry and one sibling-after egress, the same shape the step debugger already handles for loop, parallel, and try/catch parents. The step controls treat a Function instance on those terms.

**Step Over.** Stepping over a Function instance executes the entire invocation - input evaluation, internal execution, output collection, output binding - as one indivisible step in the flow the Block sits in. Breakpoints on the Function's internal Blocks are suppressed for the duration of the step. The debugger re-pauses on the Block immediately after the Function instance (its sibling-after egress), with the Function's outputs already applied to that flow's scope. When the instance already has a result from Repeat Step or an error pause, Step Over does not run the invocation again: it proceeds from that result, down the normal path when it passed and down failure routing when it failed.

**Step Into.** Stepping into a Function instance descends into the Function's inner canvas: the active canvas swaps to the body and the breadcrumb extends, mirroring a manual drill-down, and execution pauses at the first inner Block. Subsequent step actions advance through the body one Block at a time, honoring nested Functions (a step into a nested Function descends another level). When the body reaches its terminal Block, control returns to the flow the Function Block sits in at the sibling-after egress and the canvas pops back out. Step Into descends even when the instance already has a result from Repeat Step or an error pause; the body runs again step by step and that run's outcome replaces the earlier result. Stepping into a Function whose body is empty degrades to a step over - there is no inner Block to pause on, so the debugger pauses at the sibling-after egress.

**Canvas follows execution.** While debugging, the active canvas tracks where execution is paused: when a step or a continue lands the pause inside a Function body, the canvas is that Function's inner canvas with the paused Block highlighted; when execution leaves the body, the canvas pops back to the parent. This descent-and-ascent reuses the same drill machinery as manual navigation and extends to any nesting depth. Descending into a Published Function during debug is read-only, identical to its inspect view; breakpoints toggled there live on the instance.

**Skip-at-pause.** Skip-at-pause on a paused Function instance routes past the whole body to the sibling-after egress, marking the body's Blocks skipped - the same single-post-control-egress routing applied to loop, parallel, and try/catch parents. Because a Function has exactly one egress, skip never raises the diverging-parent conflict that if/else, switch, and assert-split parents do.

**Ad-hoc execution on a Function Block.** Run Current and Debug Current on a Function Block invoke only that Function as a discrete unit, resolving the Block's fields against the most recent runtime state; like any Function Block run, the invocation opens a fresh runtime scope, so its local variables start at their defaults even when an earlier run left them changed. Run from Here and Debug from Here start at the Function Block and continue through the rest of the flow it sits in.

**Ad-hoc execution inside a Function body.** Run Current and Debug Current on a block inside an opened Function body, at any depth, run that block - with the sub-tree the single-element boundary rules give it - inside that Function instance. Run from Here and Debug from Here on a block inside an opened Function body start at that block and run through the rest of that Function body; they do not continue into the flow the Function Block sits in. The run identifies the block by the path of Function instances from the Test canvas plus the block's own id. It starts from the same state as the drilled-in scoped invocation: the instance's inputs and outputs as its most recent run left them, its local variables with the values blocks wrote into them and otherwise with their definitions as they stand, otherwise the Function Block's field values over the last state of the flow it sits in, otherwise declared defaults with the advisory note after a Reset or when no run has happened. Where the run ends, the instance's inputs, local variables and outputs it produced become the state the next ad-hoc run starts from; output bindings are not applied to that flow. Inside a Remote Execution body - a body in the Function, or a body around the Function's instance - the run follows the Remote Execution rules for a run that starts inside a body.

##### REQ-3.2.1.4 Repeat Step on a paused Function

When execution is paused on a Function instance about to be invoked, Repeat Step re-executes that invocation and re-pauses in place, identical to Repeat Step on any other Block. The re-run does not roll back what the prior invocation did - its variable writes and other side effects stay. It runs the invocation again as a unit from the state as it now is and leaves the pause cursor on the Function instance, so the author can re-observe the Function without restarting the whole Test.
