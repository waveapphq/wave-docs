#### 3.5.5 Function Validation and Integrity

Function validation enforces that a saved Function is internally consistent and externally usable. Validation runs at composition time (when the Function is saved or modified) and again at runtime (when the Function is invoked). The two phases share their underlying rules; the composition-time pass catches errors early so authors fix them in the editor, while the runtime pass guards against any drift that might have been introduced after the composition-time check (a referenced Function or plugin removed from the library, for instance).

##### REQ-3.1.2.4 Function validation before save

Save-time validation rejects a Function definition that is structurally incomplete or semantically inconsistent. The validation pass produces a list of findings categorized as errors (blocking) or warnings (advisory but non-blocking). A Function with any errors cannot be saved; a Function with only warnings is saved but flagged in the authoring UI so the author is aware.

**Required-field validation.** The Function must have a name conforming to the project's naming convention, a non-empty internal subgraph (at least an entry point and one Block, depending on the chosen composition rules), and a fully described input and output contract. Each input and output entry must carry a name, a type from the supported type set, and the optionality flag (for inputs). Missing or malformed metadata produces structural errors.

**Reference existence checks.** Every plugin used by an internal Block must resolve against the plugin registry. Every Published Function used by an internal Function Block must resolve against the Functions library by identifier. Unresolved references produce errors identifying the missing entity and the internal Block whose reference is broken. References to Local Functions are validated against the owning Test's embedded definitions.

**Field completeness.** Every Block inside the Function - plugin, control or Function Block - is checked by the same per-Block field check as at the Test root. A Function Block's fields are the declared inputs of the Function it runs, so a Required input left not set is an error exactly like a required plugin setting; a Required input's default never counts as set. A value or expression present must be well-formed, and a stored field the Block does not declare is an error. An optional field left not set takes its default when the Block runs, or null when there is none, and is not an error (see REQ-3.1.3.21).

**Type compatibility of fields.** Each field's value must be compatible with the type declared on the field, checked by the same check every Block gets: type fit, allowed values, and minimum and maximum, with one set of messages. Compatibility is exact match for primitive types and structural conformance for collection and tabular types. A literal that does not fit is a composition-time error; an expression is reported when its result type can be inferred, and is otherwise checked once it is evaluated when the Block runs. Each output binding's destination is checked against the declared output type, for Function Blocks as for plugin Blocks.

**Unused parameter warnings.** An output no block in the Function writes returns its default, or null when there is none, so the Function Block's output binding may behave unexpectedly; an input no block uses means the Function is unfinished or wrong. Both are reported as a warning in the run log on every run of a Function Block (REQ-3.1.2.7), never in the Function editor, and neither blocks saving, running or publishing the Function, because a contract may legitimately precede the implementation that fills it.

**Variable scope discipline.** Internal Blocks that reference variables must reference only names declared in the Function's scope: its declared inputs (read), its declared outputs (read or write), and its own local variables. References to external scopes (system, regression, suite, the Test around the Function) are errors. Writes to a declared input are errors. This enforces the isolation contract at validation time so violations are caught before they reach runtime.

**Circular dependency detection.** When a Function is being saved into the Published library, the Function's transitive dependency graph is recomputed and checked for cycles among Published Functions. A cycle produces a save-blocking error that names the participants and the path. Local Functions are exempted from this check because they cannot participate in library-scope cycles by definition.

**Self-reference and circular nesting.** Beyond the library-scope cycle check, the platform refuses to compose a Function into itself - directly or transitively - at the moment the nesting is created on the canvas, not only at publish time. Dropping a Function into a body that is the same Function, or into a body that already contains it anywhere in its subgraph, is rejected with a message naming the offending Function. The same self-referential structure is independently caught by the recursive validation descent, so a cycle introduced by any other path (import, hand-edited file) is reported as an error rather than walked without bound. This complements the library-scope circular-dependency check: that check governs published entries, while this guard governs the composition graph as the author builds it.

**Flow consistency.** The internal subgraph must form a valid workflow: every Block reachable from the Function's entry, every edge connecting compatible Block ports, every control flow construct properly paired (try with catch, loop with body). Structural workflow validation reuses the same logic the platform applies to Test workflows; Function authoring inherits the Test workflow rules.

**Errors versus warnings.** Errors block save: a definition with errors does not reach storage. Warnings do not block save but are surfaced prominently in the authoring UI and persist with the definition so they are visible when consumers inspect the Function. The distinction follows the principle that the platform refuses to persist a broken definition but does permit definitions with advisory concerns the author has chosen to accept.

**Runtime revalidation.** When a Function is invoked, the platform revalidates the parts of the contract that could have drifted since save: reference existence, plugin and Function registry membership, and field type compatibility for values that were not statically resolvable at save time. Runtime validation failures abort the invocation with a clear error and do not produce partial execution side effects.

**Canonical validation pipeline.** A single validation pass underlies every surface that checks a Test: explicit Validate, Save, Load, Import, and Run all route through the same Block-walking pipeline, so a definition one surface accepts no other surface silently rejects. The pipeline is the single point at which structural, reference, field, scope, and version checks are applied, and it produces one findings list (errors and warnings) regardless of surface.

**Recursive descent and the issue path.** The pipeline descends Function bodies to any nesting depth. A Local Function embedded in a Test is walked into; a Local Function embedded inside that body is walked into in turn, with a defensive depth bound that protects against pathological or self-referential structures. Every finding carries the location trail from the root canvas to the element that produced it: an ordered path of the enclosing Functions and the offending leaf, each entry identified by its on-canvas identity and label. The trail excludes the regression, suite, and test ancestors, which are implicit. A Function that merely contains failing descendants is not itself a finding; only true leaves and the Functions that directly fail report a row. A reference to a Published Function inside a path is identified by its library Function name, not the Function Block's label.

**Save and Run consistency.** The reference and expression-resolution checks that determine whether a Test can execute are applied at save time as well, so a Test that saves cleanly cannot fail validation only at Run. The set of checks is identical across the two surfaces; the only difference is the moment of evaluation.

**Function-scope references.** Inside a Function body the only names in scope are the Function's declared inputs, its declared outputs, and its own local variables; external scopes (system, suite, regression, and the Test around the Function) are invisible. A reference that does not resolve within that scope is an error whose message names the isolation boundary, so a no-code author understands that the missing name must be declared as an input, output, or local rather than inherited from the Test.

**Ancestor alert propagation.** When a Test loads, the alert state of any failing element propagates up its chain of enclosing Functions to the root canvas. An outer Function carries an alert whenever any element within it, at any depth, has an issue, and an element that fails in its own right also carries the alert. The author therefore sees at the top level which Functions contain problems before drilling in.

**Shared-instance contract resolution.** A reference to a Published Function resolves its input and output contract from the specific pinned version in the library, and that resolved contract is the Function Block's field list, checked by the same field checks applied to Local Functions and to every Block. A variable produced from a Shared Function Block's output binding takes the declared type of that output rather than defaulting to an untyped value.

**Publishing a body that contains an edit-mode draft.** A Function cannot be published while any Function nested in its body is itself an unresolved edit-mode draft. Freezing such a body would capture work-in-progress inside an immutable version, so the recursive validation descent treats a nested edit-mode draft as a publish-blocking error and directs the author to resolve the nested draft - by publishing or dropping it - before the outer publish proceeds.

##### REQ-3.1.2.7 Run-log warning for an unused input or an unwritten output

The warning is about the Function's definition, not about one Function Block, so every run of a Function Block writes a warning-level entry to the run console log for each input no block in it uses and for each output no block writes, whatever the Function Block sets and whether or not the parameter has a default. The entry names the parameter and the Function, and its source is the Function Block. It is printed once per run, when the Function Block starts and before its fields are resolved, so a run that is refused or whose body fails still shows it. Local and Published Functions alike carry it, and the Function editor shows nothing for it.

An input counts as used when a block that is not muted reads it: an expression or a `{{ }}` piece in a setting, an entry of a map or list setting, a reference setting, a condition row, a Variable Setter row, or a field of a nested Function Block, and equally when a Function-local Expression or Template variable or an Expression or Template output names it. A name that only appears inside a quoted string does not count. An output counts as written when a block that is not muted assigns it, through an output binding or a Variable Setter row that targets it, and an Expression or Template output counts as written by its own kind (REQ-3.1.2.8). A muted block counts as neither a use nor a write, because it never runs; a block that no path reaches still counts, since an unreachable block is reported as an error of its own (see Flow consistency). A null value an output legitimately returns, such as a null cell from a query, is never a reason to warn.
