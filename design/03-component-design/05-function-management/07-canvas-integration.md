#### 3.5.7 Function Canvas Integration

Function instances participate in the visual workflow builder on equal footing with plugin and control instances. A Function instance is a Block on a canvas; it has the standard canvas affordances (placement, configuration, connection, deletion, copy and paste) and adds the Function-specific affordance of drill-down to inspect or edit the Function's inner canvas. The visual model treats Functions as composable units of intent the workflow author manipulates without leaving the parent canvas unless they choose to.

##### REQ-3.1.1.4 Nested Function composition (drill-down navigation)

A Function instance on a canvas is openable: the workbench canvas swaps in place to display the Function's inner canvas as the active view. The workbench page, palette, action bar, console, and Variable Manager all remain mounted; only the canvas content (the set of Blocks and edges) changes. The same canvas instance hosts every level, so the workflow author moves between the parent Test and its nested Functions without a page reload and without losing the viewport's zoom and pan state at each level.

The drill-down affordance is exposed in three converging ways on every Function instance: a glyph on the Block body, a menu entry on the instance's kebab menu, and a keyboard shortcut on the selected Block (REQ-4.2.5). All three perform the same action.

The canvas breadcrumb above the workbench tracks the active navigation path. Function segments are appended to the breadcrumb after the Test leaf, in descent order. Each Function segment is visually distinguishable from entity-list segments (suite, regression, test) so the workflow author can read the path at a glance: the leftmost segments come from the workbench's navigation origin (e.g. the suite or regression the test was opened from), the next segment is the Test, and the trailing segments are Functions descended into. Clicking any parent segment swaps the canvas back to that level; the segments to the right of the click are removed from the path.

Drill-down is recursive: a Function instance inside a drilled-into Function may itself be drilled into, and so on. The breadcrumb extends with each descent and contracts with each pop. There is no artificial cap on nesting depth.

Drilling into a Local Function opens an editable inner canvas (the same affordances - drop Blocks, draw edges, configure, delete - work exactly as they do at the Test level). Drilling into a Published Function opens a read-only inspect view; the canvas renders the Published Function's inner workflow without authoring affordances - Blocks, edges, Block fields, and the declared input/output schema are all read-only, and the create-parameter and variable-creation surfaces are suppressed rather than merely disabled. The inspect view still runs: right-clicking a Block there opens a menu with only its run and debug items (Run Current, Run from Here, Debug Current, Debug from Here, Toggle Breakpoint).

The back-arrow on the canvas breadcrumb is drill-aware. When the drill stack is non-empty, the back arrow pops one drill level (equivalent to clicking the segment immediately to the left of the leaf). When the drill stack is empty, the back arrow navigates to the workbench's originating page (e.g. the suite or test list the workbench was opened from). This gives the workflow author a single consistent affordance for "go back one step" whose meaning adapts to whether back means "up one Function" or "out of the workbench."

Run and Debug from the workbench action bar follow the active canvas. Run All - whether the active canvas is the Test or any drilled-in Function - always executes the parent Test from the top with a full reset of session state. Run Scope is canvas-sensitive: at the Test level it is equivalent to Run All (the Test is the current scope, so "run the scope" and "run all" coincide); while drilled into a Function it executes only that Function as an isolated invocation, wherever the Function's instance sits - on the Test canvas, inside a container, or inside another Function's body at any depth. The isolated invocation starts from the session's current state so the workflow author can iterate on a single Function's body without re-running upstream Blocks: the Function's inputs and outputs start as the Function Block's most recent run left them (or, when the Function Block has not run, its inputs take the values its fields give over the last state of the flow the Block sits in, a field not set taking its default), a local variable a block wrote keeps that value, and a local variable no block wrote follows its definition as it stands when the invocation starts, so an edit made after the last run is used. After Reset, or when nothing has run in the current session, the isolated invocation initializes the Function's inputs and local variables from their declared defaults, except a Current value the author set before the run, which is the value the run uses, and surfaces an advisory note that prior-run state is unavailable; a Required input with no value stops the run and names it (REQ-3.1.2.10). The right-click Run Current, Run from Here, Debug Current and Debug from Here on a block inside the drilled Function body follow the same rules: they run inside that Function instance, starting from its current state. None of these runs resets anything; Reset is the way to start clean. The drill state also re-scopes the Variable Manager to the drilled Function's parameters and local variables and filters the console to log lines emitted from within that Function's scope.

Edits made while drilled into a Local Function become part of the parent Test's dirty state. Saving the Test (the standard Save action) persists every nested edit at every depth in one operation. Popping back out of a Function is non-destructive: in-memory edits remain in the Test's dirty state until the Test is saved or discarded.

**Standalone library View.** A Published Function can also be opened directly from the shared library, with no parent Test. The library entry's detail surface offers a View affordance that opens the selected version's body in the workbench canvas as a read-only inspect view, reusing the same drill machinery the in-Test inspect view uses. Because there is no Test, the canvas breadcrumb shows only the Function, and the back affordance returns to the library detail surface rather than popping to a Test root - so the author can switch the viewed version on the detail surface and re-open the canvas. The open Function behaves as the workbench's open entity for lifecycle purposes: its clean-or-dirty state, the close affordance, and switching to another entity follow the same rules a Test does, and closing the View while an edit-mode draft is active - even one with no changes yet - first shows a notice titled "Function still in edit mode" with the text "Leaving the View drops this Function's unpublished draft."; OK closes the View and drops the draft, while Escape or the backdrop keeps the View and its draft. Only Close asks; any other way out of the View keeps the draft. From this View the author can Run and Debug the Function in isolation and can enter edit mode to revise and publish it, exactly as when drilled into a Published instance inside a Test. The only differences follow from the absence of a Test around the Function: its inputs start from their declared defaults, or from a Current value the author set before the run; a Required or secret input has no default, so the author sets its Current value (REQ-3.1.2.10), and publishing has no Function Block to re-pin, so the publish confirmation is a single outcome and the View switches to the newly published version.

**Visual distinction of Function instances.** Function instances are styled to be clearly distinguishable from plugin and control instances. The styling does not depend on the Local or Published state; from a layout perspective both look the same on the canvas, because the workflow author's mental model is "this is a Function I composed or imported." The state distinction surfaces in the authoring affordances (mutable inner canvas versus read-only inspect) rather than in the Block's silhouette.

**Palette affordances for Function authoring.** The workbench palette exposes two Function-specific affordances at its bottom action area, reachable from both expanded and collapsed palette modes. The first is a drag handle for creating a new local Function: dragging it onto the canvas inserts an empty local Function instance; clicking it without dragging surfaces a brief tooltip describing the drag affordance. The second is a button that opens the shared Function library. Function discovery is intentionally not rendered as an inline palette section because a flat list does not scale to a populated library and would crowd the existing palette regions reserved for plugins and control flow.

**Function library access in the workbench.** The shared library is presented as a non-blocking, draggable floating panel that the workflow author opens over the canvas while continuing to interact with the canvas behind it. The panel exposes free-text search across Function names, descriptions, and tags, plus a tag filter with multi-select intersection semantics. Each library entry renders as a card carrying its name, a brief description, and its tag chips; the card is itself the drag source, and dropping it on the canvas inserts a published Function reference at the drop position. The panel closes via its dismissal control or the standard cancel key. A separate management surface in the dedicated Functions library page handles deeper concerns such as publishing new versions, inspecting dependents, and bulk operations; the in-workbench panel is intentionally a lightweight browser optimized for the "find a Function and drop it in" path.

**Local Function naming.** Newly-created local Functions receive an auto-generated name of the form `Function_N`, scoped to the owning Test's workflow. The counter advances past names already taken by other Function instances inside the same Test so the user does not encounter naming collisions immediately on creation.

##### REQ-3.1.1.5 Function instance parameter configuration

Each Function Block on a canvas opens the same Block configuration window as a plugin or control Block: the same dialog shell, the same field rows for its inputs and output variables, the same one value field with expand and {x} (FIELD-1), the same save and cancel affordances, the same unsaved-changes confirmation flow. A workflow author who has used a plugin's window can use a Function Block's window without learning a new mental model; the only parts a Function Block adds are its lifecycle parts: the From library link, the version list, the library footer actions and the missing-version banner.

The window opens the way it does for any Block (double-click on the body or the gear glyph in the action cluster). It is one window for every Block: a Function Block's field list is the declared inputs of the definition it runs - the embedded definition of a Local Function, the edit-mode draft, or the pinned version of a Published Function - and its lifecycle parts are added to that window rather than drawn by a separate body.

**Local versus Published presentation.** The entity icon in the window title identifies the Block as a Function; the lifecycle badge - `L` for Local, `S` for Shared (Published) - is not repeated inside the window, since it lives on the canvas Block where the lifecycle matters (CANVAS-208, CANVAS-209). The name field is editable on both states: a per-instance label seeded on drop from the Function's name (auto-suffixed with `_N` when the base name already exists on the canvas) and renamable thereafter; renaming an instance never mutates the library entry, and on a Published instance a From-library link beneath the name preserves the link to the source library entry after the instance label diverges from it. The two states differ in two places: the version selector is hidden on Local and present on Published (Local Functions have no version concept); the footer adds a Changelog control and a Details control on Published (both pivot off the version history that Local Functions lack). Both variants carry the Profiles button, which opens the same profile binding sheet a plugin Block uses (CANVAS-214, FN-LC-9).

**Per-instance description.** Both Local and Published variants render the description field as a per-instance editable text area at the top of the body. Editing the description on a Published Function Block updates only this Function Block; it never mutates the library entry's description, which lives on the Published Function definition itself. The semantics match the description field's behavior on plugin instances.

**Input fields.** A Function Block's fields are the Function's declared inputs, read from the definition it runs (the embedded definition for a Local Function, the pinned version for a Published one), and they are stored, edited, checked and run by the same Block code as a plugin's settings. Each declared input renders as one row with name, type label, required marker and the one value field (FIELD-1), which opens in literal mode as the widget of the input's type, as a plugin field does; a value holding an expression opens in {x} mode with its text unchanged, completing the names in scope where the Block sits. Templates on text inputs, per-entry expressions in list and map inputs, and typed list and map items work as on any Block. The default rule is the shared one (FIELD-2): a free-entry input that is not Required and has a default shows that default in gray in either mode; a Required input's default is never shown, since the Function Block must set the value (VMGR-113); switching modes copies nothing in (FIELD-7), Save stores only what the author set, and the run fills a field not set from the input's default - the pinned version's default for a Published Function, and never a Required input's default. A Required input with no default shows an empty field; an optional input with no default can be null and shows the gray `null` with the null icon (FIELD-5). A row marked required that holds nothing produces a validation error. An enum input is a choice list of its allowed values, like a block setting with fixed choices, with {x} beside it; like a true / false input, it holds the Function's default from the moment the Block is created, Required included (FIELD-8, FNCFG-6, VMGR-112, REQ-3.1.2.11). A secret input renders as a block's secret field - masked and write-only, with the lock icon and {x} (FNCFG-7, REQ-3.1.2.9). When a Local Function's inputs change so that a Block's stored value breaks - the input is retyped, or its allowed values no longer hold the picked value - the value is dropped from every Function Block of that Function and the field is left empty; a literal that still fits stays, and an expression is kept and judged only when the run starts. A new choice-list or true / false input starts on its default on every Function Block, written at that moment, and a new free-entry input starts not set; a dropped value leaves the field empty with the required error, never switching it to another value. Any Required field left empty shows the Block's alert icon, and a rename carries the value to the new name. Switching a Block to another Published version applies the same rule (FNCFG-9).

**Outputs.** The output variables table is sourced from the Function's declared outputs, the same output table a plugin Block has. Each declared output renders as one row with name, type label, and an "Assign to" cell that picks (or creates) a variable in scope where the Block sits to receive the value at return. The picker is filtered by type compatibility and offers a "create new variable" affordance when the author types a name that does not yet exist in scope; a variable created this way takes the output's type and holds null until the Function returns. Outputs are not required to be bound; an unbound output is discarded on return and produces no validation error. An output declared secret seeds its row's Secret box ticked, and the author may untick it; a new variable typed into a ticked row is created secret, and an existing plain variable becomes secret on Save after a warning that names it (FNCFG-7, REQ-3.1.2.9, REQ-4.5.20).

**Empty section presentation.** A Function may declare zero inputs (or zero outputs). When a section's contract is empty, the section header is still rendered so the modal's shape remains predictable, and the body of the empty section contains a single italic muted line ("This Function declares no inputs." or "This Function declares no outputs.") between top and bottom dividers. This communicates to the reader that the absence of rows is intentional rather than a rendering bug.

**Read-only schema in Published instances.** Inside a Published instance's modal, the input and output rows display the name and type as read-only labels; only the value cell (for inputs) and the "Assign to" cell (for outputs) are editable. The schema is locked by publication; adjusting it requires editing the library entry, not the Function Block's field.

##### REQ-3.1.2.10 Values for a Function run on its own

When a Function runs alone - Run Scope or a block run while drilled into it - each input takes the Current value the Variable Manager shows for it when the run starts. A Current value the author set before the run, in the variable's window with its value switch on Current (VMGR-108), is the value the run uses, also right after Reset, which otherwise brings the input back to its declared default. A Required input's default, when it has one, serves only such a run and never a Function Block; a Required input with neither a default nor a Current value stops the run before the first block, and the run names the input (FNCFG-8, VMGR-113).
