#### 3.5.4 Function Dependencies and Resolution

A Function's implementation may invoke plugins, controls, and other Functions. Those invocations form a set of declared dependencies that describe what the Function requires in order to be loaded, validated, and executed. The dependency model is explicit and inspectable: every external reference a Function makes is recorded in the Function's metadata so that consumers and tooling can reason about reachability and integrity without scanning the entire subgraph.

##### REQ-3.1.2.3 Function dependency specification

Functions declare their dependencies as part of the Function definition. Two dependency categories exist: plugin dependencies enumerate the plugins the Function's internal Blocks use; Function dependencies enumerate the other Functions its internal Function Blocks run. Both categories are derived from the Function's subgraph at save time and stored alongside the definition for fast reference.

**Plugin dependencies.** Each plugin invoked anywhere in the Function's subgraph contributes a plugin dependency entry. The entry records the plugin's stable identifier as understood by the plugin registry. Plugin dependencies surface when the Function is loaded: the platform verifies that every dependent plugin is present and reports any missing plugins as validation errors before the Function is permitted to execute.

**Function dependencies.** Each Published Function invoked anywhere in the Function's subgraph contributes a Function dependency entry. The entry records the Published Function's library identifier. Local Functions invoked from within a parent Function are not Function dependencies in this sense: they are embedded definitions, not references, and travel with the parent Function's own definition. Only Published Function references produce dependency entries, because only those references rely on the existence of an external library entry.

The Function dependency entries are derived from the subgraph whenever a Function is published or imported; a list of Functions supplied by a client or a file is never taken as given.

**Transitive resolution.** When a workflow executes a Function, the platform resolves the Function's direct dependencies, then the dependencies of those dependencies, and so on. The full transitive closure of Function and plugin dependencies must resolve successfully before execution proceeds. If a transitively required Published Function or plugin is missing, the Function fails to load with an error identifying the missing dependency and the path through which it was reached.

**Circular dependency detection.** A Published Function must not, directly or transitively, invoke itself. The dependency graph among Published Functions is a directed acyclic graph; cycles are detected at save time when a Published Function's definition is added to or updated in the library. Attempting to publish a Function whose subgraph would introduce a cycle is rejected with a validation error that names the cycle's participants in order. Local Functions are exempt from cycle detection on their own because a Local Function cannot be referenced by anything outside its owning Test; the rule binds when the Function becomes Published.

**Usage surfacing in the library.** The Function detail page surfaces, per version, the consumers that reference that specific version: the Tests whose canvas pins it and the Published Functions whose body references it. Usage is presented as a count with a click-through list and is informational rather than a gate. Deletion - of a single version or of the whole Function - is always permitted regardless of usage; removal never cascades into or mutates the consuming Tests. A consumer left pinned to a removed version is not silently broken: the version-availability validation surfaces a missing-version alert on that consumer's load, save, and run, so the author resolves or re-pins it deliberately.

**Dependency drift on detach and publish.** When a Local Function is detached from a Published Function, the detached copy inherits the Published version's dependency declaration. As the author edits the detached copy, its dependency set may change (new plugins introduced, new Function references added or removed). When the edited copy is subsequently published as a new library entry, the new entry's dependency declaration reflects the edited subgraph; it does not inherit the original Published version's dependency list.

**Responsibility for the fields of each Block.** Dependency declarations cover what a Function references; the Function is also responsible for setting the required fields of each internal plugin Block and Function Block. Validation of those fields is covered under composition-time validation, not under the dependency declaration itself. The dependency entry says "this Function runs Function X with library identifier id-of-X"; it does not say how X's inputs are set, which is held in the fields of that Function Block.
