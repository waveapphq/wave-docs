#### 3.5.1 Function Composition and Parameterization

Functions are composed from plugin invocations, control flow elements, and other Functions, arranged into a directed subgraph with a single declared entry and a defined set of declared outputs. The composition model mirrors the workflow model used at the Test level: Blocks connected by edges, with flow semantics consistent across all levels of nesting. The distinguishing characteristic of a Function is its declared parameter contract, which specifies the typed inputs the Function accepts and the typed outputs it produces.

##### REQ-3.1.2.1 Create custom Functions with input parameters

Functions support input parameter declarations enabling their use as parameterized templates rather than fixed workflows. The parameter mechanism aligns with the plugin parameter system so workflow authors reason about a single type model across plugins, controls, and Functions.

**Input parameter declaration.** Each input parameter is described by an identity (name), a type classification, an optionality flag, an optional default value, and descriptive metadata. The type classification covers primitive types (string, integer, float, boolean) for scalar values; ordered list types (array) for homogeneous sequences; key-value types (map) for structured records; and tabular types (table) for two-dimensional matrices. Optional parameters carry default values that apply when a Function Block leaves the field not set. Required parameters must be set on every Function Block and surface as validation errors when missing; a Required parameter may still carry a default, which serves only when the Function runs on its own, never a Function Block (REQ-3.1.2.10), except that a choice-list or true / false input starts on its default when the Block is created (FIELD-8). The input rule is the same for a literal and an expression: a field that gives null fails the Function Block for a required or defaulted input and names the input; only an optional input with no default takes null, and a null item, map value or table cell inside an input reaches the Function as null. WAVE checks this when the Function Block runs, before the first block of the Function runs, so the Function needs no check of its own (see REQ-3.1.3.21). An input's declared default is always literal: a plain value, never an expression; the Function Block's field for that input holds a literal, a template or an expression like any Block field.

**Output parameter declaration.** Each output parameter is described by an identity (name), a type classification, a kind, a default value, and descriptive metadata. Outputs offer the same kind choice as a variable: Literal, Expression, and Template for text (REQ-3.1.2.8). Outputs are produced by the Function's internal logic during execution by assigning to the output's declared name; the runtime reads the final value on return and makes it available to the flow the Function Block sits in. Outputs that the Function's body does not assign during a particular run hold their declared default, or null when there is none, which reaches that flow through the Function Block's output bindings.

**Inputs as the Function Block's fields.** A Function Block's fields are the Function's declared inputs, held and edited like any Block's settings: a literal, a template on a text input, an expression over the variables visible where the Block sits (system, regression, suite or test scope, or the enclosing Function's scope), or per-entry expressions in a list or map. A field not set takes the input's default when the Block runs. The fields are evaluated in the flow the Block sits in when the Block runs; the resulting values populate the corresponding inputs inside the Function for that run.

**Output bindings on the Function Block.** Outputs returned by the Function are routed back through the Function Block's output bindings, the same output table a plugin Block has. Each output binding names a destination variable in scope where the Block sits (a test-scope variable, for instance) and the source output from the Function's declared outputs. After the Function returns, WAVE reads the declared outputs and applies the bindings, writing the produced values to the destinations the Block names.

**Type compatibility.** Each Function Block field is checked against the declared type of its input by the same check every Block's fields get: a literal when the Block is saved, an expression once it is evaluated, before the Function flow runs. The type of each output binding's destination is checked against the declared type of the corresponding Function output. Type mismatches surface as validation errors on save wherever the type can be determined statically, and as run errors when an expression's type is only knowable at execution.

**Enum-constrained parameters.** An input whose type is string, integer or float may be marked as an enum: the input's value space is restricted to a fixed list of literal values of that type, and there is no array enum (VMGR-112). The allowed-values list is part of the declaration. On a Function Block, an enum input is a choice list over the allowed values, holding the input's default from the moment the Block is created, with {x} beside it (FIELD-8); a picked value is checked when the block is saved, a variable or expression when the run starts, and a value outside the list fails the Function Block and names the input (REQ-3.1.2.11). Enum inputs are always required (the Function Block must give one of the listed values), never null and never secret, and carry a required default that is one of the allowed values.

**Parameter flow into the Function's body.** Inside the Function, declared inputs are exposed as read-only named variables in the Function's scope; declared outputs are mutable named variables in that same scope. The Function's internal Blocks reference both by bare name, exactly the way they reference local variables. The Function author maps inputs to internal Block fields and internal results to outputs, producing a self-contained component whose external contract is fully described by its declared inputs and outputs.

**Function-local variables.** A Function's own local variables are part of its definition: publishing, every published version, loading a Test and detaching a Published Function keep them with the body. A local secret variable's value is sealed at rest like a Test's secret variable (REQ-4.5.1), and a local Expression or Template variable is evaluated like a Test's (REQ-3.1.3.13, REQ-3.1.3.15).

**Self-documentation through the contract.** Because the input and output contract is part of the Function definition, workflow authors who instantiate the Function see its parameter list and types without examining its internal implementation. The composition surface is the parameter list; the implementation is encapsulated behind it. This makes Functions readable as units of intent at the parent canvas level.

##### REQ-3.1.2.8 Function output kind

An output offers the same kind choice as a variable: Literal, Expression, and Template for text; an input's declared default is always literal. An Expression or Template output acts like a Function-local expression or template variable: it is evaluated at its first read or when the Function returns, whichever comes first, evaluated once and kept, and any write by a block replaces it. It counts as written for the run-log warning (REQ-3.1.2.7). An Expression or Template output whose evaluation fails when the Function returns, or a Template output with a `{{ }}` piece whose result is null, fails the Function Block and names the output. Saving a Function checks every name an Expression or Template output reads against the Function's scope and refuses an output that reads itself.
