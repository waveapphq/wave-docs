### 3.5 Function Management

The function management subsystem provides capabilities for composing, validating, and reusing parameterized subgraph components. Functions encapsulate sequences of plugin invocations, control flow elements, and nested Function Blocks into named, type-checked units that workflow authors place the same way they place any other Block. A Function presents an external interface of declared input parameters and declared output values; its internal implementation remains encapsulated behind that interface.

**Position in the component hierarchy.** WAVE workflows are assembled from three Block kinds: plugins, controls, and functions. Plugins are atomic executors implemented in the platform (SSH, Kubernetes, HTTP, and similar). Controls express flow primitives (loops, try-catch boundaries, conditional gates). Functions are user-authored compositions of plugins, controls, and child functions, exposed through a typed parameter contract. For the workflow author, dropping a Function onto a canvas is identical to dropping a plugin or control: the same configuration window, the same fields and output bindings, the same lifecycle.

**Two lifecycle states.** A Function exists in exactly one of two states at any moment. A Local Function is a definition embedded inside an owning Test's storage; it is mutable, has no identity outside its owning Test, and exists to support iterative authoring of behavior that does not yet belong in the shared library. A Published Function is an immutable entry in the shared Functions library; it is referenced by identifier from any Test that wishes to use it. The two states share a single schema; the storage location and mutability rules differ.

**Variable isolation.** Inside a Function three categories of variables are visible: declared inputs (read-only, set by the Function Block's fields; an optional input the Block leaves not set takes its default, or null when it has none, and a required input must be set; see REQ-3.1.3.21), declared outputs (mutable, propagated back to the flow the Function Block sits in on return), and locals (mutable, scoped to this Function invocation). External scopes (system, regression, suite, and the test scope around the Function) are not visible inside a Function. Variables are referenced by name without any namespace prefix; the runtime resolves each name against the Function's declared schema and enforces direction. Any data the Function needs from outside is bound explicitly through its inputs; any data it returns flows out through its outputs and is applied to the flow the Block sits in through the Function Block's output bindings.

**Value semantics.** A Function Block's run copies values from the flow it sits in into the Function's input variables; the Function does not see that flow's variables by reference. Function outputs are read on completion and applied to that flow through the Block's output bindings. Function-internal mutations never affect that flow, and changes in that flow during Function execution never affect the running Function.

**Type validation.** Functions declare typed input and output parameters. Type compatibility between a Function Block's fields and the Function's declared types is enforced by the same field checks every Block gets, when the Block is saved and again when it runs. Type mismatches surface as validation errors before execution begins where possible, preventing classes of late-stage failures.

**Drill-down navigation.** A Function instance on a canvas is openable: the parent canvas swaps to display the Function's inner canvas, with breadcrumb navigation tracking the path. Local Functions are drilled into the owning Test; Published Functions are drilled into a read-only inspect view of the shared definition. Nested Function instances are drillable to arbitrary depth, with each level of drill preserving the parent context.
