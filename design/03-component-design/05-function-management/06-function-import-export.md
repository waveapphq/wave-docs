#### 3.5.6 Function Import and Export

Functions move between WAVE installations and into version control through import and export. The format is structured and self-contained: an exported Function carries its full definition, declared dependency list, and metadata, so an importing installation has everything required to reason about the Function before deciding to accept it.

##### REQ-3.1.2.5 Import and export Functions as files

Export produces a serialized representation of a Function definition that round-trips through import without loss. Import validates the incoming definition before it lands in the library and offers explicit conflict resolution when an incoming Function collides with an existing entry. Batch operations cover the realistic case of moving sets of related Functions together; dependency ordering is preserved so the platform processes prerequisites before consumers.

**Export format.** A Function exports as a serializable document containing the Function's identity, name, input contract, output contract, internal subgraph, declared plugin and Function dependencies, and creation and update timestamps. The format supports both YAML and JSON; both representations carry the same information and convert between each other without semantic loss. Sensitive content such as embedded secret values is masked or stripped on export by default; the author chooses whether to include sensitive values explicitly when the export is intended to be paired with a secret store. Secret values in an imported Function, its version history included, follow the one import rule (REQ-4.5.19).

**Single-Function export.** Exporting a single Function produces one document containing that Function. Function dependencies referenced by the exported Function are not bundled by default; the export carries only the dependency declarations (identifiers and metadata) so an importing installation can verify presence at import time.

**Batch export.** Exporting a set of Functions produces a single archive document containing each Function plus enough metadata to order them for import. The set is selected by enumerating Function identifiers. The batch format preserves the dependency relationship so the import side can process prerequisites first.

**Import validation.** Every incoming Function is validated before it is admitted to the library, using the same rules described under composition-time validation: required fields, reference existence, field completeness, type compatibility, variable scope discipline, and the no-cycle constraint on the Published-Function dependency graph. An import that violates any blocking rule is rejected; the user receives a finding list identifying which Function(s) failed and why. Imports with warnings only are accepted with the warnings recorded against the imported entries.

**Conflict resolution.** When an incoming Function collides with an existing Published Function in the library - on its name, on its identifier, or on both - the import surface offers three resolutions: skip (leave the existing entry unchanged and discard the incoming definition), replace (overwrite the existing entry with the incoming definition), or rename (admit the incoming definition under a new name, keeping its identifier when no library entry holds it and giving it a fresh identifier otherwise). The surface indicates which axis collided so the user understands why a given entry needs a decision. Each conflict is resolved individually; a batch import that contains multiple conflicts presents the conflicts grouped so the user can apply a uniform resolution or pick per entry. No conflict is resolved silently, and a colliding identifier is never reused without an explicit replace, so an incoming definition can never overwrite or rename an existing entry it was not meant to touch; the user always sees the choice presented, and the non-destructive rename is the default. When an incoming Function's identifier and name collide with two different library entries, the entry with the same identifier is the one a replace acts on, and a replace that would give it a name another entry holds is refused.

**Dependency ordering on batch import.** When a batch contains multiple Functions with declared Function-to-Function dependencies, the import path processes Functions in topological order so prerequisites land before consumers. If the batch is incomplete (a referenced Function is neither present in the batch nor already in the library), the affected consumers are rejected with a dependency-resolution error that names the missing Function: by the name it carries on the canvas, or by its library name and version when that version is the one missing; a placed Function with no name is reported without one. The unaffected entries in the batch still import successfully.

**Metadata preservation.** Imported Functions retain their original identifiers when imported into an installation that does not already have an entry with that identifier; in this case the imported Function is recognizable as the same entity across installations, which is useful for moving definitions between environments. On rename-resolution the imported entry keeps its identifier when no library entry holds it and receives a fresh identifier otherwise, so it never impersonates an existing entry.

**Round-trip integrity.** A Function exported and immediately re-imported into the same installation under the replace resolution leaves the library in a state semantically identical to its pre-export state. The export format includes all data required to reconstitute the Function; nothing is reconstructed lossily from defaults. This property is the basis on which version control integration relies, because diffs over Function exports are meaningful representations of the Function's evolution. Replace resolution preserves any existing version history the incoming document omits: after a replace, the entry's available versions are the union of those it already held and those the import carries, so a hand-authored single-version document can never silently truncate a multi-version library entry. A full-history export re-imported under replace therefore reproduces the entry exactly.

**Plugin dependency surface on import.** Plugin dependencies are validated against the importing installation's plugin registry. A Function whose plugin dependencies are not all satisfied by the importing installation is imported with a non-blocking warning (because the missing plugins are an installation-level concern, not a Function-definition flaw); the warning lists the missing plugin identifiers so the operator can install them before the Function is executed.
