#### 3.5.2 Function Variable Isolation

Functions enforce a strict variable visibility contract that separates Function-internal state from the scope of the flow a Function Block sits in. The isolation contract eliminates an entire class of composition errors that arise when reusable components share a global variable namespace with the flows that use them.

**Three categories of visible variables inside a Function.** When the body of a Function executes, exactly three categories of variables are visible to its internal Blocks. Declared inputs are read-only and carry the values of the Function Block's fields; an optional input the Block leaves not set takes its default, or null when it has none, and a required input must be set (see REQ-3.1.3.21). Declared outputs are write-targets: the Function's body assigns values to them during execution and the runtime reads each output's final value on return and propagates it to the flow the Function Block sits in through the Block's output bindings. Locals are mutable per-invocation variables the Function uses for intermediate computation; they exist only for the lifetime of one invocation.

**Single per-Function namespace, no prefix on references.** Inputs, outputs, and locals share a single per-Function namespace. Inside the Function, expressions and Block fields reference each variable by its bare name; there is no `input.` or `output.` syntactic prefix to write or maintain. Two variables in the same Function cannot share a name regardless of their direction (a Function cannot declare an input and an output that share a name, and a local variable cannot collide with a parameter name). The runtime resolves each reference against the Function's declared schema to determine direction and enforce it: writing to an input is rejected with a validation error.

**External scopes are hidden.** The system, regression, suite, and enclosing Test variable scopes are not visible from inside a Function. References to those scopes from within a Function's body are validation errors. A Function that needs a value from one of those scopes must declare it as an input and have the Function Block set it explicitly. This rule applies uniformly: there is no escape hatch, no implicit inheritance, and no scope walk.

**Local variables.** A Function's body may produce intermediate variables during execution (results of plugin invocations, control flow accumulators, computed expressions). Those locals exist only within the Function invocation's runtime scope. They are not part of the declared input or output schema, are not visible to the flow the Function Block sits in, and are discarded when the Function returns. Two concurrent invocations of the same Function (for example, two instances on a parent canvas, or one instance reached through different parallel branches) do not share local state.

**Why isolation matters.** The isolation contract makes Functions safely reusable: a Function authored once and dropped anywhere behaves identically regardless of what variables happen to exist in the flow the Function Block sits in. There is no risk that adding a variable to a Test will silently change the behavior of a Function the Test invokes, because the Function never sees that variable. There is no risk that two Function Blocks using the same Function will pollute each other's variables, because each invocation has its own runtime scope.

**Predictable read-write semantics.** The read-only-input rule guarantees that a Function cannot change its Function Block's fields through assignment. The write-only-output rule (seen from outside: only the Function Block's output bindings read from the Function's outputs) guarantees that a Function communicates back to the flow it is used in exclusively through declared outputs, making the data flow at the Function Block fully explicit. Reviewers reading a Function Block see every value flowing in (its fields) and every value flowing out (its output bindings); no hidden side channel exists.

**Interaction with secret values.** Secret variables flow through the input mechanism the same way as ordinary values. A Function Block that sets a secret on a Function input passes a secret-typed value into the Function's scope; the Function's internal logic operates on the secret with the same masking and propagation rules that apply at the Test level. The isolation contract does not alter how secrets are masked in logs or treated by downstream plugins.

**Interaction with nested Functions.** A Function may use other Functions in its body through Function Blocks. Each nested invocation establishes its own per-Function namespace; the parent Function's variables are not inherited by the child. To pass data from a parent Function's variables into a child Function's inputs, the parent must set the child Function Block's fields explicitly, just as a Test sets the fields of any Function Block in it. The isolation rule is recursive and uniform at every depth.
