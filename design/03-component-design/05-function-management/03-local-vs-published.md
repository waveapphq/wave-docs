#### 3.5.3 Function Lifecycle States

Every Function exists in one of two lifecycle states. The state determines where the Function's definition is stored, whether it is mutable, and how Function Blocks reference it. The transitions between states are explicit user actions; a Function does not move between states implicitly.

**Local Functions.** A Local Function's definition is embedded inside the owning Test's storage as part of the Test's workflow data. It has no identity outside its Test: two Tests that each contain a Local Function with the same author-chosen name are unrelated entities. A Local Function is mutable; the author edits it the same way they edit any other part of the Test, with normal save semantics. Local Functions exist to support iterative composition: a workflow author can build behavior up out of plugins and controls, lift a repeating pattern into a Function, refine it in place, and decide later whether the Function is worth promoting to the shared library.

**Published Functions.** A Published Function's definition lives in the shared Functions library as one entry per Function, identified by a stable identifier. Each entry holds a sequence of one or more immutable versions, each tagged with a semver triple. A canvas instance references a published Function by `(identifier, version)`; resolving the instance for rendering or execution reads the definition for that specific version from the library. Immutability is per-version: the bytes that make up `ValidateUser v1.4.2` never change once the version is recorded, so any Function Block that pins to `v1.4.2` runs the same definition for the lifetime of that pin. New work on the same library entry produces a new version alongside the old, leaving prior versions intact.

**Edit-mode draft.** A canvas instance that references a Published Function may enter edit mode, which switches that instance into a per-Test mutable draft sitting on top of the published reference. The draft is a deep copy of the source version's definition, embedded in the Test the same way a Local Function would be, but tagged with an upstream link to its `(identifier, version)` source. While the draft is active the Function Block on the canvas is visually marked, and the author can modify the body, the input and output declarations, the description, the tags, and the per-version Changelog and Details. Entering edit mode is itself an unsaved canvas edit: the draft lives in the in-memory workflow and is persisted into the Test only when the author saves the Test, so discarding the Test's unsaved changes (or closing without saving) returns the instance to a plain published reference and drops the draft. Once the Test is saved, the draft persists across subsequent Test saves and is what the execution engine runs as long as the instance remains in edit mode. The author resolves the draft in one of two ways: publish it (which records a new version of the source library entry per the chosen semver target) or drop the changes (which discards the draft contents and returns the instance to a normal published reference at the original source version). Publishing does not save the owning Test: the only persisted effect is the new immutable library version, and the instance's resulting version pin is an ordinary unsaved canvas edit the author saves whenever they choose. Other instances of the same `(identifier, version)` in other Tests are unaffected by a draft in any one Test.

**The publish transition (from Local).** Promoting a Local Function to the library is an explicit user action initiated from the Local Function's authoring context. The transition copies the Local Function's definition into the shared library as a new entry (a fresh identifier, the author-chosen name, initial version `1.0.0`). The original Local Function in the owning Test is replaced with a Published Function instance pinned to the new entry's `v1.0.0`.

**The publish transition (from edit-mode draft).** Publishing a draft records a new version of its source library entry. The new version is computed from the semver target the author chose (patch, minor, or major) and must be strictly greater than the current latest version: publishing always advances the library, so a target at or below the latest is rejected. This rules out both a backport to an older line and a pre-release of an already-released version (for example `2.0.0-dev1` once `2.0.0` exists, since a pre-release precedes its release). Library metadata (description, tags, changelog, details) is recorded on the new version from the draft while prior versions retain their own metadata untouched. The author confirms the publish through a final choice with two outcomes: re-pin this instance to the newly published version, or leave this instance on its source version. Both outcomes record the same new library version and exit the draft; they differ only in which version this one instance ends up pinned to. Publishing never saves the owning Test - the only persisted effect is the library version write, and the instance's version-pin change persists only when the author next saves the Test. In the canvas undo history the whole edit session collapses into a single version-pin-flip step on a clean reference: every in-body edit made while drafting is removed from the history and replaced by one entry describing the version change. Undoing it reverts the instance to its prior pinned version (the draft is not reachable afterward); redoing re-pins to the published version. The published library version is permanent and is never removed by undo.

**The detach transition.** The inverse operation is the detach (also called "make local"). When an author wishes to fork a Published Function entirely out of the library context, they detach it: WAVE deep-copies the resolved version's definition out of the library and embeds the copy inline as a Local Function in the owning Test. The detached copy is fully editable and has no upstream link; the library entry and all its versions are unaffected. Detach is the path for "I want to take this Function in a fundamentally different direction without polluting the library entry"; edit mode is the path for "I want to evolve this library entry to its next version".

**Why versioning makes edit-while-in-use safe.** Editing a reusable component while other consumers depend on it raises a familiar question: do consumers see the edit immediately, do they keep the old definition, or does the platform enforce a versioning model? WAVE enforces versioning. Each published version is immutable, so a consumer pinned to a specific version never sees a surprise edit. An author's edit produces a new version alongside the old; consumers continue to invoke the version they pinned to and adopt a newer version as a deliberate, explicit action (switching the version pin on their instance). Edit mode bounds the edit blast radius further: the in-progress changes live as a per-Test draft and are invisible to consumers outside that Test until the draft is published as a new version in the library.

**Identity and references.** A canvas instance referencing a Published Function carries the library identifier, the pinned version, and the Function Block's own fields and output bindings; it does not carry a copy of the definition. Resolution for rendering or execution reads the definition from `(identifier, version)` in the library when the Block is drawn or run. An edit-mode draft additionally carries the embedded draft definition plus the upstream link tag. Local Function instances carry the full definition inline. The reference styles are visually distinguishable on the canvas through the lifecycle badge (local versus shared) and through a draft mark on the badge corner when an edit-mode draft is active.

**Naming and uniqueness.** Local Function names are scoped to their owning Test: a Test may not contain two Local Functions with the same name, but two different Tests may each have a Local Function called by the same name without conflict. Published Function names are scoped to the shared library: a library may not contain two entries with the same name. Version identifiers are scoped to the entry: a library entry may not contain two versions with the same semver triple, but two different entries may each have a version called `1.0.0` without conflict.

##### REQ-3.1.2.2 Version control for Functions with metadata

Every Published Function in the shared library is a versioned artifact. The library records a sequence of one or more immutable versions for each entry, each carrying its own metadata snapshot. Workflow authors compose Tests against specific versions, publish new versions through bounded transitions, and recover gracefully when a referenced version is no longer available.

**Version model.** Each library entry is keyed by a stable identifier and holds an ordered set of versions, each tagged with a semver triple `X.Y.Z` (and optional pre-release / build metadata). A version is the unit of immutability: once a version is recorded in the library, its body, input contract, output contract, description, tags, changelog, and details cannot change. Versions are ordered by semver precedence, under which a normal release outranks its own pre-releases and build metadata is ignored. Versions are organized into major lines: every published version must be greater than the latest version of its own major line, so each major line advances monotonically and independently and multiple major lines coexist (a `1.x` line can still gain a `1.0.1` after a `2.0.0` exists, but a `2.0.0` cannot be recorded once `2.0.1` exists). Back-fill is constrained only by the target version, never by which version was used as the editing source. The version with the highest precedence across all lines is designated the latest; older versions, including the heads of lower major lines, remain readable and addressable. Versions are first-class citizens of the storage layer, not derived from snapshots of a "current" definition. A version string is bounded to a fixed maximum length, shared with the platform's other identifier-shaped fields, so it renders cleanly in the version pills and dropdowns across the UI; an over-length version is rejected at validation with the same strictness as malformed semver.

**Per-version metadata.** Description, tags, changelog, and details are recorded per version. Description and tags describe what the version does (used to fill the library card surface); changelog explains what changed since the prior version; details is long-form documentation. Switching the selected version on a published instance updates the metadata the configuration surface shows. The same library entry may carry a different description on `v1.0.0` than on `v2.0.0` because the entry's purpose may have evolved across major versions.

**Version pinning.** A canvas instance that references a Published Function pins to a specific `(identifier, version)`. The pin is recorded in the Test's workflow data and persists across saves. New publications do not auto-upgrade existing instances: an instance pinned to `v1.4.2` continues to invoke `v1.4.2` even after `v1.5.0` is published, until the author switches the pin. Default pinning behavior when an instance is first created from a library reference is the latest version available at instantiation time.

**Semver targets and edit-mode validators.** Edit-mode publishing produces a new version of the source library entry, bumped per a semver target the author selects. The target is one of patch, minor, or major, and the platform enforces what each level may change relative to the source version. Patch permits body and metadata changes only (no input or output mutations, no tag additions or removals). Minor additionally permits backward-compatible expansions: adding optional inputs, relaxing an existing input from required to optional, adding outputs, adding tags. Changing a kept parameter's default, kind or secret flag, or an enum input's allowed values, changes the contract a Function Block sees, so publish suggests a minor version for such a draft, never a patch. Changing an enum input's type is an input type change, which only a major version may carry. Major permits anything except the entry's name, which is locked across the lifetime of the library entry. The validator runs continuously during drafting so the available bump targets reflect the current draft state; a draft that violates patch and minor rules can only be published as major. Any version of the entry can be opened and edited - the opened version seeds the draft and supplies the contract the patch/minor/major compatibility rules are enforced against. The patch and minor bump targets are computed by advancing the latest version of the source's major line (so editing `2.0.1` while the `2.x` head is `2.0.2` targets `2.0.3`), never the source itself; a patch or minor therefore stays within the source's major line. The author may also type a custom semver string (to attach pre-release or build metadata, for example), which is validated against the same compatibility rules and, like every published version, must be greater than the latest version of its major line.

**Publish-as-major-of-existing.** A new major version of an existing library entry is created from an edit-mode draft. The name is locked to the existing entry, the version auto-bumps to the next major (e.g. `1.4.2` -> `2.0.0`), the changelog is required, and description and tags pre-fill from the latest version's metadata (editable so the new major can re-describe the entry). The publish dialog opened from edit mode has no library-Function picker, since the source is always known from the edit-mode context; the source is shown as a locked context chip at the top of the dialog.

**Missing-version validation.** When a Test references a Published Function at a `(identifier, version)` where the version no longer exists in the library, the platform surfaces a distinct validation error (separate from "identifier not found") and blocks Run, Validate, and Save in the canonical validation pipeline. The Function Block on the canvas carries a missing-version alert; the configuration surface for that instance shows the pinned-but-absent version in strikethrough, lists the available versions, and offers a single recovery action: switch the pin to an available version. Detach is not a viable recovery for missing-version since detach requires the source definition to copy and the source definition is exactly what is gone.

**Library surface.** The library surface (the in-canvas Functions Library modal and the standalone library page) shows entries one card per identifier, displaying the latest version on the card. Cards drive an instance creation at the latest version when dragged onto a canvas; users switch the pin on the instance afterwards through the instance configuration surface. Tag and search filters are evaluated against the latest version's metadata; older versions remain reachable through the version dropdown on an instance pinned to the entry.
