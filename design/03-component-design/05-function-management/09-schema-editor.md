#### 3.5.9 Function Schema Editor

The schema editor is the workflow author's surface for declaring a Function's typed input parameters and typed output parameters. It is the Function-side counterpart to the Function Block's configuration window (the Block window of a Function Block in a parent canvas). The schema declares the shape of the Function's external interface; each Function Block sets values for that interface through its fields.

##### REQ-3.1.1.5 Function parameter configuration forms

The schema editor lives inside the drilled-in view of a Function. It is presented as an integral part of the Variable Manager rather than a separate panel: declared input and output parameters surface as rows in the Variable Manager alongside the Function's local variables, grouped under a Parameters parent that visually separates them from the local Variables parent. Parameters are split inside the Parameters group by an Inputs / Outputs sub-separator so direction is unambiguous at a glance.

This grouping is the reason a Function-scoped Variable Manager does not need a second sidebar or modal-only editor: parameter declaration is the same kind of work as variable declaration, with the same shape of data (name, type, initial value, secret flag), so the same affordance hosts both.

Adding a parameter uses the SAME window the workflow author already knows from adding a variable, and editing one opens that window again, filled (VMGR-106). Parameter and variable windows are one design. The Add affordance in the panel header becomes a dropdown when the active scope is inside a Function; the dropdown lists Input parameter, Output parameter, and Variable. What the window adds or edits determines its title, the label of the value field (an input's is "Default value" in Add), the presence of the Kind choice (Variable and Output; an Input is always literal), the presence of Description (Input and Output), the presence of the Required flag and of the Create-enum flag (Input only), and the section the new row lands in. Beyond those, the window's fields - name, type, the value field with its Open editor button, mark-as-secret, set-to-null - are identical, and so is the layout the Variable Manager design describes (see REQ-3.1.3.11). Mark as secret makes an input or an output a secret parameter (REQ-3.1.2.9); on an input it and Create enum exclude each other (REQ-3.1.2.11).

For Inputs, the default value applies when the Function Block does not set a value AND the Required flag is off. When Required is checked, the Function Block must set a value; missing values block Test execution at composition time. A Required input may carry a default, which a Function Block never uses: it serves only when the Function runs on its own; a secret input carries none (REQ-3.1.2.10). For Outputs, the default value is the fallback returned to the Function Block if the Function's inner workflow does not write to the output before returning; null means no default, so an output nothing wrote returns null. An Output whose kind is Expression is evaluated at its first read or when the Function returns, once, and any write replaces it; it counts as written. For Variables, the default value is the variable's starting value at the Function's invocation (the same semantics as variables today).

The Required flag is rendered only in Input mode. Outputs and Variables have no mandatory-binding concept and the flag is not exposed in those modes. A new input is preset with the type's default (empty string, zero, false, empty collection). Set to null means a null default: a Function Block that sets nothing passes null (see REQ-3.1.3.24); it is off and locked on a Required or an enum input.

Editing an existing parameter is the same window pre-populated with the row's current values, Required, Description and enum included. Its value switch picks the Default or the Current value, and every other field stays editable in both, the name included (VMGR-108). Deleting a parameter removes the row and severs any reference the inner workflow had to its namespace; expressions that reference the deleted name surface as validation issues on the affected Blocks.

##### REQ-3.1.2.10 Inputs with no default

A secret input has no default, because no one could read it back. A Required input may have a default or none: a Function Block never shows or uses it and must set the value, so the default serves only when the Function runs on its own (VMGR-113). In the input window, ticking Mark as secret disables the default field, ticks Set to null and locks it, and a tooltip on the field says why: "A secret input has no default: the Function Block gives the value." (VMGR-103). Ticking Required turns Set to null off and locks it ("off while Required is set"); a Required input with no default shows an empty field. A Required true/false input has no empty value, so, as for an enum input, its default is required (VMGR-113). A secret input that still holds a default from earlier loses it the next time the Function is saved. An output, secret or not, may carry a default. Running a Function on its own takes each input's Current value, which starts from the default, as the canvas integration describes; a Required input with neither a default nor a Current value stops that run and is named.

##### REQ-3.1.2.11 Enum input parameters

Some inputs are best modeled as a fixed choice from a small set of values (a status code, a log level, a mode flag). The schema editor expresses this as an enum on an Input parameter of a Function - the enum constraint is part of the Function Block's contract (the Function Block sets one of the allowed values). Output parameters and local Variables never carry an enum: an Output is a value the Function produces and is constrained by its declared type alone; a Variable lives entirely inside the Function and has no contract with a Function Block to enumerate against. An enum input's Type is the value's type - String, Integer or Float; other base types do not enum-ify cleanly, and there is no Array enum and no separate value type (VMGR-112). "Create enum (limit the Function Block to a fixed set of values)" is the last checkbox of the input window, after Required, Mark as secret and Set to null, and is never shown in Output or Variable mode. When it is checked, an Allowed values list of the input's Type appears right under it, with no per-item type column; Required is locked on ("locked on while enum is set"), and Mark as secret and Set to null are off and locked ("off while enum is set"). While Mark as secret is ticked, Create enum is off and locked ("off while secret is set") (VMGR-104). An enum input is always Required, never secret and never null. Its default is required and picked from the allowed values: until it is set the select is empty, outlined in red with "Default value is required" under it, and Save stays disabled. While the allowed values list is empty it says so in red right away ("Enum allowed values cannot be empty"); a list that holds an empty text or the same value twice names the first one ("Allowed value at index 0 is empty", "Allowed value at index 2 (low) is already listed"), so every field that blocks Save shows why. The save check refuses an empty allowed value and a repeated one (a value equal to an earlier one once both are read as the input's type), at Function save, at Test save and in recipes. Turning an input whose value is null into an enum unticks Set to null and keeps Save disabled until the default and the Current value are set; setting the default also sets the Current value to it when the Current value is null or not an allowed value; the Current value is one allowed value. Save validates that every allowed value satisfies the Type; mismatches surface inline with Save disabled.

On a Function Block, an enum input is the choice list a block setting with fixed choices uses, listing the allowed values and holding the default from the moment the Block is created, with {x} beside it (FNCFG-6, FIELD-8). A picked value is stored as a value of the input's Type and checked against the allowed values when the block is saved; a variable or expression set instead is checked when the run starts, and a value outside the list, or a null, fails the Function Block and names the input.

##### REQ-3.1.2.1 Create custom Functions with input parameters

Declared inputs appear as read-only named variables in the Function's inner scope. Inside the Function, expressions and plugin parameters reference inputs by name without any prefix (e.g. `user_id`, not `input.user_id`); the runtime resolves the name against the declared schema and recognizes it as an input. Outside the Function (in the flow the Function Block sits in), the Function Block sets each input as one of its fields, in the same Block window a plugin uses. This separation keeps the Function self-contained: the inner workflow operates on each input by its declared name regardless of how the flow the Block sits in produced the value.

Declared outputs appear as named variables in the Function's inner scope. The Function's inner workflow assigns values to outputs from any Block that produces a value (a plugin output binding, an expression, a variable-set step) by writing to the output's name. On return, the Function's runtime reads each declared output and propagates its value to the flow the Function Block sits in per the Function Block's output binding configuration.

Both inputs and outputs carry a type and a default, which may be null (no default), except that an enum input's default is required (REQ-3.1.2.11), a Required true/false input's default is required (VMGR-113), and a secret input has none (REQ-3.1.2.10). The type list mirrors plugin parameter types: string, integer, float, boolean, array, map, table. The default is type-aware (the same value editors the Variable Manager uses for variables of that type).

##### REQ-3.1.2.9 Secret input and output parameters

Mark as secret on an input makes it act exactly as a block's secret field (SECUI-10). Whatever the Function Block passes in - a literal, a plain variable or a secret variable - is masked inside the Function from the moment it arrives, on every channel that masks a secret (REQ-4.5.3), and a literal typed into the Function Block is sealed at rest as a credential field's literal is. The variable the Function Block passes is never changed: a plain variable stays plain in the flow the Block sits in. A secret input has no default (REQ-3.1.2.10).

Mark as secret on an output makes the Function Block's outputs table seed that output's Secret box ticked (SECUI-11); the author may untick it and keep the value plain. While it is ticked, a new variable typed into the row is created secret, and an existing plain variable picked there becomes secret when the block is saved, after a warning that names it (REQ-4.5.20), and stays secret as any output-bound secret does (SECUI-4). A secret output may carry a default: it is sealed at rest and masked in the editor, the run log, MCP reads and exports.

##### REQ-3.1.2.4 Function validation before save

The schema editor enforces structural rules at parameter creation and edit time. Names use letters, digits and underscores and start with a letter; their length is bounded. Inputs, outputs, and locals share a single per-Function namespace, so duplicate names are rejected regardless of category: two Inputs named `x`, two Outputs named `x`, an Input and an Output both named `x`, or an Input and a local named `x` all surface as inline errors in the window with Save disabled.

Type-required and value-validity checks happen at window save: the type is required, and the default value (when provided) must satisfy the type. A new input is preset with the type's default (empty string, zero, false, empty collection); Set to null means a null default, and a Function Block that sets nothing passes null. For an enum input, the allowed values list must be non-empty, every item must satisfy the input's Type, and the default must be one of the allowed values.

Deeper semantic validation - reference existence inside the inner workflow, type compatibility across edges, circular dependency detection - belongs to the Function-validation pass described in the Function Validation and Integrity design. The schema editor's responsibility ends at the declaration surface: it ensures the declarations themselves are well-formed and self-consistent.

##### Variable Manager integration

When the active canvas is inside a Function, the Variable Manager re-scopes so that only the Function's own variables are visible: declared inputs (under Parameters > Inputs, with an IN badge), declared outputs (under Parameters > Outputs, with an OUT badge), and Function-local variables (under Variables, with no direction badge). External scopes - system, regression, suite, test - are hidden, both from the panel and from expression autocomplete in any field rendered inside the Function. The autocomplete suggests bare names (no `input.` or `output.` prefix); the IN / OUT badge in the suggestion list identifies each name's role. This enforces the variable-isolation contract described in the Function Variable Isolation design at the authoring surface, matching what the runtime enforces at execution time.

Outside a Function (at the Test level or in any other workbench context), the Variable Manager renders its standard layout: a flat list of variables with the existing chrome, no Parameters group, and the existing Add affordance.

The Variable Manager's existing OUT badge - which marks variables that are output-bound by a plugin or control in the workflow - is reused for declared output parameters inside the Function. The two uses never overlap visually because declared outputs live under Parameters > Outputs and plugin-output-bound variables live under Variables; the section header disambiguates the OUT badge's meaning in each location.
