### 15.1 Frontend Foundation

#### 15.1.1 React Application Architecture

##### REQ-5.2.1.1 React 19 application with Vite build system

The frontend application architecture provides the foundational structure for WAVE's web-based user interface, built as a modern single-page application optimized for the complex, data-dense workflows that test engineers interact with daily. The architecture emphasizes performance, maintainability, and seamless integration with the WAVE design system while supporting the real-time capabilities required for execution monitoring and debugging.

**Technology Foundation**: The application is built on React 19, selected for its concurrent rendering capabilities that enable smooth interactions even during intensive state updates, its mature ecosystem providing battle-tested solutions for common challenges, and its component model that aligns naturally with the design system's component patterns. TypeScript provides compile-time type safety throughout the codebase, enabling early error detection, enhanced IDE support with intelligent autocomplete and refactoring tools, and self-documenting code through explicit type definitions that serve as living documentation for component contracts and data structures.

**Build System Architecture**: Vite serves as the build system, chosen for its exceptional development experience and optimized production output. During development, Vite leverages native ES modules to serve source files directly to the browser, eliminating the bundling step entirely and enabling near-instant server startup regardless of application size. Hot module replacement operates at the component level, preserving application state while updating only the modified components, providing sub-second feedback during development iterations. Source maps are generated automatically for full debugging support, and type checking runs in parallel to avoid blocking the development workflow. For production builds, Vite produces tree-shaken bundles with dead code elimination, automatically splits code along route boundaries and dynamic import points, applies minification and compression to all assets, and generates content-hashed filenames for optimal browser caching with cache invalidation on updates.

**Application Layer Architecture**: The frontend follows a component-driven architecture with clear separation of concerns across four distinct layers. The presentation layer handles UI rendering and user interaction through components that are stateless where possible and comply with the design system specifications. The container layer manages business logic and data orchestration, connecting presentation components to state stores and service clients. The state layer provides centralized application state management with predictable update patterns through well-defined stores. The service layer abstracts API communication and data fetching from the UI, handling error transformation and request lifecycle management.

**Project Organization**: The codebase follows a feature-first organization pattern where related components, hooks, and utilities are co-located within feature modules rather than separated by technical type. Each feature module contains its own components, local state management, and utility functions, enabling developers to understand and modify features without navigating across multiple directory hierarchies. Shared components from the design system reside in a dedicated location accessible to all features, ensuring consistency while avoiding duplication. Global state stores, service clients, and cross-cutting utilities occupy their own modules at the application root level.

**Design System Integration**: The application integrates tightly with the WAVE design system defined in Section 15.7, consuming design tokens through CSS custom properties that automatically adapt to theme changes. Color tokens reference theme-aware values that switch between light and dark palettes based on user preference or system settings. Typography tokens apply the defined font families, size scale, and weight specifications consistently across all text rendering. Spacing tokens enforce the defined scale throughout layouts and component internal spacing. Component patterns from the design system provide standardized variants, states, and interaction behaviors that ensure visual and behavioral consistency across the application.

**Performance Architecture**: The architecture incorporates performance optimizations at multiple levels to meet the requirement of responsive interaction even with large datasets and complex workflows. Automatic code splitting ensures the initial bundle contains only the code necessary for the landing experience, with additional code loaded on-demand as users navigate to different features. Component lazy loading defers the loading of non-critical features until they are needed, reducing initial load time. Build-time static analysis identifies optimization opportunities including unused exports, redundant dependencies, and suboptimal import patterns.

**Development Workflow**: The development experience prioritizes rapid iteration and immediate feedback. Fast refresh preserves component state across edits, allowing developers to see the effect of changes without losing their place in the application flow. An error overlay displays runtime errors and build failures directly in the browser with full stack traces and source locations, eliminating context switches to terminal output. TypeScript integration provides instant type feedback in the IDE, catching errors as code is written rather than at build time. Path aliases eliminate complex relative import paths, making code more readable and refactoring-friendly.

#### 15.1.2 State Management

##### REQ-5.2.1.5 Zustand state management stores

The state management architecture provides centralized, predictable application state across all frontend features, enabling components to access and update shared data through selective subscriptions that minimize re-renders. The architecture supports workflow building, execution monitoring, and real-time updates that test engineers depend on daily.

**State Management Philosophy**: Zustand serves as the state management solution, selected for its minimal boilerplate, TypeScript-first design, and hooks-based API that integrates naturally with React. State updates occur through simple function calls with Zustand handling immutability internally, reducing developer overhead while maintaining centralized state predictability.

**Store Organization**: Application state is organized into domain-specific stores rather than a single monolithic store. The authentication store manages session state and login status. The execution store tracks real-time status during test runs. The workflow store maintains canvas state including node positions, selections, and undo history. Workbench stores hold the console log entries, the WebSocket connection, the session a tab holds, the palette's Recent and Most Used lists, test data uploads in progress, and the notice for a test deleted while open. The functions store holds the Function library. Application stores hold the sidebar state, the time zone, the viewport size, layout choices for the browser session, the blocked state of a page whose load failed, the secret masking settings, the SSH host policy, and the Settings navigation state. Light and dark mode, with system preference detection, is held by a theme provider rather than a store.

**Cross-Store Communication**: Stores coordinate through subscription-based patterns without tight coupling. Execution state changes trigger automatic notifications. Authentication logout clears sensitive cached data across stores. Explicit subscriptions ensure state flow remains traceable.

**Persistence and Hydration**: Critical state persists across browser sessions via local storage. Theme preference restores synchronously before first render to prevent flash. The persistence layer handles serialization and graceful degradation when storage is unavailable.

**Real-Time Integration**: WebSocket message handlers dispatch updates to appropriate stores, updating execution progress and status indicators as events arrive. Stores maintain connection awareness and reconcile state when connectivity resumes.

**API Client Integration**: Stores coordinate with the REST API client for data fetching and backend synchronization. Fetch operations translate network concerns into loading indicators and error states.

**Selective Subscriptions**: Components subscribe via selector functions extracting only required state slices, preventing re-renders from unrelated changes. This granular model maintains responsive interaction in data-dense views like the workflow builder.

**Computed State**: Stores expose memoized derived values including filtered lists and aggregated statistics, avoiding redundant calculations while invalidating on underlying state changes.

**Testing**: Stores instantiate outside React for isolated unit testing without component rendering.

#### 15.1.3 Routing Structure

##### REQ-5.2.1.2 Client-side routing with navigation history

The routing architecture provides seamless navigation throughout the WAVE application, enabling users to move between different views and features without full page reloads while maintaining full browser history integration. The routing system serves as the backbone of the single-page application experience, coordinating view rendering, state preservation, and deep linking capabilities that test engineers rely on for efficient workflow navigation.

**Client-Side Navigation Model**: The application implements client-side routing where navigation between views occurs entirely within the browser without requiring server round-trips for each page change. When users click navigation links or interact with elements that trigger route changes, the routing system intercepts these interactions and updates the view by rendering the appropriate component tree for the new route. This approach eliminates the latency and visual disruption of traditional page loads, providing instantaneous feedback that meets the performance target of route transitions completing in under 100 milliseconds. The browser's address bar updates to reflect the current route, enabling users to see their location within the application at all times.

**Navigation History Integration**: The routing system integrates fully with the browser's native history API, ensuring that standard navigation patterns work as users expect. The browser's back button returns users to their previous view with restored scroll position and, where appropriate, preserved ephemeral state such as form inputs or filter selections. The forward button reverses this action when available. Users can navigate through their session history using standard keyboard shortcuts, and the history stack accurately reflects the sequence of views visited during the session. This integration extends to programmatic navigation triggered by application logic, such as redirecting after a successful form submission or navigating to a newly created resource.

**Route Hierarchy and Structure**: Routes are organized in a hierarchical structure that mirrors the application's information architecture. Top-level routes correspond to major application sections such as test management, suite organization, regression runs, and execution monitoring. Child routes represent specific views within these sections, including detail pages for individual entities, editing interfaces, and execution result views. This hierarchy enables intuitive URL structures that users can understand and manipulate directly, supporting workflows where engineers share links to specific tests, execution results, or configuration screens with colleagues.

**Deep Linking Support**: Every significant view within the application is addressable through a unique URL, enabling deep linking that supports collaboration and workflow efficiency. Users can bookmark specific pages to return to frequently accessed resources directly. Links shared through communication tools open directly to the intended view rather than requiring navigation from a landing page. The routing system parses URL parameters and path segments to restore the complete view state, including selected entities, active tabs, applied filters, and pagination positions where applicable.

**Route-Based Code Organization**: The routing structure aligns with the code splitting strategy defined in the application architecture, with route boundaries serving as natural split points for lazy-loaded code bundles. When users navigate to a route for the first time, the associated component bundle loads on demand, keeping the initial application bundle focused on immediately necessary code.

**Navigation Guards and Transitions**: The routing system supports navigation guards that can intercept route transitions to enforce business rules or prevent data loss. When users attempt to navigate away from a view with unsaved changes, a confirmation mechanism prevents accidental data loss. Authentication guards redirect unauthenticated users to appropriate entry points while preserving their intended destination for post-authentication redirect. Route transitions apply subtle visual feedback consistent with the design system's animation specifications, providing continuity without introducing perceptible delay.

**Error Handling and Fallbacks**: The routing system handles navigation errors gracefully, displaying appropriate feedback when users attempt to access non-existent routes or resources they lack permission to view. A catch-all route provides a consistent experience for unmatched URLs, guiding users back to valid application areas. When route components fail to load due to network issues or other errors, the error boundary system provides recovery options without requiring a full application restart.

#### 15.1.4 Component Library Architecture

##### REQ-5.2.1.6 Reusable UI component library

The component library provides a comprehensive set of reusable, accessible UI building blocks that implement the WAVE design system specifications, ensuring visual and behavioral consistency across all application features while enabling rapid development of new interfaces.

**Architectural Approach**: The component library follows a headless-first architecture where behavioral logic and accessibility are provided by proven primitives, with styling applied through the design system's token-based approach. This separation enables components to maintain consistent behavior and accessibility compliance while allowing complete visual customization through design tokens. Components are owned by the application rather than consumed from an external package, providing full control over implementation details, bundle size, and the ability to customize without fighting framework constraints.

**Component Hierarchy**: Components are organized into three tiers based on their complexity and composition patterns. Primitive components form the foundation layer, providing atomic building blocks such as buttons, inputs, badges, and icons that implement single, well-defined responsibilities. Composite components combine primitives into commonly used patterns such as form fields with labels and validation feedback, search inputs with clear actions, and action menus with keyboard navigation. Feature components assemble primitives and composites into complete UI sections such as data tables with sorting and pagination, modal dialogs with form content, and notification stacks with auto-dismiss behavior.

**Design Token Integration**: All components consume design tokens exclusively for visual styling, never hardcoding colors, spacing, typography, or other visual properties. This integration enables automatic theme switching between light and dark modes without component-level logic, ensures visual consistency with the design system specifications, and provides a single point of control for design updates that propagate throughout the application. Components reference semantic tokens that describe purpose rather than appearance, allowing the design system to evolve without requiring component changes.

**Accessibility Foundation**: Every component is built on accessible primitives that handle complex accessibility requirements including keyboard navigation patterns, focus management, screen reader announcements, and ARIA attribute management. Focus indicators follow the design system specifications for visibility, and all interactive elements support keyboard operation following platform conventions.

**Component Variants and States**: Components expose variant and state APIs that correspond directly to the design system's component specifications. Button variants include primary, secondary, ghost, and danger with size options of small, medium, and large. Input states cover default, hover, focus, error, and disabled with consistent visual treatment. Card variants support default, interactive, and selected states. This alignment between design specification and component API ensures that designers and developers share a common vocabulary and that implemented components match design expectations exactly.

**Composition Patterns**: Components follow composition-over-configuration principles, exposing slots and children for flexible content while providing sensible defaults for common cases. Modal components accept header, body, and footer sections as discrete elements rather than string properties, enabling rich content without API complexity. Table components compose from header, body, and row primitives, allowing custom cell rendering and row behaviors. This approach keeps components focused on layout and behavior while delegating content decisions to consuming code.

**Form Integration**: Form-related components integrate with form state management patterns, supporting controlled and uncontrolled modes, validation feedback display, and error message association. Input components expose consistent APIs for value binding, change handling, and validation state regardless of input type. Form layout components enforce consistent spacing and label positioning across all form instances.

**Loading and Error States**: Components that represent data or async operations provide built-in support for loading skeletons, error states, and empty states. Loading skeletons match the component's dimensions and visual structure, providing perceived performance during data fetching. Error states display actionable feedback with retry mechanisms where applicable. Empty states guide users toward productive actions rather than displaying blank content.

**Animation and Transitions**: Components implement the design system's animation specifications for state changes, entrance and exit transitions, and interactive feedback. Hover and focus transitions apply the specified duration and easing. Dropdowns and modals animate according to their defined patterns. All animations respect the user's reduced-motion preference, falling back to instant state changes when motion is disabled.
