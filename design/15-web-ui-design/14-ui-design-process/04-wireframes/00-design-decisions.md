| VMGR-3 | Sort dropdown options: `Name A-Z` (default), `Name Z-A`, `Type`. Persisted in localStorage under key `var-mgr.sort`. |
| VMGR-4 | Flat variable list. No Watch List section, no scope groups, no `All Variables` collapsible header. |
| VMGR-5 | Per-row two-line grid: line 1 = variable name (mono, left) + action cluster (right); line 2 = value text (left, type-colored) + badges (right). |
| VMGR-6 | Action cluster left-to-right: eye, Inspect (magnifying glass, FIELD-11), edit, delete. Same order on every row. |

| VMGR-12 | Edit (pencil) opens the variable's one window, filled, in Edit (VMGR-106). | VMGR-13 | Row body click is a no-op; hover shows a subtle bg highlight; ArrowUp/ArrowDown moves keyboard focus across rows; Enter is a no-op. |
| VMGR-14 | Empty state copy (zero variables): centered, muted `No variables yet. Click + Add to create one.` Filter input and Add button remain visible. |

### Variable Inspect Modal

| ID | Decision |
|----|----------|
| VMGR-15 | Per-variable floating inspect modal on the DraggableSheet primitive: non-blocking, draggable by the header bar, both-axis corner-grip resize. The watcher opens at a size set by its type; true / false, integer and float watchers have a fixed size, the others resize down to a floor set by their type. One modal per variable; re-expand focuses the existing one; different variables stack with newest-on-top z-order and a 24px cascade offset. The watcher only shows values: no Edit and no rename; editing happens in the variable's window (VMGR-106). |
| VMGR-16 | Modal header: drag grip + variable name (mono) + flag badge for expression variables (`{x}`) + type badge (panel badge palette) + close X. The whole header bar is the drag handle. |
| VMGR-17 | Modal body: the full, untruncated value, mono, in the type's value color. List-view truncation rules do not apply. |
| VMGR-18 | Footer zones: the Mode pill (VMGR-62) and the view controls (left), the type-aware metric (center, mono). There is no action zone: the watcher only shows values (VMGR-106). All dropdown triggers are TEXT labels + chevron - icon-only glyph triggers are rejected. |
| VMGR-19 | Modes: `Initial` = persisted definition value, rendered dim + italic; `Current` (default on open) = runtime value when execution data exists, identical to the definition when none does (the modal can be staged as a watcher before a run). While a run is live, a variable the run has given no value shows the value the run started with, and reads `null` when it started null; once the run has ended it shows its definition again, which is what the next ad-hoc run reads. The variable's row in the panel follows the same rule, so the row, `Current` and a continued run agree: a definition edited while the run is live changes the saved value only and shows in `Initial` and in the row's definition view. Menu items are plain text + check on selected, opening upward; `Compare` is the third entry (VMGR-43). |
| VMGR-20 | Source-row indicator while a variable's modal is open: 2px indigo inset left edge + faint indigo bg tint + indigo Inspect icon. The modal is a live view: external edits appear immediately; deleting the variable closes its modal. |
| VMGR-21 | Metric describes the displayed value: string `N chars`; integer / float / boolean none; expression source `expression`. |
| VMGR-22 | Expression variables: `Initial` shows the source in expression cyan; `Current` shows the evaluated value when present (cyan, normal type metric), else the source. |

### Variable Inspect Modal - Complex Bodies

| ID | Decision |
|----|----------|
| VMGR-23 | Complex rows (array / map / table) open the same inspect modal as scalars. Array and map watchers open at the 400px default; table watchers open at 480px. Minimum is 320x124: with the compact watcher chrome the modal shrinks to a single body line. |
| VMGR-24 | Array Visual body: each element renders as a row with a muted, right-aligned, 0-based index column followed by the value; hairline separators between rows; values are full and untruncated, wrapping as needed. |
| VMGR-25 | Map Visual body: each entry renders as a row with the key in plain mono (max 45% width, wrapping) followed by the value; hairline separators between rows. |
| VMGR-26 | Table Visual body: mini-grid with a sticky uppercase muted header row. The FIRST column is a dedicated muted 0-based row-index `#` column; data columns follow. The grid scrolls horizontally when columns overflow. |
| VMGR-27 | Per-cell type tinting by the value's OWN type using the panel palette: strings sky (quoted), integers violet, floats pink, booleans orange. Nested maps render as compact one-line JSON in emerald; nested arrays in amber. |
| VMGR-28 | View dropdown in the footer-left zone, right of Mode: text trigger (`Visual` / `Code`) + chevron; menu opens upward, plain text + check on the selected entry. Present only on non-expression complex-type watchers; resets to Visual on every open (never persisted). |
| VMGR-29 | Code view: read-only CodeMirror JSON surface using the same stack and syntax tinting as the existing JSON editors (line numbers, code folding), pretty-printed 2-space JSON. Tables serialize as array-of-row-objects. No validation surface (the view is read-only). |
| VMGR-30 | Complex metrics, identical in Visual and Code views: array `N items`, map `N keys`, table `N rows x M cols`. |
| VMGR-31 | Empty complex values: centered muted italic line `no items` / `no entries` / `no rows`; the metric shows the zero count. A table with columns and no rows keeps its column header above the `no rows` line, so the columns it was set up with show. A null array, map or table shows the null look (VMGR-93), never the empty line. |
| VMGR-32 | Initial mode dims + italicizes the entire complex body; the data rendering is otherwise identical to Current. |
| VMGR-33 | Full-value fetch UX: a skeleton placeholder shows only while the FIRST fetch for a watcher is in flight; afterwards updates are stale-while-revalidate - the previous value stays rendered until the fresh one lands (no flicker). Re-fetches are event-driven off the variable's change summaries. |
| VMGR-34 | Large-value guard: the Visual body renders the first 500 rows / items / entries followed by a muted `+ N more - switch to Code view` line; the Code view always renders the complete value. |

### Variable Inspect Modal - Expression Views

| ID | Decision |
|----|----------|
| VMGR-35 | The View dropdown appears on expression-typed watchers only. Scalar expression watchers get `Literal` / `Expression`; complex expression watchers get `Visual` / `Code` / `Expression`. Literal (non-expression) scalars have NO View dropdown; literal complex watchers keep `Visual` / `Code`. No permanently disabled menu items exist. |
| VMGR-36 | View menus are plain text + check per the project-wide dropdown rule; there is no Literal (or any) icon in the menu and the trigger is an untinted text label + chevron. |
| VMGR-37 | Evaluated views (Literal / Visual / Code) render the runtime value exactly like a literal of the declared type - quoted strings, type colors. Cyan is reserved for expression source, which the Expression view renders raw in any mode. |
| VMGR-38 | Expression watcher metrics describe the displayed content: `expression` in Expression view, the plain type metric in evaluated views (no `evaluated` suffix), `no value yet` when the expression has no runtime value. |
| VMGR-39 | Expression watchers open in the evaluated view (Literal for scalars, Visual for complex); view selection is never persisted and resets on every open. |
| VMGR-40 | `Not evaluated yet.` empty state: a single centered muted italic line shown by evaluated views whenever the expression has no runtime value - while idle, while a run has not yet referenced the variable, and in history snapshots of runs that never referenced it. The copy is identical everywhere. |
| VMGR-41 | Initial mode of an expression watcher always shows the source (dim + italic): the persisted definition IS the expression. The View dropdown is disabled showing `Expression`; switching back to Current restores the previous view selection. |
| VMGR-42 | Type-mismatch safeguard on every watcher: if a runtime value's actual type does not match the declaration, the body renders an amber italic `received <actual> - declared <declared>` notice with the raw value below, tinted by its ACTUAL type, and the metric shows `type mismatch` in amber. The Code view still renders the raw payload. The guard is display-only; engine and Variable Setter type gates remain the enforcement points. |

### Variable Inspect Modal - Compare Mode

| ID | Decision |
|----|----------|
| VMGR-43 | Compare is the third Mode entry (Initial / Current / Compare, same text trigger and upward text + check menu). The body splits into plain side-by-side panes: Initial left, rendering exactly the single-mode Initial content (dim + italic definition), Current right, rendering exactly the single-mode Current content (runtime overlay, fetch pipeline, empty state, mismatch guard unchanged). No diff highlighting - deliberate performance stance for large values; the rendering itself shows the delta. |
| VMGR-44 | Pane labels are in-pane small uppercase muted labels (`Initial` / `Current`), not dimmed with the pane content. Expression watchers annotate them: `Initial - source` / `Current - evaluated`. A hairline divider separates the panes; both share one vertical scroll; table mini-grids render per pane (not full-bleed) and scroll horizontally inside their pane. |
| VMGR-45 | Compare delta metric, always-arrow while in Compare (equal counts still show the arrow): string `42 -> 84 chars` (unit once, at the end); array `3 -> 4 items`; map `2 -> 3 keys`; table `1 -> 3 rows` (rows only - the column delta is visible in the panes); integer / float / boolean keep the empty center zone. |
| VMGR-46 | Expression watchers in Compare always render the Initial pane as the cyan source (the definition IS the source). The metric's left descriptor is `expression`: evaluated `expression -> 44 chars` / `expression -> 4 items`, unevaluated `expression -> no value yet` with the `Not evaluated yet.` line in the Current pane. The mismatch guard keeps the plain amber `type mismatch` metric (no arrow). |
| VMGR-47 | View dropdown in Compare: literal complex watchers keep `Visual` / `Code` driving BOTH panes; the `Expression` item disappears (it would duplicate the Initial pane); expression scalars are left with only `Literal`, so the dropdown renders disabled showing `Literal`; expression complex watchers keep `Visual` / `Code` driving the Current pane. A stored `Expression` view selection coerces to the evaluated view while in Compare and restores on leaving. |
| VMGR-48 | Compare is never persisted (watchers always reopen in Current), changes no default or minimum sizes, and triggers no auto-resize. Idle Compare renders the definition in both panes (consistent with staging watchers before a run); the first-fetch skeleton and the 500-entry Visual cap apply per pane. |

### Current Edit (Runtime Override)

| ID | Decision |
|----|----------|
| VMGR-61 | Editing happens in the variable's window (VMGR-106), for BOTH the Initial value (the definition) and the Current value (the live value), whenever the test is NOT actively running - before a run, paused, or stopped. The pencil that opens the window is disabled only while the engine is actively executing (status `running`), visually disabled with a tooltip (VMGR-107). The watcher has no Edit. |
| VMGR-62 | The Mode control is a prominent, color-coded pill carrying its text label: indigo `Initial` (the saved definition; an input's `Default`), amber `Current` (the live, transient value), neutral `Compare`. In the watcher the pill carries a chevron and is the mode dropdown. In the variable's window the same pill, offering only Initial (inputs: Default) and Current, is the value switch on the Value label line (VMGR-108): it picks which value the window edits, and its color is the signal of which value Save changes. Supersedes the faint text-label Mode trigger for the inspect modal. |
| VMGR-63 | A Current edit in the variable's window edits the same representation as an Initial edit: a literal variable takes a new typed value; an expression variable's source/formula is edited (the cyan ExpressionField), never its evaluated value, so the variable never changes nature. The override is transient: it survives Stop and partial re-runs, is discarded by a full run (which re-seeds from definitions), and is cleared on Reset. With a live session (paused/stopped) the override mutates the runtime value (an expression is re-armed and re-evaluated on next reference); while idle it stages a pre-run override applied to the next run without touching the saved definition. A Current value of a Function's own input, output or local lands in that Function's scope (VMGR-108). |
| VMGR-64 | If a run or resume is triggered while a variable's Edit window has unsaved changes, a blocking warning modal offers Cancel / Drop Changes / Save Changes before the run proceeds (reusing the existing unsaved-changes three-way dialog). An Add window never holds a run. |
| VMGR-65 | A string watcher carries a Format selector in the footer view slot (the slot a literal string otherwise leaves empty): Plain / JSON / XML / YAML / Auto. Same text-label trigger + chevron and upward text + check menu as the Mode and View selectors. It governs the string body's syntax highlighting; when a string value is edited, the same selector lives in the "Edit value" editor (VMGR-110). |
| VMGR-66 | Auto is the default format. The format is detected from the value once when the modal opens (the trigger reads `Auto (JSON)` / `Auto (YAML)` / `Auto (XML)`, or plain `Auto`); detection never re-runs while the user types, and a manual pick holds for that watcher. The format is a display and edit aid, not part of the value, so it is never persisted - a watcher reopens in Auto. |
| VMGR-67 | Per-format linting is advisory: a malformed region is underlined but Save is never blocked, because a string value is valid as a string whether or not it parses (the deliberate contrast with the complex Code view, where invalid JSON gates Save). |
| VMGR-68 | While editing in a data format in the "Edit value" editor (VMGR-110), a Format button beside the selector pretty-prints the current text in the active format in place (a string is freeform, so it reformats the current draft rather than reverting to a last-valid structure); the button is absent for Plain. |
| VMGR-69 | A table column whose name is empty or duplicates another column's name is marked with the same destructive border the cells use, on the header name input, and gates Save. Column names must be present and unique - the table type's own rule - so the silent row-object key collision that drops a column's data can no longer be saved from the editor. |
| VMGR-70 | One shared table-schema validator backs both the Visual and the Code view and feeds a single validation strip: every offending cell and header is marked in place, and the strip states the first problem by priority - column-name problems before cell-type problems, in reading order within a class - naming the cell or column and the type expected, with a `(+N more)` count when several remain. Save is gated on the same result in both views, so the Code view is never a path to save a table the Visual view would reject. |
| VMGR-71 | The Code (JSON) view type-checks cell values against the column schema the Visual view owns, not just JSON syntax: a value whose type contradicts its column, or a reshaped JSON that adds or drops a column, blocks Save - a structural change is reported with a message pointing back to the Visual view. The Code view is data-only; it edits cell values and rows within the schema and cannot redefine the table's columns. |
| VMGR-72 | Template is a first-class value kind for string variables - a peer of Literal and Expression. Its value is a string carrying `{{ expression }}` markers that render lazily on reference (the same render-on-use model an expression variable uses), so a string variable holding a template renders wherever it is referenced. A template variable carries a cyan `{{ }}` kind badge in its panel row and modal header - the slot the expression `{x}` badge occupies - and its type is STRING. The kind is intrinsic to the value and is chosen in the variable's window, where it stays editable (VMGR-108). |
| VMGR-73 | The template watcher's View selector offers Rendered (the realized string; a centered muted `Not rendered yet.` with a `no value yet` metric before the first render) and Template (the cyan-highlighted source, metric `template`), defaulting to Rendered on open - mirroring the expression watcher's Last Evaluated / Expression pair (VMGR-35 through VMGR-39). |
| VMGR-74 | Editing a template happens in the variable's window: the name is a rename-with-refactoring input (which also rewrites `{{ }}` references), and the value is the `{{ }}`-highlighted source field with in-scope variable autocomplete, the way an expression's value is its source field (VMGR-110). The type and the kind stay editable there like every other field of the variable (VMGR-108). |
| VMGR-75 | The Format selector (VMGR-65) does not include Template; Template is a value kind, not a transient display format. The `{{ }}` highlight and in-scope variable autocomplete belong to the template kind's source body (read and edit), not to a format mode. |
| VMGR-81 | Table column widths are sticky editor state, not transient body state: a manual resize survives add / remove / move column and the Visual <-> Code round-trip. The widths live in the persistent complex-value editor (beside the carried column schema) and reset only on a fresh edit session (re-enter edit, or change the variable's type); column ops transform the widths in place (add appends an auto-fit width, delete drops it, move swaps it) instead of re-seeding all of them. The read-only value grid is unaffected. |
| VMGR-82 | The complex Visual editors (array / map / table) read as a contained data section: the grid is wrapped in an outlined, rounded container with an isolated quiet header row (subtle fill + bottom border, small uppercase muted labels) - array `#  /  Value  /  Type`, map `Key  /  Value  /  Type`, the table's existing column header banded the same way. Rows are value-first (the value field leads; the type pill is a smaller trailing tag) with hairline dividers, so the value - not the type - is the primary column. |
| VMGR-83 | The Variable Setter migrates its value editing onto the shared variable bodies while keeping its compact row layout (name input / type select / value / `{ }` literal-expression toggle / delete) and the toggle unchanged. Compact literals (integer / float / boolean) edit inline in the row through the shared scalar edit bodies, carrying numbers as exact text through the same numeric input guard create / edit use. An expression edits inline in the cyan expression field; because the `{ }` toggle already conveys the expression kind, the field shows no extra `{x}` badge. String and array / map / table show an `Edit` preview button (pencil + value summary) that opens the shared value editor. No new per-row control is added. |
| VMGR-84 | The Variable Setter string value editor opens from a string row's `Edit`. It hosts the shared string body (wrapping, line-numbered, syntax highlighting) in a draggable sheet whose header is a static `Edit value` title + STRING badge, with no variable-name input and no rename - the name and rename belong to the row. The footer carries a Kind dropdown (Literal / Template; text + check; opens upward) beside the Format dropdown (Auto / Plain / JSON / XML / YAML). Literal keeps Format active (transient display state; advisory lint never blocks Save); Template hides Format and switches the body to `{{ }}` highlighting with in-scope variable autocomplete. Cancel / Save; no Mode pill, since the setter has no Initial / Current runtime modes. |
| VMGR-85 | The Variable Setter complex value editor opens from an array / map / table row's `Edit`. It hosts the shared complex value body (per-element and per-column type pills, Visual and Code views, the exact-number input guard, and every shared validator) in a draggable sheet with the same static `Edit value` header + type badge and no name / rename. The footer carries the View dropdown (Visual / Code), the complex metric, and Cancel / Save, with the Format pretty-print button shown in Code; no Mode pill. This migration removes the Variable Setter's last use of the legacy array / map / table editor modals, so the legacy table editor modal is deleted. |
| VMGR-86 | The entity-scope variable tables (Suite / Regression / System Variables) migrate their Value column onto the shared variable bodies while keeping their authoring chrome - the selection / name input / type select / secret checkbox / delete columns and the `+ Add` row are unchanged (entity variables are user-authored, unlike profile parameters which come from a fixed schema). Only the Value column changes, replacing the one-line JSON text input (which made complex values fail their own validation) with the shared per-type affordance. |
| VMGR-87 | The entity-scope Value column mirrors the profile parameter cell exactly: integer / float / boolean edit inline through the shared scalar bodies (exact-text numbers); string and array / map / table show an `Edit` preview button (pencil + value summary, string preview in the string color, complex a muted `N items` / `N keys` / `N rows` summary) that opens the shared `Edit value` sheet; a secret holding a value shows the uniform masked clear-and-edit affordance (pencil + lock + masked dots); a null value shows the null chip instead of the preview button. The sheet is literal-only here (no Kind dropdown, empty autocomplete scope), as with profiles. ## 4.5 Entity Details vs Execution Views

**Entity Detail** (Definition) = What it IS. Static config, shared, editable.
**Execution View** (Runtime) = What happened when RAN. Dynamic, per-user/per-run, immutable.

| Aspect | Definition | Execution |
|--------|------------|-----------|
| URL | `/{entity}/{id}` | `/executions/{id}` |
| Ownership | Shared | Per-user/per-run |
| Mutability | Editable | Immutable |
| Status | None (link to history) | Running/Passed/Failed/Stopped |
| Actions | Add, Create, Run, Edit, Remove, Duplicate, Delete | Stop (running), Re-run (done) |

| ID | Decision |
|----|----------|
| PICKER-1 | Server pagination, 25 per page; the next page auto-loads when the list is scrolled near the bottom (infinite scroll). The active search + tag filter apply to every page; changing either restarts from page 1. |

| PICKER-4 | A read that fails before there is a list to keep - the first page or the tag list when the modal opens, and the first page after a search or tag change - shows the shared error state in the list area (alert icon + "Unable to load {what failed}" + "Try Again"; reuses LIST-5) instead of a silent empty list, and that "Try Again" re-reads the first page and the tag list together. The title names the read that failed rather than always naming the entity, because a tag failure that reads "Unable to load tests" says something untrue about the tests. A failed additional page does not come here: rows and a selection are already on screen, this state would throw both away over one page that did not arrive, and the pill it is retried from (PICKER-2) is where the user was already looking. |

| SSH-9 | Every numeric row on the SSH blocks (Session Open's Port, Connect timeout and keepalive rows, Session Exec's and Session Script's Timeout, Tunnel Open's Local Port and Remote Port) declares its bounds once, and they are enforced both in the form and when the block runs, as on the newer blocks |

## 4.16 SSH Tunnel Plugins

| ID | Decision |
|----|----------|
| SSHTUN-1 | SSH Tunnel builds on an open SSH Session rather than opening its own connection: SSH Tunnel Open takes a Session ID (a String bound to an SSH Session Open's Session ID output) and forwards a local port through that session's live connection, the same referencing model Execute and Close use. Multi-hop reach, authentication, and host-key policy are inherited from the session; the tunnel carries no credential or jump configuration of its own |
| SSHTUN-2 | SSH Tunnel Open renders on the shared schema-driven element config form with no bespoke component: a Forwarding group (expanded by default) with Session ID, Local Port, Remote Host, Remote Port, then a collapsed Advanced group holding one checkbox, Validate Target, off by default. The forward listens on the loopback interface only (127.0.0.1); there is no bind-address parameter |
| SSHTUN-3 | Local Port accepts 0 to auto-assign a free local port; the resolved port is surfaced as the Local Port output so downstream blocks address the tunnel. Outputs are Tunnel ID and Local Port, each with an `(i)` tooltip stating purpose. Remote Destination is not an output - it would only echo the Remote Host and Remote Port inputs |
| SSHTUN-4 | A tunnel is a child resource of its session: SSH Tunnel Close takes a Tunnel ID and is an idempotent no-op on an unknown or already-closed tunnel, and closing the owning session - or the end of the run - tears the tunnel down automatically. There is no per-tunnel lifetime scope |
| SSHTUN-5 | SSH Tunnel provides fixed local port-forwarding (one local port to one remote host and port through the session). Tunnel Open fails (hard fail), consistent with the SSH Session plugins, only when its session is not open, when the Local Port cannot be bound or, with Validate Target on, when the check of the destination fails (SSHTUN-7); a connection refused later fails only that connection and is reported per SSHTUN-6. Optional reachability is expressed by wrapping the block in a Try-Catch control |
| SSHTUN-6 | By default Tunnel Open matches plain `ssh -L`: opening binds the loopback Local Port and checks nothing else, and every connection accepted on the Local Port asks the session's server to connect to the destination afresh, so a destination that comes up later is reached by later connections and a connection that fails fails only itself. Every connection the SSH host refuses or cannot complete writes a warning to the run log naming the Local Port, the destination, the SSH host and the host's own reason, whether or not Validate Target is on. The SSH host is named as the session identifies it, which for a session opened on another tunnel's Local Port is the far host (SSH-8). A Netcat block that addresses a tunnel's Local Port reports a refusal in its own results (NETCAT-8) and adds no tunnel warning |
| SSHTUN-7 | Validate Target (checkbox in the collapsed Advanced group, off by default): at open the session's server is asked to connect to the destination once, and Tunnel Open fails if the server refuses to forward or cannot reach the destination, waiting no longer than the session's connection timeout. The connection that proved the destination is kept and becomes the first connection of the tunnel's first client (a block connecting to the Local Port, or a Netcat block addressing it), so the destination sees no connection beyond those the test makes and a listener that accepts a single connection stays usable. If the destination closed that connection before first use without sending anything, the first client gets a fresh one. Otherwise the first client receives everything the destination sent on it since open, even if the destination has closed it since. Tunnel Close, closing the session and the end of the run also close a held connection no client used. Help text: `Connects to the target once when the tunnel opens and fails if the SSH host refuses or cannot reach it. That connection is handed to the first block that uses the tunnel.` |
| SSHTUN-8 | Tunnel messages. A failed Validate Target check fails Tunnel Open with `SSH tunnel to {host}:{port} failed: {ssh_host} refused to forward (administratively prohibited)`, `SSH tunnel to {host}:{port} failed: {ssh_host} could not connect ({reason})` or `SSH tunnel to {host}:{port} failed: {ssh_host} did not connect within {n} seconds` (singular "second" when {n} is 1). Any other refusal code reads `SSH tunnel to {host}:{port} failed: {ssh_host} refused the connection ({reason})`, and a session whose SSH connection is gone reads `SSH tunnel to {host}:{port} failed: the SSH connection to {ssh_host} is closed`. The per-connection warning is `Connection through SSH tunnel 127.0.0.1:{local_port} to {host}:{port} failed: ` followed by the same cause phrase, for example `bastion could not connect (Connection refused)`. A policy refusal reads administratively prohibited, the standard name for it, because OpenSSH's own text for it ("open failed") says nothing; a failed connect carries the host's own text, for example Connection refused or No route to host |

## 4.29 HTTP Plugin Rework

| ID | Decision |
|----|----------|
| HTTP-1 | The headers map stores user intent only; the editor additionally renders the headers WAVE generates (the composed auth header, the body mode's automatic Content-Type) as read-only rows so the visible map matches the wire - superseding the earlier no-generated-rows rule (the rows are derived, never stored). Anything the user adds overrides the transport's automatic headers (Host, User-Agent, Accept, ...); a one-line note in the map editor states that standard headers are sent automatically; the full wire truth is the DEBUG trace (HTTP-15) |
| HTTP-2 | Each value in the HTTP block's request maps (header values, query param values, form field values) and each multipart text part's value is either a plain literal or a single whole-value expression - never a mix of literal text and expression fragments in one value. A literal is stored and sent verbatim (expression-looking characters in a literal stay literal and are never evaluated); an expression is one expression evaluated when the block runs, the same capability every WAVE value field offers. Map keys and part names are always literal. The value field is the standard WAVE value input with the {x} toggle that swaps to the full expression editing experience (autocomplete, live validation, full editor). The Code view keeps a valid-JSON shape: a literal value is a quoted string and an expression is a bare {{ expression }} in the value position (keys always quoted), and a value that is neither is rejected. Supersedes the earlier template-string / {{ }}-segment model, the per-entry Literal / Expression value kinds, and the explicit Code-view object form |
| HTTP-3 | Authentication is a dedicated Auth config section directly after the Headers row: an enable toggle plus mode (Basic / Bearer token / API key) with the mode's fields as sealed credential inputs, required when visible. The composed header value registers as a runtime secret at send, renders in the headers editor as a masked read-only row under the case-insensitive duplicate rule, and deleting that row disables the section; a run with a required field empty fails before sending, naming the mode. At runtime the composed header wins over a same-named header from a dynamic map. Supersedes the basic_auth/bearer/secret expression helpers and the "+ Auth" scaffold (both removed); manual auth headers stay legal |
| HTTP-4 | The amber unsecured-credential advisory (the SECFLD-2 slot inside the value field) extends to HTTP header rows: it fires when a credential-catalog key holds a plain literal value (unprotected plaintext) and stays calm for an expression value, which may reference a secret variable. Declared credential fields keep their SECFLD-2 states. It is informative only and never blocks |
| HTTP-5 | Request header values under credential-catalog keys (authorization, x-api-key, ...) register in the run's secret registry at send time regardless of authoring path - literal or expression - mirroring the existing response-side credential registration, so masking is value-based on every scrubbed surface |
| HTTP-6 | Content-Type is an ordinary header owned by the user, facilitated by a "+ Content-Type" quick-insert listing common media types plus Custom. Body modes that generate the header materialize it as a read-only generated row (HTTP-1) instead of erroring: a manual same-key row is an ordinary case-insensitive duplicate, deleting the generated row turns automatic body headers off (multipart excepted - its row is locked because the transport owns the boundary), file mode's generated type is chosen from common media types or auto-detected from the extension, and with automatic body headers off the mode's expected header becomes a non-blocking amber advisory (in-field icon plus an editor stripe listing the missing suggestions). At runtime a generated header silently overwrites a same-named header from a dynamic map. Supersedes the mode-conflict error model. There is still no Content-Type field on the Body |
| HTTP-7 | Headers key policy: duplicate-key validation is case-insensitive (HTTP semantics) and includes generated rows; Content-Length is the only rejected user row, with a message stating the transport reality (the HTTP stack blocks length overrides) rendered with canonical casing regardless of typed casing, while Transfer-Encoding is forwarded verbatim and a transport refusal fails the block with the transport's own error - superseding the earlier two-header blocklist (Host and Connection stay allowed). The same rules with the same exact messages apply in the visual editor, in Code view (including a source-level duplicate scan), at save validation, and to dynamic header maps checked when the block executes with the source named in the error. The strip shows the first message plus a "(+N more)" expander |
| HTTP-8 | The Body section is available on every method (empty means none is sent), with a Body Mode enum: Text, Form (URL-encoded), Multipart (form-data), File. In-sheet mode switches retain every mode's draft payload; only the active mode's parameters persist on save |
| HTTP-9 | Form (URL-encoded) mode edits a map of form fields whose values are each a literal or a whole-value expression (HTTP-2); the generated Content-Type appears as the read-only generated row (HTTP-6), and each config section's informational notes render together in one styled note container - superseding the bare muted note lines |
| HTTP-10 | Multipart (form-data) mode edits a Parts list in the shared sheet language: each part is Kind (Text / File) + Name + Value or Source; part names are literal and each text part's value is a literal or a whole-value expression carrying the {x} toggle (HTTP-2); a file part's filename defaults to the source basename and its part content type auto-detects. The parts Code view keeps a valid-JSON shape - a literal value quoted, an expression a bare {{ expression }} in the value position - with exact per-part messages; duplicate part names are legal per multipart semantics. The generated multipart Content-Type with its boundary is the locked generated row (HTTP-6) |
| HTTP-11 | File-source values (File body mode, multipart file parts) accept artifact://, testdata://, or an absolute or relative path, resolving where the block runs; the empty state names these forms. A `..` segment is followed wherever it leads. Inside a Remote Execution body the File body mode and multipart are not supported, so a file source never reaches the remote host |
| HTTP-12 | Response handling is a mode switch in the Assert style: Body (default - response text in the body output, as before) or File (the response streams to disk and the body output IS the path: an artifact reference on WAVE, a host path under Remote Execution; a File Name field appears, auto-derived when empty; a sha256 output is populated). Both modes honor an optional Max Size cap - empty means 1 MB in Body mode and unlimited in File mode; hitting the cap logs a WARN and truncates, never errors |
| HTTP-13 | Transport identity and network path: client certificate and client key live in the Security group renamed "TLS / Certificates", accepted as file path, variable, or inline PEM with the SECFLD credential treatment; client identity is presence-based - configuring a certificate presents it when the server asks. TLS is provided by a bundled pure-Python client rather than the host's system TLS library, so protocol-version and cipher choices are OS-independent and reproducible, identical on the local backend and inside remote-execution bundles. The group pins the negotiated protocol version (min / max across TLS 1.0-1.3, ordering validated) and orders cipher preference from a fixed, host-independent catalog of common suites shown under both OpenSSL and IANA names (unknown names rejected by name); the picker is two tables split by protocol family with TLS 1.3 independently selectable (HTTP-16). Left unset, the block offers every catalog suite inside the selected range - the default list shown in gray (FIELD-10) - and nothing else. The Connection group carries a proxy mode with two choices (WAVE setting, the default - follows Settings > Network > Proxy for a request made from the WAVE host; Off - a direct connection). Off overrides the Proxy setting for that block, and a run on the WAVE host whose request went through a proxy says so in the run log (NET-10). On a remote host the Proxy row is disabled and reads "Remote host's settings": the request uses that host's own proxy settings. The row does not show the block's own choice there, so a Save of the block's configuration on a remote host stores no proxy choice, like a hidden row (SHELL-10); when the row shows again it starts on its default, WAVE setting (FIELD-8). Requests use HTTP/1.1; there is no HTTP/2 |
| HTTP-14 | A Text body that parses as JSON while no Content-Type header is set shows the amber in-field advisory (icon + tooltip, non-blocking) suggesting one be added |
| HTTP-15 | Evidence: INFO keeps the two summary lines; at DEBUG the block logs a combined multiline trace - one entry for connect + TLS (negotiated protocol, cipher, peer identity, validity window), one entry per exchange with the headers actually sent and received (redirect hops and retry attempts each an exchange), one timing entry (connect, first byte, download, total). Bodies never appear in the trace (sizes only); credential-named header values mask by name at capture on every hop in both directions regardless of value length (the per-block unmask choice keeps them readable, and a user-marked-secret trace output extends the treatment to all hop headers); the timing total covers the wire window only - first transport event to last across all attempts - never body building or artifact writing; masking additionally applies through the run registry; the same facts bind as a structured trace output for Asserts (cert days-to-expiry, time-to-first-byte); duplicate response headers are preserved in order in the trace while the headers output stays a map |
| HTTP-16 | Cipher picker (TLS / Certificates group): two tables split by protocol family. The TLS 1.0-1.2 table carries a per-suite compatibility tag ("1.0-1.2" or "1.2") naming the versions each suite applies to; the TLS 1.3 table carries no tag (every row is 1.3). Each table supports select and drag-reorder for client preference order within its own family; order never crosses families, since the two are separate offerings on the wire. A suite is shown only when its versions fall inside the selected min / max range, and a whole table is hidden when it has no in-range suites - out-of-range suites and tables are hidden, not dimmed. Suites appear under both OpenSSL and IANA names. Unchecking every suite is a valid explicit-zero state (offer no ciphers); a Reset control returns to the default: every suite inside the range. With no list set the footer reads `All N enabled` and `Default`; a list may name suites by their OpenSSL or IANA names and the picker keeps every one. |

Auto infers each column's type in one pass, widening integer -> float -> string, with guards that keep leading-zero codes and otherwise ambiguous values as text. String keeps every column as text. From input schema takes a table variable and applies its column names and types verbatim (mapped by header name when a header row is present, else by position); the same variable may be bound as the output. |
| CSV-5 | Empty cells is an enumeration governing what a missing field becomes: null (default, a real missing value, distinct from an empty string) or the column type's default (0 / 0.0 / false / ""). The same default is what a "replace with default" mismatch (CSV-6) substitutes. |
| CSV-6 | A declared type (From input schema, or a filter's "as Type", CSV-9) is enforced against the data; Auto is inferred and never fails. On type mismatch governs the reaction when a cell will not fit a declared type: Fail (the run fails), Continue - skip row, or Continue - replace with default (the CSV-5 default). Mismatches under a Continue mode are reported per-row in the errors surface with success = false, keeping the good rows (consistent with the JSON / XML parsers). |
| CSV-7 | Sorts is a collapsible section holding an ordered priority list (top = highest priority). Each row is a column reference (CSV-9) plus a direction (Ascending / Descending) and is reorderable / removable. Add Sort appends a row. |
| CSV-8 | Filters is a collapsible section of per-column blocks. Add Filter creates a block whose header is a column reference (CSV-9) plus an "as Type". Inside a block, Add Literal adds an operator + value condition (operators come from the block type, reusing the assertion control's per-type operator sets, is null and not null included; a null cell follows the check rule of REQ-3.1.3.25) and Add Expression adds a per-row predicate (CSV-10); conditions combine with AND / OR reusing the assertion builder's grouping (no duplicate builder). Blocks AND together. |
| CSV-9 | The column reference (Sorts and Filters) is a Name / Index mode selector plus a value field, because at design time the column names are not known. The value is free text by default; it is forced to Index and the selector disabled when Has header row is off; it becomes a searchable dropdown only when a schema is provided (Column types = From input schema). Index is 0-based, matching the Table type and the table visualization. Fixed-width mode / direction / as-Type dropdowns keep the value fields aligned across rows. Where the Transform's source is a bound table (Serialize, and Excel Write) the column names always exist, so Name stays available whatever the header setting says - there the header control only decides whether the names are written out. |
| CSV-10 | A filter Expression condition is a per-row predicate over its block's column, exposed as the scoped variable `_cell` (this column's value in the current row); workflow variables remain in scope. `_cell` is surfaced by the row's `(i)` hint and the expression editor autocomplete, with placeholder `_cell != None`. A block's "as Type" is auto-set and disabled when a schema is provided. |
| CSV-11 | Output Variables use the standard outputs table (info, Parameter, Type, Secret, Assign to). Parse outputs: Table (Table), Row Count (Integer), Schema (Array of column name / type). Serialize outputs: CSV Content (String) and Success (Boolean). |
| CSV-12 | Filters and sorts built in the config sheet are stored and run in one shape: a filter condition is the same condition item the check blocks use (Assert, If/Else, Switch, While, Wait Until), so a filter runs exactly as built. |

## Switch/Case Control

| ID | Decision |
|----|----------|
| SWITCH-1 | Switch is a container control, not a diverging one: N case lanes, an optional `default` lane, and an always-present `then` lane. A case's sub-flow runs and returns to the Switch; execution leaves only through `then`, so a Switch never dead-ends the flow. This is the difference from If/Else (CANVAS branch model), whose branches become the main flow and which halts when nothing matches. |
| SWITCH-2 | Cases carry conditions built with the same assertion builder If/Else uses, evaluated top to bottom. There is no first-branch special case: every case is equal, so all of them can be renamed, reordered and deleted. |
| SWITCH-3 | Each case carries a Break switch. Break on ends the Switch after that case runs. Break off continues to the next branch, which decides on its own condition, so a case never runs on another case's condition. A newly added case defaults to Break on, making an untouched Switch behave like If/Else. |
| SWITCH-4 | `default` is optional and sits last. It runs when no case matched, and equally when a case above it falls through - carrying no condition, it has nothing to refuse with. Nothing follows it, so it ends the Switch and needs no Break switch. |
| SWITCH-5 | Lane colors encode role: case lanes take the conditional category orange, `default` takes a muted neutral, `then` takes the same neutral the other container controls use for their exit (Try/Catch, For Loop). The reader can tell branch from fallback from exit without hovering. |
| SWITCH-6 | Lanes render no text labels; the branch name is the handle's accessible name and appears in a hover tooltip. Lane tooltips use a shorter delay than the rest of the app, because wiring is a rapid scan across several lanes. This matches If/Else and Try/Catch rather than introducing a labeling idiom on one control. |
| SWITCH-7 | Block width grows by one handle slot per case, plus one for `default` when present and one for `then`, reusing the existing branching-block width rule. |
| SWITCH-8 | The config sheet renders stacked case cards: chevron, CASE badge, branch name field, Break switch, reorder arrows, delete. The Break switch sits in the header so a collapsed card still shows whether that case falls through. The DEFAULT card uses the neutral badge and reads "Runs when no case matched, or when a case above falls through". |
| SWITCH-9 | Fall-through has no extra annotation in the card. The Break switch state is the single signal, keeping the editor visually identical to If/Else apart from that one control. |
| SWITCH-10 | Add buttons below the list are "+ Case" and "+ Default", with "+ Default" disabled once a default exists - the same affordance and disabled rule If/Else uses for "+ Else". |
| SWITCH-11 | A disabled Switch skips every case and continues through `then`, identical to a disabled Try/Catch or For Loop. Because a single fall-through path past the sub-graph now exists, Skip-while-paused works on a Switch instead of being refused. |
| SWITCH-12 | Switch produces no output value. Which case ran is visible on the canvas paint and in the run log, and a case's own steps set whatever a later step needs - the same contract as If/Else. |
| SWITCH-13 | Inside any sub-flow (a container slot or a Function body), the cases and default a Switch did not run paint skipped, the same as the branches an If/Else or a split Assert did not take there; a rejoin block keeps the status of the path that ran |

## Wait Until Control

| ID | Decision |
|----|----------|
| WAIT-1 | The condition is authored with the same assertion builder Assert, If/Else, Switch and While use. Wait Until adds no condition idiom of its own; what an author already knows about writing an assertion is what they use here. |
| WAIT-2 | Two timing parameters lead the panel: a required Timeout that bounds the whole wait, and an optional Check Interval that spaces the rounds, defaulting to one second. An optional Timeout Message names, in the author's own words, what the wait was for; it is what the run log prints when the wait gives up. |
| WAIT-3 | Wait Mode selects the block's shape the way Assert's Single / Split selects its handles. Retry gives the block a `retry` lane holding a sub-flow that runs on every round to try to make the condition true, plus the always-present `then` exit. Watch gives it `then` alone: the wait only re-checks. Execution leaves a Wait Until only through `then` in both modes, so it never dead-ends the flow. |
| WAIT-4 | Running out of time is weighed by Fail Current Scope, the same in Retry and Watch mode. Enabled, the timeout is a block failure: the block paints red and the flow stops at the wait like any failed block, so a surrounding Try/Catch is the way to react to a wait that never landed, and otherwise the Function or Test it runs in ends failed. Disabled, it is informational: the block paints amber and the flow continues down `then`. |
| WAIT-5 | Lane colors encode role, as they do on every other container control: `retry` takes the repeated-sub-flow blue the loop bodies use, `then` takes the container-exit neutral. Lanes render no text; the lane name is the handle's accessible name and shows in a hover tooltip. |
| WAIT-6 | Wait Until produces two values an author can bind: whether the condition came true, and how long the wait took. Nothing else needs binding - which round satisfied the condition is visible in the run log. |
| WAIT-7 | A running Wait Until reads as alive the same way every other running block does - the RUNNING badge and the canvas run pulse - and carries nothing block-specific beside them. How far along a wait is comes from the run log, which prints a line per round, and the final duration binds through the elapsed output. Elapsed-against-limit is a canvas-wide timing concern rather than one control's badge, and a block card has no room for a second badge next to RUNNING. |
| WAIT-8 | A round checks the condition first and leaves immediately if it is already true, so a satisfied Wait Until costs nothing. Otherwise the retry sub-flow runs, the check interval elapses, and the condition is checked again. The timeout bounds the whole wait, including a retry sub-flow still in progress. |
| WAIT-9 | A disabled Wait Until skips its retry sub-flow and continues through `then`, identical to a disabled Try/Catch, For Loop or Switch, so Skip-while-paused works on it. |

## Parallel Control

| ID | Decision |
|----|----------|
| PARALLEL-1 | Parallel is a container control, not a diverging one: one lane per branch plus an always-present `then` lane. Branch sub-flows dead-end at their own end and execution leaves only through `then`, which is the join. Same shape as Try/Catch, Switch and Wait Until, so disable, skip-while-paused and step behave identically on all four. |
| PARALLEL-2 | Branch lanes take violet - a color no other lane role uses - and `then` keeps the container-exit neutral. Blue already means the path Try/Catch attempts, cyan a repeated sub-flow, orange a Switch case and green the Assert pass lane; a fan-out is a distinct role and gets a distinct color rather than overloading one. Lanes render no text, the branch name is the handle's accessible name and its hover tooltip. |
| PARALLEL-3 | Branches are authored as rows on the config sheet: BRANCH badge, name field, an optional per-branch time limit, reorder arrows, delete. A name rather than a bare count, because the name is what the lane tooltip, the run log and the report print - "branch 2" tells a reader nothing months later. Minimum two branches; the last two rows cannot be deleted, since one branch is a sequence the canvas already expresses. |
| PARALLEL-4 | Join mode is a radio section where Wait Until puts Wait Mode and Assert puts Branching Mode: Wait for all (default) or First to finish. There is no condition-based join - a condition-gated wait is authored inside a branch with Wait Until in Watch mode, using the assertion builder the product already has. |
| PARALLEL-5 | Time limits are optional at two levels and independent: one per branch on its row, one for the whole section in Input Parameters. A single section-wide limit cannot express "this branch may take 30s, that one may take all day". Running out of time is a branch failure, so it ends the section like any other failure. |
| PARALLEL-6 | Parallel produces no output variables. Branches share the test's live variables, so what a branch computed is already readable after the join; a branch that must report something names a variable and writes it, exactly as a block outside the section would. |
| PARALLEL-7 | A running Parallel carries no branch counter or countdown on the block - several branch lanes and several blocks simply carry live status at once, the same treatment every running block gets. Elapsed-against-limit is a canvas-wide timing concern, not one control's badge, and the same ruling that withdrew the Wait Until countdown applies here. |
| PARALLEL-8 | Debugging keeps one cursor: the first branch to hit a breakpoint becomes the paused block and the section parks, siblings holding at their next block boundary. Step drives the paused branch, Continue releases the section, and a sibling that was also holding a breakpoint surfaces as the paused block next. Two competing cursors on one canvas would have no coherent Step. |

## Quick Insert - the Functions half

> Extends CANVAS-231 through CANVAS-237.

Quick Insert offers two halves of one catalog. The built-in half - every plugin, every control and the New Function creator row - is held in the browser. The published-Function half comes from the server, is the only half that can be large, and is the only half that can fail.

| ID | Decision |
|----|----------|
| CANVAS-241 | The Functions half is paged and searched on the server, following the shared picker contract (PICKER-1): a fixed page of 25 rows, the next page requested when the list is scrolled near its bottom, the active query sent with every request, and a changed query starting again at the first page. The whole library is therefore reachable from the picker, not just the rows that happened to arrive first. The built-in half stays in the browser and filters as the author types, so the half that cannot fail never waits on the network. The query is held briefly before it is sent, and clearing the field is sent at once. |
| CANVAS-242 | One permanent status line sits between the list and the keyboard hint strip and always describes the Functions half. Nothing is drawn inside the list and nothing floats over it. The list here shows about ten rows at a time with the hint strip flush beneath it, and on an unfiltered open the Functions group sits about forty rows below the fold, so anything drawn inside the list is out of view exactly when it matters. ## Tooltip surface and sidebar search

| ID | Decision |
|----|----------|
| SHELL-7d | The tooltip carries an arrow pointing at its trigger, filled and outlined like the surface. Tooltips routinely attach to controls a few pixels apart - a block's action cluster, a row of table controls - where a floating label alone does not say which control it describes. |

## Session continuity

| ID | Decision |
|----|----------|
| SESS-9 | A participant's identity lasts as long as its browser tab, across reloads. A reload is a continuation, not a departure: the tab returns as the same participant and resumes what it held, with no read-only interval in between. Minting a new identity on every page load made a tab a stranger to the session it had owned a second earlier. |
| SESS-10 | Two tabs are always two participants, including when one is duplicated from the other. A tab that finds its identity already live elsewhere in the same browser takes a fresh one, so the single-active-session guarantee cannot be broken by copying a tab. |
| SESS-11 | Departure is announced by the tab from wherever it is in WAVE, not inferred from a connection going quiet. A holder who browses to another page keeps the session and keeps reporting; a connection can stop being noticed long after the person has gone, and a session that outlives its owner by that margin is indistinguishable to everyone else from one still in use. A departing tab's claim is kept for a short, bounded moment so a reload lands back in it, then the session is free. |
| SESS-12 | A session is never held by a participant with nothing behind it. Losing a connection releases what it held unless that same participant is already present on another connection - the case a reload creates, and the reason a late-noticed dead connection can never evict a tab that has already returned. Ending a session administratively releases what it held by the same rule, so the roster and the lock always agree. |

## Blocked page after a failed load step

> Extends LIST-4 through LIST-6 with a fourth page state.

| ID | Decision |
|----|----------|
| LIST-10 | Loading a surface is more than one read, and each read is one of two kinds, classified by what the surface does with it. The records the surface exists to show are primary; every other read is supporting. Primary failure keeps the existing full-page error state (LIST-5) because there is nothing left to render, and supporting failure blocks the surface, because it renders perfectly and every claim it then makes about the user's data is unfounded. A third kind for reads that only enrich something already usable is rejected: the enrichment is still presented as fact, so a filter menu built from a tag list that never arrived tells the user these are their tags when nobody knows. There is no optional read and no failure quietly absorbed. |
| LIST-11 | A read that fails is never reported as an empty result. Emptiness is something the server said; failure is the absence of anything said at all, and substituting one for the other turns a dropped request into a false statement about the user's data. The environments case is what this rule is drawn from: one failed request told the user they had no environments when they had several, opened the editor with every value blank, and left Save enabled over data that had never been loaded. |
| LIST-12 | The blocked page is one state, entered the moment the failure is known. The route content blurs and a card sits over it with a warning icon, a title naming what did not load, a second line that agrees with that title ("This page cannot be used until it loads." for one failed read, "This page cannot be used until they load." for more than one), a folded Details disclosure and a single Try Again. No modal, no interstitial, no two-step. |
| LIST-13 | Blocked means inert, not covered. Nothing in the blocked region takes a click, a tap, a keystroke or the Tab key, and removing the covering layer does not bring it back. A transparent layer that swallows pointer events is rejected: focus, the keyboard and assistive technology reach straight through it, so the page would stay fully operable for anyone not driving it with a mouse. The card sits outside the blocked region, otherwise it dies with the page. |
| LIST-14 | Blocking stops where the page ends and the application begins. The navigation sidebar and its controls stay sharp and fully usable, so leaving is always one click away. A failed read on one page is no reason to take the whole product away. |
| LIST-15 | The card has no Cancel and no close control. Dismissal would hand the user back a page that cannot be trusted, which is the exact state the block exists to prevent, so there is nothing for it to mean. Navigating away is the way out, and the live sidebar is what makes that available at all times. |
| LIST-16 | Try Again re-runs only the reads that failed. Nothing else is re-fetched, no state is discarded and the records already on the page are untouched. On success the card goes and the page is completely normal; on failure the card stays and carries the newest failure in place of the previous one, so attempts do not accumulate. |
| LIST-17 | Details are folded by default and carry method and path, status, duration, request id, timestamp and the server's own message. The panel is height-capped and scrolls on both axes, so a one-line reason and a hundred-line trace occupy the same space: Try Again never moves and the card never grows past the window. A copy control sits in the panel's top-right corner, icon only, with a tooltip, visible only while the details are open; it holds its corner while the panel scrolls and copies the whole payload rather than the visible part, because the reason to copy a trace is to paste all of it somewhere else. |

## Blocked surfaces beyond the page

| ID | Decision |
|----|----------|
| LIST-18 | The blocked surface is whatever the failed read serves. For a page that is the route content; for a modal that performs its own reads it is the modal, and the failure lands in the error state that modal already owns rather than blurring the page behind it. Blurring the page behind an open modal is rejected: the user is inside the modal and has not left it, so a card on the surface they cannot see puts a second Try Again on screen competing with the one already in front of them. One failure model and one retry gesture per surface. |
| LIST-19 | A read the surface started for itself, such as restoring earlier work in the background, blocks on failure exactly like one the user asked for. Treating unrequested reads as exempt was rejected: their results are used the same way and the surface makes the same claims from them, so exempting them buys nothing but a quieter wrong answer. Interrupting someone who asked for nothing is only a trap when there is no way out, and here there is nothing to dismiss and the sidebar stays live, so leaving is one click. |

## Blocking precedence, ownership and scope

> Refines LIST-10 through LIST-19.

| ID | Decision |
|----|----------|
| LIST-20 | When the read a surface exists to show fails, that surface shows the error state it already owns and nothing is blocked, whatever else failed in the same load; a block the surface had already raised is cleared. Primary failure wins outright because the block has nothing left to guard - the records never arrived, so neither did the editors and filter menus the supporting data was going to serve. Letting both states stand was rejected: the full-page error state carries its own Try Again, and blocking renders that control inert underneath the card, so the user has to get past the block before reaching the one thing that reloads the page and a one-click recovery costs two. |
| LIST-21 | A block belongs to the surface that raised it, and only that surface clears it. A surface finishing a clean load never erases a card another surface put up, and a failure raised later never takes the place of one the user has not answered yet. One slot shared by the whole application was rejected: any load finishing anywhere silently removes the failure the user is reading, leaving a page that is still unusable with nothing left on screen to say why. A surface that goes away clears its own block, so no block outlives the surface it describes. |
| LIST-22 | A stopped surface names every read that failed in that load, not just the first; on a blocked page the details then carry each failed read's request and reason under its own name. Try Again re-runs exactly that set, and the card narrows to whichever of them failed again. Naming one and dropping the rest was rejected: the surface then reports as fixed a failure the user was never told about, and after a retry they watched succeed it stays stopped with nothing on screen to say why. |
| LIST-23 | A surface reads only what its visible content needs. A page divided into sections reads a section's data when the user opens that section, so a section nobody is looking at cannot block the page over data that is not on screen. Loading everything a page might eventually need on arrival was rejected: it makes the whole page hostage to the least relevant thing in it, and someone reading the About section of Settings would be stopped by a tag list that section never uses. |

## Retry, the one reply that is not a failure, and where a failure is reported

> Refines LIST-10 through LIST-23.

| ID | Decision |
|----|----------|
| LIST-24 | Every retry a surface offers, the card's and the surface's own alike, re-runs each of that surface's reads that failed in the load and shows only what those fresh attempts come back with. No reason is ever replayed from memory, so recovery is one gesture and every reason on screen describes an attempt just made. Re-running part of the set and remembering the rest was rejected after it was seen to fail twice over: a surface whose own retry re-read only its records put the card straight back up quoting a supporting read that attempt had never touched and that may already have recovered, and leaving one failed load then cost two separate retries. |
| LIST-25 | A supported answer saying a capability is not enabled on this install is an answer, not a failure: the caller takes the documented default for that capability being off, nothing is blocked and nothing is reported. Some capabilities are legitimately switched off in a working product, and blocking on one of them would stop every page of an install that is behaving exactly as configured. The line is drawn at what came back and never at how much the caller wanted the data, so anything refused for another reason, timed out, undelivered or unreadable is a failure and is reported, and the distinction is never inferred, so no failure may be read as "probably switched off". Where the default exists for safety rather than convenience, such as keeping secrets masked until the server says they may be shown, the safe default holds while the failure is reported, so a failed read can never reveal what a working install would have kept hidden. Calling such a read merely optional was rejected: optional is the caller's opinion of the data rather than something the server said, and it would readmit every swallow this family exists to remove. |
| LIST-26 | Where a failure is reported follows what the user was doing. A read a surface performs in order to become usable blocks that surface; an action the user just triggered reports at the gesture that started it, in the toast that would have confirmed it or the error line of the dialog it was started from; a read repeating on a timer reports in place and keeps the last good data on screen. One treatment for all three was rejected in both directions: blocking on a failed export takes away a page that still works over something the user can simply try again, and reporting a failed load in a toast leaves an unusable page looking normal once the toast fades. What none of the three allows is silence, or a default the user would read as an answer. |

## K8s Read Blocks

| ID | Decision |
|----|----------|
| K8SREAD-1 | Search by is an explicit three-way mode - Name, Selector, List - with no combinations. Name reads one object and fails when it is missing; Selector and List return a list that may legitimately be empty with Count 0. An earlier design folded a name into the field selector and was killed: live testing showed the tick silently changed the response type, changed the required RBAC verb from get to list, changed cardinality, and turned a missing object into a passing check |
| K8SREAD-2 | Resource Type is a Default / Custom selector sitting before Kind. Default renders Kind as a grouped searchable dropdown of the kinds a stock Kubernetes install serves; Custom replaces it with a plain string field. WAVE does not gate the value against a frozen list, because live discovery is the only authority that is right for custom resources and a list goes stale the moment an operator is installed; a kind the cluster does not serve fails the block on WAVE's own discovery message |
| K8SREAD-3 | Kind is singular. Kind is singular by definition in Kubernetes; the plural is the resource name, a different thing. List modes do not pluralize it |
| K8SREAD-4 | Kind short names render as inline muted secondary text to the right of the label on the same row, matching the one shipped precedent (the HTTP block's body_mode). Not a second line: rows stay single-height so the list does not double in height. Kinds without a short name render plain with no reserved gap |
| K8SREAD-5 | Kind picker groups are delimited by a tinted heading band spanning the list width. Groups are ordered Workloads, Networking, Config, Storage, Cluster; members are alphabetical within each group. A search field sits at the top of the list |
| K8SREAD-6 | Output Format is Map (default), Table, JSON, YAML, driving a single Result output whose type follows the format. JSON and YAML are strings, not parsed structures, so a workflow that only wants to store the response as an artifact does not pay for a parse it never uses. Map is the default because it is the most usable without a further parsing step |
| K8SREAD-7 | Table returns every column the cluster provides. There is no -o wide switch: wide is kubectl hiding lower-priority columns to fit a terminal, which is not a constraint a workflow has. This is a response-shape decision with no config-sheet surface |
| K8SREAD-8 | The Advanced group holds the per-block overrides of the session's context defaults: a plain always-visible Namespace field, All namespaces where the block has one, and impersonation. All namespaces sits above the Namespace field and hides it when ticked, because they are mutually exclusive. There is no API version override: the cluster's live discovery resolves a kind to the version that cluster prefers. All namespaces is offered only where it can apply, matching kubectl each time: it is absent in Get's Name mode and in Top's Name mode, because a named object is read from one namespace; absent whenever Top measures nodes, which are cluster-scoped; and absent from Logs entirely. Advanced opens collapsed; Connection and the block's own verb group open expanded, so the sheet opens on the rows an author has to fill in |
| K8SREAD-9 | A read block's own outputs are unconditional, and so is Success. Error and Reason are the one gate: they belong to Record and continue, the only setting under which a cluster refusal can reach them, so the default sheet is not carrying two rows that can never be filled. Names and Count ride on Get because the response always carries names when no column selection is happening, and feeding a following for-each block is the case that justifies them |
| K8SREAD-10 | Failure Handling renders as its own quiet group at the foot of every operational block: one On error row, Fail the block as default, Record and continue as the alternative. On Top it carries its own wording, because a cluster with no metrics API hard-fails in both modes. The group opens collapsed, like Advanced. Record and continue finishes the block amber, not green, and writes one WARN line naming what the cluster refused, so a recorded failure stays visible on the canvas and in the console without stopping the run |
| K8SREAD-11 | Events names the involved object's kind through the same Default / Custom pair and the same grouped searchable Kind picker as Get, under a selector labeled Object Type. What the value names differs and the copy says so: Get names a kind to read, while Events names the kind of the object an event is about. Both resolve it the same way - through the cluster's live discovery, which turns the singular, the plural or the short name into the canonical kind - and Events then puts that canonical kind into the involved-object field selector. A kind the cluster does not serve fails the block rather than answering with zero events, because a silent empty list would read as a passing check |
| K8SREAD-12 | There are no reveal ticks. A control whose only job is to reveal the field beneath it does not exist: the field is always visible and optional, and its emptiness carries the meaning, exactly as an omitted kubectl flag does. Applied first to Namespace, which was a tick and a field and is now one plain optional row on every block in the family, empty meaning the namespace the session carries. A tick that genuinely changes behavior rather than merely revealing a row is untouched by this and stays |
| K8SREAD-13 | There is no API version override. The pair that pinned a kind to a chosen version is gone: kubectl has no such flag, it disambiguates a kind through the resource argument itself, and the cluster's own live discovery resolves a kind to the group and version that cluster prefers, which is what keeps one workflow correct across clusters serving the same kind at different versions. A block whose kind is fixed never needed the pair at all |
| K8SREAD-14 | Error and Reason render only when On error is Record and continue; Success renders under both settings. The reason is mechanical rather than stylistic: a block's outputs are bound only after its call returns, so under Fail the block a cluster refusal unwinds past the binding and those two never receive a value at all, not even an empty one, leaving a variable bound to them holding whatever it held before or, inside a loop, a stale value from an earlier pass. Success is the deliberate exception, visible under both settings even though it shares the same mechanism and is only ever written true, so that one outcome check binds on every block whatever its setting; it is recorded as an exception on purpose so nobody later reads it as an oversight |
| K8SREAD-15 | A format option is named after the type it yields. Where the mode changes the shape of Result, Output Format is two rows sharing one label, identical but for the first option's word, so exactly one of them renders and the label can never disagree with the type the output declares: on Get the first option reads Map for a read by name and Array in Selector and List modes. Events returns a list whatever the mode, so it carries a single row whose first option simply reads Array. Both rows store the same value, so nothing downstream changes. Leaving one Map option that sometimes hands back an array was killed as the defect that prompted the rule |
| K8SREAD-16 | K8s Logs offers a structured shape and not only text. Output Format sits under the Timestamps tick with String as the default, the text exactly as the cluster returns it. The second option follows the tick: Array, one entry per line, while Timestamps is off, and Table, the time and the message in separate columns, while it is on, because the cluster prefixes the timestamp itself and that prefix is the only thing a line can safely be split on. Offering Table in both states was rejected: with nothing to split on it would be an array wearing a table's clothes. Timestamps therefore decides which row renders, which is why it takes a literal and carries no expression toggle |
| K8SREAD-17 | K8s Top's Usage is a table rather than a list of maps. Its columns follow the measurement, which is data and not schema: pods give name, cpu and memory, plus a container column when the per-container breakdown is on; nodes give name, cpu, memory, capacity cpu, capacity memory, allocatable cpu and allocatable memory. Capacity and allocatable each carry a cpu and a memory figure while a table cell holds one scalar, so each becomes two columns; teaching cells to hold a map was costed and declined, because it changes a shared core model and the variable editor would save such a cell back as text. The trade is stated rather than hidden: a table is for reading, so anything asserting on a single figure reads a cell |
| K8SREAD-18 | Every read that hands back objects strips Kubernetes' own field-management bookkeeping out of them, the way kubectl does by default, so a result carries the object's content and not the record of which controller last wrote each field. It is unconditional and has no control on the sheet: that bookkeeping is never what a test asserts on, and left in it would dominate the size of every stored result |
| K8SREAD-19 | Get's JSON and YAML are WAVE's own re-serialization of the parsed objects, not the bytes the cluster sent. The stripping above runs first, so the text and the structured result describe exactly the same objects and the two forms cannot disagree; asking for text is a choice of encoding, never a different read |
| K8SREAD-20 | Container is a required row on K8s Logs too, with no default and nothing to leave empty, and the client-side defaulting that used to stand behind an empty row - reading the pod first, then taking the container a cluster author annotated as its default, or else the first one the pod declares - is gone with it. That defaulting worked and matched what kubectl logs does; it is dropped so that every block in the family that names a container names it the same way (K8SEXEC-9), which is worth more here than parity with kubectl's own client-side choice |

## K8s Write Blocks

| ID | Decision |
|----|----------|
| K8SWRITE-1 | Apply is the family's one create-and-update block, and it writes server-side always. Which mechanism it uses to write is internal and never reaches the sheet: there is no client-side or server-side control, and the one visible consequence, a field-ownership conflict with whatever tool wrote the field before, is resolved silently in the author's favor rather than surfaced as a choice. Client-side apply is also not implementable correctly inside the standard-library-only core the family is built on, so server-side is the honest answer as well as the invisible one. What gets applied is either a pasted manifest, several documents included and applied in order, or a short form that builds exactly one object of one of three kinds: ConfigMap, Secret, or Job either from an image or from an existing CronJob run now. Deployment, CronJob and Ingress forms are not offered - a Deployment generator too minimal to matter, test-created CronJobs an anti-pattern since a test triggers an existing one through the Job option, and Ingress needing a repeating rules editor - and there is no Namespace form because anything useful about a namespace arrives with a quota or a policy object beside it, which is more than one object and therefore a manifest |
| K8SWRITE-2 | Apply's Result takes the type its path yields: a map when a form built the object, an array with one entry per document when a manifest did, and text for JSON or YAML. It is not always an array, though a shape which never changes is easier to index, because a form builds exactly one object and which path the sheet is on is settled while the sheet is being edited, so the type is knowable at design time - the same reason Get varies its own Result type (K8SREAD-6). Output Format is therefore two gated rows sharing one label, the first option reading Map in Form mode and Array in Manifest mode, so the word and the declared type never disagree (K8SREAD-15). Apply offers three formats and not four: Table is absent, because on a write the fact worth reporting is created versus configured, which lives in the cluster's response and not in the object, and Summary already carries it one row per object. The divergence from the read blocks is considered, not drift |
| K8SWRITE-3 | A Secret form's Data is a declared credential on a wire name of its own, while the ConfigMap form's Data is untouched and stays readable. The values are visible and editable while the author is typing them, and protected once stored: the row then carries the shared protected-value affordance instead of the entries, showing neither the keys nor how many there are, and reopening it takes the shared confirmation, which clears the stored value so the author re-enters it. Being a declared credential is what protects it - it is sealed in the saved test and masked on the block's input line and on every other surface where the run is recorded - and every written value also registers with the run's secret registry, so a value that reaches an output is masked there too. Registration alone would not protect them, because it does not cover the block's input line. The Secret's type is chosen from Opaque (the default), kubernetes.io/tls and kubernetes.io/dockerconfigjson, the two typed forms offering the key names the cluster demands for them as quick inserts; basic-auth and ssh-auth are not offered because nothing in core Kubernetes reads them - there they are a labeling convention - so a test that wants one writes a manifest. Kubernetes fixes a Secret's type when the object is created and does not let it change |
| K8SWRITE-4 | Apply carries no Dry run, and the Job form no Environment. Measured rather than argued: the dry-run flag appears once on the whole kubectl quick reference, and there on run rather than on apply, and not once across 1142 real tests and 154 real CI commands, while kubectl's own job creation has no environment flag at all, so an Environment row would fail the parity rule outright. A manifest carries environment variables for the flows that need them |
| K8SWRITE-5 | Delete keeps Cascade and Wait until gone and drops Field Selector. Cascade is the one delete option whose effect is dramatic - Background, Foreground and Orphan leave the cluster in three different states - and kubectl's own default pair, Background plus wait, returns before the children are gone, so a test asserting that no pods remain needs Foreground and must be able to reach it. Field Selector earns its place on a read block and not on a delete. Deleting a name that is already gone is an error, exactly as it is in kubectl, and Ignore not found is the row that turns it into a pass with a count of zero, while a selector matching nothing is a success without it. No output reports prior existence: it would duplicate Success and, with Wait until gone unticked, would claim something WAVE has not observed |
| K8SWRITE-6 | Scale carries neither a precondition nor a wait. kubectl's current-replicas precondition is left out, though it is one of only four scale examples in the quick reference: prominence in a reference is not the same as a control WAVE needs, and the tick would cost the sheet a mode and a conditional row to guard against a race a test can check with a read block instead. No wait control appears either, because kubectl's scale waits through a timeout that defaults to zero and carries both the decision and the duration in one value, so surfacing it would put a second duration on a sheet that already has a request timeout. Delete has a wait tick and Scale has nothing because kubectl's delete wait is a plain on-off flag defaulting to on |
| K8SWRITE-7 | Rollout gains Undo and not history. Undo is a real state change with no other route to it, so it earns an operation, and it takes an optional revision, empty meaning the one before the current. Rollout history is already reachable by reading ReplicaSets with a selector, so it does not earn an operation of its own. Rollout's Kind is a fixed list of the three workload kinds that have a rollout - Deployment, StatefulSet and DaemonSet - with no Default / Custom pair, because a kind without a rollout has nothing to restart, report on or roll back |
| K8SWRITE-8 | An output that an input choice invalidates is hidden. An output the chosen mode cannot fill with anything meaningful is absent from the output list in that mode, so nothing can bind it there, while an output carrying a real value in every mode stays unconditional. This reverses an earlier ruling that no output is ever gated. Two instances exist: Rollout's Status renders only under the Status operation, because after a restart or an undo it would describe the cluster a moment after a write rather than the write itself; and Error and Reason render only under Record and continue, for the binding reason recorded in K8SREAD-14 |
