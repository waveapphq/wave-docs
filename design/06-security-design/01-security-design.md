## 6. Security Design

### 6.1 Credential Management

The system implements a secure credential management pipeline:

**Storage Flow**:
- User credentials are encrypted before storage
- Profile-based credential references avoid hardcoding
- Runtime decryption only when needed

### 6.2 Security Measures

**Data Protection**
- AES-256-GCM authenticated encryption for credentials at rest
- Pluggable encryption key provider (swappable key source)

**Access Control**
- Profile-based credential isolation
- Secret masking in all output channels (execution logs, console output, HTML reports, JSON artifacts, WebSocket messages) for explicitly marked secret variables

**Network Security**
- Certificate validation
- SSH key management
- Connection encryption

#### Credential Encryption at Rest

##### REQ-4.5.1 Credential encryption at rest

Every secret value WAVE persists is stored encrypted, so a reader of the file store - a backup, a shared volume, an exported definition, a version-control checkout - never sees a credential in cleartext. Encryption is a property of storage, complementary to masking: masking governs what the engine emits about a run, encryption governs what sits on disk between runs.

The protected surface is exactly the set of values designated secret: secret-flagged variables at every scope (system, regression, suite, test, and entity scope), the credential fields of connection profiles (passwords, tokens, API keys, private keys, passphrases, bind passwords), any secret literal a variable setter persists into a block's configuration, and any literal typed into a plugin's declared credential input field (an SSH session's password, private key, or passphrase). A user does not mark a plugin input secret; a plugin declares which of its input fields carry credentials, and a literal in such a field is sealed the same way a secret variable or setter literal is, while an input holding an expression references a variable whose value is already sealed at its own scope. No field a block declares secret carries a default value (SECUI-13). A Function input the author marks secret is such a field too: a literal typed into the Function Block for it is sealed, and whatever reaches it is masked inside the Function, while the default of a Function output marked secret is sealed at rest (REQ-3.1.2.9). Certificate authorities and other non-secret fields remain in cleartext; encryption never obscures content that is not a credential, so definitions stay readable and comparable except at their secret leaves.

A secret value is sealed the moment it is saved and stays sealed through every load and listing; an export carries the sealed value unless the exporter makes the explicit per-export choice described below. An empty secret is stored empty: with no value there is nothing to seal or mask, so every read, export and run display shows it as empty, while any other value, whitespace included, is sealed and masked. It is unsealed only at the boundary where real bytes are required - a run resolving the value, a live connection being established, or a server-side expression evaluation whose result is masked before display - the same boundary at which the value registers for masking. The engine therefore always computes on real values while the stored and exported forms carry only ciphertext. Each sealed value is a self-describing, authenticated envelope: any component recognizes a sealed WAVE secret and detects tampering without consulting a schema. A value that arrives in cleartext (freshly authored, hand-edited, or imported) is sealed on its next save rather than rejected, and the system converges any stored cleartext secret to sealed form at startup, including historical entity versions, so the at-rest guarantee covers the whole store rather than only newly written data. Envelopes are location-independent: because definitions are portable, a sealed value remains decryptable after import, duplication, rename, or version copy.

Encryption uses authenticated symmetric encryption (AES-256-GCM) under a key supplied by a pluggable key provider, decoupling the source of the key from every place that seals or unseals a value so it can be replaced without touching call sites. Key material is always provisioned to the installation through its configuration and is never generated by the server on its own, so an installation holds its key before the first secret is sealed and no self-invented key ever needs migrating away from. WAVE ships no key: each installation makes its own with one documented command that prints a new random key. An installation with no key configured refuses to start, and the refusal names that command; one whose key does not open the sealed check value WAVE keeps in its data folder refuses to start too. When a value cannot be unsealed - an unavailable or wrong key, or ciphertext that fails its integrity check - the operation fails fast rather than proceeding on a corrupt or absent credential. The key itself never enters the data folder, an export or a backup (REQ-4.5.17).

Because a sealed value opens only where the same key is held, every export of secret-carrying content takes an explicit, per-export choice of the secret form it emits. The default masks: secret values are replaced by the canonical placeholder, producing a file that is safe to share and can never leak a credential. Keeping values encrypted emits the envelopes unchanged, producing a file whose secrets open on any WAVE holding the same key - the natural form for backups - while remaining opaque everywhere else. Decrypting emits real values in cleartext for deliberate migration; the choice is visibly warned in the interface, requires the encryption key (it fails cleanly when the key is absent, wrong, or the ciphertext fails its integrity check), and is never a default. The chosen handling governs every secret carrier in the exported document, including credentials embedded in historical entity versions. Every import and restore brings each form back to the at-rest guarantee by one rule (REQ-4.5.19).

#### Secret Key

##### REQ-4.5.17 Secret key identity and export

The secret key is the one value every sealed secret of an installation depends on, so WAVE treats it the way established tools treat theirs: it belongs to the installation, never to its shared work. WAVE ships no key. Each installation makes its own with one documented command that prints a new random key, and sets it in the installation's config file or in an environment variable; without one WAVE refuses to start, and the refusal names that command. The server never generates the key on its own, and the key is never written into the data folder, into an export or into a backup. A backup that carried its own key would defeat the protection the key provides.

#### Secrets on Import and Restore

##### REQ-4.5.19 One rule for secrets on every import and restore

Every way secret values enter WAVE from a file follows one rule: importing tests, suites, regressions, Functions, profiles, system variables and environments, and restoring a backup. WAVE recognizes a locked value by its marker alone, never by its shape or by a name.

- A value without the locked-value marker is plain and is stored locked with the current key exactly as given. The placeholder a masked export leaves is the exception: it carries no value, so it is treated like a value WAVE cannot open - stored as null, the secret owed until a person enters the real value - except that it never replaces a real secret already stored at the same place, which is kept. The export file itself still carries the placeholder.
- A value locked with the current key is stored as it is.
- A value locked with another key is changed to null: it stays a secret, holds nothing and shows as owed until a person enters the real value. An import preview names each such value before anything is written.

Environments carry no secret fields, so the rule has nothing to act on there.

A secret held as null - in a variable or typed into a block setting - fails the block that uses it before anything is sent, naming the field or the setting. A credential left empty on purpose is stored as empty text, never null, so it still means nothing was given.

#### Making a Variable Secret

##### REQ-4.5.20 Warning before a Save makes a variable secret

A variable becomes secret on purpose, never as a side effect nobody saw. When saving a block would turn an existing plain variable into a secret - a ticked Secret box in its outputs table, including the row a secret Function output seeds (REQ-3.1.2.9), or a ticked Secret box on a Variable Setter row - WAVE first asks the person to confirm, naming every variable the save would change, one or many, in a scrolling list with no cap. Canceling returns to the block with nothing saved; confirming saves the block and makes each named variable secret, which it then stays (SECUI-4, SECUI-12). A new variable typed into a ticked Secret row is created secret with no question, because no plain value is being changed.

#### Secret Masking

##### REQ-4.5.3 Secret masking in logs

Secret masking is a run-wide guarantee: values designated secret cannot appear in cleartext in any engine-produced output. Designation is always explicit (a variable flag, a plugin parameter or output declaration, a user marking on a plugin output, or a plugin registering an acquired credential); the system never infers secrecy from names or value shapes. Every observability channel is covered - execution logs, console streams, terminal output, HTML/JSON reports, execution artifacts and snapshots, failure summaries, WebSocket messages, and debugger views - through value scrubbing of outbound text plus structural masking of variable-shaped payloads, all rendering one canonical placeholder that reveals nothing of the protected value.

The engine itself always computes on real values; masking applies only to outbound copies, and masked representations never round-trip into stored values or execution state. Secret values are masked by default. Settings > General holds one reveal flag per surface (run output, test variables, shared variables and credential input fields), and the MCP reveal tool works only when its surface's flag is on and consent is given. The other two deliberate exposure paths are byte-transforming a value (a conscious user act) and the per-block unmask option declared in the test definition, whose exposure is therefore reviewable and versioned. Content a workflow deliberately writes as its function (user-instructed file output) is the user's product and is not rewritten; the masking guarantee governs what the engine says about a run, not what the run is instructed to produce. The full masking model is specified in the variable system design (component design 3.6.5).

#### Execution Trust Model

WAVE executes as a dedicated operating-system user, and that account is the sandbox: every filesystem path, network capability, and process right available to a workflow is exactly what the operating system grants that user. Plugins that accept host paths therefore reach precisely the files the WAVE user can read or write - no more, no less. Granting or reducing that reach is an operating-system administration act (user permissions, group membership, mount visibility), not an application setting; WAVE deliberately maintains no second, application-level filesystem policy that could drift from the real one.

A workflow's outbound TLS is likewise a controllable test capability, not a hardened client posture. The HTTP client plugin uses a bundled pure-Python TLS client so a test can pin any protocol version from TLS 1.0 to 1.3 and offer a specific cipher list - deliberately including legacy versions a hardened client would refuse - in order to exercise and verify how a server-under-test responds. This is scoped to the plugin's outbound test traffic and is independent of WAVE's own control-plane API.
